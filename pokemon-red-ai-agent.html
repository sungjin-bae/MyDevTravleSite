LLM이 포켓몬 레드를 플레이하는 법

에뮬레이터 위에서 대형 언어 모델이 실제로 게임을 조작하는 오픈소스 에이전트 sesang06/pokemon_red_ai를 읽었습니다. LLM이 “게임을 본다 → 다음 한 수를 정한다 → 버튼을 누른다 → 결과를 확인한다”를 어떻게 구조로 만들어 두었는지, 스레드 모델부터 장기 기억까지 그림과 함께 따라갑니다.

🎮

이 글 읽는 법위→아래가 곧 “한 번의 판단이 게임을 움직이는 순서”입니다. 초록·파랑 상자와 그림만 따라가도 전체 구조가 잡히고, 검은 코드와 파일 위치는 “⌄ 더 깊이” 안에 접어 뒀으니 궁금할 때만 펼치세요.

한 줄 요약

“LLM은 제안만, Python이 실행·판정” 하는 포켓몬 레드 자동 플레이 런타임입니다. Gemini가 다음 행동 하나를 JSON으로 고르면, 결정적 코드가 그것을 검증해 에뮬레이터에 넣고, 실제 RAM 변화로 성공 여부를 판정합니다.

큰 흐름

게임을 관찰(RAM+화면) → Planner가 한 수 계획 → Executor가 실제로 실행 → 전후 RAM을 비교해 검증 → Interpreter가 결과를 해석해 목표·기억을 갱신 → 다음 사이클. 최대 1만 사이클 반복.

가장 중요한 설계

게임은 전용 스레드에서 실시간으로 계속 돌아갑니다. LLM이 몇 초 생각해도 게임이 얼지 않아요. AI는 흐르는 게임에 입력을 “던지고” 결과를 관찰할 뿐, 프레임을 멈추거나 몰아서 돌리지 않습니다.

권위 순서

실제 RAM > 검증기 > 행동 계획 > 장기 기억 > LLM 추론. 대화창이 열려도, RAM 인벤토리가 실제로 바뀌기 전엔 “아이템 받음”으로 처리하지 않습니다. LLM은 성공을 선언할 수 없어요.

01 · 무엇을 하는 프로젝트인가

에뮬레이터 + 멀티에이전트 LLM + 실시간 대시보드

구성 요소는 네 덩어리입니다. PyBoy가 실제 포켓몬 레드 ROM을 구동하는 게임보이 에뮬레이터, Google ADK(Agent Development Kit) 위의 세 LLM 에이전트가 두뇌, MCP(Model Context Protocol) 스타일 툴 계약이 에이전트와 게임 사이의 인터페이스, 그리고 FastAPI/WebSocket + React 대시보드가 지금 무슨 일이 일어나는지를 실시간으로 보여주는 창입니다.

ROM·세이브 파일은 저장소에 포함되지 않고, 합법적으로 구한 ROM을 로컬에 두고 씁니다. 이 글은 “코드가 어떤 구조로 이 일들을 엮는가”에 집중합니다.

🧩

비유하자면게임패드를 쥔 사람(LLM) 옆에, 그 사람이 “위로 세 칸”이라고 말하면 실제로 버튼을 눌러 주고 “정말 움직였는지” 화면과 메모리로 확인해 주는 냉정한 심판(결정적 Python)이 붙어 있는 구조입니다. 심판은 사람 말을 믿지 않고 메모리(RAM)만 믿습니다.

02 · 큰 그림

하나의 게임, 세 겹의 스레드

핵심을 먼저 그림으로 봅시다. 게임을 소유한 세션이 맨 아래, 그 위에 AI 루프, 맨 위에 대시보드가 있고, 셋은 스레드가 다릅니다.

⏱️

왜 이렇게?PyBoy는 스레드 안전하지 않습니다. 그래서 단 하나의 티커 스레드만 에뮬레이터를 만지게 하고, 나머지는 전부 “명령을 큐에 넣고 기다리는” 방식으로 바꿔 재진입 충돌을 원천 차단했습니다. 덕분에 observe()는 에뮬레이터 락을 절대 잡지 않고 발행된 스냅샷만 복사하므로, LLM이 느려도 게임 프레임이 밀리지 않습니다.

더 깊이 — 두 개의 락과 커맨드 큐

_env_lock(RLock)은 에뮬레이터를, _snapshot_condition(별도 락)은 발행된 스냅샷을 지킵니다. 중첩은 항상 env_lock → snapshot_condition 한 방향뿐이라 두 락 사이 데드락이 성립하지 않습니다. 버튼 입력은 커맨드로 큐에 쌓이고, 티커 스레드가 이를 꺼내 실행합니다.

# session.py — 어떤 호출자도 PyBoy를 직접 만지지 않는다
def _submit_emulator_command(self, kind, *args):
    command = _EmulatorCommand(kind=kind, args=args)
    with self._frame_condition:
        self._emulator_commands.append(command)   # 큐에 넣고
        self._frame_condition.notify_all()
    while not command.completed.wait(timeout=0.05):  # 티커가 처리할 때까지 대기
        ...
    return command.result

def _execute_emulator_command(self, command):    # ★티커 스레드에서만 실행★
    with self._env_lock:
        if command.kind == "button":
            env.button(str(command.args[0]), frames=int(command.args[1]))

발췌: src/pokemon_agent/session.py (403–451행 요약)

03 · AI 에이전트

세 역할 — 그런데 둘만 LLM이다

Google ADK 위에 세 역할이 있습니다. 흥미롭게도 실제로 Gemini를 호출하는 건 둘뿐이고, 실행은 결정적 Python입니다. “LLM은 제안, Python이 실행”이라는 철학이 여기서 드러납니다.

세 역할과 구현. Planner·Interpreter만 LLM이고 Executor는 결정적 코드다.
역할정체하는 일
Planner네이티브 LlmAgent (Gemini)압축된 상태(+스크린샷)를 보고 다음 행동 1개를 JSON으로 결정
Executor결정적 Python (LLM 아님)그 행동을 검증(sanitize)하고 툴 클라이언트로 실제 실행
Interpreter네이티브 LlmAgent (Gemini)결과를 해석해 목표(goal)를 갱신하고, 필요하면 기억을 저장

각 LLM 역할은 프롬프트 + 스키마 + 후처리기로 이루어집니다. 위임(transfer)은 꺼져 있어 서로 넘기지 않고, 자동 함수 호출은 4회로 제한됩니다. 그리고 후처리기가 LLM 출력을 결정적으로 검증합니다 — 범위를 벗어난 좌표나 이상한 버튼 토큰은 여기서 걸러집니다.

행동은 딱 두 종류입니다.

// 버튼: 완전한 입력 시퀀스 하나 (wait 토큰으로 대기 삽입)
{"type":"buttons", "buttons":["a","wait","a"], "reason":"advance_dialog"}

// 이동: 현재 맵의 world 좌표로. 경유지(waypoints) 후 target
{"type":"move", "waypoints":[[9,5],[16,5]], "target":[24,8], "reason":"follow_route_exit"}

LLM은 “어디로”만 고릅니다. 충돌 회피·경로 탐색(Dijkstra)은 Python이 소유합니다.

🛡️

권위 순서가 코드로 강제됨Executor는 sanitize에 실패한 행동을 안전한 wait로 강등하고, 좌표는 0~255로 하드 바운드합니다. 성공 판정은 LLM 문장이 아니라 전후 RAM 비교로만 이뤄집니다. 예: 오박사 대화가 열리거나 닫혀도 RAM 인벤토리가 0→5로 바뀌기 전엔 “몬스터볼 받음”이 되지 않습니다.

04 · 한 사이클

관찰 → 계획 → 실행 → 검증 → 해석

실제 구동부는 PokemonRedTeamAgent._run_async_impl입니다. done이 될 때까지 아래 여섯 단계를 반복하고, 각 단계마다 대시보드에 상태를 발행합니다.

  • observe — client.observe()로 RAM+화면 스냅샷을 가져오고 모드(오버월드/대화/전투/메뉴)를 분류.
  • PLAN — 압축 상태(+스크린샷)를 Planner LLM에 전달 → Gemini가 JSON 반환 → 파싱·검증해 active_action_plan 확정. 여기서 LLM 출력이 걸러집니다.
  • execute — Executor가 버튼/이동을 실제 게임에 적용(다음 절).
  • verify — 실행 전후 RAM을 비교(state diff)해 무슨 일이 일어났는지 결정적으로 판정.
  • interpret — Interpreter LLM이 결과를 해석해 목표를 갱신하고, 필요 시 기억을 저장.
  • checkpoint — 상태 저장 후 done이 아니면 반복.
🧵

LLM이 생각하는 동안 게임은?계속 돌아갑니다. 에뮬레이터는 독립된 티커 스레드에서 60fps로 전진하므로, 플래너가 응답을 기다리는 몇 초 동안 오버월드에선 캐릭터가 가만히 서 있고 대화·전투 애니메이션은 자연스럽게 이어집니다. 프레임을 몰아서 돌리지 않아 대화나 애니메이션이 “점프”하지 않는 것도 이 설계의 이점입니다.

05 · 입력을 던지는 법

에뮬레이터에 이벤트 던지기 — MCP를 통해서?

“MCP 툴 계약”이 인터페이스인 건 맞지만, 기본 실행 경로는 MCP 프로토콜이 아니라 in-process 함수 호출입니다. Executor는 PokemonToolClient라는 추상화만 호출하고, 구현이 두 가지 있습니다.

PokemonToolClient — 두 구현

src/pokemon_agent/adk_agent/client.py

InProcessMcpClient
기본(CLI·Web). 서브프로세스 없이 mcp_server.press_buttons(...) 함수를 직접 호출.
StdioMcpClient
진짜 MCP. pokemon_agent.mcp_server를 별도 프로세스로 띄우고 stdio로 session.call_tool(...).

어느 쪽이든 결국 모듈 전역 _SESSION(PokemonSession)에 도달하고, 거기서 실제 에뮬레이터 접근이 일어납니다.

🗺️

이동(move)은 조금 특별move_to_world_cell은 목표 world 좌표를 받아, Session 내부에서 충돌 격자에 Dijkstra를 돌려 방향 시퀀스를 만든 뒤 여러 버튼 명령을 순차 제출합니다. 목표가 화면 밖이면 보이는 가장자리까지 이동 → 재관찰 → 다시 계획을 반복(화면 단위 리플래닝)합니다. 맵이 바뀌면 좌표계가 달라지므로 의도적으로 이동을 중단합니다.

참고 — 저장소의 독립 pokemon-mcp 서버(진짜 stdio MCP 표면)는 별개 진입점이지만, 기본 자동 플레이는 InProcessMcpClient를 쓰므로 그 경로 없이도 동작합니다.

06 · 대시보드

이벤트가 흐르는 길 — 세 소스에서 브라우저까지

대시보드로는 세 종류의 소스가 하나의 LiveEventHub로 모입니다.

세 소스가 하나의 허브로 수렴한다.
소스어떻게
(a) 게임 관측티커 스레드가 스냅샷 발행 → 리스너가 최신 1개만 저장(coalescing) + 이벤트 신호 → 전용 스레드가 깨어나 hub.publish_observation
(b) 런타임 상태AI 루프가 단계마다 _publish → hub.publish_runtime (계획/실행/검증/해석 phase)
(c) ADK 트레이스planning_done 등 트레이스가 sink로 연결 → hub.publish_trace

허브 내부는 이렇게 흐릅니다.

  • RLock 아래에서 상태를 병합.
  • _emit_state_if_due가 델타(직전 대비 바뀐 필드만) 계산.
  • call_soon_threadsafe로 각 구독자의 asyncio 큐에 복사본 투입 — 백그라운드 스레드가 asyncio 큐를 직접 안 건드리게 하는 브리지.
  • WebSocket 핸들러가 queue.get() → send_json.
⚖️

덜 중요한 건 아끼고, 중요한 건 즉시화면·좌표처럼 잦은 갱신은 state_hz(1~30Hz)로 제한하지만, 계획·실행·검증·에러 같은 의미 있는 이벤트는 즉시 강제 발행합니다(force=True). 클라이언트는 접속 시 전체 snapshot을 받고 이후 델타/이벤트를 적용하며, 끊기면 backoff로 재연결해 새 snapshot으로 복구합니다. 서버와 클라이언트의 병합 규칙(딕셔너리는 병합, 배열·스칼라는 교체)이 의도적으로 동일해서 델타만으로 서버 상태가 그대로 재현됩니다.

07 · 장기 기억

저장은 어떻게, 에이전트는 어떻게 접근하나

“저장”이 두 종류라 구분이 중요합니다. 에이전트가 기억으로 읽고 쓰는 건 (A) 장기 기억뿐이고, 나머지는 로그·체크포인트입니다.

(A) 장기 기억 — 단일 JSON 저장소

data/long_term_memory.json · src/pokemon_agent/memory/file_memory.py

키 형식
<type>:<name> — type은 map·npc·pokemon·event 4종만 허용
쓰기 방식
temp 파일에 쓰고 os.replace로 교체 (크래시-원자적)
병합 연산
append(기존 값에 \n 병합, 중복·부분집합이면 스킵) 또는 replace

에이전트는 오직 ADK 툴로만 접근합니다. 두 툴이 있고, 역할별로 붙는 툴이 다릅니다.

메모리 툴과 역할별 권한. Planner는 읽기만 가능하다.
툴PlannerInterpreter
search_memory(queries=[…])✅ 현재 맵 지식 조회✅
save_memory(entries=[…])❌ 저장 불가✅ 갱신 있을 때만
🔒

두 가지 안전장치임의 키를 못 넣습니다 — 툴이 memory_type+name으로 키를 내부 생성합니다. 그리고 거짓말을 못 합니다 — 실제 저장 여부(memory_written)는 LLM의 자기보고가 아니라 save_memory 툴이 실제로 호출됐는지(활동 로그)에서 파생됩니다. 프롬프트에 기억이 자동 주입되지도 않고, Planner가 저장하지도 못합니다.

더 깊이 — save_memory 툴이 실제로 하는 일 
# memory_tools.py — 여러 항목을 한 번에 원자적으로 저장
def save_memory(entries):
    """Atomically append to or replace multiple
       map, NPC, Pokemon, or event memories."""
    result = save_memory_entries(store, entries, source="result_interpreter")
    if activity is not None:
        activity.append({"tool": "save_memory", **result})  # 활동 로그 ← 여기서 memory_written 파생
    return result

발췌: src/pokemon_agent/adk_agent/agents/memory_tools.py

(B) 목표(goal)는 장기 기억 JSON과 별개인 휘발성 상태입니다. Interpreter의 update_goal(main, sub) 툴로만 바뀌고 data/adk_runtime_state.json에 스냅샷으로 남습니다. (C) 원시 액션은 날짜별 JSONL(logs/actions/)과 ADK SQLite에, PyBoy 세이브스테이트는 states/에 저장됩니다 — 이건 “기억”이 아니라 로그·체크포인트입니다.

08 · 정리

한눈에

🎯 이 에이전트의 핵심 구조

  • 게임은 전용 티커 스레드에서 실시간으로 돈다 — LLM 지연이 프레임을 막지 않는다.
  • LLM은 제안, Python이 실행·판정 — Planner·Interpreter만 Gemini, Executor·검증·경로탐색은 결정적.
  • 한 사이클 = observe → plan → execute → verify → interpret → checkpoint, 최대 1만 회.
  • 입력은 커맨드 큐로 — 툴 클라이언트(기본 in-process) → _SESSION → 티커 스레드가 env.button().
  • 대시보드는 세 소스 → 허브 → 델타/이벤트 → WebSocket → React, 중요한 이벤트는 즉시 발행.
  • 장기 기억은 <type>:<name> JSON을 ADK 툴로만 접근, 실제 저장 여부는 툴 활동에서 파생.

전체를 관통하는 한 문장은 이겁니다 — “대화창이 무슨 말을 하든, 스크린샷이 무엇을 보여주든, 아이템·배지·스토리 보상을 받았다는 걸 증명하는 건 오직 RAM이다.” LLM은 이 냉정한 심판 위에서만 움직입니다.

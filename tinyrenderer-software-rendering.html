한 줄 요약

“GPU API가 내부에서 하는 일”을 500줄로 재현한 교육용 렌더러. 서드파티 그래픽스 라이브러리가 0개다 — 선형대수도, TGA 이미지 입출력도 직접 짰다. 입력은 삼각형 메시 OBJ + 텍스처, 출력은 framebuffer.tga 한 장. GUI도 없다.

파이프라인

OBJ 로드 → 정점 셰이더가 MVP 변환(ModelView·Perspective) → 원근분할로 NDC → Viewport로 스크린 → 바운딩박스 + 무게중심(barycentric) 래스터화 → z-buffer 깊이 판정 → 프래그먼트 셰이더로 색 결정 → 픽셀 기록. GPU 파이프라인의 축소판이다.

래스터화의 우아함

스크린 3점으로 만든 ABC 행렬 하나로 다 한다. if (ABC.det() < 1) return; 한 줄이 백페이스 컬링 + 서브픽셀 폐기를 동시에 처리하고, ABC.invert_transpose() * {x,y,1} 한 번의 행렬곱이 픽셀의 무게중심 좌표를 곧바로 뽑는다.

셰이딩

매 픽셀마다 삼각형의 위치·uv 미분으로 Darboux 프레임(접선공간)을 즉석에서 풀어 탄젠트공간 노멀맵을 적용하고, 그 위에 Phong(ambient + diffuse + specular)을 얹는다. 접선 벡터를 모델에 저장하지 않고 프래그먼트 셰이더가 직접 계산하는 점이 포인트.

01 · 무엇을 증명하는 코드인가

“GPU를 쓰는 법”이 아니라 “GPU가 하는 일”

저자의 의도는 분명하다 — 이건 GPU 애플리케이션을 어떻게 짜는지가 아니라, GPU가 내부에서 무엇을 하는지를 보여주는 자료다. 그래서 외부 라이브러리를 일절 쓰지 않는다. 선형대수(geometry.h)와 이미지 입출력(tgaimage)까지 전부 직접 구현했고, 유일한 선택적 의존성은 래스터라이저 루프에 붙은 #pragma omp parallel for 한 줄(OpenMP)뿐이다. OpenMP가 없어도 (직렬로) 그대로 컴파일·동작한다.

파일 지도 — 각 파일이 파이프라인의 어느 조각을 담당하는가
파일역할핵심
geometry.h선형대수vec<n>·mat<r,c> 템플릿, 재귀 행렬식, invert_transpose
tgaimage.*이미지 I/OTGA 읽기/쓰기(RLE 포함), get/set 픽셀, BGRA
model.*모델·텍스처OBJ 파싱, 디퓨즈·노멀·스페큘러 3종 텍스처 로드
our_gl.*파이프라인MVP/뷰포트 행렬, rasterize(), z-buffer, IShader
main.cpp드라이버PhongShader 정의 + 렌더 루프 + 출력

전체 코드는 최종 결과물 기준 약 500줄. 저자는 학생들이 이 렌더러를 만드는 데 보통 10~20시간이 걸린다고 적어 두었다. 실행하면 800×800 framebuffer.tga가 나온다.

02 · 수학과 이미지

직접 짠 벡터·행렬, 그리고 TGA

geometry.h는 이 렌더러의 뼈대다. 컴파일타임 크기를 갖는 vec<n>(double 저장)과 row-major mat<nrows,ncols>(각 행이 vec) 템플릿에, 내적·행렬곱·스칼라 연산을 연산자 오버로드로 얹었다. 흥미로운 부분은 행렬식을 템플릿 메타프로그래밍 재귀로 푼다는 점이다 — dt<n>이 0행 라플라스 전개로 dt<n-1>을 부르고 dt<1> 특수화가 재귀를 끝낸다. 여인수(cofactor)로 invert/invert_transpose/transpose를 일반 차원으로 구현한다.

  • invert_transpose()가 주인공이다. 이 하나가 두 곳에서 결정적으로 쓰인다 — 법선 변환(ModelView.invert_transpose() * normal)과, 래스터라이저의 무게중심 좌표 계산(ABC.invert_transpose()). 뒤에서 왜 “전치의 역”이 정확히 무게중심을 주는지 나온다.
  • 동차좌표에 embed/proj 헬퍼가 없다. 대신 vec4의 중괄호 초기화(위치는 w=1, 방향은 w=0)와 멤버 .xy()/.xyz()가 그 역할을 한다. 아주 간결하다.

tgaimage는 18바이트로 packed된 TGA 헤더, BGRA 순서 색상, 픽셀당 bpp바이트 버퍼를 다룬다. 무압축(datatype 2/3)과 RLE(10/11) 양쪽을 읽고 쓰며, get/set로 픽셀에 접근하고 상하·좌우 flip을 지원한다. “이미지에 점 하나 찍기”만 제공되는 상태에서 시작해 선분·삼각형을 직접 구현해 나가는 게 이 튜토리얼의 출발점이다.

색이 BGRA로 저장된다는 사실은 뒤에서 노멀맵 디코드({c[2],c[1],c[0]}로 R,G,B를 뽑는다)와 스페큘러 샘플([0]=첫 바이트=B)의 근거가 된다.

03 · 모델을 읽는다

OBJ 삼각형 + 3종 텍스처, 그리고 노멀맵 디코드

Model 생성자가 Wavefront .OBJ를 한 줄씩 파싱한다. 정점 v(위치, w=1), 텍스처좌표 vt, 법선 vn(정규화, w=0)을 각각 별도 벡터에 담고, 면 f의 v/vt/vn 인덱스 삼중쌍을 세 개의 평행 인덱스 배열에 저장한다(정점·uv·법선 개수가 서로 다를 수 있으니까). 몇 가지 관용적 처리가 정확도를 만든다.

  • 1-기반 → 0-기반. OBJ 인덱스는 1부터라 --f/--t/--n으로 감소시켜 저장한다. 삼각형 + v/vt/vn 3인덱스 형식만 지원(쿼드나 인덱스 누락 면은 에러).
  • V좌표 뒤집기 {u, 1-v}. OBJ 텍스처 원점은 좌하단인데 렌더러 샘플링은 좌상단 기준이라, vt를 세로로 뒤집어 저장해 텍스처가 상하로 안 뒤집히게 맞춘다.
  • 파일명 규약으로 텍스처 자동 로드. diablo3_pose.obj면 옆의 _diffuse(알베도)·_nm_tangent(탄젠트공간 노멀맵)·_spec(스페큘러) .tga를 자동으로 읽는다. 같은 폴더의 _nm.tga(오브젝트공간 노멀맵)는 이 코드가 읽지 않는다.

노멀맵 디코드가 재밌다. model.normal(uv)는 텍셀(BGRA)을 {R,G,B,0}로 재배열한 뒤 ×2/255 − 1로 [0,255] 바이트를 [-1,1] 벡터로 매핑하고 정규화한다. 즉 RGB 세 채널이 탄젠트공간 법선의 x·y·z를 인코딩한 것이다. 샘플링은 모두 최근접 이웃(bilinear·UV 래핑 없음)이라 uv가 면 안에 있다고 가정한다.

접선(tangent) 벡터는 모델에 저장하지 않는다 — 탄젠트공간 노멀맵을 쓰려면 접선/종법선이 필요한데, 이건 프래그먼트 셰이더가 삼각형의 uv·위치 미분으로 매 픽셀 계산한다(→ 06).

04 · 좌표계 여행 (MVP)

오브젝트 → 눈 → 클립 → NDC → 스크린

렌더링은 결국 한 점을 여러 좌표계로 갈아 태우는 여정이다. 이 렌더러는 세 개의 전역 “OpenGL 상태” 행렬(ModelView·Perspective·Viewport)로 그 여정을 구현한다.

한 정점이 거치는 좌표계와 그걸 옮기는 행렬 (검증: our_gl.cpp·main.cpp 직접 대조)
공간→ 변환무슨 일
오브젝트(object)ModelViewlookat이 만든 카메라 기저 회전 R × 이동 T. center가 눈공간 원점이 된다.
눈(eye/view)Perspective행렬 [3][2] = −1/f 항 하나로 clip.w = 1 − z/f. f는 카메라~center 거리.
클립(clip)원근분할 ÷w네 성분을 clip.w로 나눠 NDC로. 여기서 원근 왜곡이 생긴다.
NDCViewportw/2, h/2 스케일 + 오프셋으로 화면 픽셀 좌표. .xy()만 취함.
스크린(screen)—래스터라이저가 이 2D 삼각형을 픽셀로 채운다(→ 05).
  • OBJ 로드 — Model(filename)이 지오메트리와 3종 텍스처를 읽는다
  • 상태 행렬 구성 — lookat→ModelView, init_perspective(norm(eye-center))→Perspective, init_viewport→Viewport, init_zbuffer
  • 정점 셰이더 ×3 — 면마다 vertex(f,0/1/2)로 오브젝트→눈→클립 변환, 삼각형(Triangle) 조립
  • 래스터화 — rasterize(clip, shader, framebuffer)가 원근분할·뷰포트·무게중심·z-buffer·프래그먼트를 처리

05 · 래스터화와 z-buffer

스캔라인이 아니라 “바운딩박스 + 무게중심”

이 렌더러의 심장이자 가장 우아한 부분이다. 스캔라인/에지워킹이 아니라, 삼각형을 감싸는 사각형(바운딩박스)의 모든 픽셀을 훑으며 각 픽셀이 삼각형 안인지 무게중심 좌표로 판정하는 방식이다. 전체 함수를 그대로 보자.

void rasterize(const Triangle &clip, const IShader &shader, TGAImage &fb) {
    vec4 ndc[3]    = { clip[0]/clip[0].w, ... };            // ① 원근분할: clip → NDC
    vec2 screen[3] = { (Viewport*ndc[0]).xy(), ... };      // ② NDC → 스크린 좌표

    mat<3,3> ABC = {{ {screen[0].x, screen[0].y, 1}, ... }};   // 세 점을 '행'으로
    if (ABC.det() < 1) return;   // ③ 백페이스 컬링 + 1px 미만 폐기를 한 줄로

    auto [bbminx,bbmaxx] = std::minmax({screen[0].x, ...});  // ④ 바운딩 박스
#pragma omp parallel for                                    // x-루프 병렬화
    for (int x=max(bbminx,0); x<=min(bbmaxx, fb.width()-1); x++)
      for (int y=max(bbminy,0); y<=min(bbmaxy, fb.height()-1); y++) {
        vec3 bc_screen = ABC.invert_transpose() * vec3{x,y,1};  // ⑤ 무게중심을 한 방에
        if (bc_screen.x<0 || bc_screen.y<0 || bc_screen.z<0) continue; // 삼각형 밖
        double z = bc_screen * vec3{ndc[0].z, ndc[1].z, ndc[2].z};  // ⑥ 깊이 선형보간
        if (z <= zbuffer[x+y*fb.width()]) continue;   // ⑦ z-buffer (클수록 가까움)
        auto [discard, color] = shader.fragment(bc_clip);   // ⑧ 원근보정 무게중심 전달
        if (discard) continue;
        zbuffer[x+y*fb.width()] = z;
        fb.set(x, y, color);
      }
}

our_gl.cpp — 주석·클램프는 지면상 축약, 핵심 로직은 원문 그대로

💡 왜 invert_transpose() * {x,y,1}이 무게중심을 주는가

ABC는 삼각형 세 점을 행으로 담았다. 점을 열로 담은 행렬을 M이라 하면 ABC = Mᵀ. 그런데 invert_transpose()는 Aᵀ의 역, 즉 (Mᵀ)⁻ᵀ = M⁻¹을 돌려준다. 무게중심 좌표 [α,β,γ]는 정의상 M·[α,β,γ] = {x,y,1}을 만족하므로, M⁻¹·{x,y,1}이 바로 [α,β,γ]다.

덕분에 에지별 루프도, 신호넓이 비율 계산도 없이 단 한 번의 행렬곱으로 무게중심이 나온다. 그리고 세 성분 중 하나라도 음수면 그 픽셀은 삼각형 밖 — 판정도 공짜다.

🔪 det() < 1 — 컬링 두 가지를 한 줄로

ABC.det()는 삼각형의 부호 있는 넓이(의 2배)다. 음수면 와인딩이 반대 = 뒷면이니 백페이스 컬링, 1 미만이면 한 픽셀도 못 덮으니 폐기. 두 판정이 부등식 하나에 합쳐졌다. 이 det은 앞서 본 재귀 템플릿 메타프로그래밍으로 계산된다.

📏 z-buffer — “클수록 가깝다”

std::vector<double>를 −1000(먼 곳 센티넬)으로 채워 시작. 깊이 z는 원근분할 뒤 NDC의 z를 스크린 무게중심으로 선형보간한 값(원근보정 무게중심 아님 — 분할 후엔 깊이가 스크린에서 선형이라 이게 옳다). z <= zbuffer면 폐기, 통과하면 zbuffer를 갱신하고 픽셀을 찍는다.

미묘하지만 중요한 점: 깊이 보간엔 bc_screen(스크린 무게중심), varying(uv·법선) 보간엔 bc_clip(원근보정 무게중심)을 쓴다. 프래그먼트 셰이더에 넘어가는 건 bc_clip이다. 이 구분이 원근 텍스처가 왜곡되지 않게 하는 핵심이다.

06 · 셰이딩

매 픽셀 Darboux 프레임 + Phong

프래그먼트 셰이더는 두 가지를 한다 — (1) 탄젠트공간 노멀맵을 눈공간 법선으로 들어올리고, (2) 그 법선으로 Phong 라이팅을 계산한다. 접선 벡터를 모델이 안 갖고 있으므로, 셰이더가 삼각형의 위치 미분(모서리)과 uv 미분으로 접선·종법선을 즉석에서 푼다. 이게 Darboux 프레임이다.

std::pair<bool,TGAColor> fragment(const vec3 bar) const {
    mat<2,4> E = { tri[1]-tri[0], tri[2]-tri[0] };            // 눈공간 삼각형 두 모서리
    mat<2,2> U = { uv[1]-uv[0], uv[2]-uv[0] };                // 대응하는 uv 증분
    mat<2,4> T = U.invert() * E;                              // E=U·T 를 풀어 접선/종법선
    mat<4,4> D = { normalized(T[0]),                          // tangent
                   normalized(T[1]),                          // bitangent
                   normalized(nrm[0]*bar[0]+nrm[1]*bar[1]+...), // 보간 법선
                   {0,0,0,1} };                                // Darboux 프레임
    vec2 uv = varying_uv[0]*bar[0] + ...;
    vec4 n = normalized(D.transpose() * model.normal(uv));   // 탄젠트공간 법선 → 눈공간
    vec4 r = normalized(n*(n*l)*2 - l);                     // 반사벡터  r = 2(n·l)n − l
    double ambient  = .4;
    double diffuse  = max(0., n*l);                        // 램버트
    double specular = (.5+2.*sample2D(model.specular(),uv)[0]/255.)
                     * pow(max(r.z, 0.), 35);              // r.z: 카메라가 +z축에 있어서
    TGAColor c = sample2D(model.diffuse(), uv);
    for (int ch : {0,1,2})
        c[ch] = min(255, c[ch]*(ambient + diffuse + specular));
    return {false, c};                                     // 폐기 안 함
}

main.cpp — PhongShader::fragment

  • Darboux 프레임을 해석적으로 푼다. E = U·T(E=눈공간 모서리, U=uv 증분)를 T = U.invert()·E로 풀면 T의 두 행이 접선(∂P/∂u)·종법선(∂P/∂v)이다. 접선·종법선·법선으로 4×4 프레임 D를 세운다.
  • 노멀맵을 눈공간으로 들어올린다. n = normalized(D.transpose() * model.normal(uv)) — 텍셀에서 디코드한 탄젠트공간 법선을 Dᵀ로 변환해 실제 조명 계산에 쓸 눈공간 법선을 얻는다.
  • Phong 세 항. ambient 0.4 고정 + diffuse max(0, n·l) + specular. 반사벡터는 r = 2(n·l)n − l, 스페큘러는 pow(max(r.z,0), 35). r.z를 바로 쓰는 이유는 눈공간에서 카메라가 +z축에 있어 시선 벡터 (0,0,1)과의 내적이 곧 r.z이기 때문.
  • 합성. RGB 채널마다 디퓨즈 텍셀 × (ambient + diffuse + specular)를 255로 클램프. 스페큘러 강도는 스펙맵의 첫 바이트로 픽셀별 조절.

07 · 정리와 관찰

작아서 다 보이는 그래픽스 교과서

배울 점

추상화가 딱 GPU만큼만 있다. 상태 행렬(MVP·Viewport), 정점/프래그먼트 셰이더 분리, z-buffer, varying 보간 — 실제 그래픽스 API 개념이 500줄 안에 1:1로 대응된다. “래스터화가 뭐냐”, “무게중심 좌표가 왜 필요하냐”를 코드로 만져 볼 수 있다.

영리한 지점

선형대수를 게임처럼 쓴다. invert_transpose 한 함수가 법선 변환과 무게중심 계산 두 곳에서 재활용되고, det() < 1이 컬링 둘을 겸한다. 수학을 이해하면 코드가 짧아진다는 걸 보여주는 사례.

한계(의도된)

프로덕션용이 아니다. CPU 단일 패스, 최근접 텍스처 샘플링(bilinear 없음), 안티에일리어싱·클리핑 없음, 삼각형+3인덱스 OBJ만. 전부 “원리를 드러내려고” 의도적으로 뺀 것들이다. 저자도 “내 코드를 그대로 쓰지 말고 직접 짜 보라”고 권한다.

한 문장으로: “GPU가 삼각형 하나를 픽셀로 바꾸는 과정을, 숨은 라이브러리 없이 전부 눈으로 볼 수 있게 만든 코드.” 그래픽스 파이프라인을 처음 제대로 이해하려는 사람에게 이보다 좋은 표본은 드물다.

분석 방법: 저장소를 얕은 클론 후 3개 병렬 리더(수학·이미지 / 모델·텍스처 / 파이프라인·셰이딩)로 코드를 읽고, 래스터화·z-buffer·좌표계·셰이딩 수식은 별도 검증 에이전트가 our_gl.cpp·main.cpp를 직접 대조했다. 그 과정에서 “vertex()는 IShader 가상함수가 아니다”, “T = U.invert()·E(순서)”, “깊이 보간은 스크린 무게중심” 세 가지를 확인·정정했다.

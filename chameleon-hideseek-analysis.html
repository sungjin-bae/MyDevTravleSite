카멜레온 위장 게임, 그림으로 뜯어보기

언리얼 엔진으로 만든 숨바꼭질 위장 게임(공개 저장소 octopus7/chameleon)을 코드부터 읽었습니다. “몸에 어떻게 색을 칠하나”와 “여러 명이 어떻게 같은 게임을 보나(네트워크)” 두 질문을 그림과 함께 위에서 아래로 차근차근 풀어봅니다.

🧭

이 글 읽는 법위에서 아래로 순서대로 읽으면 됩니다. 파란 상자(쉽게 말하면)와 그림만 따라가도 전체가 잡히고, 회색으로 접힌 “⌄ 더 깊이”는 코드까지 궁금할 때만 펼치세요.

한 줄 요약

숨는 사람이 자기 몸을 배경색으로 칠해 숨고, 술래가 시간 안에 찾는 게임입니다. “색칠” 부분과 “게임 규칙·네트워크” 부분이 코드에서 깔끔하게 나뉘어 있어요.

색칠

물컹한 몸에 스프레이로 칠하듯 색을 입힙니다. 클릭 한 번이 두 곳(몸 꼭짓점 색 + 표면 그림 3장)에 동시에 반영되고, 몸을 움직여도 자국이 몸에 붙어 따라옵니다.

네트워크

서버가 심판입니다(서버 권위). 서버가 정한 라운드 상태·역할만 모두에게 내려가고, 특별한 통신 기술 없이 언리얼 엔진의 기본 기능만 씁니다.

가장 큰 함정

위장 게임인데 칠한 색이 남에게 안 보입니다. 색칠은 “내 화면에서만” 일어나고 아직 공유되지 않아요. 온라인 접속(EOS)도 계획만 있고 아직 코드엔 없습니다.

01 · 어떤 게임인가

색칠하는 카멜레온과, 그걸 찾는 술래

🦎

쉽게 말하면이름 그대로예요. 숨는 쪽은 물컹한 카멜레온 몸을 가지고, 주변 색을 찍어 자기 몸을 배경에 맞춰 칠해 숨습니다. 술래는 제한 시간 안에 그 카멜레온을 찾아 다가가면 “잡음”이 됩니다.

코드는 크게 두 덩어리로 나뉩니다. 이 구분이 글 전체의 지도예요 — 색칠이 궁금하면 왼쪽(플러그인), 네트워크가 궁금하면 오른쪽(게임 규칙)을 보면 됩니다.

🎨 ChameleonPainter 색칠 담당

Plugins/ChameleonPainter

몸 만들기, 브러시로 칠하기, 색 고르는 팔레트·스포이드, 스프레이 효과. 네트워크 코드는 전혀 없습니다 — 순수하게 “내 화면에서의 색칠”만 담당.

🎮 HideSeek 규칙 담당

Source/HideSeek

라운드 진행, 술래·숨는이 역할 나누기, 잡기 판정, 그리고 여러 명을 맞춰주는 네트워크(동기화)가 전부 여기에 있습니다.

02 · 몸에 색을 칠하는 법

클릭 한 번이 몸에 색으로 남기까지

🖌️

쉽게 말하면스프레이로 벽에 낙서하는 것과 같아요. 몸의 어딘가를 클릭하면 그 자리에 물감이 묻습니다. 다만 이 몸은 미리 만든 3D 캐릭터가 아니라, 프로그램이 그때그때 빚어낸 물컹한 덩어리예요.

클릭에서 색이 남기까지는 아래 순서로 흘러갑니다. 위에서 아래로 따라가 보세요.

🏷️

③이 왜 중요한가몸은 걸을 때 출렁입니다. 만약 “움직이는 순간의 위치”에 색을 찍으면 다음 순간 자국이 몸에서 미끄러져요. 그래서 스티커를 팔에 붙이면 팔을 움직여도 스티커가 따라오듯, 색을 “가만히 선 몸” 기준 위치로 바꿔 저장합니다. 덕분에 걸어도 위장 무늬가 몸에 착 붙어 있어요.

왜 두 갈래(④a·④b)로 칠할까요? 꼭짓점 색은 계산이 가벼워 즉시 보이고, 표면 그림 3장은 픽셀 단위라 훨씬 세밀합니다. 둘을 함께 써서 “빠른 반응 + 자세한 표현”을 동시에 얻습니다.

더 깊이 — 몸을 빚는 법, 색이 섞이는 공식, 데이터 구조

몸체 생성(marching tetrahedra). 21개의 가우시안 “덩어리(FBodyBlob)”가 만드는 스칼라 필드를 격자로 훑어 등가면(FieldThreshold=0.62)을 추출, UProceduralMeshComponent 위에 매 생성마다 CPU로 메시를 만듭니다. 이때 표면을 24개 UV 섬으로 펼쳐 두는데(6×4 아틀라스) 이게 ④b 텍스처 칠하기의 좌표가 됩니다. 걷기용 13개 절차 본과 스킨 웨이트도 이 단계에서 만듭니다.

색 섞기 공식. ④a(꼭짓점 색)는 스트로크가 추가될 때마다 RebuildVertexColors가 모든 꼭짓점을 처음부터 다시 계산합니다(정점수 × 스트로크수). 각 점은 바탕색에서 시작해 반경 안의 스트로크마다 거리 falloff = pow(1−정규화거리, Falloff)만큼 HSV 색공간으로 보간됩니다. ④b(텍스처)는 안쪽 반경까지 꽉 채우고 가장자리만 페더링하는 방식이라 falloff 곡선이 조금 다릅니다. 색 블렌딩은 둘 다 HSV 보간이라 RGB 직선 보간과 색 전이가 다릅니다.

FChameleonPaintStroke(자국 하나의 데이터): 위치·노멀(가만히 선 몸 기준), 반경(기본 12, 브러시 18cm), 강도, falloff, 색, 거칠기(0.84), 금속감(0). 이 배열 PaintStrokes는 UPROPERTY조차 아닌 순수 멤버라 복제·저장 대상이 아닙니다 — 04장에서 다룰 “색이 남에게 안 보이는” 이유의 근거입니다.

바탕색 vs 초기화. SetCamouflageBaseColor는 몸 전체 바탕색만 바꾸고, ClearPaint가 스트로크와 텍스처를 전부 되돌리는 완전 초기화입니다. 스포이드로 화면·표면 색을 찍어 브러시 색으로 쓰는 기능도 있습니다.

03 · 색을 고르는 법

팔레트로 고르거나, 스포이드로 찍거나

🎯

쉽게 말하면그림판의 색 고르기와 똑같습니다. 팔레트(컬러 피커)에서 직접 고르거나, 스포이드로 화면 속 색을 콕 찍어 그대로 브러시 색으로 씁니다. 배경색을 찍어 위장하는 게 이 게임의 핵심 재미죠.

  • 팔레트(컬러 피커) — RGB·HSV 슬라이더, 색상환, 자주 쓰는 색 11개, 최근 쓴 색 10개, 적용 버튼이 있습니다. 전부 하나의 “현재 색” 값을 함께 바라보며 바꿉니다.
  • 스포이드 — 두 방식. 월드에 광선을 쏴 맞은 표면의 색을 읽거나, 화면에 실제로 찍힌 픽셀 색을 그대로 읽습니다.
  • 팔레트는 색칠에 직접 손대지 않습니다 — “색이 바뀌었다”는 신호만 보내고, 캐릭터가 그 색을 받아 브러시 색으로 씁니다(느슨한 연결).
더 깊이 — 순수 C++ UMG, 커스텀 Slate 색상환, 픽셀 읽기

UI는 블루프린트가 아니라 순수 C++ UMG로 짜였고, 디자이너 위젯이 없으면 코드로 위젯 트리를 통째로 만듭니다. 색상환은 UMG가 아니라 커스텀 Slate 리프위젯(SChameleonHSVColorWheel)으로, 바깥 링=색상(Hue) 96세그먼트, 안쪽 사각 디스크=채도/명도 34×34를 마우스 드래그로 편집합니다. 컨트롤끼리 서로를 갱신하다 무한 루프에 빠지지 않게 bUpdatingControls 가드를 씁니다. 스포이드의 화면 픽셀 읽기는 Viewport::ReadPixels, 표면 색 읽기는 히트 지점의 UV로 머티리얼 텍스처를 샘플하거나 벡터 파라미터를 조회합니다.

04 · 여러 명이 함께 하기(네트워크)

서버가 심판이고, 정해진 것만 모두에게 내려간다

⚖️

쉽게 말하면여러 명이 같은 게임을 하려면 “누구 말이 진짜냐”를 정하는 심판이 필요합니다. 여기선 서버가 심판이에요. 서버가 정한 것(누가 술래인지, 몇 초 남았는지)만 모두에게 똑같이 내려가고, 플레이어는 그걸 받아 보기만 합니다. 이런 방식을 “서버 권위”라고 부릅니다.

내려가는 정보는 딱 “라운드 상태·역할·발각 여부”뿐이고, 서버→플레이어 방향의 특별 메시지(RPC)는 두 개밖에 없습니다 — 입력 잠그기와 화면 전환 연출. 플레이어→서버 방향은 아예 없어서, 지금 구조에선 플레이어가 서버 상태를 직접 바꿀 수 없습니다.

⚠️ 온라인 접속(EOS)은 “계획”일 뿐, 아직 코드엔 없다

저장소에 EOS(Epic Online Services) 통합 계획 문서가 있어 “온라인 붙었나?” 착각하기 쉽지만, 실제 코드엔 온라인 접속 기능이 하나도 배선돼 있지 않습니다. 관련 의존성은 주석 처리 상태이고, 세션 생성·로그인 같은 호출도 0건입니다.

즉 지금은 한 컴퓨터/PIE에서 테스트하는 단계이고, 서버 권위 구조만 “나중에 온라인 붙이면 되도록” 미리 갖춰 둔 상태예요.

더 깊이 — 실제로 복제되는 값과 RPC 전수(코드 근거)

아래는 검증 에이전트가 DOREPLIFETIME·헤더 매크로를 직접 대조한 결과입니다. 모두 서버→전 클라 방향이며, 이 중 “칠한 색”은 없습니다.

RPC는 정확히 2개, 둘 다 서버→소유 클라(Client·Reliable)입니다: ClientSetHideSeekInputEnabled(이동/시야 입력 잠금), ClientPlayHideSeekTransition(페이드·전환 UI + Niagara 연출). 플레이어→서버(Server RPC)와 브로드캐스트(NetMulticast)는 0건. 이동은 언리얼 기본 캐릭터 복제에 맡깁니다.

05 · 한 판이 흘러가는 순서

서버가 시계를 쥐고 단계를 넘긴다

⏱️

쉽게 말하면한 판은 대기 → 술래 뽑기 → 방 로딩 → 숨는 시간 → 찾는 시간 → 결과 순으로 흘러갑니다. 이 진행과 시계(남은 시간)를 모두 서버가 쥐고, 플레이어에겐 결과만 내려보냅니다. 그래서 사람마다 시간이 어긋날 일이 없어요.

여기서 눈여겨볼 점은 시계를 서버가 쥔다는 것입니다. 플레이어 화면이 각자 초를 세는 게 아니라, 서버가 0.2초마다 “남은 시간”을 계산해 내려보내요. 그래서 모두의 시계가 항상 같습니다.

더 깊이 — 상태머신 전이, 서버 시계, 이중 기록·수동 갱신

상태머신은 서버 GameMode가 타이머로 구동합니다: WaitingForPlayers → SelectingSeeker → SeekerLobbyWait → LoadingPlayRoom → HideTime(35s) → SeekTime(90s) → RoundEnded → 리셋. 클라와 AIController엔 상태머신 로직이 없고 복제된 상태를 읽기만 합니다. 방(PlayRoom)은 LoadStreamLevel로 라운드마다 스트리밍 로드/언로드합니다.

서버 시계. SetPhase가 단계 종료 시각을 잡고, 0.2초 주기 ClockTimer가 (종료시각 − 현재시각)을 GameState.RemainingSeconds에 써서 복제합니다.

수동 OnRep. RepNotify는 원래 “값을 받은 클라”에서만 자동 실행됩니다. 그래서 서버는 값을 바꾼 뒤 OnRep_*를 직접 호출해, 리슨 서버·스탠드얼론 호스트에서도 UI 델리게이트(OnRoundPhaseChanged 등)가 똑같이 발화되게 합니다.

포획 판정은 SeekTime 동안 일정 주기로 서버가 술래–숨는이 거리²를 검사(CaptureRadius=160cm)해 잡힘 처리합니다. AI 참가자도 사람과 완전히 같은 복제 컴포넌트를 쓰고 bAIControlledParticipant 플래그만 추가입니다.

06 · 프로젝트 구조

4개 모듈, 그리고 “콘텐츠를 코드로 만든다”

🧱

쉽게 말하면코드가 게임 본체 + 색칠 플러그인으로 나뉘고, 각각 실행용·에디터용이 있어 총 4덩어리입니다. 특이한 점은 블루프린트·머티리얼·맵 같은 게임 콘텐츠를 파일로 저장하지 않고 “코드로 생성”한다는 것 — 새로 받아도 코드가 알아서 똑같이 만들어냅니다.

⚠️ 그냥 열면 숨바꼭질이 아니라 “색칠 연습장”이 뜬다

콘텐츠를 만드는 두 스크립트가 “기본으로 열 맵” 설정을 서로 덮어씁니다. 현재 저장소 설정은 색칠 테스트 맵을 가리키고 있어, 프로젝트를 그대로 실행하면 숨바꼭질 라운드가 아니라 위장 채색 샌드박스가 열립니다. 숨바꼭질을 보려면 HideSeek 쪽 콘텐츠 스크립트를 돌려 기본 맵을 로비로 바꿔야 합니다.

더 깊이 — 모듈·의존성·콘텐츠 생성 스크립트·레벨 스트리밍

4개 C++ 모듈: 게임 = HideSeek(실행) + HideSeekEditor(에디터), 플러그인 = ChameleonPainter(실행) + ChameleonPainterEditor(에디터). 실행 의존성은 AIModule·EnhancedInput·NavigationSystem·Niagara·UMG + 몸체용 ProceduralMeshComponent. 온라인 모듈은 없습니다.

콘텐츠 생성: 플러그인은 CanContainContent=false이고, 두 에디터 커맨들릿이 블루프린트·데이터애셋·위젯·머티리얼(노드 그래프째)·Enhanced Input·맵을 코드로 만듭니다. 목적은 “새 체크아웃에서도 C++ + ini + 원본 PNG만으로 전체 콘텐츠를 결정적으로 재생성”하는 것입니다.

레벨: 로비(L_HideSeek_Lobby)가 상시 지속 레벨, 방(L_HideSeek_PlayRoom)이 그 안의 동적 스트리밍 서브레벨입니다. 참고로 채색의 핵심 설정 bSupportUVFromHitResults=True도 여기 들어 있습니다(광선 히트에서 UV를 얻어 칠하기 위함).

07 · 정리

뼈대는 잘 섰고, 살은 아직 로컬에

잘한 점

역할이 깔끔하게 나뉘어 있습니다. 색칠(플러그인)과 규칙·네트워크(게임 모듈)가 완전히 분리돼 읽기 쉽고, 서버 권위 구조는 나중에 온라인을 붙이기 좋게 미리 갖춰졌습니다.

주의할 점

색칠은 아직 프로토타입 성능입니다. 몸을 매번 새로 빚고, 색이 추가될 때마다 전 꼭짓점을 다시 계산합니다. 저장소 TODO도 이걸 최적화 과제로 적어 뒀습니다.

가장 큰 구멍

위장 게임의 핵심인 “칠한 색”이 공유되지 않습니다. 지금 그대로 온라인에 넣으면 내가 칠한 위장이 술래에게 안 보여요. 계획 문서는 “색을 가벼운 이벤트로 서버가 복제하라”는 방향을 제시하지만 아직 미구현입니다.

한마디로 “여럿이 함께 할 뼈대는 잘 서 있는데, 정작 이 게임을 이 게임답게 만드는 색칠 공유가 아직 빠져 있다”는 상태입니다. 다음 한 걸음이 뭔지 분명한, 공부하기 좋은 코드예요.

분석 방법: 저장소를 얕은 클론 후 4개 병렬 리더(색칠 / 색 고르기·입력 / 네트워크 / 구조)로 코드를 읽고, 네트워크·동기화 주장은 별도 검증 에이전트가 DOREPLIFETIME·RPC 매크로를 직접 grep해 대조했습니다.

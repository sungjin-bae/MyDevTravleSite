Q1 CPP-01 주니어 서술형 스택 vs 힙 메모리

스택(stack)과 힙(heap) 메모리의 차이를 할당/해제 방식, 속도, 크기, 수명 관리 관점에서 설명하세요. 그리고 다음 코드에서 벡터 객체 v 자체와 v가 담는 실제 요소 데이터는 각각 어느 영역에 놓이는지 답하세요.

void Update() {
    std::vector<int> v;
    v.push_back(10);
    v.push_back(20);
}

마지막으로, 게임 코드에서 스택과 힙을 각각 언제 쓰는 것이 적절한지 예를 들어 설명하세요.

모범답안 보기
  • 스택(자동 저장 기간): 함수 호출 프레임에 자동 할당되고 스코프를 벗어나면 자동 소멸(RAII의 기반). 스택 포인터만 이동하면 되어 할당/해제가 매우 빠르지만, 크기가 제한적(스레드 스택은 보통 수백 KB~수 MB 수준, 예: Windows 메인 스레드 기본 1MB)이라 큰 배열이나 깊은 재귀는 스택 오버플로 위험이 있다. 지역 변수와 함수 매개변수가 여기에 놓인다.
  • 힙(동적 저장 기간, 자유 저장소): new/malloc으로 런타임에 할당하고 수명을 프로그래머(또는 스마트 포인터/컨테이너)가 관리한다. 크기가 크지만 할당 비용이 높고 단편화가 생길 수 있으며, 해제를 놓치면 누수가 발생한다.
  • 위 코드: v라는 벡터 헤더(내부 포인터·size·capacity)는 스택에 있지만, push_back으로 담은 요소 버퍼(10, 20)는 힙에 있다. 스코프 종료 시 v의 소멸자가 힙 버퍼를 해제한다.
  • 게임 예시: 프레임마다 계산하는 작은 임시 벡터/행렬 값은 스택, 개수가 런타임에 정해지고 수명이 스코프를 넘어가는 엔티티·리소스는 힙(가급적 std::vector/unique_ptr로 관리).
  • 오개념 교정: "new를 안 쓰면 무조건 스택"은 부정확하다. 전역/static은 정적 저장 기간(별도 영역)이고, 멤버 변수는 소속 객체가 놓인 곳(스택 객체면 스택, 힙 객체면 힙)에 따라간다.

채점 포인트

  • 자동 저장 기간 vs 동적 저장 기간
  • 속도·크기·수명관리·오버플로 차이
  • vector 헤더는 스택, 요소 버퍼는 힙
  • 전역/static은 별도 정적 영역
Q2 CPP-02 주니어 단답형 const 정확성 / constexpr / 참조 vs 포인터

다음 네 가지 짧은 질문에 각각 간결히 답하세요.

  1. const int* p 와 int* const p 의 차이는?
  2. const 와 constexpr 의 핵심 차이는? constexpr 함수는 항상 컴파일 타임에 평가되나요?
  3. 참조(reference)와 포인터(pointer)의 차이를 2가지 이상 드세요.
  4. 멤버 함수 뒤에 붙는 const(예: int Size() const;)는 무엇을 보장하나요?
모범답안 보기
  1. const int* p: 가리키는 대상이 const → 대상 값 변경 불가, 포인터 재지정은 가능. int* const p: 포인터 자체가 const → 재지정 불가, 대상 값 변경은 가능. (오른쪽에서 왼쪽으로 읽으면 쉽다. const int* const p는 둘 다 const.)
  2. const 는 "읽기 전용(불변)"을 보장할 뿐 컴파일 타임 상수라는 보장은 아니다(런타임 초기화도 가능). constexpr 는 컴파일 타임 상수 평가가 가능함을 뜻한다. constexpr 변수는 반드시 컴파일 타임 상수지만, constexpr 함수는 상수 인자로 상수 문맥에서 호출되면 컴파일 타임에, 런타임 인자로 호출되면 런타임에 평가된다(항상 컴파일 타임 아님). 항상 컴파일 타임을 강제하려면 C++20의 consteval.
  3. 참조는 (a) 반드시 초기화되고 이후 재바인딩 불가, (b) 정상적으로는 null이 될 수 없음, (c) 대상 그 자체처럼 문법상 사용(역참조·주소 연산 불필요). 포인터는 null 가능, 재지정 가능, 포인터 산술 가능, 자기 자신도 크기를 가진 객체.
  4. 그 멤버 함수가 (mutable이 아닌) 객체 상태를 수정하지 않음을 보장하고, this가 const T*가 되어 const 객체에서도 호출 가능해진다.

채점 포인트

  • const 위치는 오른쪽→왼쪽으로 해석
  • constexpr 함수는 문맥에 따라 CT 또는 RT
  • 참조=재바인딩 불가·null 불가
  • const 멤버함수=비변경 보장·const 객체 호출 가능
Q3 CPP-03 주니어 코드분석 가상 소멸자 / vtable / 소멸 순서

다음 코드에서 delete e; 시점에 무슨 문제가 발생하나요? 근본 원인과 수정 방법을 설명하고, override 키워드의 역할, 그리고 (수정 후) 객체가 소멸되는 순서를 서술하세요.

class Entity {
public:
    ~Entity() { /* 공통 정리 */ }        // (1)
    virtual void Update() {}
};

class Player : public Entity {
    std::vector<int> inventory_;         // 힙을 소유하는 멤버
public:
    ~Player() { /* Player 자원 해제 */ }
    void Update() override {}
};

int main() {
    Entity* e = new Player();
    e->Update();
    delete e;                            // (2)
}
모범답안 보기
  • 문제 (2): ~Entity()가 가상(virtual)이 아니므로, 기반 클래스 포인터로 파생 객체를 delete 하는 것은 미정의 동작(UB) 이다. 표준은 "정적 타입과 동적 타입이 다르고 정적 타입의 소멸자가 non-virtual이면 UB"라고 규정한다. 실제 구현 대부분에서는 ~Entity()만 실행되고 ~Player()가 호출되지 않아, inventory_(vector)를 포함한 파생 멤버 자원이 정리되지 않는 누수가 생긴다.
  • 수정: 다형적으로(기반 포인터로 delete) 쓸 기반 클래스는 가상 소멸자 필수. virtual ~Entity() = default; 로 선언한다.
  • vtable/vptr: 가상 함수가 하나라도 있으면 클래스마다 vtable이 생기고 객체에 vptr이 심긴다. 소멸자가 virtual이면 vtable을 통해 런타임 동적 타입의 소멸자부터 올바르게 호출된다.
  • 소멸 순서(수정 후): ~Player() 본문 실행 → Player의 멤버(inventory_) 소멸 → ~Entity() 본문 실행. 즉 생성의 정확한 역순이다.
  • override: Update가 기반의 가상 함수를 실제로 재정의하는지 컴파일러가 검증해 준다(시그니처 오타 등을 컴파일 에러로 잡음). final은 추가 재정의/상속을 금지한다.
  • 오개념 교정: "가상 함수가 있으니 소멸자도 자동으로 가상이 된다"는 틀렸다. 소멸자는 반드시 명시적으로 virtual 선언해야 한다.

채점 포인트

  • non-virtual dtor로 base 포인터 delete = UB(파생 멤버 누수)
  • 수정: virtual ~Entity()
  • 소멸 순서=파생→멤버→기반(생성의 역순)
  • override는 재정의 시그니처 검증(자동 virtual 아님)
Q4 CPP-04 미들 서술형 스마트 포인터 / 순환참조 / 제어 블록

std::unique_ptr, std::shared_ptr, std::weak_ptr의 용도와 차이를 설명하세요. 이어서 shared_ptr의 순환 참조(cyclic reference) 가 왜 메모리 누수를 유발하는지, weak_ptr로 어떻게 해결하는지 설명하고, shared_ptr의 제어 블록(control block) 이 무엇인지 답하세요.

모범답안 보기
  • unique_ptr: 단독 소유. 복사 불가, 이동만 가능. 오버헤드가 사실상 없어(커스텀 deleter 없으면 raw 포인터 크기) 기본 선택지.
  • shared_ptr: 공유 소유. strong 참조 카운트가 0이 되면 대상을 삭제한다. 객체 포인터 + 제어 블록 포인터로 보통 포인터 2개 크기.
  • weak_ptr: 소유하지 않는 관찰자. strong count에 영향을 주지 않으며, lock() 호출 시점에 대상이 살아 있으면 shared_ptr를 얻는다(아니면 빈 것).
  • 순환 참조: A가 B를, B가 A를 서로 shared_ptr로 잡으면 외부 참조가 모두 사라져도 서로의 strong count를 1 이상 유지시켜 카운트가 0이 되지 않는다 → 둘 다 해제되지 않아 누수. 게임에서 부모↔자식, 옵저버 상호 참조에서 흔하다.
  • 해결: 소유 방향만 shared_ptr로 두고, 역방향(소유하지 않는 쪽, 예: 자식→부모)을 weak_ptr 로 만들어 사이클을 끊는다.
  • 제어 블록: shared_ptr가 관리하는 별도의 (힙) 블록으로, strong count, weak count, deleter/allocator 를 담는다. 객체 메모리는 strong count가 0이면 해제되지만, weak_ptr가 남아 있으면 제어 블록은 weak count가 0이 될 때까지 유지된다. make_shared는 객체와 제어 블록을 한 번의 할당으로 합쳐 성능·지역성 이점이 있다(단 weak_ptr가 살아 있는 동안 객체 메모리도 함께 잡혀 있는 트레이드오프).
  • 오개념 교정: "shared_ptr는 스레드 세이프"는 절반만 맞다. 참조 카운트 증감은 원자적이라 안전하지만, 가리키는 객체의 데이터 접근은 별도 동기화가 필요하다.

채점 포인트

  • unique=단독소유, shared=공유(strong count), weak=비소유 관찰
  • 순환참조 시 strong count가 0이 안 되어 누수
  • 역참조를 weak_ptr로 끊어 해결
  • 제어 블록=strong/weak count+deleter, make_shared 단일할당
Q5 CPP-05 미들 코드분석 반복자 무효화 (iterator invalidation)

다음 코드는 짝수를 제거하려는 의도입니다. 무슨 문제가 있으며 왜 위험한지 설명하고, 올바른 수정안을 제시하세요. 또한 std::vector에서 반복자/포인터가 무효화되는 규칙을 정리하세요.

std::vector<int> v = {1, 2, 4, 6, 3, 8};
for (auto it = v.begin(); it != v.end(); ++it) {
    if (*it % 2 == 0) {
        v.erase(it);   // 짝수 제거
    }
}
모범답안 보기
  • 버그: vector::erase(it)는 지워진 위치 이후의 모든 반복자·참조·포인터를 무효화한다. 무효화된 it을 그대로 ++it 하는 것은 UB이며, 실무적으로도 요소를 건너뛴다. 위 예처럼 연속된 짝수(2,4,6, …)를 지나면 erase 직후 다음 원소로 밀려온 값을 ++it로 뛰어넘어 일부 짝수가 남는다.
  • 수정 1 (erase 반환값 사용): erase는 다음 유효 반복자를 반환한다.
for (auto it = v.begin(); it != v.end(); ) {
    if (*it % 2 == 0) it = v.erase(it);
    else ++it;
}
  • 수정 2 (권장, erase-remove 관용구, O(n)):
v.erase(std::remove_if(v.begin(), v.end(),
        [](int x){ return x % 2 == 0; }), v.end());
// C++20이면: std::erase_if(v, [](int x){ return x % 2 == 0; });
  • vector 무효화 규칙: push_back/insert가 capacity를 초과해 재할당하면 모든 반복자·참조·포인터가 무효화된다. erase는 지운 지점부터 end까지 무효화된다.
  • 노드 기반 컨테이너와의 차이: std::list/std::map/std::set은 노드 기반이라 erase가 삭제된 원소의 반복자·참조만 무효화하고 나머지 반복자·참조는 유지된다. 다만 삭제된 it 자체는 무효화되므로, 위 루프처럼 erase(it) 후 다시 ++it 하는 것은 이들 컨테이너에서도 여전히 UB다 — it = c.erase(it)(C++11+) 또는 옛 관용구 c.erase(it++)로 다음 반복자를 받아야 한다. unordered_map은 rehash 시 반복자만 무효화되고(원소에 대한 포인터·참조는 유지) 그 외에는 삭제 원소만 무효화된다.
  • 오개념 교정: v.erase(it); ++it; 가 "그냥 다음으로 넘어간다"는 생각은 위험하다 — 어떤 컨테이너든 삭제된 반복자를 다시 증가시키면 안 되고, 반드시 erase의 반환값을 받아야 한다.

채점 포인트

  • erase는 지운 지점 이후 반복자 무효화 → ++it은 UB
  • 수정: it = v.erase(it) 반환값 사용
  • 권장: erase-remove / std::erase_if
  • 재할당 시 vector 전체 무효; list/map은 삭제 원소만 무효(나머지 유지)이나 erase 반환값은 여전히 필요
Q6 CPP-06 미들 서술형 이동 시맨틱 / std::move / rule of 0·3·5 / 완벽전달

이동 시맨틱(move semantics)과 std::move가 무엇인지 설명하세요. 특히 "std::move가 실제로 무언가를 이동시킨다"는 표현이 왜 부정확한지, 이동 후 원본 객체의 상태는 어떤지 서술하세요. 이어서 rule of 0/3/5 를 설명하고, 완벽 전달(perfect forwarding) 에서 std::forward의 역할이 std::move와 어떻게 다른지 답하세요.

모범답안 보기
  • 이동 시맨틱: 임시(rvalue)나 더 이상 쓰지 않을 객체의 자원(힙 버퍼 등)을 깊은 복사 대신 "빼앗아" 넘기는 것. 이동 생성자/이동 대입 연산자(T(T&&), T& operator=(T&&))가 이를 구현한다. 예: vector 이동은 내부 포인터만 옮기고 원본을 빈 상태로 둔다.
  • std::move: 실제로 이동을 수행하지 않는다. 인자를 rvalue 참조로 캐스팅만 하는 것(static_cast<T&&>)이다. 그 결과 오버로드 해석이 이동 생성자/대입을 선택하게 만들 뿐이며, 실제 이동은 그 생성자/대입 본문 안에서 일어난다.
  • 이동 후 원본: 유효하지만 미지정(valid-but-unspecified) 상태다. 다시 대입하거나 소멸시키는 것은 안전하지만, 값에 의존하는 사용(use-after-move)은 논리 버그다.
  • rule of 0: 자원을 직접 관리하지 말고 vector/unique_ptr 같은 RAII 멤버로만 구성해 특수 멤버 함수를 하나도 선언하지 않는 것(가장 권장). rule of 3: 소멸자·복사 생성자·복사 대입 중 하나를 직접 정의하면 대개 셋 다 필요하다. rule of 5: 이동까지 고려하면 이동 생성자·이동 대입을 더해 5개를 함께 고려한다. 주의: 사용자가 소멸자나 복사 연산을 선언하면 이동 연산이 자동 생성되지 않는다.
  • 완벽 전달: 템플릿의 T&&(전달 참조/forwarding reference)로 받은 인자의 값 카테고리(lvalue/rvalue)를 하위 함수로 그대로 넘기기 위해 std::forward<T>(x)를 쓴다. std::move는 무조건 rvalue로 캐스팅하는 반면, std::forward는 원본이 lvalue면 lvalue로, rvalue면 rvalue로 조건부 캐스팅한다.
  • 오개념 교정: "std::move가 이동을 실행한다", "이동 후 원본을 자유롭게 써도 된다"는 모두 틀리다.

채점 포인트

  • std::move는 이동이 아니라 rvalue로의 캐스팅
  • 이동 후 원본=valid-but-unspecified
  • rule of 0/3/5, 소멸자·복사 선언 시 이동 자동생성 안 됨
  • forward는 조건부·move는 무조건 rvalue 캐스팅
Q7 CPP-07 시니어 실무시나리오 STL 컨테이너 시간복잡도 / 메모리 레이아웃

게임 서버에서 수만 개의 엔티티를 관리합니다. 핵심 요구는 (a) ID로 빠른 조회, (b) 매 프레임 전체 순회하며 업데이트 두 가지입니다.

std::vector, std::map, std::unordered_map의 시간 복잡도와 메모리 레이아웃(캐시 지역성) 을 비교하고, 어떤 컨테이너(또는 조합)를 선택할지 트레이드오프와 함께 설명하세요.

모범답안 보기
  • 시간 복잡도: vector — 인덱스 접근 O(1), 끝 삽입 amortized O(1), 값 검색 O(n), 임의 위치 삽입/삭제 O(n). map(균형 이진 트리) — 조회/삽입/삭제 O(log n), 키 정렬 유지. unordered_map(해시) — 평균 O(1), 최악 O(n)(충돌·리해시), 순서 없음.
  • 메모리 레이아웃: vector는 연속 메모리라 전체 순회 시 캐시 지역성이 최고이고 프리페치에 유리하다. map/unordered_map은 요소마다 별도 노드를 할당하는 노드 기반이라 순회 시 pointer chasing으로 캐시 미스가 잦다. unordered_map은 버킷 배열 + 노드 구조라 순회가 메모리상 흩어진다.
  • 권장 설계(하이브리드): 매 프레임 도는 (b) 업데이트가 hot path이므로 엔티티 본체는 연속 배열(vector 혹은 SoA) 에 두어 순회 캐시 효율을 확보하고, (a) 조회는 ID→인덱스 매핑용 unordered_map (또는 ID가 조밀하면 vector 인덱스/slot map)을 별도로 둔다. 이러면 조회는 평균 O(1), 순회는 연속 접근으로 둘 다 만족한다.
  • 실무 팁: 크기를 알면 reserve()로 재할당(및 반복자/포인터 무효화)을 방지한다. unordered_map은 rehash 시 반복자 무효화·노드 할당 비용이 있다. 정렬이 정말 필요할 때만 map. vector 중간 삭제가 잦으면 순서 무관 시 swap-and-pop, 안정 ID가 필요하면 slot map을 고려한다.
  • 오개념 교정: "unordered_map이 항상 map보다 빠르다"는 단정은 위험하다(작은 N, 정렬 필요, 최악 케이스, 캐시 특성에 따라 다름). "O(1)이면 실제로도 항상 빠르다"도 상수·캐시를 무시한 오해다.

채점 포인트

  • vector 연속=캐시 지역성·O(1) 접근 / map O(log n) 정렬 / unordered_map 평균 O(1)
  • 노드 기반은 pointer chasing으로 캐시 미스
  • 하이브리드: 연속 저장 순회 + ID→인덱스 맵
  • reserve로 재할당·무효화 방지, 복잡도≠실측 속도
Q8 CPP-08 시니어 코드분석 미정의 동작 / 객체 수명 / 무효화 / use-after-move

다음 세 함수에는 각각 서로 다른 원인의 미정의 동작(UB)이 숨어 있습니다. (1), (2), (3) 각각의 원인을 진단하고 수정안을 제시한 뒤, 이들을 관통하는 공통 원칙을 서술하세요.

const std::string& FindName(int id) {
    std::string name = LookupName(id);
    return name;                     // (1)
}

void Tick(std::vector<Actor>& actors) {
    Actor* boss = &actors[0];
    actors.push_back(Actor{});       // (2)
    boss->Update();
}

void Give(std::unique_ptr<Item> item) {
    g_inventory.push_back(std::move(item));
    item->OnEquip();                 // (3)
}
모범답안 보기
  • (1) 지역 변수 참조 반환 → dangling: name은 함수 반환과 함께 소멸하는데 그 참조를 반환한다. 호출부가 그 참조를 사용하면 수명이 끝난 객체 접근(UB)이다. 수정: 값으로 반환(std::string FindName(int id)) — RVO/이동으로 비용이 크지 않다.
  • (2) 재할당에 의한 포인터 무효화: &actors[0]로 얻은 boss는 push_back이 capacity를 넘겨 재할당하면 기존 버퍼가 해제되어 dangling이 된다(vector 재할당 시 모든 포인터·참조·반복자 무효화). 수정: push_back 이후 인덱스로 다시 접근(actors[0].Update();), 또는 미리 reserve()로 재할당 방지, 또는 순회 중 컨테이너 크기 변경을 피한다.
  • (3) use-after-move: std::move로 소유권을 넘긴 뒤 item은 unique_ptr 규약상 nullptr이다. item->OnEquip()는 널 역참조(UB). 수정: 이동 전에 필요한 호출을 하거나, 컨테이너에 넣은 뒤 새 소유자를 통해 접근한다(g_inventory.back()->OnEquip();).
  • 공통 원칙: 참조·포인터·반복자는 대상 객체의 수명과 (컨테이너의 경우) 재할당 여부에 종속되는 "빌린 핸들"이다. 핸들의 유효 구간을 항상 의식하고, 소유권을 이전(move)한 뒤에는 원본을 값 용도로 쓰지 않아야 한다.

채점 포인트

  • (1) 지역 변수 참조 반환=dangling → 값 반환
  • (2) push_back 재할당으로 포인터 무효 → reserve/인덱스 재접근
  • (3) move 후 unique_ptr는 nullptr → 널 역참조
  • 빌린 핸들의 수명·무효화·소유권 이전 인식

Q9 CPX-01 주니어 단답형 람다 캡처

아래 세 람다는 어떤 클래스의 멤버 함수 안에 있고, 본문에서 지역 변수와 멤버 변수를 사용한다고 가정한다. 세 캡처 절의 의미를 각각 한 줄로 설명하고, 이 람다를 std::thread나 이벤트 콜백처럼 자신을 생성한 스코프보다 오래 사는 곳에 넘길 때 어떤 캡처가 위험한지 답하시오.

auto a = [=]   { /* ... */ };
auto b = [&]   { /* ... */ };
auto c = [this]{ /* ... */ };
모범답안 보기
  • [=]: 람다가 사용하는 외부 변수를 캡처 시점의 값(복사본)으로 저장한다. 복사본은 기본적으로 const이며 mutable을 붙이면 람다 내부에서만 수정 가능(원본엔 영향 없음).
  • [&]: 외부 변수를 참조로 잡아 원본을 직접 읽고 쓴다.
  • [this]: 멤버 접근을 위해 this 포인터를 값으로 복사한다(객체 자체가 아니라 포인터). 결과적으로 멤버는 참조처럼 접근된다.

스코프보다 오래 사는 곳에 넘길 때 위험한 것은 [&](그리고 [this])다. 지역 변수/객체가 파괴된 뒤 dangling reference에 접근해 UB가 된다. 이 경우 필요한 것만 값 캡처하거나, 수명이 필요하면 shared_ptr를 캡처하거나 [obj = std::move(x)] 같은 초기화 캡처(C++14)를 쓴다. 객체 자체의 복사가 필요하면 [*this](C++17)로 객체를 복사할 수 있다.

흔한 오해: [=]면 this까지 값 복사되어 안전하다는 생각 — [=]도 멤버 접근 시엔 this 포인터만 복사하므로 객체 수명 문제는 그대로다. (C++20에서 [=]의 암시적 this 캡처는 deprecated이고 [=, this]를 명시하도록 권장한다.)

채점 포인트

  • [=] 값복사 / [&] 참조 / [this] 포인터 복사 정확 구분
  • 오래 사는 콜백에서 [&]·[this]는 dangling → UB
  • [=]도 this는 포인터만 복사(객체 수명 미해결) 오해 교정, 객체 복사는 [*this]
Q10 CPX-02 주니어 서술형 데이터 레이스 / mutex

(1) 데이터 레이스(data race)의 정의를 말하고, 왜 이것이 단순히 "값이 좀 틀리는" 수준이 아니라 정의되지 않은 동작(UB)인지 설명하시오. (2) std::mutex + std::lock_guard로 어떻게 방지하는지, (3) std::lock_guard와 std::unique_lock의 차이를 설명하시오.

모범답안 보기
  • 데이터 레이스: 둘 이상의 스레드가 같은 메모리 위치에 접근하고, 그중 최소 하나가 쓰기이며, 그 접근들 사이에 happens-before 관계(동기화)가 없는 상태. C++ 표준상 이는 정의되지 않은 동작이다. "값이 찢어지는(torn)" 정도로 끝나지 않는 이유는, 컴파일러가 "레이스는 없다"를 전제로 레지스터 캐싱·명령 재배열 등 공격적 최적화를 하기 때문이다. 따라서 무한 루프, 크래시 등 임의의 결과가 표준상 허용된다. volatile은 원자성도 스레드 간 가시성·순서도 주지 않으므로 해결책이 아니다.
  • lock_guard로 방지: RAII 객체로, 생성 시 lock(), 소멸 시 unlock()을 자동 호출한다. { std::lock_guard<std::mutex> lk(m); /* 임계 영역 */ }처럼 감싸면 예외가 나도 스코프 이탈 시 안전하게 해제된다.
  • lock_guard vs unique_lock: lock_guard는 가볍고 스코프 내내 잠금 고정, 이동·수동 unlock 불가. unique_lock은 유연 — std::defer_lock으로 지연 잠금, 중간 unlock/relock, try_lock, 이동 가능하며 condition_variable::wait에 필수(대기 중 뮤텍스를 풀었다 다시 잠가야 하므로). 유연성 대신 소유 여부 플래그만큼의 약간의 오버헤드가 있어, 기본은 lock_guard(또는 다중 뮤텍스 데드락을 피하는 C++17 std::scoped_lock)를 쓰고 필요할 때만 unique_lock을 쓴다.

채점 포인트

  • 데이터 레이스 3요소(같은 위치·1개 이상 쓰기·동기화 없음)와 UB
  • volatile은 해결책 아님 명시
  • lock_guard=RAII / unique_lock=유연·cv.wait 필수 차이
Q11 CPX-03 주니어 코드분석 원자성 / atomic

아래 코드는 8개 스레드가 전역 카운터를 각 10만 번씩 증가시켜 800000을 기대한다.

#include <thread>
#include <vector>
#include <cstdio>

int g_kill_count = 0;   // 여러 몬스터 처치 스레드가 누적

void worker() {
    for (int i = 0; i < 100000; ++i)
        ++g_kill_count;
}

int main() {
    std::vector<std::thread> ts;
    for (int i = 0; i < 8; ++i) ts.emplace_back(worker);
    for (auto& t : ts) t.join();
    printf("%d\n", g_kill_count);   // 기대: 800000
    return 0;
}

출력이 800000이 아닐 수 있는 이유는? int를 volatile int로 바꾸면 해결되는가? 올바른 수정을 두 가지 제시하시오.

모범답안 보기
  • 원인: ++g_kill_count는 읽기→수정→쓰기(read-modify-write) 3단계라 원자적이지 않다. 여러 스레드가 동기화 없이 접근하므로 데이터 레이스(UB)이고, 실제로는 증가가 서로 덮여 유실되어 800000보다 작은(그리고 실행마다 달라지는) 값이 나오는 것이 전형적이다.
  • volatile은 해결책이 아니다: volatile은 컴파일러의 일부 최적화(레지스터 캐싱 제거 등)만 막을 뿐, 원자성도, 스레드 간 happens-before(가시성·순서)도 보장하지 않는다. RMW 자체가 여전히 쪼개져 UB가 남는다. (volatile은 MMIO 등 하드웨어 접근용이지 스레드 동기화 도구가 아니다.)
  • 올바른 수정 2가지:
  1. std::atomic<int> g_kill_count{0};로 바꾼다. ++g_kill_count가 원자적 RMW가 된다. 이 카운터는 최종 합만 필요하고 다른 데이터와 순서 의존이 없으며 최종 읽기는 join()(happens-before 제공) 이후이므로 g_kill_count.fetch_add(1, std::memory_order_relaxed);로 완화해 더 빠르게 할 수 있다.
  2. std::mutex로 보호하고 lock_guard 스코프 안에서 증가시킨다. 정확하지만 단순 카운터엔 atomic보다 과하다.
  • 가점: 이 케이스에선 atomic이 mutex보다 적합하며 relaxed로 최적화 가능하다는 점을 짚으면 좋다.

채점 포인트

  • ++는 비원자 RMW → 데이터 레이스로 증가 유실
  • volatile은 원자성·가시성 미보장(해결 아님)
  • atomic(가능하면 relaxed) 또는 mutex 두 수정 제시
Q12 CPX-04 미들 서술형 SoA vs AoS / 캐시 지역성

아래처럼 총 128바이트인 엔티티 수만 개를 매 프레임 순회하며 위치만 갱신(pos += vel * dt)하는 루프가 있다.

struct Entity { Vec3 pos; Vec3 vel; Quat rot; Mesh* mesh; float hp; /* ... 총 128B */ };

AoS(Array of Structs)와 SoA(Struct of Arrays)의 차이를 설명하고, 이 루프에서 어느 쪽이 캐시 관점에서 유리한지 캐시 라인/프리페치 관점으로 설명하시오. 또한 SoA가 항상 정답이 아닌 경우를 하나 드시오.

모범답안 보기
  • AoS: 한 Entity에 모든 필드가 모여 배열로 나열(Entity arr[N]). SoA: 필드별로 분리된 병렬 배열(Vec3 pos[N]; Vec3 vel[N]; ...).
  • 이 루프에선 SoA가 유리하다. 캐시 라인(보통 64B)에 실제로 읽고 쓰는 pos/vel만 조밀하게 담겨 라인 활용률이 높고, 순차 접근이라 하드웨어 프리페처가 잘 예측한다. 반면 AoS는 128B 구조체에서 pos/vel만 필요해도 rot/mesh/hp까지 같은 라인에 끌려와 메모리 대역폭을 낭비하고 캐시 미스가 늘어난다. 덤으로 SoA는 동일 타입이 연속이라 SIMD 벡터화도 쉬워진다.
  • SoA가 항상 정답은 아니다: 한 엔티티의 여러 필드를 함께 자주 접근하는 경우(예: 충돌 처리에서 한 객체의 pos·radius·mask를 묶어 사용), 또는 개별 엔티티를 랜덤 접근하거나 삽입·삭제가 잦은 경우엔 AoS가 지역성·코드 단순성에서 낫다. 핵심은 "무엇을 함께 읽는가"라는 접근 패턴에 맞춰 고르는 것(데이터 지향 설계의 요지)이지, "SoA가 무조건 빠르다"가 아니다.

채점 포인트

  • AoS/SoA 메모리 배치 정확 정의
  • 핫 필드만 순회 시 SoA가 캐시 라인 활용·프리페치·SIMD 유리
  • 함께 읽는 필드·랜덤 접근 많으면 AoS(접근 패턴이 기준)
Q13 CPX-05 미들 코드분석 string_view 수명

다음 코드의 (A), (B), (C) 지점에서 각각 무엇이 문제인지 std::string_view의 본질과 함께 설명하고, 수정 방향을 제시하시오.

#include <string>
#include <string_view>

std::string_view make_greeting(const std::string& name) {
    std::string s = "Hello, " + name;   // 지역 std::string
    return s;                            // (A)
}

std::string_view pick(std::string_view a, std::string_view b, bool use_a) {
    return use_a ? a : b;
}

int main() {
    std::string_view g = make_greeting("world");                  // (B)
    std::string_view p = pick("abc", std::string("xyz"), false);  // (C)
    // 이후 g, p 사용...
}
모범답안 보기
  • 핵심: std::string_view는 비소유(non-owning) 타입이다. 포인터 + 길이만 들고 있고, 가리키는 문자 버퍼의 수명은 관리하지 않는다.
  • (A)/(B): 지역 std::string s는 make_greeting 반환과 동시에 파괴된다. 반환된 view는 곧바로 dangling이 되고, g(B)를 통해 접근하면 UB다. 수정: 반환 타입을 값 std::string으로 바꾸거나(가장 간단), 버퍼 수명을 호출자가 소유하도록 설계한다.
  • (C): use_a가 false이므로 pick은 b를 반환하는데, b는 인자로 넘긴 임시 std::string("xyz")를 가리킨다. 이 임시는 그 full expression(세미콜론)까지만 살아 있으므로, pick이 반환한 view를 p에 담은 직후 임시가 파괴되어 p는 dangling이 된다. 반면 "abc"는 문자열 리터럴이라 정적 수명이라 그 자체는 안전하다(문제는 std::string(...) 임시 쪽). 수정: 임시 대신 수명이 충분한 std::string 변수를 넘기거나, view가 아니라 값을 보관한다.
  • 결론: string_view/span은 읽기 전용 함수 파라미터엔 훌륭하지만, 소유가 필요한 곳(멤버 저장, 소유를 넘기는 반환값)에 쓰면 안 된다. 파라미터엔 string_view, 저장·반환엔 string이 원칙이다.

채점 포인트

  • string_view=비소유(포인터+길이), 수명 미관리
  • (A)/(B) 지역 string 반환·(C) use_a=false로 반환된 b가 임시 인자 참조 → dangling UB
  • 리터럴은 정적 수명이라 안전, 파라미터엔 view·저장엔 string
Q14 CPX-06 미들 실무시나리오 틱 루프 / 락 최소화

게임 서버가 4 FPS(250ms) 단일 스레드 틱 루프에서 모든 게임 로직을 처리하고, 네트워크 수신(I/O)과 DB/Redis 작업은 별도 스레드 풀에서 돈다. 팀에서 "성능을 위해 게임 로직 스레드를 여러 개로 쪼개고 락으로 공유 상태를 보호하자"는 제안이 나왔다. 이 접근의 위험과, 실무에서 더 선호되는 대안(메시지 패싱·큐, 작업 위임)을 설명하고, 왜 단일 스레드 + 오프로딩이 오히려 유리할 수 있는지 논하시오.

모범답안 보기
  • 로직을 멀티스레드+락으로 쪼갤 때의 위험: 게임 상태는 상호 참조가 많아(플레이어·몬스터·존이 서로를 건드림) 세밀한 락 분할이 어렵다. 락 경합으로 오히려 느려지고, 락 순서 실수로 인한 데드락, false sharing, 재현 불가능한 레이스 등으로 복잡도와 리스크가 급증한다. "락을 잘 거는 것"보다 어렵고 위험하다.
  • 선호 패턴: 단일 스레드 게임 로직 + 무거운 작업 위임. I/O 스레드는 수신 패킷을 lock-free 또는 locked 큐에 넣고, 게임 스레드는 매 틱 시작에 큐를 드레인해 순차 처리한다(액터/메시지 패싱). DB·Redis 요청은 워커 스레드로 던지고(비동기·논블로킹), 결과를 다시 큐로 받아 다음 틱에 반영한다. 즉 공유 가변 상태 자체를 없애 로직 경로에 락이 필요 없게 만든다.
  • 단일 스레드 + 오프로딩의 이점: 로직에 락이 없으니 경합·데드락이 사라지고, 실행이 결정적(deterministic)이라 버그 재현·디버깅이 쉽다. 락을 줄이는 최선은 잘게 거는 것이 아니라 공유를 제거하는 것이다. 확장은 스레드 쪼개기가 아니라 존/샤드 단위로 프로세스·인스턴스를 나누는 것으로 한다.
  • (이 프로젝트의 GameWorker 단일 스레드 + DBWorker/RedisWorker 풀 구조가 정확히 이 패턴이다.)

채점 포인트

  • 로직 멀티스레드+락은 경합·데드락·재현불가 리스크
  • 단일 스레드 로직 + 큐 드레인/워커 위임으로 공유 제거
  • 확장은 락 세분화가 아니라 존·샤드 분리로
Q15 CPX-07 시니어 실무시나리오 memory_order / lock-free 핸드오프

한 스레드가 큰 결과 버퍼를 채운 뒤 ready 플래그를 세우고, 다른 스레드가 그 플래그를 폴링하다 true가 되면 버퍼를 읽는 lock-free 핸드오프를 만든다. relaxed / acquire / release / seq_cst의 의미를 설명하고, 아래 코드에서 왜 relaxed가 틀렸는지, 올바른 memory_order 조합을 제시하시오.

std::atomic<bool> ready{false};
Buffer g_buf;   // 비원자 데이터

// 생산자
void produce() {
    fill(g_buf);                                   // (1) 버퍼 채우기
    ready.store(true, std::memory_order_relaxed);  // (2)
}
// 소비자
void consume() {
    while (!ready.load(std::memory_order_relaxed)) {} // (3)
    use(g_buf);                                        // (4)
}
모범답안 보기
  • 의미:
  • relaxed: 원자성만 보장하고, 다른 메모리 연산과의 순서·가시성은 보장하지 않는다(순수 카운터 등에 적합).
  • release(store 측): 이 store 이전에 발생한 모든 읽기/쓰기가 이 store 뒤로 재배열되지 않게 하고, 짝이 되는 acquire로 이 값을 읽은 스레드에게 그 쓰기들이 보이도록 보장한다.
  • acquire(load 측): 이 load 이후의 접근이 load 앞으로 재배열되지 않게 하고, 짝 release 이전의 쓰기들을 관측하게 한다.
  • seq_cst: acquire/release 효과에 더해 모든 seq_cst 연산에 대한 단일 전역 순서까지 보장한다. atomic 연산의 기본값이며 가장 강하고 약간 비싸다.
  • 왜 relaxed가 틀렸나: relaxed store/load는 (1)의 버퍼 쓰기와 (2)의 플래그 쓰기 사이에 아무 순서·가시성 관계를 만들지 않는다. 따라서 소비자가 (3)에서 true를 관측하더라도 (1)의 버퍼 내용이 아직 그 스레드에 보이지 않을 수 있고(컴파일러·CPU 재배열), (4)에서 오래된/부분적인 데이터를 읽어 데이터 레이스(UB)가 된다.
  • 올바른 조합: 생산자 ready.store(true, std::memory_order_release), 소비자 ready.load(std::memory_order_acquire). 이 release-acquire 짝이 happens-before를 형성해 (1)의 모든 쓰기가 (4)에서 보이도록 보장한다. seq_cst로 둬도 정확하지만 이 단일 플래그 핸드오프엔 acquire/release로 충분하고 더 저렴하다.
  • 오해 교정: relaxed는 "느슨해도 결국 순서가 맞겠지"가 아니라 명시적으로 순서·가시성이 없는 것이다. 또한 while 스핀은 코어를 태우므로 실전에선 C++20 atomic::wait/notify나 condition_variable을 고려한다.

채점 포인트

  • relaxed/acquire/release/seq_cst 의미 정확 구분
  • relaxed는 (1)↔(2) 순서·가시성 없어 (4)가 오래된 데이터 읽음(UB)
  • release-acquire 짝이 happens-before 형성(seq_cst는 과함)
Q16 CPX-08 시니어 코드분석 false sharing

아래에서 a와 b는 서로 다른 변수라 두 스레드가 각각 독립적으로 증가시키는데도, 둘을 동시에 돌리면 각각 따로 돌릴 때보다 훨씬 느리다. 정확성 문제(계산 결과)는 없다. 왜 느린가? 원인의 이름과 하드웨어 메커니즘을 설명하고, C++11/C++17 표준을 활용한 수정을 제시하시오.

#include <atomic>
#include <thread>

struct Counters {
    std::atomic<long> a{0};
    std::atomic<long> b{0};
};
Counters g;

void hammer_a() { for (long i=0;i<10'000'000;++i) g.a.fetch_add(1, std::memory_order_relaxed); }
void hammer_b() { for (long i=0;i<10'000'000;++i) g.b.fetch_add(1, std::memory_order_relaxed); }
// 스레드1: hammer_a, 스레드2: hammer_b
모범답안 보기
  • 원인: false sharing(거짓 공유). a와 b가 같은 캐시 라인(보통 64바이트)에 함께 놓여 있어, 논리적으로는 독립이어도 캐시 일관성 프로토콜(MESI 등) 입장에선 두 코어가 같은 라인을 번갈아 쓰는 것으로 취급된다. 한 코어가 라인을 수정하면 다른 코어의 라인 사본이 무효화(invalidate)되어, 상대는 다음 접근 때 라인을 다시 가져와야 한다. 이 소유권 핑퐁이 매 반복 일어나 원자 연산은 정확하지만 성능이 처참해진다.
  • 수정: 두 카운터를 서로 다른 캐시 라인으로 분리(패딩/정렬).
// C++11: 명시적 정렬 (alignas는 크기도 정렬 배수로 패딩하므로 각 카운터가 64B를 차지)
struct alignas(64) PaddedCounter { std::atomic<long> v{0}; };
struct Counters { PaddedCounter a, b; };
// C++17: 하드웨어 상수 사용
#include <new>
struct Counters {
    alignas(std::hardware_destructive_interference_size) std::atomic<long> a{0};
    alignas(std::hardware_destructive_interference_size) std::atomic<long> b{0};
};
  • 더 나은 설계: 애초에 스레드 로컬 카운터로 각자 누적한 뒤 마지막에 한 번만 합치면, 공유 자체가 사라져 false sharing과 원자 연산 비용이 모두 없어진다.
  • 채점: 원인 명명(false sharing) + 캐시 라인/무효화 메커니즘 설명 + alignas(또는 hardware_destructive_interference_size)나 thread-local 합산 중 하나 이상 제시.

채점 포인트

  • 원인=false sharing(같은 캐시 라인 공유)
  • MESI 무효화·라인 소유권 핑퐁으로 성능 저하 설명
  • alignas(64)/hardware_destructive_interference_size 또는 thread-local 합산

Q17 UE-01 주니어 단답형 리플렉션 매크로

언리얼의 리플렉션 매크로 UCLASS(), USTRUCT(), UPROPERTY(), UFUNCTION(), GENERATED_BODY()는 각각 무슨 역할을 하나요? 특히 UPROPERTY()가 단순한 '에디터 노출용'이 아니라 엔진 동작에 필수인 이유를 한 가지 이상 설명하세요.

모범답안 보기

이 매크로들은 컴파일 전 UHT(Unreal Header Tool) 가 스캔해 리플렉션 메타데이터와 보일러플레이트 코드를 생성하는 표식입니다.

  • GENERATED_BODY(): UHT가 생성한 코드(생성자 헬퍼, 리플렉션 글루)를 클래스 본문에 삽입하는 자리. UCLASS/USTRUCT마다 필수입니다.
  • UCLASS(): UObject 파생 클래스를 리플렉션 대상으로 등록 → GC, 직렬화, CDO(Class Default Object), 블루프린트 노출이 가능해집니다.
  • USTRUCT(): 구조체를 리플렉션 대상으로 만듭니다. UObject가 아니라 값 타입이며 구조체 자체는 GC 대상이 아닙니다(단, 도달 가능한 USTRUCT 안의 UPROPERTY UObject 포인터는 GC가 추적합니다).
  • UPROPERTY(): 멤버를 리플렉션에 노출합니다. 에디터/BP 노출·직렬화·네트워크 리플리케이션뿐 아니라 GC가 UObject 참조를 추적하게 만듭니다. UPROPERTY로 표시된 UObject 포인터만 GC 도달성 그래프에 포함되어 대상이 살아있고, 대상이 파괴되면 포인터가 자동 null로 정리됩니다. 그래서 단순 노출용이 아니라 '참조 유지'에 필수입니다.
  • UFUNCTION(): 함수를 리플렉션에 노출 → BlueprintCallable, RPC(Server/Client/NetMulticast) 지정, 다이나믹 델리게이트 바인딩(AddDynamic) 등에 필요합니다.

채점 포인트

  • UHT가 매크로를 스캔해 리플렉션/보일러플레이트 생성, GENERATED_BODY는 삽입 지점
  • UPROPERTY는 GC 도달성 추적에 필수(단순 에디터 노출 아님)
  • UFUNCTION은 BP 노출·RPC·다이나믹 델리게이트 바인딩에 필요
Q18 UE-02 주니어 서술형 액터 생명주기

AActor의 주요 생명주기 콜백을 호출 순서대로 나열하고, 각각 어떤 초기화 코드를 넣어야 하는지 설명하세요. 특히 생성자(Constructor) 와 BeginPlay() 중 게임플레이 초기화는 어디에 두어야 하며 그 이유는 무엇인가요?

모범답안 보기

대략적인 순서는 생성자 → 컴포넌트 등록/PostInitializeComponents → BeginPlay → 매 프레임 Tick(bCanEverTick 시) → EndPlay → 파괴(BeginDestroy) → GC 입니다.

  • 생성자: 인스턴스뿐 아니라 CDO 생성 시에도 호출되고, 이 시점엔 월드나 다른 액터가 아직 없을 수 있습니다. 따라서 CreateDefaultSubobject로 컴포넌트를 만들고 기본값을 세팅하는 용도로만 씁니다. 월드/다른 액터에 의존하는 로직은 금지입니다.
  • BeginPlay(): 액터가 '플레이가 시작된 월드'에 스폰·배치되어 게임이 시작될 때 한 번 호출됩니다. 이때는 월드와 다른 액터가 유효하므로 참조 캐싱, 타이머 시작, 델리게이트 바인딩 등 게임플레이 초기화는 여기에 둡니다.
  • Destroy() 는 즉시 메모리를 해제하지 않습니다. EndPlay(사유) 호출 후 pending kill(garbage)로 표시되고, 실제 파괴(BeginDestroy/FinishDestroy)는 이후 GC가 수행합니다.

흔한 오해: 생성자에서 GetWorld()로 다른 액터를 찾거나 초기화하는 것 → CDO/에디터 로드 시점에 크래시하거나 미정의 동작을 유발합니다. 게임플레이 초기화는 반드시 BeginPlay에서 하세요.

채점 포인트

  • 순서: 생성자 → BeginPlay → Tick → EndPlay → 파괴/GC
  • 생성자=CDO에서도 호출·컴포넌트 생성/기본값 전용, 월드 의존 금지
  • BeginPlay=월드/타 액터 유효, 게임플레이 초기화 위치
  • Destroy는 즉시 해제 아님(EndPlay→pending kill→GC)
Q19 UE-03 주니어 단답형 게임플레이 프레임워크

게임플레이 프레임워크에서 APawn, AController(특히 APlayerController/AAIController), AGameModeBase, AGameStateBase의 역할을 각각 한두 문장으로 구분해 설명하세요. 또 이 중 서버(권한)에만 존재하며 클라이언트에 복제되지 않는 클래스는 무엇인가요?

채점 포인트

  • Pawn=몸 / Controller=두뇌 분리, PlayerController vs AIController
  • GameMode=규칙, 서버 전용·미복제
  • GameState=클라로 복제되는 전역 상태
Q20 UE-04 미들 코드분석 GC와 UPROPERTY

다음 오브젝트 풀 코드에는 잠재적 크래시 버그가 있습니다. 원인과 수정 방법을 설명하세요.

UCLASS()
class AProjectilePool : public AActor
{
    GENERATED_BODY()

private:
    // 미리 스폰해 재사용할 발사체 풀
    TArray<AProjectile*> PooledProjectiles;

public:
    void Prewarm()
    {
        for (int32 i = 0; i < 20; ++i)
        {
            AProjectile* P = GetWorld()->SpawnActor<AProjectile>();
            P->SetActorHiddenInGame(true);
            PooledProjectiles.Add(P);
        }
    }

    AProjectile* Acquire()
    {
        AProjectile* P = PooledProjectiles.Pop();
        P->SetActorHiddenInGame(false);
        return P; // 수 초/수 프레임 뒤 실제 사용
    }
};
모범답안 보기

버그: PooledProjectiles가 UPROPERTY()로 표시되어 있지 않습니다. GC는 UPROPERTY로 표시된 참조만 도달성 그래프에서 추적하고, 대상이 파괴될 때 그 포인터를 자동으로 null로 정리해 줍니다. 이 TArray는 그 대상이 아닙니다.

여기서 담기는 것이 월드에 스폰된 AActor라는 점이 중요합니다. 스폰된 액터는 소속 ULevel의 액터 배열(엔진 내부 UPROPERTY)이 참조하므로, UPROPERTY 누락만으로 다음 GC 사이클에 곧바로 수거되지는 않습니다. 따라서 '언젠가 GC가 다 지워서 크래시'라는 설명은 정확하지 않습니다.

진짜 결함은 그 액터가 어떤 이유로든 파괴될 때 드러납니다 — 명시적 Destroy(), 레벨 스트리밍/언로드, 월드 종료 등. 이때 PooledProjectiles는 UPROPERTY가 아니므로 GC가 raw 포인터를 자동 null 처리해 주지 않고, 배열에는 파괴된 액터를 가리키는 댕글링 포인터가 남습니다. Acquire()나 이후 사용 시점에 이 포인터를 역참조하면 크래시합니다. (만약 풀에 담는 것이 액터가 아니라 NewObject로 만든 일반 UObject였다면, 이를 붙잡는 UPROPERTY 참조가 하나도 없으므로 다음 GC에서 즉시 수거되어 훨씬 즉각적으로 터집니다.)

어느 경우든 '월드가 대신 살려주니 괜찮다'에 기대는 것은 위험합니다 — 파괴 경로에서 auto-null 보장이 없기 때문입니다.

수정: 멤버를 UPROPERTY()로 표시하고, UE5에서는 TObjectPtr를 사용합니다.

UPROPERTY()
TArray<TObjectPtr<AProjectile>> PooledProjectiles;

이렇게 하면 GC가 참조를 추적해 대상을 살려두고, 대상이 파괴되면 포인터를 자동으로 null로 정리해 댕글링을 막습니다. TObjectPtr는 에디터 빌드에서 접근 추적/인크리멘털 GC를 지원하고 쉬핑에서는 raw 포인터로 최적화되며, GC 시맨틱 자체는 UPROPERTY raw 포인터와 동일합니다.

채점 포인트

  • UPROPERTY 누락 → GC 추적/파괴 시 auto-null 대상에서 제외됨
  • 스폰 액터는 ULevel이 참조해 즉시 GC되진 않지만, 파괴 시 auto-null이 안 돼 댕글링 발생(비-액터 UObject였다면 즉시 수거)
  • '월드가 잡아주는 참조'에 의존하면 안 됨
  • UPROPERTY + TObjectPtr(TArray<TObjectPtr<>>)로 수정, 파괴 시 자동 null
Q21 UE-05 미들 코드분석 델리게이트/BP 상호운용

다음 다이나믹 멀티캐스트 델리게이트 바인딩 코드는 컴파일은 통과하지만 런타임에 델리게이트가 브로드캐스트될 때 크래시/실패합니다. 원인과 수정 방법을 설명하고, 다이나믹 델리게이트와 일반(비-다이나믹) 델리게이트의 차이도 함께 언급하세요.

DECLARE_DYNAMIC_MULTICAST_DELEGATE_OneParam(FOnHealthChanged, float, NewHealth);

UCLASS()
class AHealthActor : public AActor
{
    GENERATED_BODY()
public:
    UPROPERTY(BlueprintAssignable)
    FOnHealthChanged OnHealthChanged;
};

UCLASS()
class UHealthWidget : public UUserWidget
{
    GENERATED_BODY()
public:
    void Bind(AHealthActor* Actor)
    {
        Actor->OnHealthChanged.AddDynamic(this, &UHealthWidget::HandleHealthChanged);
    }

    void HandleHealthChanged(float NewHealth);   // 여기 주목
};
모범답안 보기

원인: AddDynamic은 다이나믹 델리게이트 전용 바인딩으로, 함수를 이름(FName) 기반으로 리플렉션을 통해 찾아 호출합니다(AddDynamic(obj, &Class::Func) 매크로는 함수 포인터와 함께 "Func" 문자열을 FName으로 넘깁니다). 따라서 핸들러 HandleHealthChanged는 반드시 UFUNCTION()으로 표시되어 리플렉션 시스템에 등록되어야 합니다.

중요한 뉘앙스: UFUNCTION이 없어도 컴파일 자체는 통과합니다. 문제는 런타임입니다 — 델리게이트가 Broadcast()될 때 각 바인딩이 FindFunctionChecked(FName)으로 대상 UFunction을 찾는데, 등록된 UFUNCTION이 없어 개발 빌드에서 assert/크래시(쉬핑에서는 조용히 실행되지 않거나 미정의 동작)합니다. 즉 '빌드 에러'가 아니라 '런타임 바인딩/호출 실패'입니다.

수정:

UFUNCTION()
void HandleHealthChanged(float NewHealth);

다이나믹 vs 일반 델리게이트 차이:

  • 다이나믹(DECLARE_DYNAMIC_*): 이름 기반이라 느리지만 블루프린트에 노출/직렬화가 가능합니다. BlueprintAssignable로 BP에서 바인딩할 수 있고, C++에서는 AddDynamic/RemoveDynamic으로 바인딩하되 핸들러에 UFUNCTION이 필수입니다.
  • 일반(DECLARE_MULTICAST_DELEGATE_*): C++ 전용이고 빠르지만 BP 노출/직렬화가 안 됩니다. AddUObject/AddSP/AddLambda 등으로 바인딩하며 UFUNCTION이 필요 없습니다.

보너스: UObject 대상은 AddDynamic/AddUObject로 바인딩하면 대상 파괴 시 안전하게 처리되지만, raw 델리게이트에 람다로 캡처한 상태는 수명에 주의해야 합니다.

채점 포인트

  • AddDynamic은 FName(리플렉션) 기반 호출이라 핸들러에 UFUNCTION 필수
  • UFUNCTION 누락은 컴파일 통과·런타임 Broadcast 시 FindFunctionChecked assert(빌드 에러 아님)
  • 수정: HandleHealthChanged에 UFUNCTION() 추가
  • 다이나믹=BP 노출·직렬화·느림 / 일반=C++ 전용·빠름·UFUNCTION 불필요
Q22 UE-06 미들 실무시나리오 프로퍼티 리플리케이션

멀티플레이어 게임에서 서버가 Health 값을 바꿨는데 클라이언트의 체력바에 반영되지 않습니다. 프로퍼티 리플리케이션이 동작하기 위한 필수 조건들을 체크리스트로 설명하고, ReplicatedUsing(RepNotify)의 동작 — 특히 서버에서도 OnRep이 자동 호출되는지 — 를 정확히 설명하세요.

모범답안 보기

체크리스트:

  1. 액터가 복제 대상: 생성자에서 bReplicates = true;(또는 런타임 SetReplicates(true)). 아니면 아무 것도 복제되지 않습니다.
  2. 프로퍼티 표시: UPROPERTY(Replicated) 또는 UPROPERTY(ReplicatedUsing = OnRep_Health).
  3. GetLifetimeReplicatedProps 오버라이드 + 등록: #include "Net/UnrealNetwork.h" 후 Super::GetLifetimeReplicatedProps(...) 호출, DOREPLIFETIME(AMyActor, Health); 추가. 이걸 빠뜨리는 것이 가장 흔한 원인입니다.
  4. 값 변경은 서버에서만: 프로퍼티 리플리케이션은 서버→클라 단방향입니다. HasAuthority()인 서버에서 바꿔야 하고, 클라에서 바꿔봐야 반영되지 않으며 다음 복제로 덮어써집니다.
  5. 관련성(relevancy)/연결: 액터가 해당 클라에 relevant해야 하고 NetUpdate가 발생해야 합니다(도먼시/컬링/거리 확인).

RepNotify(OnRep_) 동작:

  • 값이 실제로 바뀌어 클라에 도착하면 클라이언트에서 OnRep 함수가 호출됩니다(이때 UI 갱신). 값이 직전 복제값과 동일하면 기본적으로 복제도 OnRep도 일어나지 않습니다.
  • 서버에서는 값을 세팅해도 OnRep이 자동 호출되지 않습니다. 서버에서도 동일 로직을 태우려면 세팅 후 OnRep 함수를 직접 호출해야 합니다. "OnRep은 서버·클라 모두 자동 호출된다"는 흔한 오해로, 틀립니다.

오해 교정: 프로퍼티 리플리케이션은 양방향이 아니며 서버가 권위입니다. 클라의 변경을 서버에 반영하려면 Server RPC를 써야 합니다.

채점 포인트

  • bReplicates + UPROPERTY(Replicated) + DOREPLIFETIME 3종이 모두 필요
  • 값 변경은 서버(권한)에서만, 리플리케이션은 단방향
  • OnRep은 클라에서만 자동 호출(서버는 수동 호출)
  • DOREPLIFETIME/GetLifetimeReplicatedProps 누락이 최빈 원인
Q23 UE-07 시니어 서술형 스마트 포인터

언리얼의 스마트 포인터 계열(TSharedPtr/TSharedRef/TWeakPtr, TWeakObjectPtr, TUniquePtr)과 UObject 참조 방식을 정리하세요. 특히 UObject를 std::shared_ptr로 관리하면 안 되는 이유와, TWeakPtr와 TWeakObjectPtr의 차이를 명확히 설명하세요.

모범답안 보기

UObject는 엔진의 GC가 소유·수명을 관리하며, 오직 NewObject/SpawnActor로 생성되고 GC만이 파괴합니다. 따라서 new/delete나 refcount 스마트 포인터로 UObject를 관리해서는 안 됩니다.

std::shared_ptr 금지 이유:

  1. refcount가 0이 되면 delete를 호출하는데, UObject를 수동 delete하면 GUObjectArray/GC 상태가 손상되어 크래시·이중 해제가 발생합니다.
  2. shared_ptr의 참조는 GC 도달성에 잡히지 않으므로 애초에 대상을 살려두지도 못합니다(GC는 UPROPERTY/AddReferencedObjects 등록 참조만 봅니다). 즉 살리지도 못하면서 파괴는 망가뜨립니다.

UObject 참조 방식:

  • 강한 참조/수명 유지: UPROPERTY()(UE5는 TObjectPtr). GC가 살려두고 파괴 시 자동 null. (UPROPERTY로 둘 수 없는 곳이라면 FGCObject::AddReferencedObjects나 TStrongObjectPtr로 등록.)
  • 약한 참조: TWeakObjectPtr<T> — 대상을 살려두지 않고, GC로 파괴되면 안전하게 무효화됩니다(IsValid()로 확인). 캐시·옵저버·순환 참조 회피에 적합.

비-UObject용: TSharedPtr/TSharedRef/TWeakPtr, TUniquePtr는 GC가 관리하지 않는 순수 C++ 객체(Slate 위젯, 런타임 데이터 구조 등)에 씁니다. TSharedRef는 항상 유효(널 불가), TUniquePtr는 단독 소유입니다.

TWeakPtr vs TWeakObjectPtr: TWeakPtr는 TSharedPtr(언리얼 자체 refcount 시스템)의 약한 짝이고, TWeakObjectPtr는 UObject GC 시스템의 약한 참조입니다. 서로 다른 수명 시스템이므로 혼용하면 안 됩니다 — 특히 UObject를 TSharedPtr나 std::shared_ptr에 넣지 마세요.

채점 포인트

  • UObject는 NewObject/SpawnActor + GC 전용, 수동 delete/refcount 관리 금지

Q24 UE-08 시니어 실무시나리오 네트워크 RPC

클라이언트가 발사 버튼을 누르면 (1) 서버 권위로 발사를 처리하고 (2) 모든 클라이언트에 총구 화염 등 연출을 재생하려 합니다. 어떤 RPC(Server/Client/NetMulticast)와 신뢰성(Reliable/Unreliable) 조합으로 설계할지, 각 RPC의 호출 주체·실행 위치·소유권(authority/ownership) 조건을 포함해 설명하세요. 또 RPC가 실행되지 않는 흔한 원인도 두 가지 이상 드세요.

모범답안 보기

설계:

  1. 입력을 받은 클라이언트가 UFUNCTION(Server, Reliable, WithValidation) 서버 RPC(예: Server_Fire)를 호출 → 서버에서 실행. 입력 유실을 막기 위해 Reliable, WithValidation의 _Validate에서 치트 검증(연사 속도·탄약 등).
  2. 서버가 권위 로직을 수행합니다(탄약 차감, 히트/데미지 판정, 필요 시 복제되는 발사체 액터 스폰).
  3. 연출은 서버가 UFUNCTION(NetMulticast, Unreliable) 멀티캐스트(예: Multicast_PlayMuzzleFX)를 호출 → 서버 + 모든 관련 클라에서 실행. 코스메틱이므로 Unreliable로 대역폭을 절약합니다(빈번한 이펙트를 Reliable로 보내면 채널 포화 위험). 발사체를 복제 스폰한다면 연출을 발사체 자체에서 처리해 멀티캐스트를 생략할 수도 있습니다.

각 RPC 규칙:

  • Server RPC: 소유 클라이언트에서 호출 → 서버에서 실행. 대상 액터가 그 클라의 연결에 소유(Owning) 되어야 합니다(PlayerController와 그가 possess한 Pawn이 이를 만족). 비소유 클라의 Server RPC는 드롭됩니다.
  • Client RPC(Owning): 서버에서 호출 → 해당 소유 클라에서만 실행.
  • NetMulticast: 서버에서 호출 → 서버와 모든 관련 클라에서 실행. 클라가 호출하면 로컬에서만 돌아 의미가 없습니다.

RPC 미실행 흔한 원인:

  • 액터가 복제 대상이 아님(bReplicates == false).
  • 소유권/권한 불일치(비소유 클라의 Server RPC, 클라가 호출한 Multicast).
  • 잘못된 쪽에서 호출(예: Client RPC를 클라가 호출).
  • _Implementation 미구현, 또는 WithValidation의 _Validate가 false 반환(해당 클라 연결이 끊어짐).
  • 액터가 클라에 relevant하지 않음(거리/컬링/도먼시).

채점 포인트

  • 입력=Server Reliable RPC + 검증 → 서버 권위 처리
  • 연출=NetMulticast Unreliable(반드시 서버에서 호출)
  • Server RPC엔 ownership 필요, Multicast/Client는 서버에서만 유효
  • 미실행 원인: 복제 off·소유권 불일치·잘못된 호출측·relevancy·검증 실패

C#에서 string은 불변(immutable)입니다.

  1. "불변"이 정확히 무슨 의미인가요?
  2. 루프에서 result += token; 으로 문자열을 수천 번 이어붙이면 어떤 성능 문제가 생기나요?
  3. StringBuilder는 이를 어떻게 해결하며, 반대로 StringBuilder가 오히려 불리한 경우는 언제인가요?
모범답안 보기
  1. 불변 = 한 번 만들어진 string 인스턴스의 내용은 절대 바뀌지 않는다. s += "x", Replace, Substring 등은 기존 객체를 수정하는 것이 아니라 새 string 객체를 할당해 반환하고 원본은 그대로 둔다.
  2. result += token 을 N번 하면 매 반복마다 (점점 길어지는) 새 문자열을 할당하고 기존 내용을 통째로 복사한다 → 전체 복사 비용이 대략 O(N²), 그리고 버려지는 임시 문자열이 대량 생겨 GC 압박이 커진다. Unity처럼 매 프레임 문자열을 만들면 특히 치명적이다.
  3. StringBuilder는 내부에 가변 char 버퍼를 두고 Append로 그 버퍼에 이어붙이며, 용량이 모자랄 때만 재할당(대략 2배 증가)한다. 마지막에 ToString()을 한 번만 호출해 문자열을 만들므로 평균 O(N) 에 근접한다.
  4. 다만 연결 횟수가 적거나 컴파일 타임 상수 연결("a" + "b", 상수 폴딩)·string.Concat/보간 문자열로 충분한 경우엔 StringBuilder 생성 오버헤드가 오히려 손해다. "무조건 StringBuilder"는 아니다.

채점 포인트

  • 불변=수정이 아니라 새 객체 할당, 원본 유지
  • += 루프는 O(N²) 복사 + 대량 GC garbage
  • StringBuilder=가변 버퍼로 비용 상환(평균 O(N))
  • 소수 연결엔 오히려 과함(상수 폴딩/Concat)

다음 코드에는 눈에 잘 안 보이는 힙 할당(박싱)이 숨어 있습니다. (A)~(C)에서 어떤 일이 일어나는지 짚고, 개선안을 제시하세요.

var list = new System.Collections.ArrayList();
for (int i = 0; i < 10000; i++)
{
    list.Add(i);            // (A)
}
foreach (object o in list)
{
    sum += (int)o;          // (B)
}

object count = list.Count;                     // (C)
Console.WriteLine("총 " + count + "개");
모범답안 보기
  • (A) 박싱(boxing): ArrayList는 요소를 object로 저장한다. 값 타입인 int를 넣을 때마다 힙에 박스 객체가 하나씩 생성된다 → 여기서만 10,000개의 임시 힙 객체가 생겨 GC 부담이 크다.

  • (C) list.Count(int)를 object에 대입하면서 또 박싱이 일어난다. object로 받을 이유가 없다.
  • 개선: 제네릭 List<int>를 사용하면 내부적으로 int[]에 저장하므로 박싱/언박싱이 완전히 사라진다. 또한 List<int> 같은 구체 타입을 foreach 하면 구조체 열거자(List<int>.Enumerator)가 값 타입으로 쓰여 열거 자체도 추가 힙 할당이 없다(단, IEnumerable<int>로 캐스팅해 돌리면 박싱된 열거자가 힙에 생긴다). (C)는 그냥 int count = list.Count;.
  • 핵심(오개념 교정): 박싱은 "값 타입을 object나 인터페이스로 취급"할 때 발생한다. 컬렉션(ArrayList), params object[], 인터페이스 캐스팅, string.Format/String.Concat(object,object)(값 타입을 문자열에 + 연결) 등 눈에 안 띄는 곳에서 새기 쉽다.

채점 포인트

  • ArrayList 저장/조회 = 박싱·언박싱 반복
  • List<int>로 전환 시 박싱 제거 + 구체 타입 foreach는 struct 열거자로 무할당
  • 박싱 조건: 값 타입 → object/인터페이스
  • (C)의 object 대입도 불필요한 박싱

    actions.Add(() => Console.Write(i));
}
foreach (var a in actions)
    a();
모범답안 보기

  • 이유: 람다는 변수의 값이 아니라 변수 자체(를 담은 클로저 객체의 필드)를 캡처한다. for 루프의 i는 루프 전체에서 단 하나의 변수이므로 5개의 람다가 같은 i를 공유한다. 실제 호출은 루프가 끝난 뒤 일어나고 그때 i는 이미 5다 → 캡처 시점이 아니라 호출 시점의 값을 읽어 모두 5.

for (int i = 0; i < 5; i++)
{
    int copy = i;                       // 반복마다 새 변수
    actions.Add(() => Console.Write(copy));
}
// 출력: 01234
  • 언어 버전 함정: foreach의 반복 변수는 C# 5.0부터 매 반복마다 별개의 변수로 취급되도록 언어 명세가 바뀌어 이 버그가 사라졌다. 하지만 for 루프의 i는 여전히 하나의 변수이므로 위 문제가 그대로 남는다. 즉 "foreach는 괜찮지만 for는 여전히 위험"이 정확한 정리다.

채점 포인트

Q29 CS-05 미들 서술형 IDisposable·finalizer 소멸 시점

GC가 메모리를 알아서 회수하는데도 IDisposable/using이 필요한 이유를 소멸 시점(결정성) 관점에서 설명하세요. finalizer(~MyClass)와는 무엇이 다르며, finalizer를 함부로 쓰면 안 되는 이유는 무엇인가요?

모범답안 보기
  • GC는 관리(managed) 메모리만, 그것도 비결정적(nondeterministic) 시점에 회수한다. 파일 핸들, 소켓, DB 커넥션, 네이티브 포인터 같은 비관리 자원은 GC가 언제 정리할지 보장하지 못한다.
  • IDisposable.Dispose() 는 "지금, 명시적으로" 자원을 해제하는 결정적 계약이다. using (var f = ...) { } 은 블록을 벗어날 때(예외가 나도 finally에서) Dispose()를 반드시 호출한다. C# 8의 using var f = ...;는 스코프 끝에서 해제한다.
  • finalizer(~Type, 실제로는 Object.Finalize 재정의)는 GC가 객체를 수거할 때 호출되는 안전망이라 호출 시점이 비결정적이고, 프로세스 종료 시 호출된다는 보장조차 없다.
  • finalizer 남용 위험: finalizer가 있는 객체는 finalization queue를 거쳐 최소 두 번의 GC 사이클을 더 살아남아야 회수되고(수명 연장·상위 세대 승격) GC에 부담을 준다. 표준은 Dispose(bool) 패턴 + GC.SuppressFinalize(this) 로, 정상적으로 Dispose가 호출되면 finalizer를 건너뛰게 하는 것이다. finalizer는 비관리 자원을 직접 쥔 클래스의 최후 안전망으로만 둔다(요즘은 SafeHandle로 대체하는 것이 권장된다).
  • 오개념 교정: "using이 객체를 메모리에서 즉시 제거한다"는 틀렸다. using은 Dispose()를 호출할 뿐이고, 메모리 회수는 여전히 GC의 몫이다.

채점 포인트

  • GC=비결정적·관리 메모리 한정 → 비관리 자원엔 부적합
  • Dispose/using=결정적 해제(finally 보장)
  • finalizer=비결정적 + 수명 연장/승격 부담
  • Dispose(bool) 패턴 + SuppressFinalize, using≠메모리 해제
Q30 CS-06 미들 실무시나리오 GC 세대·LOH·GC.Collect

Unity 게임에서 특정 상황마다 프레임이 뚝뚝 끊깁니다(스파이크). 프로파일러를 보니 GC가 튀고 있습니다. 팀원은 "매 프레임 GC.Collect()를 한 번씩 불러서 미리 청소하자"고 제안합니다.

  1. Gen0/Gen1/Gen2 세대별 GC의 의미와, 왜 스파이크로 이어지는지 설명하세요. (Unity의 실제 GC가 이 모델과 같은지도 함께 짚으세요.)
  2. LOH(Large Object Heap) 가 왜 별도 문제인지 설명하세요.
  3. 팀원의 GC.Collect() 제안에 대해 어떻게 조언하겠습니까?
모범답안 보기
  1. 세대별 GC는 "대부분의 객체는 짧게 산다"는 세대 가설(generational hypothesis)에 기반한다. 갓 할당된 객체는 Gen0에서 자주·빠르게 수집되고, 살아남으면 Gen1, 또 살아남으면 Gen2로 승격된다. Gen2 수집은 힙 전체를 훑어 가장 비싸다. 매 프레임 임시 garbage(문자열 연결, LINQ, 박싱, 클로저 캡처, 임시 배열/컬렉션)를 많이 만들면 GC가 빈번히 발생해 프레임 스파이크로 나타난다.
  • 중요한 단서(오개념 교정): 이 Gen0/1/2 세대 모델과 아래의 LOH는 .NET CoreCLR/.NET Framework의 GC 이야기다. Unity의 기본 스크립팅 GC(Mono·IL2CPP 모두)는 Boehm(Boehm–Demers–Weiser) conservative GC로, 비세대(non-generational)·비압축(non-compacting) 이다. 즉 Unity에는 Gen0/1/2 구분도, 별도 LOH도 없고, 수집이 일어날 때마다 관리 힙 전체를 stop-the-world로 마킹한다. 힙이 커질수록 한 번의 수집이 통째로 비싸지는 이것이 Unity 스파이크의 직접 원인이다. (Unity의 Incremental GC는 이 마킹을 여러 프레임에 쪼개 스파이크를 완화하지만 여전히 Boehm이다.) 세대별 모델은 .NET 서버 코드에서 유효한 개념으로 알아 두면 된다.
  1. LOH: (.NET 기준) 대략 85,000바이트 이상의 객체(큰 배열/버퍼 등)는 Large Object Heap에 할당된다. LOH는 기본적으로 압축(compaction)을 하지 않아 단편화가 쌓이고, LOH 수집은 비싼 Gen2 수집과 함께 일어난다(필요 시 GCSettings.LargeObjectHeapCompactionMode로 1회 압축을 강제할 수는 있다). Unity의 Boehm 힙에는 별도 LOH 개념이 없지만, "큰 버퍼를 매 프레임 새로 할당하지 말고 재사용(풀링) 하라"는 교훈은 양쪽 모두 동일하게 적용된다.
  2. GC.Collect()를 매 프레임 부르는 것은 나쁜 조언이다. 강제로 전체 수집을 유발해 오히려 더 큰 스파이크를 만들고(.NET에선 세대 가설까지 무력화), Boehm에서도 매번 전체 힙을 스캔하게 만들 뿐이다. 근본 해결은 GC를 자주 부르는 게 아니라 할당 자체를 줄이는 것: 오브젝트 풀링, StringBuilder/캐싱, 박싱·클로저 제거, LINQ를 핫패스에서 배제. GC.Collect는 로딩 화면 등 "어차피 멈춰도 되는" 지점에서만 한정적으로 쓰고, Unity라면 Incremental GC 활용도 고려한다.
  • 오개념 교정: "GC.Collect를 자주 부르면 메모리가 깨끗해져 성능이 좋아진다"는 틀렸다 — 전체 수집 비용(과 .NET의 경우 승격 왜곡)으로 대개 악화된다.

채점 포인트

  • Gen0 잦고 저렴 / Gen2 전체 수집 비쌈 + 승격 — 단, 이는 .NET CoreCLR 모델
  • Unity 기본 GC=Boehm(비세대·비압축, 매 수집 전체 힙 스캔)이라 Gen0/1/2·LOH 없음
  • LOH 85KB+ 비압축(.NET) → 단편화, 풀링으로 대응(교훈은 Unity에도 동일)
  • 근본 해결=매 프레임 할당 감소, GC.Collect 매 프레임 금지(로딩 등 한정)
Q31 CS-07 시니어 코드분석 async/await·SynchronizationContext deadlock

다음은 단일 스레드 SynchronizationContext가 있는 클라이언트(UI/게임)의 버튼 핸들러입니다. 실행하면 화면이 그대로 멈춰버립니다(deadlock). 원인을 설명하고, 우선순위대로 해결책을 제시하세요.

public async Task<string> LoadDataAsync()
{
    await Task.Delay(1000);   // 완료 후 원래 컨텍스트로 복귀 시도
    return "data";
}

public void OnButtonClick()
{
    string result = LoadDataAsync().Result;   // 동기적으로 결과 대기
    label.Text = result;
}
모범답안 보기
  • 데드락 원인: LoadDataAsync 안의 await Task.Delay(...)는 ConfigureAwait 지정이 없으면 완료 후, 캡처해 둔 SynchronizationContext(= UI 스레드) 위에서 나머지 continuation(return "data")을 재개하려 한다. 그런데 UI 스레드는 .Result에서 블로킹되어 그 continuation을 실행할 틈이 없다. UI 스레드는 태스크 완료를 기다리고, 태스크는 UI 스레드가 비어야 완료되니 서로를 기다린다 → 데드락.
  • 핵심은 단일 스레드 컨텍스트에서 async 코드를 .Result/.Wait()로 동기 대기(sync-over-async) 하는 것이 위험하다는 점이다. (컨텍스트가 없는 ThreadPool에선 이 특정 데드락은 안 나지만 스레드 낭비 등 다른 문제는 여전하다.)
  • 해결책(우선순위):
  1. 근본책 — 끝까지 async로("async all the way"): 이벤트 핸들러는 async void가 허용되므로 public async void OnButtonClick() 안에서 label.Text = await LoadDataAsync();. 절대 .Result/.Wait()로 막지 않는다.
  2. 라이브러리 코드라면 내부 await에 .ConfigureAwait(false)를 붙여 컨텍스트 복귀를 하지 않게 하면 이 데드락을 피할 수 있다(단 이후 UI를 직접 만지는 코드가 없어야 함).
  • 오개념 교정: "async가 새 스레드를 만든다"는 흔한 오해다. await는 스레드 생성이 아니라 continuation 스케줄링이며, 이 데드락은 스레드 부족이 아니라 컨텍스트 재진입 불가 때문이다.

채점 포인트

  • await가 SynchronizationContext로 복귀 시도 + .Result가 그 스레드 블록 → 상호 대기
  • sync-over-async 금지, async all the way
  • 라이브러리는 ConfigureAwait(false)로 회피
  • async≠새 스레드(오개념 교정)
Q32 CS-08 시니어 실무시나리오 yield/지연 실행·다중 열거·LINQ 비용

팀원이 활성 적 목록을 IEnumerable<Enemy> GetActiveEnemies() 로 만들었는데, 내부는 yield return으로 비싼 필터링(또는 파일/DB 조회) 을 수행합니다. 호출부는 다음처럼 씁니다.

var enemies = GetActiveEnemies();
if (enemies.Any())
{
    foreach (var e in enemies) { /* ... */ }
    int n = enemies.Count();
}

무슨 문제가 있고, LINQ/이터레이터의 지연 실행(deferred execution) 관점에서 왜 그런지, 어떻게 고치는지 설명하세요.

모범답안 보기
  • yield return 이터레이터와 LINQ의 Where/Select 등은 지연 실행이다. GetActiveEnemies()를 호출한 시점엔 아무 것도 실행되지 않고, 실제로 열거될 때마다(Any, foreach, Count, ToList …) 처음부터 다시 실행된다.
  • 따라서 위 코드는 Any() 1회 + foreach 1회 + Count() 1회 = 시퀀스를 세 번 열거하고, 그때마다 내부의 비싼 필터/조회가 세 번 반복 실행된다(multiple enumeration). 매번 원소가 새로 생성되어 참조 동일성이 깨지거나, 그 사이 소스가 바뀌면 결과가 달라지는 미묘한 버그도 난다.
  • 해결: 한 번만 구체화(materialize) 한다.
var enemies = GetActiveEnemies().ToList();  // 필터 1회만 실행
if (enemies.Count > 0)
{
    foreach (var e in enemies) { /* ... */ }
    int n = enemies.Count;   // List라면 O(1) 프로퍼티
}
  • 지연 실행의 순기능/주의 균형: 지연 실행은 무한 시퀀스, 조기 종료(First/Take), 파이프라이닝에 유리하다. 하지만 결과를 여러 번 쓰거나, 지연 중 소스가 변하거나, 루프 변수를 캡처해 나중에 평가할 때 함정이 된다. 또한 LINQ 체인은 연산자마다 이터레이터/델리게이트 객체를 할당하므로 매 프레임 도는 핫패스에서는 할당 비용도 고려해야 한다.
  • 오개념 교정: "IEnumerable을 변수에 담으면 그 시점의 스냅샷"이라는 생각은 틀렸다. 담은 것은 결과가 아니라 실행 방법(쿼리) 이다. 스냅샷이 필요하면 ToList()/ToArray()로 고정해야 한다.

채점 포인트

  • 지연 실행 = 열거할 때마다 처음부터 재실행
  • 다중 열거로 비싼 작업 반복 + 비결정성 버그
  • ToList/ToArray로 1회 구체화(그 후 Count는 O(1))
  • IEnumerable≠스냅샷, LINQ 체인 할당 비용(핫패스)

Q33 UN-01 주니어 서술형 MonoBehaviour 생명주기

MonoBehaviour의 주요 생명주기 콜백(Awake, OnEnable, Start, FixedUpdate, Update, LateUpdate, OnDisable, OnDestroy)이 호출되는 순서를 나열하세요. 그리고 다음을 설명하세요.

  1. Awake와 Start는 각각 어떤 초기화에 쓰는 것이 적절한가?
  2. OnEnable/OnDisable은 Awake/Start와 무엇이 다른가?
모범답안 보기

호출 순서

Awake → OnEnable → Start → (매 프레임: FixedUpdate → Update → LateUpdate) → OnDisable → OnDestroy
  • Awake: 스크립트 인스턴스가 로드될 때 생애 1회. 컴포넌트의 enabled 체크와 무관하게 호출되지만, 소속 GameObject가 active여야 한다(비활성으로 시작하면 활성화 시점까지 지연). 씬 로드 시 모든 Awake가 모든 Start보다 먼저 끝난다. → GetComponent 캐싱 등 자기 자신의 초기화에 사용.
  • Start: 첫 Update 직전 1회, 컴포넌트가 enabled일 때(disabled면 활성화 시점까지 지연). 모든 Awake가 끝난 뒤이므로 다른 오브젝트 참조에 의존하는 초기화에 안전.
  • OnEnable / OnDisable: 활성/비활성이 토글될 때마다 반복 호출. 이벤트 구독/해제, 풀링 재사용 시 상태 리셋에 사용.
  • OnDestroy: 파괴 시 1회. 정리 작업(파괴 시 OnDisable→OnDestroy 순).

흔한 오개념 교정: Awake/Start가 매 활성화마다 불린다고 오해하기 쉽지만 둘 다 생애 1회다. 반복적인 활성/비활성 대응은 OnEnable/OnDisable의 역할이다. 또한 물리 이동은 가변 프레임의 Update가 아니라 FixedUpdate에 두어야 한다.

채점 포인트

  • 순서 Awake→OnEnable→Start→FixedUpdate/Update/LateUpdate→OnDisable→OnDestroy
  • Awake=자기 초기화·모든 Awake가 Start보다 먼저, Start=타 오브젝트 참조
  • Awake/Start는 생애 1회 vs OnEnable/OnDisable은 토글마다 반복
  • 비활성 GameObject는 Awake가 활성화 시점까지 지연
Q34 UN-02 주니어 서술형 Update vs FixedUpdate

Update와 FixedUpdate의 호출 시점 차이를 설명하고, Time.deltaTime과 Time.fixedDeltaTime이 각각 무엇인지 답하세요. 또한 (1) Rigidbody 물리 이동, (2) Input.GetKeyDown 같은 단발 입력은 각각 어느 콜백에 두어야 하며 그 이유는 무엇인가요?

모범답안 보기
  • Update: 매 프레임 1회, 호출 간격이 프레임레이트에 따라 가변. Time.deltaTime = 직전 프레임 이후 경과 시간(가변).
  • FixedUpdate: 물리 스텝마다 고정 간격(기본 0.02초 = 50Hz) 호출. 한 프레임에 0번 이상 여러 번 불릴 수 있다(프레임이 느리면 몰아서 여러 번, 아주 빠르면 그 프레임엔 0번). Time.fixedDeltaTime = 고정 스텝 값.
  • 물리 이동은 FixedUpdate에 둔다. 물리 엔진과 스텝을 맞춰야 지터/터널링이 줄고 결과가 프레임레이트에 독립적이다.
  • 단발 입력(GetKeyDown/GetKeyUp)은 Update에 둔다. 이 값은 프레임 단위로만 1프레임 true인데, FixedUpdate는 해당 프레임에 아예 실행되지 않을 수 있어 입력을 놓칠 수 있다.

보충: FixedUpdate 안에서 Time.deltaTime을 읽으면 실제로는 Time.fixedDeltaTime 값을 반환하므로 물리 코드에서 Time.deltaTime을 곱해도 동작상 문제는 없다.

채점 포인트

  • Update=가변 프레임 deltaTime, FixedUpdate=고정 0.02s fixedDeltaTime
  • FixedUpdate는 한 프레임에 0~N회 호출 가능
  • 물리는 FixedUpdate, 단발 입력은 Update(안 그러면 입력 유실)
  • FixedUpdate 내 deltaTime은 fixedDeltaTime을 반환
Q35 UN-03 주니어 코드분석 Camera.main·GetComponent 캐싱

다음 스크립트가 매 프레임 실행됩니다. 성능 관점의 문제 2가지를 지적하고, 추가로 물리 API를 잘못된 콜백에서 호출하는 문제가 있다면 함께 짚은 뒤, 개선한 코드를 제시하세요.

public class Follower : MonoBehaviour
{
    public Transform target;

    void Update()
    {
        var rb = GetComponent<Rigidbody>();
        Vector3 dir = target.position - Camera.main.transform.position;
        rb.MovePosition(transform.position + dir.normalized * Time.deltaTime);
    }
}
모범답안 보기

문제점

  1. GetComponent<Rigidbody>()를 매 프레임 호출 — 컴포넌트 조회 비용이 반복 발생한다. Awake/Start에서 한 번 캐싱해야 한다.
  2. Camera.main을 매 프레임 접근 — 내부적으로 "MainCamera" 태그 오브젝트를 찾는 조회다(2020.2+에서 결과를 캐싱하도록 개선됐으나, 캐시가 무효화되면 다시 탐색하므로 매 프레임 접근은 여전히 지양). 참조를 캐싱한다.
  3. (물리 API 배치) Rigidbody.MovePosition은 물리 API이므로 Update가 아니라 FixedUpdate에서 호출하는 것이 옳다. Update에서의 물리 이동은 스텝 불일치로 지터를 유발한다.

개선 예시

public class Follower : MonoBehaviour
{
    public Transform target;
    private Rigidbody _rb;
    private Transform _camTr;

    void Awake()
    {
        _rb = GetComponent<Rigidbody>();
    }

    void Start()
    {
        _camTr = Camera.main.transform;   // 씬 카메라가 확정된 뒤 1회
    }

    void FixedUpdate()
    {
        Vector3 dir = target.position - _camTr.position;
        _rb.MovePosition(_rb.position + dir.normalized * Time.fixedDeltaTime);
    }
}

채점 포인트

  • GetComponent 매 프레임 호출 → Awake/Start에서 캐싱
  • Camera.main은 태그 탐색이므로 참조 캐싱
  • MovePosition은 물리이므로 FixedUpdate로 이동
Q36 UN-04 미들 코드분석 코루틴·WaitForSeconds GC

다음 코루틴은 오래 도는 스포너입니다. GC(가비지 컬렉션) 관점에서 문제를 지적하고 개선하세요. 또한 WaitForSeconds와 WaitForSecondsRealtime의 차이, yield return null과의 차이도 설명하세요.

IEnumerator SpawnLoop()
{
    while (true)
    {
        Spawn();
        yield return new WaitForSeconds(1f);
    }
}
모범답안 보기

문제: WaitForSeconds는 참조형(클래스)이라 루프를 돌 때마다 new로 힙 할당이 발생 → 반복적인 GC 가비지 누적. WaitForSeconds는 상태가 사실상 불변이라 루프 밖에서 한 번 만들어 재사용하면 무할당으로 처리할 수 있다.

IEnumerator SpawnLoop()
{
    var wait = new WaitForSeconds(1f);   // 1회만 생성
    while (true)
    {
        Spawn();
        yield return wait;               // 재사용
    }
}

차이 설명

  • yield return null: 다음 프레임까지 한 프레임 대기(할당 없음). 참고로 yield return 0은 int가 object로 박싱되므로 대신 null을 쓴다.
  • WaitForSeconds(t): 스케일된 시간(Time.timeScale 영향)만큼 대기. timeScale = 0이면 영영 끝나지 않는다.
  • WaitForSecondsRealtime(t): 실제(unscaled) 시간으로 대기 → 일시정지(timeScale=0) 중에도 진행. 단, 이 타입은 내부 상태(대기 종료 시각)를 갖는 mutable 객체라 동시에 여러 코루틴에서 같은 인스턴스를 공유하면 안 된다.

보충: WaitForEndOfFrame, WaitForFixedUpdate 같은 yield 명령 객체도 캐싱해 재사용할 수 있다.

채점 포인트

  • 매 반복 new WaitForSeconds가 힙 할당 → 루프 밖 캐싱 재사용
  • WaitForSeconds는 timeScale 영향, Realtime은 unscaled
  • yield return null=다음 프레임, yield return 0은 박싱 주의
Q37 UN-05 미들 서술형 코루틴 vs async/await

Unity 코루틴과 C# async/await(Task)를 (1) 실행 스레드, (2) 생명주기/자동 취소, (3) 반환값·예외·취소 처리, (4) 할당 관점에서 비교하세요. 각각 어떤 상황에 쓰는 것이 적절한가요?

모범답안 보기
  • 실행 스레드: 코루틴은 항상 메인 스레드에서 프레임 단위로 스케줄된다. async/await 자체는 스레드를 새로 만들지 않으며(Task.Run 등을 써야 스레드풀에서 실행), Unity의 SynchronizationContext 덕분에 await 후 메인 스레드로 복귀할 수 있다. 단, Unity API는 메인 스레드에서만 안전하므로 백그라운드에서 Transform 등을 만지면 안 된다.
  • 생명주기/자동 취소: 코루틴은 MonoBehaviour에 종속되어 GameObject가 비활성(SetActive(false))/파괴되면 자동 중단된다(컴포넌트의 enabled=false만으로는 멈추지 않는 점에 주의). Task는 오브젝트가 파괴돼도 자동으로 취소되지 않아 파괴된 객체 접근·누수 위험이 있다 → CancellationToken(2022.2+의 destroyCancellationToken)으로 직접 취소해야 한다.
  • 반환값·예외·취소: 코루틴은 반환값을 받기 어렵고 예외 전파가 제한적이다(예외 시 해당 코루틴만 중단·로그). async/await는 반환값, try/catch 예외 처리, CancellationToken 취소가 자연스럽다.
  • 할당: Task/async는 상태머신·Task 객체 할당이 생긴다. 이를 줄이려면 ValueTask나 UniTask(무할당·Unity 친화)를 쓴다.

정리: 프레임 기반 연출·간단 타이머·씬 종속 로직은 코루틴, 반환값/예외/취소가 필요한 IO·네트워크·비동기 로직은 async/await(가급적 UniTask)가 적합하다.

오개념 교정: "async/await면 멀티스레드다"는 틀렸다 — await는 스레드를 만들지 않는다.

채점 포인트

  • 코루틴=메인 스레드 프레임 스케줄, await는 스레드 생성 아님
  • 코루틴은 오브젝트 파괴/비활성 시 자동 중단, Task는 수동 CancellationToken 필요
  • async는 반환값·예외·취소에 유리, 할당은 UniTask/ValueTask로 완화
  • async/await=멀티스레드 오개념 교정
Q38 UN-06 미들 실무시나리오 GC 스파이크 진단

모바일 빌드에서 몇 초마다 짧은 프레임 드랍(hitch)이 발생합니다. 프로파일러를 보니 매 프레임 GC Alloc이 수 KB씩 잡히고 주기적으로 GC.Collect 스파이크가 뜹니다. Update/코루틴에서 런타임 힙 할당을 유발하는 흔한 원인 4가지와 각 회피법을 제시하고, 이런 상황에서 오브젝트 풀링이 왜 도움이 되는지 설명하세요.

모범답안 보기

흔한 할당 원인과 회피법

  1. 문자열 연결/보간: "Score: " + score처럼 매 프레임 새 문자열 생성. → 값이 바뀔 때만 갱신, StringBuilder, TextMeshPro의 SetText(포맷, 인자)로 무할당 갱신.
  2. 박싱(boxing): 값 타입이 object로 승격되는 경우 — (구버전 Mono/IL2CPP에서) enum 키 Dictionary의 기본 비교자, params object[], 구조체를 인터페이스로 전달, 값 타입을 받는 로그 오버로드 등. → 전용 제네릭 오버로드, enum엔 커스텀 IEqualityComparer 지정.
  3. 람다/클로저 캡처: 지역 변수를 캡처하는 람다는 매번 클로저 객체를 할당(특히 매 프레임 이벤트 구독/등록). → 캡처 없는 static 람다 사용, 델리게이트를 필드에 캐싱해 재사용.
  4. 인터페이스를 통한 foreach: List<T>를 직접 foreach하면 열거자가 struct라 할당이 없지만, 같은 리스트를 IEnumerable<T>/IList 등 인터페이스 타입으로 순회하면 그 struct 열거자가 박싱되어 할당된다. → 구체 타입으로 순회하거나 인덱스 for 루프.

(그 밖에 매 프레임 GetComponent, Camera.main, new WaitForSeconds, LINQ, 잦은 Instantiate/Destroy도 주범이다.)

오브젝트 풀링이 도움되는 이유: 총알·이펙트처럼 빈번한 Instantiate/Destroy는 매번 힙 할당을 만들고 Destroy된 객체는 GC 대상이 되어 스파이크를 유발한다. 풀링은 객체를 미리 생성해 두고 SetActive 토글로 재사용하여 할당/해제 자체를 없애므로 GC 압박과 hitch를 근본적으로 줄인다.

채점 포인트

  • 문자열·박싱·람다 캡처·인터페이스 foreach가 대표 할당원
  • List<T> 직접 foreach는 무할당, 인터페이스 순회는 박싱
  • 각 원인의 무할당 대안(SetText·전용 오버로드·static 람다·for)
  • 풀링=Instantiate/Destroy 제거로 GC 스파이크 완화
Q39 UN-07 시니어 코드분석 ==null 오버로드·파괴된 오브젝트

아래 코드에서 대상 GameObject를 Destroy()한 뒤에도 (A) 분기가 참이 되어 이미 파괴된 대상에 접근하는 버그가 보고되었습니다.

public class Weapon : MonoBehaviour
{
    private IDamageable _target;   // 인터페이스 타입 필드

    public void SetTarget(GameObject go)
    {
        _target = go.GetComponent<IDamageable>();
    }

    void Update()
    {
        if (_target != null)       // (A)
            _target.ApplyDamage(10);
    }
}

Unity의 ==null 동작과 연관지어 원인을 설명하고, 왜 인터페이스 타입으로 담으면 함정에 빠지는지, 올바른 처리법을 제시하세요.

모범답안 보기

원인: UnityEngine.Object는 ==/!= 연산자를 오버로드하여, C# 참조가 아직 살아 있어도 네이티브(C++) 객체가 파괴됐으면 null처럼 보이게 만든다(이른바 fake null). 그래서 Component == null은 파괴 후 true가 된다.

그러나 이 오버로드는 컴파일 타임 정적 타입이 UnityEngine.Object(또는 파생)일 때만 적용된다. 위 코드의 _target은 정적 타입이 인터페이스 IDamageable이므로 오버로드가 적용되지 않고 C#의 기본 참조 비교가 쓰인다. 파괴된 오브젝트라도 관리 힙의 참조는 여전히 non-null이므로 _target != null이 true → 파괴된 객체에 접근해 MissingReferenceException이 발생한다.

해결

  • 인터페이스와 별개로 UnityEngine.Object 참조를 함께 보관하거나, 검사 시점에 캐스팅해 오버로드를 태운다.
if (_target as UnityEngine.Object != null)   // (_target as UnityEngine.Object) != null 로 파싱, 오버로드 적용
    _target.ApplyDamage(10);
  • 혹은 필드를 MonoBehaviour/Component 타입으로 들고, 사용할 때만 인터페이스로 캐스팅한다. 파괴 시점에 명시적으로 참조를 비워주는 것도 안전하다.

추가 함정: null 조건 연산자 ?.와 null 병합 ??도 오버로드된 ==를 타지 않으므로(순수 참조 null 검사) UnityEngine.Object에 쓰면 fake null을 감지하지 못한다 → Unity 객체에는 ?./?? 대신 명시적 == null 비교를 사용한다.

채점 포인트

  • UnityEngine.Object의 오버로드된 ==는 파괴 시 fake null 반환
  • 정적 타입이 인터페이스/object면 오버로드 미적용 → 기본 참조 비교
  • as UnityEngine.Object 캐스팅 후 ==null 검사로 해결
  • ?. 와 ??는 오버로드를 안 타므로 Unity 객체에 지양
Q40 UN-08 시니어 실무시나리오 DOTS·IL2CPP/AOT·Addressables

수천 개의 유닛을 동시 시뮬레이션하는 전략 게임의 성능/출시를 준비 중입니다. 다음 세 가지를 판단해 주세요.

  1. DOTS(ECS) / Job System / Burst 도입 여부의 판단 기준과 각 구성요소의 역할.
  2. iOS 빌드는 IL2CPP를 사용합니다. Mono 대비 차이와 AOT 제약(제네릭/리플렉션)이 코드(및 DOTS)에 주는 영향.
  3. 런타임 에셋 로딩을 Addressables로 갈지 Resources로 갈지.
모범답안 보기

1) DOTS/Job/Burst

  • ECS: 데이터 지향(SoA)으로 동종 컴포넌트를 캐시 친화적 chunk에 모아 두어, 수천~수만의 동질 엔티티에 같은 로직을 반복할 때 캐시 미스를 줄인다.
  • Job System: 안전성 검사가 있는 NativeContainer 기반으로 로직을 여러 코어에 병렬화(메인 스레드 밖에서 안전 실행).
  • Burst: Job/수치 코드를 LLVM으로 SIMD 네이티브로 컴파일해 대폭 가속.
  • 판단 기준: 대량·동질 엔티티에 CPU 바운드 데이터 병렬성이 있을 때 이득. 소수 오브젝트·복잡한 개별 게임플레이·기존 MonoBehaviour 자산이 많으면 과설계다. 전면 ECS 없이 IJob+NativeArray+Burst만 부분 도입하는 절충도 유효하다.

2) IL2CPP vs Mono / AOT

  • Mono는 IL을 런타임 JIT 컴파일(빠른 iteration, 주로 에디터/개발). IL2CPP는 IL→C++→네이티브 AOT 컴파일로 성능·코드 보호에 유리하나 빌드가 느리다. iOS는 JIT가 금지되어 IL2CPP가 사실상 필수다.
  • AOT 제약: 런타임 코드 생성이 불가하다. System.Reflection.Emit 등은 못 쓰고, 값 타입 제네릭 인스턴스화가 코드에 실제로 등장하지 않으면 AOT에 그 버전이 없어 런타임 예외가 날 수 있다(코드 스트리핑과 겹치면 link.xml로 보존 필요). 리플렉션 의존 직렬화/DI도 주의.
  • DOTS와의 관계: Burst 자체가 AOT 컴파일러라 IL2CPP/AOT 환경과 궁합이 좋다.

3) Addressables vs Resources

  • Resources 폴더는 내용이 빌드에 통째로 포함되어 초기화가 느려지고 메모리·용량 관리가 어려워 대규모에는 공식적으로 비권장이다.
  • Addressables는 주소 기반 비동기 로드/언로드, 참조 카운팅, 에셋번들·원격(CDN)/패치, 메모리 제어를 제공한다. 대량 유닛/DLC/원격 콘텐츠가 있는 이 프로젝트에는 Addressables가 정답이다.

채점 포인트

  • ECS=캐시친화 대량 엔티티, Job=병렬화, Burst=SIMD 네이티브; 동질·대량일 때 도입
  • iOS는 JIT 금지→IL2CPP(AOT) 필수, Mono는 JIT
  • AOT는 Reflection.Emit 불가·값타입 제네릭/스트리핑 예외(link.xml)
  • 대규모/원격은 Resources 비권장→Addressables(비동기·참조카운팅)

Q41 G-01 주니어 단답형 벡터 내적/외적

정규화(normalize)된 두 방향 벡터 A, B가 있다.

  1. 내적(dot) A·B의 값이 0 / 양수 / 음수일 때 두 벡터의 각도 관계를 각각 쓰시오.
  2. 적이 플레이어의 시야 정면 반각(half-angle) 30° 이내에 있는지 판정하려면 내적/외적 중 무엇을 쓰며, 판정식을 쓰시오. (플레이어 forward와 플레이어→적 방향을 사용)
  3. 3D에서 외적(cross) A×B 결과 벡터의 방향과 크기가 각각 무엇을 의미하는지 쓰시오.
모범답안 보기
  1. 정규화되어 있으면 A·B = |A||B|cosθ = cosθ. 0 → 수직(90°), 양수 → 예각(0°~90°, 같은 방향 성향), 음수 → 둔각(90°~180°, 반대 방향 성향).
  2. 내적을 쓴다. toTarget을 정규화한 뒤 Vector3.Dot(forward, toTarget) >= cos(30°) 이면 시야 안. cos는 각이 커질수록 작아지므로 부등호는 >=. 흔한 실수는 전체 시야각(60°)을 그대로 쓰는 것 — 반드시 반각(30°)의 코사인과 비교해야 하고, 두 벡터(forward와 toTarget)를 모두 정규화해야 한다. 참고로 이 판정은 반각 30°의 원뿔(cone) 안쪽을 검사한다. (좌/우 어느 쪽인지 구분은 외적을 쓴다.)
  3. 방향: 두 벡터가 이루는 평면에 수직인 벡터(오른손 법칙; Unity는 왼손 좌표계라 Vector3.Cross는 왼손 법칙을 따른다 — Unity 공식 문서 명시). 크기: |A||B|sinθ, 즉 두 벡터가 만드는 평행사변형의 넓이.

채점 포인트

  • cosθ 부호로 각도 구간(수직/예각/둔각) 판정
  • 시야 판정은 내적 + 반각 코사인 비교, 두 벡터 정규화 필수
  • 외적=수직 벡터, 크기=|A||B|sinθ(평행사변형 넓이)
Q42 G-02 주니어 서술형 delta time / 프레임 타이밍

Unity에서 이동 코드를 transform.position += velocity * Time.deltaTime 처럼 작성한다.

  1. Time.deltaTime을 곱하는 이유와, 곱하지 않고 += velocity만 하면 어떤 문제가 생기는지 설명하시오.
  2. 이동·타이머 같은 로직은 Update()에서 처리하면서, 물리(Rigidbody) 는 왜 FixedUpdate()에서 다뤄야 하는지 설명하시오.
모범답안 보기
  1. Time.deltaTime은 직전 프레임과 현재 프레임 사이의 경과 시간(초)이다. 프레임 레이트는 기기 성능·부하에 따라 계속 변하므로, 프레임당 고정량을 더하면 속도가 프레임률에 비례해 달라진다(60fps에서 30fps의 2배 속도). velocity(= 초당 이동량)에 deltaTime을 곱하면 프레임률과 무관하게 초당 동일한 이동량으로 정규화된다. 곱하지 않으면 고사양 기기에서 더 빨라지고 프레임 드랍 시 느려져 밸런스·체감이 하드웨어에 종속된다.
  2. 물리 시뮬레이션은 수치 적분의 안정성·결정성을 위해 고정 timestep이 필요하다. Update()는 가변 간격이라 적분 오차, 충돌 관통(tunneling), 비결정적 결과가 생긴다. FixedUpdate()는 고정 간격(기본 0.02초, 50Hz)으로 물리 스텝과 동기되므로 Rigidbody의 힘/velocity 조작은 여기서 해야 한다. (참고: FixedUpdate 안에서의 Time.deltaTime은 Time.fixedDeltaTime 값을 반환한다.)

채점 포인트

  • deltaTime을 곱해 프레임률 독립적인 초당 속도로 정규화
  • 미적용 시 고fps에서 빨라지는 하드웨어 의존 버그
  • 물리는 고정 timestep(FixedUpdate) 필요 — 적분 안정성/결정성
Q43 G-03 주니어 코드분석 delta time 버그

아래 미사일은 초당 10유닛 전진, 초당 90° 회전, 3초 뒤 파괴를 의도했다. 실제로는 어떻게 동작하며(특히 프레임률에 따라), 어떻게 고쳐야 하는가?

public class Missile : MonoBehaviour
{
    public float speed = 10f;      // 초당 이동 속도(의도)
    public float turnSpeed = 90f;  // 초당 회전 각도(의도)
    public float lifeTime = 3f;    // 3초 후 파괴(의도)

    void Update()
    {
        transform.position += transform.forward * speed;
        transform.Rotate(0f, turnSpeed, 0f);

        lifeTime -= 1f;
        if (lifeTime <= 0f)
            Destroy(gameObject);
    }
}
모범답안 보기

세 줄 모두 Time.deltaTime이 빠져 프레임당 처리되므로 전부 프레임률에 종속된다.

  • 이동·회전(초당 값이 fps에 비례해 폭주): 60fps 기준 이동 10×60 = 600유닛/초, 회전 90×60 = 5400°/초. 30fps에선 프레임 수가 절반이므로 이 초당 값들이 절반(300유닛/초, 2700°/초)이 된다.
  • 수명(오히려 저fps에서 더 오래 생존): lifeTime은 프레임마다 1씩 줄어 정확히 3프레임 뒤 파괴된다. 이 3프레임은 프레임률과 무관하게 일정하므로, 벽시계 시간으로는 60fps에서 약 0.05초, 30fps에서 약 0.1초로 저사양(저fps) 기기에서 더 오래 산다(이동·회전 속도와는 반대 방향의 종속성). 결국 이동·회전·수명 모두 기기마다 결과가 달라진다.
  • 수정: 이동·회전·수명 감소 모두 Time.deltaTime을 곱/차감한다.
transform.position += transform.forward * speed * Time.deltaTime;
transform.Rotate(0f, turnSpeed * Time.deltaTime, 0f);
lifeTime -= Time.deltaTime;

추가로, 고속 이동체는 프레임 간 충돌 관통(tunneling)이 생길 수 있으므로 물리 충돌이 중요하면 Rigidbody+FixedUpdate 또는 레이캐스트 기반 이동을 고려한다. 단순 수명 처리는 Destroy(gameObject, 3f)로 대체할 수도 있다.

채점 포인트

  • 세 줄 모두 deltaTime 누락 → 프레임률 종속
  • 이동/회전 초당 값은 fps에 비례해 폭주(60fps에서 600유닛/초·5400°/초)
  • lifeTime은 항상 3프레임 뒤 파괴 → 저fps일수록 벽시계 생존시간이 더 김(이동/회전과 반대 방향 종속)
  • 이동/회전/수명 모두 deltaTime 곱·차감으로 수정
Q44 G-04 미들 서술형 쿼터니언/짐벌락/slerp

회전을 다룰 때 다음을 설명하시오.

  1. 오일러각(Euler angles)으로 회전을 직접 다룰 때 발생하는 짐벌락(gimbal lock) 이 무엇이며, 쿼터니언(quaternion) 이 이를 어떻게 회피하는가?
  2. 두 회전을 부드럽게 보간할 때 Lerp 대신 Slerp 를 쓰는 이유는? 쿼터니언을 성분별로 그냥 선형보간(Lerp)하면 어떤 문제가 있는가?
모범답안 보기
  1. 짐벌락: 오일러각은 세 축 회전을 순차 적용하는데, 특정 자세(예: pitch가 ±90°)에서 두 회전축이 정렬되면 회전 자유도가 3→2로 붕괴해 한 축의 회전이 소실된다. 그 결과 특정 방향으로 못 돌거나 자세가 급격히 튄다. 쿼터니언은 4D 단위 쿼터니언으로 축-각(axis-angle) 회전을 직접 표현하므로 순차 축 회전이라는 구조 자체가 없어 짐벌락이 없고, 회전 합성이 곱으로 간단하며 특이점이 없다. (단, 쿼터니언을 다시 오일러각으로 변환해 저장·표시하면 그 오일러 표현에서는 짐벌락이 다시 나타날 수 있다.)
  2. Slerp(구면 선형보간)는 두 회전을 4D 초구 위 대원 호(great arc)를 따라 등각속도로 보간한다. 성분별 Lerp는 직선 보간이라 (1) 결과가 단위 길이를 벗어나 정규화가 필요하고, (2) 각속도가 일정하지 않아 중간이 빠르거나 느려진다. 또한 q와 -q는 같은 회전을 나타내므로, 보간 전 내적 부호를 확인해 dot<0이면 한쪽 부호를 뒤집어 최단 경로로 돌아야 먼 길로 회전하지 않는다. (Unity의 Quaternion.Slerp/Lerp는 내부적으로 최단 경로 처리 및 결과 정규화를 해 준다.) 각도차가 작으면 정규화 Lerp(nlerp)가 시각적으로 충분하고 더 저렴한 대안이 된다.

채점 포인트

  • 짐벌락=축 정렬로 자유도 소실, 쿼터니언은 축-각 표현이라 없음(단 오일러 변환 시 재발 가능)
  • Slerp=대원 호 등각속도 보간
  • 성분별 Lerp는 비단위·비등속, q/-q 최단경로 처리 필요
Q45 G-05 미들 코드분석 Lerp 프레임 의존 스무딩

카메라가 타깃을 부드럽게 따라가도록 아래처럼 작성했다. 이 코드는 프레임률이 높을수록 더 빨리 따라붙는 문제가 있다. 왜 그런지 설명하고, 프레임률에 독립적으로 만드는 방법을 제시하시오.

void Update()
{
    transform.position = Vector3.Lerp(transform.position, target.position, 0.1f);
}
모범답안 보기

Vector3.Lerp(a, b, t)는 a에서 b쪽으로 t 비율만큼 이동시킨다. 매 프레임 t=0.1을 적용하면 "프레임당" 10%씩 접근하므로, 프레임 수가 많은 고fps 기기에서 초당 훨씬 여러 번 접근해 더 빨리 수렴한다. 즉 지수 감쇠의 시정수가 프레임률에 종속된다.

흔한 오해: Vector3.Lerp(a, b, Time.deltaTime)로 바꾸면 프레임 독립이 된다는 것 — 이는 근사일 뿐 정확히 프레임 독립이 아니다(프레임당 고정 비율 감쇠가 아니므로). 정확한 프레임 독립 지수 감쇠는 감쇠율 k(1/초)에 대해 t = 1 - exp(-k·dt) 형태여야 한다.

float k = 5f; // 감쇠율(1/초)
transform.position = Vector3.Lerp(transform.position, target.position,
                                  1f - Mathf.Exp(-k * Time.deltaTime));

또는 스프링 기반의 Vector3.SmoothDamp(ref velocity)를 사용한다. 카메라 추적은 렌더링 직전 최신 타깃 위치를 반영하려면 LateUpdate에서 처리하는 것이 좋다.

채점 포인트

  • 고정 t를 매 프레임 적용 → 프레임당 감쇠라 고fps에서 빨라짐
  • Lerp(a,b,deltaTime)은 정확한 프레임 독립이 아님(오개념 교정)
  • 정확한 해: t = 1 - exp(-k·dt) 또는 SmoothDamp
Q46 G-06 미들 실무시나리오 TCP vs UDP

실시간 대전 액션 게임(초당 20~30회 상태 업데이트)의 네트워크 전송 계층을 설계한다. TCP와 UDP 중 무엇을 기반으로 하겠는가? head-of-line blocking, 신뢰성/순서보장, 지연 관점에서 근거를 설명하고, UDP를 택했을 때 신뢰성이 필요한 메시지(채팅, 아이템 획득 확정 등)는 어떻게 처리할지 서술하시오.

모범답안 보기

실시간 위치/상태 동기는 UDP 기반이 표준이다.

  • TCP 문제: 순서·신뢰성을 보장하지만 패킷 손실 시 재전송을 기다리느라 뒤따르는 데이터가 막히는 head-of-line blocking이 발생한다. 실시간 상태는 "가장 최신 값"만 중요하고 오래된 패킷은 버려도 되므로, TCP의 순서보장이 오히려 지연을 유발한다. Nagle 알고리즘도 지연 원인(TCP_NODELAY로 끄지만 HOL 문제는 남음)이다.
  • UDP 선택: 순서·신뢰성이 없으므로 애플리케이션에서 필요한 것만 구현한다. 상태 동기는 매 틱 전체/델타 스냅샷을 보내므로 패킷이 손실돼도 다음 틱이 덮어써 재전송이 불필요하고, 시퀀스 번호로 오래된(순서 뒤바뀐) 패킷은 폐기한다.
  • 신뢰성 필요 메시지: ACK+재전송+시퀀싱을 갖춘 신뢰성 UDP 채널을 별도로 두거나(비신뢰/신뢰·순서보장 채널을 분리), 그런 메시지만 별도 신뢰 채널로 보낸다. 실무에서는 ENet/RakNet, Unreal의 신뢰/비신뢰 RPC, Unity Transport 등이 이런 채널 개념을 제공한다.
  • 아이템 획득 같은 확정성 이벤트는 서버 권위로 결정해 신뢰 채널로 통지하고, 클라는 서버 확정을 최종 진실로 삼는다.

채점 포인트

  • 실시간 동기는 UDP — TCP는 HOL blocking으로 오래된 데이터가 막음
  • 손실 시 재전송 대신 다음 스냅샷이 덮어씀 + 시퀀스로 구식 폐기
  • 신뢰 필요 메시지는 별도 신뢰 채널(ACK/재전송) 또는 서버 권위 확정
Q47 G-07 시니어 서술형 예측·재조정·보간·지연보상

서버 권위(server-authoritative) 방식의 온라인 FPS/액션 게임에서 다음 세 기법이 각각 어떤 문제를 풀고 어떻게 동작하는지 설명하시오. 또한 각 기법이 로컬 플레이어와 원격 플레이어에 어떻게 다르게 적용되는지 밝히시오.

  1. 클라이언트 예측(client-side prediction)과 서버 재조정(server reconciliation)
  2. 스냅샷/엔티티 보간(snapshot interpolation)
  3. 지연 보상(lag compensation)
모범답안 보기

서버 권위는 치팅 방지에 좋지만 입력→서버 왕복(RTT)만큼 반응 지연이 생긴다. 세 기법으로 이 지연을 감춘다.

  1. 클라 예측 + 재조정(로컬 플레이어): 입력을 서버로 보내는 동시에 클라가 같은 시뮬레이션을 즉시 로컬 적용해 조작 지연을 0처럼 보이게 한다. 각 입력에 시퀀스 번호를 붙이고, 서버는 권위 상태와 "마지막으로 처리한 입력 번호"를 회신한다. 클라는 그 권위 상태로 되돌린 뒤 아직 확인되지 않은 입력들을 다시 재생(replay)해 재예측하고, 서버 값과 어긋나면 부드럽게 보정한다(reconciliation). 예측이 맞으면 눈에 띄지 않는다.
  2. 스냅샷 보간(원격 플레이어): 다른 플레이어는 예측하지 않는다. 서버 스냅샷을 버퍼에 쌓아 약간 과거 시점(interpolation delay, 예: 100ms)을 두 스냅샷 사이 보간으로 렌더한다. 낮은 틱레이트나 패킷 손실에도 부드럽게 보인다. 미래를 추정하는 외삽(extrapolation)은 오차 위험이 커서 보통 보간을 우선한다.
  3. 지연 보상(서버, 히트 판정): 원격 플레이어를 과거 시점으로 보다 보니, 쏜 순간 슈터 화면의 타깃 위치와 서버 현재 위치가 다르다. 서버는 발사 명령에 담긴 클라 타임스탬프/틱으로 과거 상태를 되감아(rewind) 그 시점의 히트박스로 판정한다 → "본 대로 맞는다". 대가로 피격자 입장에선 코너 뒤에서 맞는(shot-around-corner) 현상이 생긴다.

정리: 로컬 플레이어=예측+재조정(즉각 반응), 원격 플레이어=스냅샷 보간(부드러운 표현), 히트 판정=서버 되감기(lag compensation). 결과적으로 각 클라는 같은 월드를 "로컬은 현재, 원격은 과거"라는 서로 다른 시간축에서 본다.

채점 포인트

  • 로컬=예측+시퀀스 기반 재조정(replay)로 입력 지연 은폐
  • 원격=버퍼링 후 과거 시점 스냅샷 보간(외삽보다 우선)
  • 지연보상=서버가 클라 타임스탬프로 과거 히트박스 되감기
  • 로컬은 현재/원격은 과거 — 서로 다른 시간축
Q48 G-08 시니어 실무시나리오 DOD/ECS/브로드페이즈

수만 개의 유닛(적·발사체)이 매 프레임 이동·충돌 검사를 하는 RTS/디펜스 게임에서, 전통적 OOP(각 Entity가 Update()를 돌며 서로를 O(n²)로 검사)로 심각한 프레임 저하가 발생한다. 데이터 지향 설계(DOD) 와 브로드페이즈(broadphase) 관점에서 어떻게 최적화하겠는가? 캐시 지역성, 충돌 브로드페이즈 자료구조, 병렬화, ECS를 근거로 서술하시오.

모범답안 보기

우선순위는 알고리즘 복잡도 → 데이터 레이아웃 → 병렬/SIMD 순이며, 모두 프로파일링 기반으로 진행한다.

  • 브로드페이즈(O(n²) → 근접 후보만): 공간 분할로 충돌 후보를 좁힌 뒤 정밀 검사(narrow phase)만 수행한다. 대량 균질 유닛에는 uniform grid/spatial hash가 평균 상수시간 삽입·조회로 특히 유리하고, 분포가 불균일하면 quadtree/BVH, 축 정렬 이동이 많으면 sweep-and-prune을 고려한다.
  • 캐시 지역성(DOD): OOP는 엔티티가 힙에 흩어진 참조/객체(AoS 성향)로 놓이고 가상함수 Update()의 vtable 간접호출까지 겹쳐 캐시 미스·분기 예측 실패가 잦다. 데이터를 SoA(positions[], velocities[] …)로 모아 연속 메모리를 선형 순회하면 캐시 히트율과 SIMD 친화성이 오른다. "객체별 Update 호출"이 아니라 "같은 연산을 배열 전체에 일괄 적용"하는 데이터 변환 파이프라인으로 재구성한다.
  • ECS: 컴포넌트(데이터)를 아키타입/청크 단위 연속 배열로 저장하고 시스템이 배치로 처리해 DOD를 구조적으로 강제한다. Unity DOTS(Entities + Burst + Job System)가 대표적이다.
  • 병렬화: 이동·브로드페이즈 갱신처럼 독립적인 데이터 병렬 작업은 Job System/멀티스레드로 분산하고 Burst로 SIMD 컴파일한다. 단, 쓰기 경합을 피하려면 읽기 단계와 쓰기 단계를 분리해야 한다.

채점 포인트

  • 브로드페이즈(spatial hash/grid, BVH, sweep-and-prune)로 O(n²) 제거
  • 힙 산재 객체+가상함수 → SoA 연속 배열로 캐시 지역성/SIMD 확보
  • ECS(DOTS/Burst/Job)로 배치 처리 + 데이터 병렬화
  • 알고리즘→레이아웃→병렬 순, 프로파일 기반

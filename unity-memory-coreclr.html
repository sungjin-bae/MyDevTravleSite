먼저 못박기

이 세션의 mark-sweep-compact · LOH · decommit · 세대별 GC는 대부분 “앞으로 올 CoreCLR GC” 이야기입니다. 지금 빌드하는 Unity(Mono/IL2CPP)는 여전히 Boehm GC(보수적 · 비세대별 · non-compacting) 세계라는 점을 먼저 구분해야 나머지가 어긋나지 않습니다.

관리 힙 릭 1순위

이벤트/델리게이트 미해제가 가장 흔한 관리 힙 누수입니다. publisher가 delegate로 subscriber를 강하게 붙잡아 GC가 못 건드립니다. OnDisable/OnDestroy에서 -=로 반드시 해제하세요.

GC 스파이크 줄이는 3대장

NonAlloc(재사용 버퍼) · 바이너리 직렬화(MemoryPack) · 문자열(ZString). 공통 원리는 하나 — “매 프레임/매 호출 새로 할당하지 말고, 미리 만든 버퍼를 재사용해 gen0 가비지를 없앤다”입니다.

인스턴싱 ≠ 풀링

“렌더 메쉬 인스턴스”의 인스턴스는 오브젝트 재활용(풀링)이 아니라 GPU Instancing — 같은 메시+머티리얼을 드로우 콜 하나로 묶어 그리는 렌더링 기법입니다. 그리고 네이티브 메모리는 GC가 안 건드리니 Object.Destroy() / NativeArray.Dispose()로 직접 정리해야 합니다.

01 · 큰 그림

유니티 메모리 구조와 CoreCLR 전환: 세션 개요

Unity의 메모리는 관리 힙 · 네이티브 메모리 · GPU 메모리로 나뉩니다. 그리고 그 관리 힙을 굴리는 GC가 지금의 Boehm(보수적·비세대별·non-compacting)에서 .NET CoreCLR의 정밀·세대별·compacting GC로 갈아타는 중이라는 것이 이 세션 전체를 관통하는 핵심 축입니다.

그림 Unity 런타임 메모리의 세 영역 — GC가 보는 곳은 하나뿐

핵심 — GC 튜닝으로 해결되는 건 왼쪽 관리 힙뿐. 텍스처 메모리 압박·네이티브 릭은 GC가 아니라 Addressables 언로드·압축 포맷 같은 네이티브 측 대책이 필요하다.

Unity 런타임 메모리는 크게 세 영역으로 나눠서 보는 게 출발점입니다. 첫째, 관리 힙(managed heap) — 여러분이 C#에서 new로 만든 클래스 인스턴스, 배열, 문자열, 델리게이트 같은 관리 객체가 사는 곳이고, GC가 자동으로 회수하는 대상입니다. 둘째, 네이티브 메모리(native memory) — 엔진의 C++ 코어가 관리하는 영역으로, Texture / Mesh / AudioClip 같은 에셋 데이터, 씬 그래프, 물리 엔진 상태 등이 여기 삽니다. C# 쪽 Texture2D 객체는 관리 힙의 얇은 래퍼일 뿐이고 실제 픽셀 데이터는 네이티브 메모리에 있습니다. 셋째, GPU 메모리(VRAM) — 렌더링에 실제로 쓰이는 텍스처/버퍼가 올라가는 그래픽스 드라이버 관할 영역입니다. 이 세션의 GC 이야기는 오직 첫 번째, 관리 힙에만 해당합니다. 네이티브/GPU 메모리는 GC가 건드리지 않고 엔진이 참조 카운팅/명시적 해제로 관리합니다.

이 구분이 중요한 이유는, 초보자가 흔히 "GC가 다 알아서 청소해 주겠지"라고 오해하기 때문입니다. GC는 관리 힙만 봅니다. 텍스처를 Resources.Load로 잔뜩 올려놓고 참조만 놓아버리면 네이티브 메모리는 새지 않지만, Instantiate한 GameObject를 Destroy 안 하거나 이벤트 구독을 해제 안 해서 관리 객체가 계속 참조되면 그건 관리 힙 릭입니다. 반대로 큰 텍스처의 메모리 압박은 GC 튜닝으로 해결되지 않고 Addressables 언로드/압축 포맷 같은 네이티브 측 대책이 필요합니다. 어느 영역이 문제인지 먼저 가르는 것이 최적화의 첫 단추입니다.

이제 이 세션의 진짜 주제. Unity는 오랫동안 C# 코드를 두 가지 스크립팅 백엔드로 실행해 왔습니다 — Mono(JIT, 데스크톱/에디터 기본)와 IL2CPP(C#을 C++로 변환 후 AOT 컴파일, 콘솔/모바일/WebGL 등). 그런데 이 둘 모두 밑바탕의 GC로 Boehm(BDW) 보수적 수집기를 공유합니다. Unity는 이 오래된 Mono 런타임을 Microsoft의 .NET CoreCLR 런타임으로 교체하는 대규모 전환을 진행 중입니다. 공개된 로드맵상 CoreCLR은 Unity 6.7 LTS에서 실험적(Experimental) 데스크톱 플레이어 백엔드로 등장하고, 2026년 말 Unity 6.8에서 스크립팅 런타임의 기본 자리를 이어받아 Mono가 은퇴 수순에 들어갑니다. IL2CPP는 콘솔처럼 AOT가 필수인 플랫폼을 위해 계속 남습니다. CoreCLR 전환의 핵심 동기가 바로 최신 C#/.NET 지원(.NET 10 / C# 14)과 함께 이 세션에서 배운 정밀·세대별·compacting GC를 얻는 것입니다.

그래서 세션의 각 개념이 왜 하나로 꿰이는지가 여기서 드러납니다. '세대별(generational)'은 CoreCLR GC가 gen0/gen1/gen2로 객체를 나이대별로 관리하며 대부분 짧게 죽는 객체(gen0)만 자주 수집해 비용을 낮추는 방식입니다. 'mark-sweep-compact'는 도달 가능한 객체를 표시(mark)하고, 죽은 객체를 자유 공간으로 회수(sweep)하며, 살아있는 객체를 한쪽으로 모아 조각화(fragmentation)를 없애는(compact) 과정입니다 — Boehm은 이 compact 단계가 없습니다. 'LOH(Large Object Heap)'는 기본 85,000바이트 이상의 큰 객체를 위한 별도 힙으로, 이동 비용이 커서 기본적으로 compact 안 하고 sweep으로만 관리되며 gen2 취급으로 수집됩니다. 'decommit'은 gen2 수집 후 살아있는 객체가 없는 세그먼트/리전을 OS에 반납(가상 메모리 해제)하는 동작입니다. 이 네 가지는 전부 "CoreCLR GC가 어떻게 관리 힙을 다루는가"의 세부이고, 그래서 CoreCLR 전환이 세션 전체의 배경 서사입니다.

정리하면 대조는 이렇습니다. 현재(Mono/IL2CPP + Boehm): 보수적(conservative) 스캔, 비세대별(매 수집마다 전체 힙 순회 → 힙이 커질수록 느려짐), non-compacting(조각화 누적, 힙이 한 번 커지면 잘 줄지 않음), 기본 incremental 모드로 수집 부하를 여러 프레임에 분산. 미래(CoreCLR + .NET GC): 정밀(precise) — 어디가 참조인지 정확히 알고 스캔, 세대별(gen0만 자주 → 짧은 pause), compacting(조각화 해소 + 힙 축소 가능), LOH 별도 관리, gen2 후 세그먼트/리전 decommit으로 OS에 메모리 반납. 성능·최신 C# 관점에선 분명한 진보지만, compacting GC는 객체가 물리적으로 이동한다는 뜻이라 네이티브 포인터를 붙잡아 두는 unsafe/pinning 코드나 도메인 리로드 가정에 의존한 코드는 재검토가 필요합니다.

덤으로, 에디터 워크플로우에도 큰 변화가 예고돼 있습니다. 지금 Mono 기반에서는 스크립트 재컴파일이나 Play 모드 진입 때 도메인 리로드(domain reload)로 관리 코드 공간(AppDomain)을 통째로 언로드/리로드합니다. CoreCLR 기반(6.8 목표)에서는 이 AppDomain 개념이 최신 .NET의 Assembly Load Context(ALC)로 바뀌어, 재컴파일/Play 모드 전환 시 관리 코드 공간을 통째로 리셋하지 않고 변경된 코드만 부분 리로드하는 방향이라, static 상태가 자동으로 초기화된다는 기존 가정이 깨질 수 있습니다. Unity가 6.5부터 [OnEnteringPlayMode]/[AutoStaticsCleanup] 같은 Lifecycle Management API를 도입해 개발자가 static 리셋을 명시적으로 처리하도록 준비시키는 것도 이 전환의 일부입니다. 이건 GC 자체는 아니지만 "CoreCLR가 온다"는 같은 물결의 일부이므로 함께 기억해 두시면 좋습니다.

이 세션에서 배운 GC 개념(세대별·compact·LOH·decommit)은 대부분 오른쪽 CoreCLR 열의 성격입니다. Dusk Hollow가 쓰는 Unity 6.3 LTS는 여전히 왼쪽(Boehm) 세계입니다.

“유니티 메모리 구조와 CoreCLR 이해하기 세션”

✅ 정리 & 바로잡기

먼저 큰 그림을 잡고 가시죠. 이 세션에서 배운 mark-sweep-compact, LOH, 세대별 GC, decommit 같은 개념들은 "지금 내가 빌드하는 Unity가 이렇게 동작한다"가 아니라, 대부분 "앞으로 올 CoreCLR GC가 이렇게 동작한다"는 이야기입니다. 이 점을 헷갈리면 나머지 개념이 전부 어긋나기 때문에 먼저 못박고 갑니다. 현재 출시된 Unity(Mono / IL2CPP 스크립팅 백엔드)는 Boehm-Demers-Weiser(BDW) GC를 씁니다. 이 GC는 (1) 보수적(conservative) — 스택/레지스터의 비트 패턴을 "포인터일 수도 있다"고 보수적으로 간주해 스캔하고, (2) 비세대별(non-generational) — gen0/1/2 구분 없이 매 수집마다 힙 전체를 훑고, (3) non-compacting — 살아있는 객체를 옮겨 빈틈을 메우지 않습니다. 반면 세션에서 배운 세대별·mark-sweep-\"compact\"·LOH·세그먼트 decommit은 전부 .NET CoreCLR GC의 성격입니다. 즉 지금 여러분이 Dusk Hollow를 빌드하는 Unity 6.3 LTS는 여전히 Boehm 세계이고, 세션 내용은 "곧 오는" CoreCLR 세계를 미리 배운 것이라고 이해하시면 정확합니다.

📌 핵심 정리

  • Unity 메모리는 관리 힙(C# 객체, GC 대상) / 네이티브 메모리(에셋·엔진, GC 무관) / GPU 메모리(VRAM) 세 영역으로 나뉜다.
  • GC는 오직 관리 힙만 회수한다 — 텍스처 메모리 압박이나 네이티브 릭은 GC 튜닝이 아니라 Addressables/명시적 언로드로 해결한다.
  • 현재 출시 Unity(Mono·IL2CPP)는 Boehm(BDW) GC: 보수적(conservative) + 비세대별(non-generational) + non-compacting + 기본 incremental 모드.
  • 미래 CoreCLR GC는 정밀(precise) + 세대별(gen0/1/2) + mark-sweep-compact + LOH 분리 + 세그먼트/리전 decommit — 세션에서 배운 개념들은 대부분 이 CoreCLR 쪽 성격이다.
  • 로드맵상 CoreCLR은 6.7 LTS에 Experimental 데스크톱 플레이어 백엔드로 등장, 2026년 말 6.8에서 기본 스크립팅 런타임이 되고 Mono는 은퇴 예정. IL2CPP는 AOT 필수 플랫폼용으로 잔존.
  • compacting GC는 객체가 실제로 이동하므로, pinning/unsafe 포인터 코드와 도메인 리로드(→ ALC 부분 리로드)에 의존한 static 상태 가정은 CoreCLR 전환 시 재검토가 필요하다.

⚠ 버전·플랫폼 주의 (공식 문서·실기 재확인 권장)

  • [버전 의존] CoreCLR 타임라인(6.5 Lifecycle API → 6.6 Fast Enter Play Mode 기본 → 6.7 LTS 실험적 CoreCLR 데스크톱 플레이어 → 6.8에서 Mono 대체, .NET 10/C# 14 기반)은 Unity가 공개한 로드맵 기준이며 아직 진행 중입니다. 실제 릴리스 버전 숫자와 일정은 변동될 수 있으니 단정하지 말고 최신 공식 로드맵으로 재확인하세요. Dusk Hollow가 쓰는 Unity 6.3 LTS는 여전히 Mono/IL2CPP + Boehm 세계입니다.
  • [플랫폼 의존] IL2CPP는 CoreCLR 전환 후에도 콘솔 등 AOT가 필요한 플랫폼에서 계속 사용됩니다. 즉 '모든 플랫폼이 CoreCLR로 간다'가 아니라 'CoreCLR 호환 플랫폼에서 CoreCLR을 쓸 수 있게 된다'가 정확한 표현입니다. 초기 실험 단계는 데스크톱 플레이어부터 시작합니다.
  • [임계값 숫자] LOH의 85,000바이트 기준은 .NET GC의 기본값이며 runtimeconfig.json의 System.GC.LOHThreshold(과거 GCLOHThreshold)로 조정 가능합니다(기본값보다 큰 값만 허용). 다만 Unity가 CoreCLR을 통합하며 이 기본값/조정 가능성을 그대로 노출할지, 별도 정책을 둘지는 Unity 측 CoreCLR 백엔드가 성숙해야 확정됩니다 — 현시점 단정 불가. 또한 LOH는 원칙적으로 compact하지 않지만 메모리 제한 컨테이너 등 특정 조건에서는 compact되기도 합니다.
  • [구현 세부] .NET 6+는 64비트에서 기존 segment 모델을 region 모델로 대체해 OS 메모리 반납(decommit)이 더 세분화됐습니다. Unity가 통합할 CoreCLR 버전(.NET 10 목표)의 GC 세부 동작은 해당 .NET 버전 기준이므로, 'segment' 표현은 개념 설명용이고 실제로는 region 기반일 수 있습니다.
  • [동작 의존] CoreCLR에서 도메인 리로드 없이(=AppDomain 대신 Assembly Load Context) Play 모드 진입 시 static 상태 처리는 Lifecycle Management API(6.5+ 도입, Unity.Scripting.LifecycleManagement 네임스페이스)에 의존하며, 이 API의 최종 형태와 기본 동작은 아직 확정 진행 중입니다.

02 · GC 동작 원리

Mark → Sweep → Compact: GC가 살아있는 객체를 정리하는 3단계

추적형 GC는 도달 가능한 객체를 표시(Mark)하고, 도달 불가능한 객체를 회수(Sweep)한 뒤, 살아남은 객체를 앞으로 밀어 단편화를 없애는(Compact) 3단계로 동작합니다. Compact가 비싼 이유는 객체를 옮기면서 그 객체를 가리키던 모든 참조 주소를 갱신해야 하기 때문이고, 그래서 세대별 GC는 매 수집마다 Compact를 하지 않습니다.

그림 Mark → Sweep → Compact: 힙이 정리되는 3단계

왜 Compact가 비싼가 — 산 객체를 물리적으로 복사(memcpy)하는 것보다, 그 객체를 가리키던 모든 참조 주소를 새 위치로 갱신해야 하기 때문. 이 정밀 갱신이 가능한 precise GC(CoreCLR)에서만 Compact가 성립하고, 보수적 스캔인 Boehm에는 이 단계 자체가 없다.

세대별(generational) GC — 대부분 객체는 일찍 죽는다는 '세대 가설'에 따라 gen0을 자주·얕게 수집하고, 비싼 Compact는 gen2(full) 때만 선택적으로 수행한다. (CoreCLR 특성)

추적형(tracing) GC의 뼈대는 세 단계입니다. Mark(표시) 단계에서는 루트 집합(root set)에서 출발해 참조를 따라가며 도달 가능한 객체를 모두 표시합니다. 루트는 실행 중인 스레드의 스택에 올라간 지역 변수/매개변수, CPU 레지스터, 정적(static) 필드, GC 핸들 등 '지금 코드가 확실히 접근할 수 있는 시작점'을 말합니다. 여기서 도달하지 못한 객체는 프로그램이 더 이상 접근할 방법이 없으므로 죽은 것으로 간주됩니다. 여기서 중요한 정확성 포인트가 하나 있는데, 도달 불가능(unreachable)과 '논리적으로 필요 없음'은 다릅니다. GC는 '개발자가 이 객체를 더 안 쓸 것'을 아는 게 아니라 '참조로 도달할 수 없음'만 판단합니다. 그래서 정적 필드나 이벤트 구독에 참조가 남아 있으면 논리적으로 죽었어도 회수되지 않습니다(managed 메모리 릭의 전형).

Sweep(회수) 단계에서는 Mark에서 표시되지 않은(=도달 불가능한) 객체가 차지하던 영역을 회수해 빈 공간으로 되돌립니다. 이때 살아있는 객체들 사이사이에 죽은 객체가 있던 자리가 '구멍'으로 남게 되는데, 이 상태가 바로 힙 단편화(fragmentation)입니다. Sweep만 하는 GC는 이 구멍들을 free list로 관리해 재사용하지만, 새로 할당할 객체 크기에 딱 맞는 연속 공간을 찾기 어려워지는 문제가 생깁니다. 참고로 사용자님이 적으신 '스왑'과 혼동되기 쉬운 부분이 여기인데, sweep은 메모리를 서로 맞바꾸는 게 아니라 죽은 영역을 '쓸어담아' 가용 공간으로 표시하는 것뿐이라 이 단계 자체는 데이터 복사 비용이 크지 않습니다.

Compact(압축) 단계가 실제로 비싼 단계입니다. 살아남은 객체들을 힙의 한쪽(보통 앞쪽)으로 촘촘히 밀어 붙여 중간의 구멍들을 없앱니다. 결과적으로 힙은 '앞쪽은 살아있는 객체가 연속으로 채워지고, 뒤쪽은 하나의 큰 빈 공간'인 깔끔한 상태가 됩니다. 이렇게 하면 다음 할당이 포인터를 앞으로 밀기만 하면 되는 bump-pointer 방식으로 매우 빨라지지만, 대가가 있습니다. 객체를 물리적으로 새 주소로 복사(이동)해야 하고, 이동한 객체를 가리키던 모든 참조의 주소값을 새 위치로 갱신해야 합니다. 이 '참조 주소 갱신'이 Compact 비용의 핵심입니다. 메모리 memcpy 비용에 더해, 어떤 참조가 어디를 가리키는지 정밀하게 알고 있어야만 안전하게 주소를 고칠 수 있습니다. 바로 이 '정밀하게 안다'는 요구 때문에 Compact는 정밀(precise) GC에서만 가능하고, 스택을 보수적으로 추측하는 Boehm 같은 GC에서는 불가능합니다.

그렇다면 세대별(generational) GC는 왜 매번 Compact를 하지 않을까요? 근거는 '세대 가설(generational hypothesis)' — 대부분의 객체는 아주 짧게 살고 죽는다는 경험칙입니다. .NET CoreCLR GC는 힙을 gen0(갓 할당된 작은 객체), gen1(gen0에서 한 번 살아남은 객체, 완충 지대), gen2(오래 산 객체)로 나눕니다. 사용자 코드는 gen0(또는 큰 객체는 LOH)에만 할당할 수 있고, gen1·gen2로의 '승격(promotion)'은 GC만 수행합니다. gen0은 자주, 작게, 빠르게 수집하고, gen2 전체를 훑는 무거운 수집은 드물게만 합니다. 매 수집마다 힙 전체를 Compact하면 '거의 안 죽는 gen2 객체까지 매번 옮기는' 낭비가 생기므로, GC는 gen0 같은 작은 영역을 주로 정리하고 단편화가 실제로 문제될 때(주로 full/gen2 수집)에만 Compact를 수행합니다. 즉 Compact는 '항상'이 아니라 '필요할 때'의 최적화 선택입니다.

LOH(Large Object Heap)는 이 절충의 대표적인 예외 케이스입니다. .NET에서 대략 85,000바이트 이상의 객체는 일반 힙(SOH)이 아니라 LOH에 할당되며, 논리적으로 gen2와 함께 수집됩니다(LOH는 gen2 GC 때만 회수됩니다). LOH는 기본적으로 Compact를 하지 않고 Sweep만 합니다. 큰 객체를 옮기는 복사 비용이 워낙 커서, 죽은 큰 객체 자리를 free list로 재사용하는 편이 낫다고 판단하기 때문입니다. 그래서 LOH는 단편화에 취약하고, 필요하면 GCSettings.LargeObjectHeapCompactionMode에 CompactOnce를 지정해 다음 full blocking GC 때 한 번 압축하도록 명시적으로 요청할 수 있습니다(요청 후 값은 자동으로 Default로 리셋됩니다). 다만 '기본은 절대 자동 압축 안 함'이라고 단정하면 부정확한데, .NET Core 3.0 이상에서 컨테이너 환경으로 실행되면 LOH가 자동으로 압축되는 경우가 있습니다. 정리하면, Sweep은 '죽은 것 회수', Compact는 '산 것을 몰아붙여 구멍 제거 + 참조 주소 갱신', 그리고 세대·LOH 구분은 '이 비싼 Compact를 언제·어디서 얼마나 할지'를 조절하는 장치입니다.

마지막으로 Unity 관점의 대조를 명확히 해두겠습니다. 지금 출시용 Unity(Mono/IL2CPP)의 Boehm GC는 conservative(보수적)·non-generational·non-compacting입니다(Unity 공식 매뉴얼에서 명시). 스택을 스캔하며 '포인터처럼 생긴 값'을 전부 참조 후보로 보수적으로 취급하기 때문에, 그 값이 진짜 참조인지 확신할 수 없어 객체를 이동시킬 수 없습니다. 그래서 오늘 배운 Compact도, gen0/1/2 세대 구조도 현재 Boehm에는 없습니다. 반면 Unity가 전환 중인 CoreCLR GC는 precise(정밀)·generational·moving/compacting이라 이 모든 개념이 그대로 적용됩니다. Unity는 CoreCLR 백엔드를 현재 실험(Experimental) 단계로 데스크톱(macOS/Windows/Linux) 위주로 제공하고 있고, 공개된 로드맵상 6.7대에서 기술 프리뷰가 등장하고 6.8을 목표로 스크립팅 런타임을 CoreCLR로 대체(.NET 10 / C# 14 기반)하며 Mono를 은퇴시키는 방향으로 알려져 있습니다. 다만 IL2CPP는 콘솔·모바일 등 NativeAOT/CoreCLR가 못 미치는 플랫폼 때문에 유지될 예정입니다.

✅ 정리 & 바로잡기

먼저 용어 하나만 부드럽게 바로잡을게요. 메모에 "마크 앤 스왑"이라고 적으셨는데, 정확한 표현은 Mark-and-Sweep(마크 앤 스윕)입니다. 발음이 비슷해서 "스왑(swap)"으로 잘못 들리기 쉬운데, 여기서 두 번째 단계는 메모리를 맞바꾸는 swap이 아니라 쓸어담아 회수하는 sweep입니다. "메모리 복사 비용이 크다"고 적으신 부분은 정확합니다. 다만 그 비용이 발생하는 지점은 sweep이 아니라 세 번째 단계인 Compact(컴팩트)입니다. Compact는 살아있는 객체를 힙 앞쪽으로 물리적으로 이동(복사)시키는 단계라서, 옮긴 객체를 가리키던 모든 참조의 주소값도 함께 고쳐줘야 하기 때문에 비쌉니다. 그리고 가장 중요한 맥락 하나. 이 세션에서 배우신 Mark-Sweep-Compact와 세대별 GC는 대부분 "앞으로 올 CoreCLR GC" 이야기입니다. 지금 여러분이 빌드로 출시하는 Unity(Mono/IL2CPP 백엔드)가 쓰는 Boehm GC는 세대 구분이 없고(non-generational), 객체를 옮기지 않으며(non-compacting), 스택을 보수적으로 스캔하는(conservative) GC입니다. 즉 "Compact 단계 자체가 없는" GC예요. 그래서 오늘 배운 개념은 "미래에 오는 것"과 "지금 쓰는 것"을 구분해서 이해하시는 게 핵심입니다.

📌 핵심 정리

  • Mark = 루트에서 도달 가능한 객체 표시, Sweep = 도달 불가능 객체 회수, Compact = 살아있는 객체를 앞으로 밀어 단편화 제거.
  • 메모의 '스왑'은 정확히는 Sweep(스윕)이며, 복사 비용이 큰 단계는 Sweep이 아니라 Compact다.
  • Compact가 비싼 진짜 이유는 memcpy보다 '이동한 객체를 가리키던 모든 참조 주소를 정밀하게 갱신'해야 하기 때문이다.
  • 세대 가설(대부분 객체는 일찍 죽음)에 따라 gen0을 자주 얕게 수집하고, 무거운 Compact는 full/gen2 수집 때만 선택적으로 수행한다.
  • LOH(약 85,000바이트 이상)는 복사 비용 때문에 기본적으로 Sweep만 하고, 압축은 명시적 요청 시(또는 .NET Core 3.0+ 컨테이너 환경에서 자동으로) 수행된다.
  • 오늘 배운 Compact·세대별 개념은 전부 정밀·이동형 CoreCLR GC 이야기이고, 현재 출시용 Unity의 Boehm GC는 보수적·비세대·비압축이라 Compact 자체가 없다.

⚠ 버전·플랫폼 주의 (공식 문서·실기 재확인 권장)

  • [버전 의존] LOH 임계값 '약 85,000바이트'는 .NET 런타임의 현재 기본 구현값이며 runtimeconfig.json의 System.GC.LOHThreshold로 조정할 수 있는 설정값입니다(설정 시 기본값 85000보다 커야 함). 코드에서 상수처럼 하드코딩하지 마세요.
  • [동작/환경 의존] 'LOH는 기본적으로 자동 압축 안 함'은 데스크톱 기준으로는 맞지만 절대 규칙은 아닙니다. .NET Core 3.0 이상 컨테이너 환경에서는 LOH가 자동으로 압축되는 경우가 있으므로, 실행 환경에 따라 동작이 달라질 수 있습니다.
  • [버전/플랫폼 의존] Unity의 CoreCLR 백엔드는 현재 Experimental이며 데스크톱(macOS/Windows/Linux) 위주입니다. '기술 프리뷰 시점(예: 6.7대)'이나 'Mono 은퇴/정식화 시점(예: 6.8, .NET 10 / C# 14)' 같은 구체적 버전·연도 숫자는 Unity 공식 로드맵 발표에 따라 바뀔 수 있어 단정하기 어렵습니다(프로덕션 준비는 2027 이후라는 관측도 있음).
  • [플랫폼 의존] IL2CPP는 CoreCLR/NativeAOT가 지원하지 못하는 콘솔·일부 모바일 플랫폼 때문에 계속 유지될 전망이며, 따라서 CoreCLR GC 특성이 모든 타깃 플랫폼에 동일하게 적용된다고 가정하면 안 됩니다.
  • [동작 뉘앙스] '항상 Compact를 안 한다'가 아니라 '매 수집마다는 안 한다'가 정확합니다. GC는 단편화 정도, 수집 세대(gen2/full 여부), 힙 상태 등을 종합해 Compact 여부를 런타임에 결정하므로 결정론적으로 예측하기 어렵습니다.
  • [개념/명칭 주의] LOH를 비공식적으로 'gen3'라 부르는 관례가 있지만, 공식 문서상 LOH는 별도 세대가 아니라 gen2 GC 시점에 함께 수집되는 별도 힙입니다. 또한 gen0/gen1이 함께 올라가는 ephemeral segment, OS로 메모리를 되돌리는 decommit, background GC, DATAS(.NET 8+, .NET 10에서 기본 동작 변화) 등은 CoreCLR GC 세부 구현이며 .NET 버전에 따라 진화하므로 특정 동작을 고정된 사실로 인용할 때 주의하세요.

03 · LOH

LOH(Large Object Heap): 큰 객체를 위한 별도 힙

85,000바이트 이상의 객체는 CoreCLR/.NET GC에서 일반 힙(SOH)이 아니라 LOH라는 별도 영역에 할당됩니다. LOH는 객체 이동/복사 비용이 커서 기본적으로 compact하지 않고 sweep(free-list 재활용)만 하며, gen2로 취급되어 수집 빈도가 낮습니다. 다만 이 개념은 현재 출시된 Unity의 Boehm GC에는 없고, 앞으로 오는 CoreCLR 백엔드의 GC 특성이라는 점이 중요합니다.

그림 85,000바이트로 갈리는 SOH vs LOH — LOH는 compact를 안 해 구멍이 남는다

단편화 함정 — 총 여유 메모리는 충분해도 연속 공간이 없어 새 세그먼트를 확보 → working set 부풀음. 그래서 큰 버퍼는 매 프레임 재할당하지 말고 ArrayPool<T>·풀로 재사용한다.

강제 압축—LargeObjectHeapCompactionMode = CompactOnce

LOH(Large Object Heap)는 .NET CoreCLR GC가 관리하는 힙 중 큰 객체 전용 영역입니다. 어떤 객체가 85,000바이트 이상이면 GC는 이를 일반 객체가 가는 SOH(Small Object Heap) 대신 LOH 세그먼트에 자동으로 배치합니다. 이 85,000바이트라는 숫자는 임의로 정한 게 아니라 Microsoft가 성능 튜닝을 거쳐 정한 경험적 임계값입니다. 여기서 말하는 '크기'는 객체 하나의 크기 기준이며, 대표적으로 큰 배열(예: 큰 byte[], float[], 큰 텍스처/오디오 버퍼, 큰 문자열)이 이 경계를 넘어 LOH로 갑니다. 반대로 작은 객체 수천 개는 각각이 작으면 SOH에 남습니다.

LOH가 별도로 존재하는 이유가 바로 메모가 짚으신 '복사 비용'입니다. CoreCLR GC는 일반 힙에서는 compaction(살아남은 객체를 힙 앞쪽으로 밀어붙여 빈틈을 없애고 연속된 여유 공간을 확보하는 것)을 수행합니다. compaction은 객체를 물리적으로 다른 주소로 옮기고(memcpy), 그 객체를 참조하던 모든 포인터를 새 주소로 갱신하는 작업입니다. 객체가 크면 이 복사 자체가 비싸집니다. 그래서 GC는 LOH를 기본적으로 compact하지 않습니다. 대신 죽은 큰 객체가 남긴 자리를 free-list로 기록해 두었다가, 다음에 비슷한 크기의 큰 객체를 할당할 때 그 자리를 재사용합니다. 이것이 'sweep 후 재활용' 전략이며, 메모에 쓰신 '별도로 관리'가 정확히 이 부분입니다.

이 non-compacting 정책의 부작용이 LOH 단편화(fragmentation)입니다. 크기가 다른 큰 객체들이 할당·해제를 반복하면, free-list에 있는 빈 구멍보다 새로 요청한 객체가 조금 더 커서 그 구멍에 못 들어가는 상황이 생깁니다. 그러면 총 여유 메모리는 충분한데도 연속된 공간이 없어 새 세그먼트를 확보하게 되고, 결과적으로 프로세스 메모리 사용량(working set)이 실제 살아있는 데이터보다 부풀어 오릅니다. 게임처럼 장시간 실행되며 큰 버퍼를 자주 재할당하는 워크로드에서 특히 신경 써야 하는 지점입니다.

단편화가 심각해졌을 때를 위한 탈출구가 GCSettings.LargeObjectHeapCompactionMode입니다. 이 값을 GCLargeObjectHeapCompactionMode.CompactOnce로 설정하면, 다음 번 full blocking GC(gen2 수집) 때 딱 한 번 LOH를 compact합니다. 기본값은 Default이고, 이때는 LOH를 compact하지 않고 sweep만 합니다. 이름 그대로 CompactOnce는 '한 번만'이라 compaction이 수행된 뒤 자동으로 Default로 되돌아갑니다. 실제로는 이 프로퍼티만 설정한다고 즉시 일어나지 않고, 보통 GC.Collect()를 함께 호출해 full blocking GC를 유도합니다. 다만 이 compaction은 stop-the-world로 프레임을 크게 끊을 수 있으므로, 게임에서는 로딩 화면이나 씬 전환처럼 히칭이 눈에 안 띄는 순간에만 신중하게 써야 합니다.

수집 빈도 관점에서 LOH 객체는 gen2로 취급됩니다. CoreCLR GC는 gen0 < gen1 < gen2 순으로 수집 빈도가 낮은데, 큰 객체는 세대 승격(promotion) 과정을 거치지 않고 처음부터 gen2에 할당됩니다. LOH는 오직 gen2 GC(= full GC) 때만 수집됩니다. gen2 GC는 가장 비싸고 가장 드물게 일어나므로, LOH 객체는 자주 회수되지 않습니다. 이게 의미하는 바는 명확합니다. 큰 임시 버퍼를 프레임마다 새로 할당하면(예: 매 프레임 new byte[100000]), 그 죽은 버퍼들이 다음 gen2 GC까지 LOH에 계속 쌓여 메모리 압력과 단편화를 동시에 키운다는 것입니다. 그래서 실무 권장은 '큰 버퍼는 재할당하지 말고 pool로 재사용'하거나 ArrayPool<T>를 쓰는 것입니다.

마지막으로 Unity 맥락에서의 정정이 가장 중요합니다. 지금 출시된 Unity(Mono/IL2CPP 스크립팅 백엔드)는 Boehm GC를 사용하며, Boehm은 conservative(스택을 보수적으로 스캔)하고 non-generational(비세대별)이며 non-moving(객체를 절대 이동시키지 않음)입니다. Boehm은 애초에 객체를 옮기지 않으므로 'compact 하냐 마냐'라는 구분도, 세대별 개념도, gen2로 취급되는 LOH라는 구분도 없습니다. 즉 세션에서 배우신 LOH·compaction·세대별 GC는 Unity가 전환을 진행 중인 .NET CoreCLR GC의 특성입니다. Unity가 공개한 로드맵상 CoreCLR는 데스크톱 플레이어에서 experimental 단계로 먼저 들어오고 이후 릴리스에서 Mono를 대체하는 흐름이며, 프로덕션 기본 백엔드는 아직 Boehm 기반이므로, 이 개념들은 '앞으로 오는 CoreCLR' 그림으로 학습하시는 것이 정확합니다.

✍ 세션에서 받아적은 메모

“너무 큰 애들은 LOH에 별도로 할당... 컴팩트시 메모리 복사비용이 커서 별도로 관리”

✅ 정리 & 바로잡기

메모에 적으신 방향은 정확합니다. "큰 객체를 LOH에 별도 할당하고, compaction 시 메모리 복사 비용이 커서 별도로 관리한다"는 서술은 CoreCLR/.NET GC의 실제 동작과 일치합니다(Microsoft 공식 문서 확인). 다만 두 가지를 바로잡고 강조드리고 싶습니다. 첫째, 정확한 임계값은 "약 85KB"가 아니라 정확히 85,000바이트(≈83KB, 85,000 / 1024)입니다. 그리고 이 값은 "이상(>=)"이면 LOH로 갑니다. 즉 84,999바이트 객체는 일반 힙(SOH), 85,000바이트 객체는 LOH입니다. Microsoft 공식 문서도 이 숫자가 "성능 튜닝을 통해 결정된 값"이라고 명시합니다. 둘째, "재활용 맞어?"라는 부분에 대한 답입니다. LOH는 compact(객체를 앞으로 밀어붙여 빈틈을 메우는 것)를 기본적으로 하지 않는 대신, 죽은 객체 자리를 free-list(빈 공간 목록)로 관리해 다음 큰 객체 할당 때 그 자리를 재사용합니다. 그래서 "재활용"은 맞습니다. 단, 이건 compaction(자리 이동을 통한 정리)이 아니라 sweep 방식의 재활용입니다. 그래서 크기가 제각각인 객체가 들고 나면 빈 구멍이 남는 단편화(fragmentation)가 생길 수 있습니다. 가장 중요한 오해 바로잡기: 이 LOH 개념 전체가 "지금 쓰는 Unity(Mono/IL2CPP)"의 것이 아니라 "앞으로 오는 CoreCLR GC"의 것입니다. 현재 Unity가 쓰는 Boehm GC는 non-compacting(애초에 객체를 절대 이동시키지 않음)이고 비세대별(conservative)이라, 애초에 "LOH를 compact 하냐 마냐"라는 구분 자체가 존재하지 않습니다. 세션에서 배우신 LOH/compaction/세대별 이야기는 대부분 CoreCLR 전환 이후의 그림으로 이해하시는 게 정확합니다.

📌 핵심 정리

  • 임계값은 정확히 85,000바이트이며 '이상(>=)'이면 LOH로 감 (약 83KB, 성능 튜닝으로 정해진 값) — Microsoft 공식 문서 확인
  • LOH는 기본적으로 compact하지 않고 sweep + free-list 재활용만 함 → 큰 객체 이동 복사(memcpy + 포인터 갱신) 비용이 커서
  • sweep 재활용 특성상 크기가 제각각인 객체가 오가면 단편화(fragmentation)가 발생할 수 있음
  • GCSettings.LargeObjectHeapCompactionMode = CompactOnce로 다음 full blocking GC 때 한 번 강제 compact 가능 (기본값 Default는 compact 안 함) — .NET Framework 4.5.1+ / .NET Core 확인
  • LOH 객체는 gen2로 취급되어 gen2(full) GC 때만 수집 → 수집 빈도가 낮음, 큰 버퍼 프레임마다 재할당 금물
  • 이 LOH/compaction/세대별 개념은 전부 CoreCLR GC의 것 — 현재 Unity의 Boehm GC(비세대별·non-moving·conservative)에는 LOH 개념 자체가 없음

⚠ 버전·플랫폼 주의 (공식 문서·실기 재확인 권장)

  • Unity의 CoreCLR 전환은 진행 중인 로드맵입니다. 현재(Unity 6.3 LTS 포함) 프로덕션 기본은 Mono/IL2CPP + Boehm GC이며, CoreCLR가 experimental 상태로 도입된 뒤 어느 버전에서 기본 백엔드가 되는지의 구체적 시점·버전 숫자는 단정할 수 없습니다 (버전 의존 · 확인 필요).
  • 85,000바이트 임계값은 .NET 기본값입니다. 런타임 구성(GCLOHThreshold / 환경변수 DOTNET_GCLOHThreshold 등)으로 조정할 수 있으나, 사용 가능 여부와 정확한 설정 키는 .NET 버전·플랫폼에 따라 다릅니다 (버전 의존). 특별한 이유 없이 바꾸는 것은 권장되지 않습니다.
  • (수정됨) 원문의 'double[]는 요소 1000개 이상이면 85,000바이트 미만이어도 LOH로 간다'는 서술은 부정확하므로 삭제/정정합니다. double 1000개 = 약 8,000바이트로 85,000 임계값에 한참 못 미쳐 SOH에 할당됩니다. 과거 일부 CLR 구현에서 double 배열을 정렬(alignment) 이유로 다르게 취급한 사례가 언급되긴 하나, '요소 수 1000 기준으로 LOH行'이라는 규칙은 공식 문서로 확인되지 않습니다. 이런 저수준 세부는 런타임 구현·버전에 강하게 의존하므로 실전에서 의존하지 마십시오 (버전 의존 · 확인 필요).
  • LOH의 gen2 취급, sweep/free-list 동작, CompactOnce 의미는 .NET CoreCLR/.NET(Framework 4.5.1+) 기준으로 서술했습니다. 또한 컨테이너에서 메모리 하드 리밋(GCHeapHardLimit 등)이 걸리거나 .NET Core 3.0+ 컨테이너 환경에서는 LOH가 자동 compact되는 케이스가 있습니다. 미래 CoreCLR-on-Unity 환경에서 이 API/동작이 그대로 노출·권장되는지는 Unity의 GC 통합 방식에 따라 달라질 수 있습니다 (플랫폼 의존).
  • LOH compaction은 full blocking(stop-the-world) GC라 프레임 히칭을 유발합니다. 게임에서 CompactOnce + GC.Collect() 조합은 반드시 로딩/씬 전환 등 은폐 가능한 구간에서만 사용해야 하며, 효과와 비용은 실제 워크로드·타깃 하드웨어(예: Steam Deck)에서 프로파일로 검증해야 합니다 (플랫폼 의존).

04 · Decommit

Decommit: GC가 비운 메모리를 OS에 돌려주는 방식 (플랫폼 의존)

GC가 회수한 메모리를 실제로 OS에 반환하는 단계가 decommit입니다. Windows는 VirtualFree(MEM_DECOMMIT)로 페이지를 커밋 해제하고, Linux/macOS는 munmap 또는 madvise 계열 힌트를 쓰는데, 특히 macOS에서 쓰이는 MADV_FREE는 지연 회수라 RSS 지표에 늦게 반영됩니다. 강사 말대로 “이런 게 있구나” 수준으로 가볍게 알아두면 충분한 주제입니다.

그림 Reserve → Commit → Decommit: 메모리 확보와 반납의 생애주기

포인트 — decommit은 commit의 역방향. GC는 '곧 다시 쓸' 영역은 반납하지 않고 붙들어 두는 트레이드오프로 동작한다(예: GCRetainVM).

같은 decommit이라도 플랫폼마다 방식과 지표(RSS) 반영 시점이 다르다 — 그래서 플랫폼 간 메모리 모니터링 수치를 1:1로 비교하면 안 된다.
플랫폼반환 메커니즘RSS(실사용) 반영
WindowsVirtualFree(MEM_DECOMMIT)즉시 감소 지표에 잘 잡힘
Linuxmunmap · madvise(MADV_DONTNEED)즉시 — 빠르게 떨어짐
macOS · BSDmadvise(MADV_FREE) — 지연 회수늦게 반영 "안 줄어 보임" = leak 아님

먼저 용어를 정리하겠습니다. 메모리 확보는 보통 두 단계입니다. reserve(예약)는 가상 주소 공간만 잡아두는 것이고, commit(커밋)은 그 주소에 실제 물리 메모리(또는 페이지 파일 백업)를 연결해 쓸 수 있게 만드는 것입니다. decommit은 이 반대 방향으로, 커밋했던 페이지를 다시 풀어 물리 메모리를 OS에 돌려주는 동작입니다. GC가 객체를 mark-sweep-compact로 정리하고 나면 힙 안에 빈 공간이 생기는데, 이 빈 공간의 페이지를 OS에 반환하는 최종 단계가 바로 decommit이라고 보시면 됩니다.

Windows에서는 이게 명확합니다. .NET GC는 더 이상 필요 없는 힙 영역에 대해 VirtualFree를 MEM_DECOMMIT 플래그로 호출합니다. 그러면 해당 페이지의 물리 저장소가 해제되고 상태가 'reserved(예약만 된)' 상태로 돌아갑니다. 주소 공간은 유지하되 물리 메모리만 반납하는 것이라, 나중에 다시 쓸 때는 재-commit만 하면 되어 빠릅니다. 이 방식은 작업 관리자에서 보이는 실사용 메모리가 비교적 즉각적으로 줄어드는 특징이 있습니다.

Unix 계열(Linux/macOS)은 결이 다릅니다. GC는 mmap/munmap으로 가상 메모리를 잡고 풀며, 페이지를 '이제 안 쓴다'고 알릴 때 madvise(MADV_DONTNEED) 또는 MADV_FREE 같은 조언(advisory) 호출을 씁니다. 여기서 두 플래그의 방향을 정확히 구분하는 게 중요합니다. MADV_DONTNEED는 즉시 물리 페이지를 회수하도록 유도해 RSS가 곧바로 줄어드는 편입니다. 반대로 MADV_FREE는 '나중에 메모리가 부족해지면 그때 회수해도 된다'는 지연 회수 힌트라, 커널이 압박을 받기 전까지는 RSS가 그대로 유지될 수 있습니다. 즉 어떤 플래그를 쓰느냐에 따라 지표 반영 시점이 정반대로 갈립니다.

특히 macOS(및 BSD 계열)에서 '메모리가 안 줄어드네?'라고 보이는 현상은, 이 플랫폼들에서 지연 회수 성격의 MADV_FREE가 쓰이는 경향 때문입니다. 실제로는 OS가 필요시 회수할 수 있는 상태로 표시만 해둔 것이지 새는 것(leak)이 아닙니다. 반대로 Linux에서 MADV_DONTNEED 경로를 타면 RSS가 훨씬 빨리 떨어집니다. 이 플래그·플랫폼 조합 차이 때문에 플랫폼별 메모리 모니터링 결과를 1:1로 비교하면 안 된다는 점만 기억하시면 됩니다.

한 가지 중요한 배경. decommit 정책은 GC가 '곧 다시 쓸 것 같은 메모리는 굳이 반환하지 않고 남겨둔다'는 트레이드오프 위에서 동작합니다. 매번 반환했다가 다시 커밋하면 그 자체가 비용이기 때문에, GC는 재사용 가능성이 높은 영역은 커밋 상태로 붙들어 두는 편입니다. GCRetainVM 설정은 삭제 대상 세그먼트를 OS에 즉시 반환할지, 재사용을 위해 대기(standby) 목록에 남겨둘지를 조절하는 노브입니다(주로 서버 GC 시나리오에서 의미가 큽니다). 게임 클라이언트(워크스테이션 GC)에서는 보통 기본값으로 충분하고 직접 만질 일은 드뭅니다.

마지막으로 이 개념이 왜 'CoreCLR 이야기'인지입니다. 현재 출시된 Unity의 Mono/IL2CPP는 Boehm GC를 쓰는데, 이건 비세대별·non-compacting·보수적(conservative) GC라서 힙을 compact해서 페이지 단위로 깔끔하게 비우고 OS에 돌려주는 그림 자체가 약합니다. reserve/commit/decommit을 세대별·compacting 힙 위에서 정교하게 관리하는 이야기는 Unity가 전환 중인 .NET CoreCLR GC의 특성입니다. Unity 공식 로드맵상 CoreCLR은 6.7 즈음 실험적 데스크톱 프리뷰(별도 스크립팅 백엔드 옵션)로 등장하고, 6.8에서 Mono를 대체(.NET 10 / C# 14 기반)하는 방향으로 알려져 있습니다. 그래서 이 항목은 '지금 내 게임에서 이렇게 동작한다'가 아니라 '앞으로 CoreCLR 백엔드에서 이렇게 동작할 개념'으로 받아들이는 게 맞습니다.

✍ 세션에서 받아적은 메모

“윈도우에서는 디커밋으로 할당된 메모리를 반환함. 하지만 다른 플랫폼에서는 안됨. 그래서 그냥 들었다 수준으로만 알고있자.”

✅ 정리 & 바로잡기

메모에 적으신 "다른 플랫폼에서는 안됨"은 절반은 맞고 절반은 오해입니다. Linux/macOS에서도 GC는 메모리를 OS에 돌려줍니다. 다만 방식이 달라서 겉으로 티가 덜 날 뿐입니다. Windows는 VirtualFree(MEM_DECOMMIT)로 페이지를 확실히 "커밋 해제(decommit)"해서 물리 메모리 사용량(작업 집합/RSS)이 즉시 눈에 띄게 줄어듭니다. 반면 Unix 계열은 munmap으로 완전히 반납하거나, madvise(MADV_DONTNEED / MADV_FREE) 같은 "이 페이지 이제 안 쓴다"는 힌트를 커널에 주는 방식입니다. 여기서 한 가지 정밀하게 짚을 부분이 있습니다. 두 플래그의 성격이 반대라는 점입니다. MADV_DONTNEED는 오히려 RSS를 즉시 줄이는 편이고, MADV_FREE가 "메모리가 부족해지면 그때 가져가라"는 지연 회수라 RSS에 바로 반영되지 않습니다. macOS(및 BSD 계열)에서 "반환이 안 되는 것처럼" 보이는 현상은 정확히는 이 MADV_FREE의 지연 특성 때문입니다(런타임이 macOS에서 MADV_FREE를 쓰는 경향). 즉 "안 된다"기보다 "반환은 되지만 시점과 지표 반영이 플랫폼/플래그마다 다르다"가 정확한 표현입니다. 그리고 이 개념 자체가 정밀·compacting GC를 가진 CoreCLR/.NET 계열 이야기라는 점도 함께 기억해 두시면 좋습니다. 강사가 "가볍게 알아두라"고 한 판단은 타당합니다. 게임 로직 짤 때 직접 건드릴 일이 거의 없고, 런타임 버전마다 세부 동작이 계속 개선돼 왔기 때문입니다.

📌 핵심 정리

  • decommit = 커밋했던 페이지의 물리 메모리를 OS에 돌려주는 최종 단계, reserve/commit의 역방향입니다.
  • Windows: VirtualFree(MEM_DECOMMIT)로 페이지를 커밋 해제 → 물리 메모리가 비교적 즉시 반환되고 지표에도 잘 잡힙니다.
  • Linux/macOS: mmap/munmap + madvise 힌트 방식. 단, MADV_DONTNEED는 RSS를 즉시 줄이고 MADV_FREE는 지연 회수라 방향이 반대입니다.
  • macOS에서 메모리가 안 줄어 보이는 건 leak이 아니라, 지연 회수 성격의 MADV_FREE가 RSS에 늦게 반영되기 때문일 수 있습니다.
  • GC는 '곧 다시 쓸' 메모리는 반환하지 않고 붙들어 두는 트레이드오프로 동작합니다 (예: GCRetainVM, 주로 서버 GC 맥락).
  • 이 정밀 decommit 개념은 CoreCLR GC 특성이며, 현재 Unity의 Boehm(비세대별·non-compacting·보수적) GC와는 다릅니다.
  • 강사 조언대로 게임 개발자가 직접 다룰 일은 드물어 '이런 게 있다' 수준으로 알아두면 충분합니다.

예시 (csharp) · GC가 OS에 반환하지 못하도록 붙든 메모리 vs 실제 힙 크기를 구분해 보는 진단 스니펫. 수치 해석은 플랫폼별로 다르므로 절대값이 아니라 추이로 볼 것.

// .NET(CoreCLR) 기준 진단 예시 — 개념 확인용
var info = GC.GetGCMemoryInfo();

// 힙에 커밋된 총 바이트(아직 OS에 반환 안 된 것 포함)
long committed = info.TotalCommittedBytes;
// 실제 살아있는 객체가 쓰는 힙 크기
long heapSize  = info.HeapSizeBytes;

// committed - heapSize 가 크면: GC가 재사용 대비로 붙들고 있거나
// 아직 decommit(OS 반환) 전인 영역이 많다는 신호.
// 단, 플랫폼(특히 macOS)에서는 이 값이 OS 실사용 지표(RSS)와
// 곧바로 일치하지 않을 수 있음 — 지연 회수(MADV_FREE) 때문.
UnityEngine.Debug.Log($"committed={committed} heap={heapSize} slack={committed - heapSize}");

// 주의: GetGCMemoryInfo는 CoreCLR/.NET 계열 API로,
// 현재 Unity의 Mono/IL2CPP(Boehm GC) 환경에서는 노출 API가 다를 수 있음.

⚠ 버전·플랫폼 주의 (공식 문서·실기 재확인 권장)

  • 버전/플랫폼 의존: madvise 플래그(MADV_DONTNEED vs MADV_FREE) 선택과 실제 회수 시점, RSS 반영 여부는 OS 커널 버전과 .NET 런타임 버전에 따라 계속 바뀌어 왔습니다. 두 플래그의 방향(DONTNEED=즉시, FREE=지연)은 일반적 설명이며, 특정 런타임/커널 조합의 정확한 동작은 참고만 하시기 바랍니다.
  • 버전 의존: '언제/얼마나' decommit할지의 임계값과 정책 숫자는 GC 내부 구현 세부라 런타임 버전마다 달라집니다. 구체 수치는 단정하지 않았습니다.
  • 아키텍처 의존: .NET 7부터 64비트 Windows/Linux GC가 segment에서 region 기반으로 바뀌면서 decommit 세부 동작이 달라졌습니다. GCRetainVM 같은 설정의 의미도 이 구조 변화에 영향을 받습니다. Unity가 최종 통합할 CoreCLR/GC 버전에 따라 체감이 또 달라질 수 있습니다.
  • Unity 맥락 의존: CoreCLR 스크립팅 백엔드는 조사 시점 기준 실험/프리뷰 단계이며, 공식 로드맵상 6.7 실험적 데스크톱 프리뷰 → 6.8 Mono 대체(.NET 10 / C# 14) 취지로 알려져 있으나 일정과 버전 숫자는 계속 갱신됩니다. Unity 공식 발표를 확인하세요.
  • 확신 낮음 주제: 이 항목 전체가 강사도 '가볍게 알아두라'고 한 영역입니다. 프로덕션에서 메모리 이슈를 잡을 땐 이 개념보다 실제 프로파일러(Unity Memory Profiler 등) 측정치를 우선하세요.

05 · 이벤트 릭

이벤트/델리게이트 미해제 메모리 릭 — publisher가 subscriber를 붙잡는다

C# 이벤트는 publisher가 델리게이트를 통해 subscriber를 강하게 참조합니다. publisher가 더 오래 살면 -= 로 해제하기 전까지 subscriber는 절대 GC되지 않으며, 이건 Boehm이든 CoreCLR이든 GC 종류와 무관하게 동일하게 발생합니다.

그림 릭의 방향 — publisher가 subscriber를 붙잡는다 (그 반대가 아님)

주의 — 이 릭은 GC 알고리즘(Boehm/CoreCLR) 문제가 아니라 참조 그래프 문제라 어느 GC에서도 동일하게 발생. 해결은 오직 -= 로 사슬을 끊는 것.

구독/해제는 subscriber의 활성화 패턴에 맞춰 짝을 이뤄야 한다 — 무조건 정답인 조합은 없다.
구독(+=) 시점해제(-=) 시점적합한 경우
OnEnableOnDisable비활성·재활성이 잦은 오브젝트 (대칭이 가장 깔끔)
Awake / StartOnDestroy생성 후 계속 켜져 있는 오브젝트
익명 람다 e => {}-= 불가named method를 쓰거나 람다를 필드에 저장해야 해제 가능

작동 원리부터 짚겠습니다. publisher.SomeEvent += subscriber.Handler; 라고 쓰면, 내부적으로 publisher가 들고 있는 델리게이트(멀티캐스트 델리게이트)의 호출 목록(invocation list)에 항목이 하나 추가됩니다. 인스턴스 메서드를 구독할 경우 이 델리게이트 항목은 '어떤 메서드'인지뿐 아니라 '어떤 인스턴스에서 호출할지', 즉 Target(= subscriber 인스턴스에 대한 참조)까지 함께 붙잡습니다. 결과적으로 publisher -> 델리게이트 -> subscriber 방향으로 강한 참조 사슬이 생깁니다. 방향이 중요합니다. 흔히 'subscriber가 publisher를 구독한다'는 표현 때문에 subscriber가 publisher를 붙잡는다고 착각하기 쉬운데, 실제로 수명 문제를 일으키는 건 그 반대 방향, 즉 publisher가 subscriber를 붙잡는 쪽입니다.

그래서 릭이 나는 조건은 명확합니다. publisher가 subscriber보다 오래 사는 경우입니다. 전형적으로 오래 사는 publisher는 싱글턴 매니저(GameManager, EventBus, InputManager 같은 것), static 이벤트, 씬 전환에도 파괴되지 않는 DontDestroyOnLoad 객체입니다. 반대로 subscriber는 잠깐 떴다 사라지는 UI 패널, 적 유닛, 스폰됐다 파괴되는 오브젝트인 경우가 많죠. 이때 subscriber 쪽에서 Destroy를 호출하거나 씬을 언로드해서 '이제 이 객체는 끝났다'고 생각해도, 오래 사는 publisher의 델리게이트가 여전히 subscriber를 가리키고 있으면 GC는 그 객체를 도달 가능한 것으로 보고 절대 수거하지 않습니다. 메모리가 조금씩 새다가, 씬을 반복해서 열고 닫으면 같은 종류의 죽은 객체가 계속 쌓이는 전형적인 누수 패턴이 됩니다.

Unity에서는 이 릭이 메모리 낭비로만 끝나지 않고 더 지저분한 증상을 냅니다. subscriber가 MonoBehaviour이고 그 GameObject가 Destroy()로 파괴됐다고 합시다. Unity의 파괴된 오브젝트는 관리되는(managed) 래퍼 객체와 네이티브(C++) 객체가 분리돼 있어서, 네이티브 쪽은 사라져도 델리게이트가 붙잡고 있는 managed 래퍼는 살아남습니다(이른바 'fake null' 상태 — 참조는 null처럼 보이도록 == 연산자가 오버로드돼 있지만 실제 C# null은 아닙니다). 그 상태에서 나중에 publisher가 이벤트를 발화(invoke)하면 호출 목록에 남아 있는 그 핸들러가 실제로 실행됩니다. 여기서 정확히 짚자면, 예외는 '발화하는 순간' 저절로 터지는 게 아니라, 실행된 핸들러 본문이 파괴된 그 MonoBehaviour의 멤버(transform, GetComponent 결과, 자신의 필드 등)에 접근하려는 순간 MissingReferenceException(UnityEngine 네임스페이스의 예외, C# 기본 NullReferenceException과는 별개)이 터집니다. 핸들러가 파괴된 객체를 건드리지 않고 무해하게 지나가면 예외 없이 '이미 죽은 객체의 콜백이 실행되는' 논리 버그만 남습니다. 즉 미해제는 (1) subscriber가 GC되지 않는 메모리 릭과 (2) 파괴된 대상에 대한 이벤트 발화로 인한 예외/논리 버그, 두 문제를 동시에 만듭니다.

해결책은 사용자 메모대로 -= 로 짝을 맞춰 명시적으로 해제하는 것입니다. Unity에서는 구독/해제를 MonoBehaviour의 라이프사이클 쌍에 맞춰 넣는 것이 표준입니다. 대칭이 가장 깔끔한 조합은 OnEnable에서 +=, OnDisable에서 -= 입니다. 오브젝트가 비활성/재활성될 때마다 정확히 대칭으로 붙었다 떨어지기 때문입니다. 반면 Start나 Awake에서 한 번만 구독하는 경우에는 반드시 OnDestroy에서 해제해야 합니다. 여기서 흔한 실수 두 가지를 조심하세요. 첫째, OnEnable에서 구독했는데 해제는 OnDestroy에서 하면, 비활성화됐다 다시 활성화될 때 OnEnable이 다시 불려 중복 구독이 쌓입니다(핸들러가 한 이벤트에 두 번, 세 번 호출됨). 둘째, -= 는 반드시 += 와 동일한 델리게이트여야 끊깁니다. 익명 람다(e => {...})로 구독하면 그 람다 인스턴스를 어딘가 필드에 저장해 두지 않는 한 나중에 같은 참조로 -= 를 걸 수 없어 해제가 불가능합니다. 그래서 나중에 해제할 이벤트는 람다 대신 named method를 쓰거나, 람다를 필드에 보관하세요.

규모가 커지면 수동 해제 대신 보완책을 고려할 수 있습니다. 대표적으로 (1) Weak Event 패턴 — publisher가 subscriber를 WeakReference로 붙잡아, subscriber에 대한 다른 강한 참조가 사라지면 GC가 수거할 수 있게 하는 방식이고, (2) IDisposable 구독 토큰 — 구독 시 해제 로직을 담은 disposable을 돌려받아 Dispose() 한 번으로 끊는 방식(Rx 계열의 IDisposable 구독, R3/UniRx의 AddTo(this) 패턴 등)입니다. 다만 Weak Event는 구현이 까다롭고 호출 오버헤드가 있으며, subscriber가 언제 사라질지 예측하기 어려워져 오히려 디버깅이 힘들어질 수 있습니다. MVP 단계에서는 보통 OnEnable/OnDisable 또는 OnDestroy에서 짝 맞춰 -= 하는 명시적 해제만으로 충분하고, 이게 의도가 가장 명확합니다.

다시 한번 강조하면, 이 문제는 스터디에서 배운 CoreCLR로의 전환과는 직교(orthogonal)합니다. CoreCLR의 정밀·세대별·compacting GC는 '수거 대상으로 판정된 쓰레기를 더 효율적으로 치우고 힙을 정리하는' 능력이 뛰어난 것이지, '무엇을 쓰레기로 볼지'의 판정 기준(= 루트에서 도달 가능한가)은 Boehm과 근본적으로 같습니다. 오히려 CoreCLR에서 주의할 점은 별개로 있습니다. Unity가 공지한 대로 CoreCLR 기반 런타임에서는 플레이 모드 진입/재컴파일 시 managed 도메인을 리로드하지 않고 AppDomain.CurrentDomain.DomainUnload도 더 이상 발생하지 않기 때문에, '에디터에서 플레이 종료하면 static 상태가 알아서 초기화되겠지'라고 은연중에 기대하던 코드가 상태를 그대로 물고 갈 수 있습니다. static 이벤트에 남은 구독이나 static 컬렉션에 쌓인 참조는 여전히 명시적으로 정리해 줘야 합니다(Unity가 이를 돕는 [ClearOnReload]류 정리용 어트리뷰트를 함께 제공할 예정으로 공지했으나, 정확한 이름·적용 범위는 마이그레이션 시점에 확인이 필요합니다).

✍ 세션에서 받아적은 메모

“이벤트 델리게이트 해제를 해줘야 정상적으로 GC 처리가 된다.”

✅ 정리 & 바로잡기

메모의 핵심 결론("해제해야 정상적으로 GC 된다")은 정확합니다. 다만 한 가지 오해를 미리 바로잡고 싶습니다. 이 릭은 세션에서 배운 GC 알고리즘(mark-sweep-compact, 세대별, LOH, decommit)과는 별개의 문제입니다. 즉 "Boehm이 보수적이라서 이벤트 릭이 난다"거나 "CoreCLR의 정밀·세대별 GC로 바뀌면 이벤트 릭이 자동으로 해결된다"는 얘기가 아닙니다. 이건 GC가 아무리 똑똑해도 못 고치는, 순전히 참조 그래프(reference graph)의 문제입니다. GC의 역할은 "루트(root)에서 도달 가능한 객체는 살려둔다"는 것뿐인데, publisher가 살아있고 그 델리게이트가 subscriber를 가리키는 한 subscriber는 여전히 도달 가능(reachable)합니다. GC 입장에서는 "이건 아직 쓰이는 객체"로 판단하는 게 정상 동작이지 버그가 아닙니다. 그래서 Mono/IL2CPP(Boehm)에서든, 앞으로 올 CoreCLR에서든 동일하게 릭이 나고, 해결책도 동일하게 "-= 로 명시적으로 끊어주기"입니다.

📌 핵심 정리

  • publisher가 델리게이트를 통해 subscriber를 강하게 참조한다 — 참조 방향은 publisher -> subscriber이며, 릭은 publisher가 subscriber보다 오래 살 때 발생한다.
  • 이 릭은 GC 알고리즘 문제가 아니라 참조 그래프 문제다. Boehm이든 CoreCLR이든 동일하게 발생하고, GC 세대·compaction·LOH와는 무관하다.
  • 해결은 +=와 짝을 이루는 -= 명시적 해제. Unity 표준은 OnEnable/OnDisable 대칭 또는 Start/Awake 구독 + OnDestroy 해제.
  • Unity에서는 미해제 시 메모리 릭뿐 아니라, 파괴된 MonoBehaviour 핸들러가 실행돼 그 본문이 fake-null 객체를 건드릴 때 MissingReferenceException이 터진다(발화 자체가 아니라 핸들러 내부 접근에서 발생).
  • 익명 람다로 구독하면 동일 참조가 없어 -= 로 못 끊는다 — 해제 대상 이벤트는 named method를 쓰거나 람다를 필드에 저장하라.
  • 규모가 커지면 Weak Event 패턴이나 IDisposable 구독 토큰(AddTo 등)을 보완책으로 고려할 수 있다.

⚠ 버전·플랫폼 주의 (공식 문서·실기 재확인 권장)

  • (버전/플랫폼 의존) CoreCLR 전환은 2026년 공개 로드맵상 Unity 6.7 LTS에서 실험적(experimental) 데스크톱(macOS/Windows/Linux) 플레이어로 먼저 제공되고, 6.8에서 Mono를 대체하는 것으로 공지되어 있습니다. 현재 프로젝트가 핀한 Unity 6.3 LTS는 여전히 Mono/IL2CPP(Boehm GC) 기준이므로, 이 문서의 CoreCLR 관련 서술은 '앞으로 올' 동작입니다. 6.7의 CoreCLR 플레이어는 명시적으로 '프로덕션 부적합 기술 프리뷰'로 안내되며, 정확한 버전 숫자·default 여부·범위는 공식 로드맵이 변동될 수 있어 단정하지 않습니다.
  • (버전/플랫폼 의존) CoreCLR에서 도메인 리로드가 사라지고 AppDomain.DomainUnload가 발화하지 않는다는 점은 Unity 공식 공지 기반이나, 이를 보완하는 static 정리용 어트리뷰트의 정확한 이름과 실제 마이그레이션 시점의 세부 동작은 릴리스별로 확인이 필요합니다.
  • OnEnable/OnDisable vs OnDestroy 중 어느 쌍을 쓸지는 subscriber의 활성화 패턴에 따라 다릅니다. 비활성/재활성이 잦은 오브젝트는 OnEnable/OnDisable이, 생성 후 계속 켜져 있는 오브젝트는 Start/Awake + OnDestroy가 적합합니다. 무조건 정답인 조합은 없습니다.
  • UnityEvent(인스펙터에서 연결하는 이벤트)와 순수 C# event/Action은 수명·해제 규칙이 다소 다릅니다. 위 서술은 C# event/델리게이트 기준이며, UnityEvent는 별도 검토가 필요합니다.
  • MissingReferenceException이 터지는 정확한 조건은 핸들러가 파괴된 오브젝트의 멤버에 접근하는지 여부에 따라 달라집니다(접근하지 않으면 예외 없이 논리 버그만 남을 수 있음). 세부 동작은 무엇을 건드리느냐에 의존합니다.

06 · NonAlloc

NonAlloc API — 매 호출 배열 할당을 없애 GC 스파이크를 줄이는 패턴

NonAlloc API는 호출자가 미리 만들어 둔 배열이나 List에 결과를 채워 넣게 해서, 호출할 때마다 힙에 새 배열을 할당하는 것을 피하는 오버로드 패턴입니다. 프레임마다 반복 호출되는 물리 쿼리에서 gen0 가비지를 없애 GC 히칭을 줄이는 것이 목적입니다.

그림 매 프레임 새 배열 vs 버퍼 재사용 — gen0 가비지의 차이

함정 — 반환값은 실제 채워진 개수(int)이지 배열 길이가 아니다. 버퍼는 스스로 커지지 않으므로 넘친 히트는 조용히 잘린다 → for는 반드시 반환 개수만큼만 돌리고, count == 버퍼길이면 버퍼 확대를 고려한다.

같은 최적화지만 3D와 2D의 API 상태가 다르다 (Unity 6.3 기준) — 실제 [Obsolete] 도입 버전은 Editor 컴파일 경고로 확인 권장.
구분3D · Physics2D · Physics2D

먼저 "왜 할당이 문제인가"부터 짚겠습니다. Unity에서 Physics.RaycastAll(origin, dir)이나 Physics.OverlapSphere(center, radius) 같은 API는 히트 결과를 담은 새 배열을 만들어 반환합니다. 이 배열은 관리 힙(managed heap)에 할당되고, 다음 프레임에 다시 호출하면 이전 배열은 쓰레기가 됩니다. 한 번이면 무시할 만하지만, 조준선 검사·근접 감지·바닥 체크처럼 매 프레임(혹은 여러 오브젝트에서 매 프레임) 호출되는 코드라면 gen0에 가비지가 빠르게 쌓입니다. gen0가 가득 차면 GC가 수집을 시작하고, Unity의 현재 기본 GC(Boehm, non-generational·부분적으로 incremental)에서는 이 수집이 프레임 중간에 튀어나와 눈에 띄는 히칭(스파이크)을 만들 수 있습니다.

NonAlloc 계열 API는 이 문제를 "버퍼 재사용"으로 해결합니다. 호출자가 RaycastHit[] 배열을 한 번 만들어 필드로 들고 있다가, Physics.RaycastNonAlloc(origin, dir, _hitBuffer)처럼 그 배열을 넘기면 Unity가 그 안에 결과를 덮어써 줍니다. 반환값은 배열이 아니라 "이번에 실제로 채워진 히트 개수(int)"입니다. 배열 자체는 매 호출 재사용되므로 프레임당 힙 할당이 0에 수렴하고, 결과적으로 GC 압력과 프레임 히칭이 줄어듭니다. 같은 아이디어가 물리 밖에도 넓게 적용됩니다. GetComponents<T>()는 새 배열을 반환하지만 GetComponents(List<T> results)는 넘겨준 List에 채워 넣고, Mesh.GetVertices(List<Vector3>)나 Physics2D의 GetContacts(List<ContactPoint2D>)도 같은 재사용 오버로드입니다. 즉 "NonAlloc"이라는 단어가 붙어 있지 않아도, "결과를 담을 컬렉션을 인자로 받는 오버로드"는 전부 같은 계열의 최적화입니다.

여기서 반드시 알아야 할 함정이 반환값과 버퍼 크기의 관계입니다. NonAlloc 계열은 버퍼 배열의 길이를 자동으로 늘려 주지 않습니다. 버퍼가 8칸인데 실제 히트가 12개라면, 앞 8개만 채워지고 나머지 4개는 조용히 버려집니다. Unity 공식 문서와 JetBrains(Rider/ReSharper) 인스펙션 문서 모두 "메서드가 배열을 리사이즈하지 않으며, 더 많은 결과가 있었는지 알려 주지도 않는다"고 명시합니다. 그래서 for 루프를 배열 길이(_hitBuffer.Length)로 돌리면 안 되고, 반드시 반환된 개수만큼만 순회해야 합니다. 버퍼 크기는 "현실적으로 나올 수 있는 최대 히트 수" 또는 "그 이상은 어차피 필요 없다"는 상한을 기준으로 넉넉히 잡으세요. 반대로 정말로 모든 히트를 하나도 빠짐없이 받아야 하는 상황(예: 관통 판정에서 모든 대상)에서는 할당 버전이 오히려 안전할 수 있습니다.

최신 Unity(6.x, 6.3 LTS 포함) 동향에서 가장 헷갈리기 쉬운 부분은 3D와 2D가 서로 다르다는 점입니다. 3D 쪽 Physics.RaycastNonAlloc / OverlapSphereNonAlloc 등은 Unity 6.3(6000.3) ScriptReference 기준으로도 여전히 정식 지원(supported)이며 obsolete로 표시되어 있지 않습니다. 반면 2D 쪽 Physics2D의 *NonAlloc 접미사 메서드들은 방향성이 다릅니다. Unity는 Physics2D에서 별도의 NonAlloc 메서드를 없애고, 일반 메서드(Raycast, OverlapCircle 등)에 배열 또는 List<T>와 ContactFilter2D를 받는 non-allocating 오버로드로 통합하는 흐름을 잡았습니다. 실제 UnityCsReference에는 Physics2D.deprecated.cs가 존재하고, 커뮤니티 답변에서도 이들 NonAlloc이 "향후 deprecate 예정"으로 언급됩니다. 다만 실제 [Obsolete] 경고가 언제/어느 버전에서 붙는지는 버전·플랫폼에 따라 다르므로 단정하지 마시고, 실제 사용하는 에디터에서 컴파일 경고로 직접 확인하시길 권합니다.

그래서 지금 코드를 새로 짠다면 방향은 이렇습니다. 2D에서는 NonAlloc 메서드 대신 List<RaycastHit2D>를 받는 Physics2D.Raycast(origin, dir, contactFilter, results) 같은 오버로드를 쓰세요. List 오버로드는 결과가 List 용량 안에 들어가면 재할당이 일어나지 않고, 필요하면 List가 스스로 늘어난 뒤 다음부터 다시 재사용되므로 "넉넉히 잡되 잘리지는 않는" 절충이 가능합니다(고정 배열의 조용한 잘림 문제를 완화). 3D에서는 RaycastNonAlloc을 그대로 써도 되지만, 최신 감성으로는 결과 버퍼를 받는 오버로드 계열을 일관되게 쓰는 편이 낫습니다.

마지막으로, 한 프레임에 수백~수천 개의 레이를 쏘는 대량 쿼리라면 개별 RaycastNonAlloc 호출을 반복하는 것보다 배치 API가 권장됩니다. RaycastCommand(및 Overlap*Command 계열)를 NativeArray로 준비해 RaycastCommand.ScheduleBatch로 C# Jobs에 태우면, 메인 스레드 부담을 크게 줄이고 여러 워커 스레드에서 병렬로 처리할 수 있습니다(Burst와도 조합 가능). 대신 잡 스케줄은 비동기라 결과를 그 프레임에 즉시 못 받고 통상 1프레임 지연이 생기며, jobHandle.Complete() 이후에만 결과 NativeArray에 접근해야 한다는 제약이 있습니다. 정리하면, 소수의 매 프레임 쿼리는 버퍼 재사용(NonAlloc/List 오버로드), 대량 병렬 쿼리는 RaycastCommand + Jobs가 각각의 자리라고 보시면 됩니다.

✍ 세션에서 받아적은 메모

“non alloc api? 이건 뭐임 gc 를 줄일수 있대.”

✅ 정리 & 바로잡기

결론부터 말씀드리면, NonAlloc API는 특별한 마법 기능이 아니라 "결과를 담을 버퍼를 호출자가 미리 준비해서 넘기는" 오버로드 스타일입니다. 대표적으로 Physics.RaycastNonAlloc, Physics.OverlapSphereNonAlloc, 그리고 GetComponents(List<T>), Mesh.GetVertices(List<T>) 같은 것들이 여기에 해당합니다. 예를 들어 Physics.RaycastAll(...)은 호출할 때마다 결과 RaycastHit[] 배열을 새로 힙에 할당해서 돌려주는데, 이 배열이 매 프레임 버려지면 gen0 가비지가 쌓이고 결국 GC가 돌면서 프레임이 튑니다. RaycastNonAlloc은 이미 만들어 둔 배열에 결과를 덮어써 주므로 매 호출 할당이 사라지죠. 그래서 "GC를 줄일 수 있다"는 말은 맞습니다. 다만 한 가지 오해를 바로잡을 부분이 있습니다. "NonAlloc"이라는 이름 자체가 최신 API로 넘어가는 흐름은 아니라는 점입니다. 특히 2D(Physics2D)에서는 NonAlloc 접미사가 붙은 메서드들이 레거시로 취급되고, 대신 일반 Raycast/OverlapCircle 등에 배열 또는 List<T>를 받는 오버로드를 쓰라는 방향으로 정리되고 있습니다. 즉 "할당을 피한다"는 아이디어는 그대로 살아 있지만, 그걸 표현하는 API 이름과 형태가 바뀌고 있는 것입니다. 또 하나, GC를 줄인다고 해서 GC 종류(Boehm이든 향후 CoreCLR 기반이든)에 의존하는 기법이 아닙니다. 이건 관리 힙 할당 자체를 없애는 기법이라, 어떤 GC를 쓰든 일관되게 이득입니다.

📌 핵심 정리

  • NonAlloc API = 호출자가 미리 만든 배열/List에 결과를 채워 넣어, 호출마다 새 배열을 힙에 할당하는 것을 피하는 오버로드 패턴.
  • RaycastAll·OverlapSphere·GetComponents<T>()는 매 호출 새 배열 반환 → 반복 호출 시 gen0 가비지 폭증 → GC 스파이크(프레임 히칭). 재사용 버퍼는 프레임당 할당을 0에 수렴시킴.
  • GC 종류와 무관한 최적화: 관리 힙 할당 자체를 줄이므로 Boehm(현행)에서도, 향후 어떤 GC에서도 일관되게 이득.
  • 반환값은 배열이 아니라 "실제로 채워진 개수(int)". for 루프는 배열 길이가 아니라 이 반환 개수만큼만 돌려야 함.
  • 버퍼는 리사이즈되지 않는다 → 버퍼보다 많은 히트는 조용히 잘림. 넉넉히 잡거나 반환 개수를 확인하고, 버퍼는 필드로 보관해 재사용.
  • 3D(Physics.RaycastNonAlloc 등)는 Unity 6.3에서도 정식 지원. 2D(Physics2D.*NonAlloc)는 일반 메서드의 배열/List 오버로드로 통합되는 레거시 흐름.
  • 2D 신규 코드는 List<RaycastHit2D> + ContactFilter2D 오버로드 권장(잘림 완화 + 재사용 이점).
  • 한 프레임 대량 쿼리는 개별 NonAlloc 반복 대신 RaycastCommand.ScheduleBatch(C# Jobs, Burst 병렬) 권장 — 단, 통상 1프레임 지연.

예시 (csharp) · 재사용 버퍼로 매 프레임 할당 제거 — 반환 개수만큼만 순회 (3D 예시 + 2D List 오버로드 대안)

using System.Collections.Generic;
using UnityEngine;

public class GroundProbe : MonoBehaviour
{
    [SerializeField] private LayerMask _mask;

    // 1) 버퍼는 필드로 한 번만 만들어 재사용한다 (매 프레임 new 금지).
    private readonly RaycastHit[] _hits = new RaycastHit[8];

    private void FixedUpdate()
    {
        Vector3 origin = transform.position;
        Vector3 dir = Vector3.down;

        // 2) 반환값 = 실제로 _hits에 채워진 개수. 배열은 리사이즈되지 않는다.
        int count = Physics.RaycastNonAlloc(origin, dir, _hits, 5f, _mask);

        // 3) 반드시 count 만큼만 순회 (_hits.Length가 아니라).
        //    count == _hits.Length 이면 잘렸을 수 있으니 버퍼를 키우는 걸 고려.
        for (int i = 0; i < count; i++)
        {
            RaycastHit hit = _hits[i];
            Debug.DrawLine(origin, hit.point, Color.green);
        }
    }
}

// ---- 2D 신규 코드 권장형: NonAlloc 접미사 대신 List<T> 오버로드 ----
// List는 넘친 만큼만 한 번 커지고 이후 재사용되어 '조용한 잘림'을 완화한다.
public class Ground2DProbe : MonoBehaviour
{
    private readonly List<RaycastHit2D> _results = new(8);
    private ContactFilter2D _filter; // Start에서 SetLayerMask 등으로 구성

    private void FixedUpdate()
    {
        int count = Physics2D.Raycast(
            transform.position, Vector2.down, _filter, _results, 5f);

        for (int i = 0; i < count; i++)
        {
            // _results[i] 사용
        }
    }
}

⚠ 버전·플랫폼 주의 (공식 문서·실기 재확인 권장)

  • 3D vs 2D 상태가 다름: Physics.RaycastNonAlloc 등 3D는 Unity 6.3(6000.3) 기준 정식 지원(obsolete 아님). Physics2D의 *NonAlloc은 레거시 취급/향후 deprecate 방향 — 정확한 [Obsolete] 도입 버전은 버전·플랫폼 의존이므로 실제 Editor 컴파일 경고로 확인 권장.
  • 반환값 시맨틱을 혼동하기 쉬움: 반환은 '채워진 개수'이지 '전체 히트 수'가 아님. 버퍼가 꽉 찼다면(count == 버퍼 길이) 잘린 히트가 있었는지 알 수 없음.
  • 버퍼는 스스로 커지지 않음: 배열 오버로드는 크기 고정. 정말 모든 히트가 필요하면 넉넉히 잡거나(상한 산정) 예외적으로 할당 버전(RaycastAll)을 쓰는 편이 안전.
  • List<T> 오버로드는 용량을 넘으면 그때 한 번 재할당이 일어남(그 프레임엔 GC 발생 가능). 초기 용량을 예상 최대치로 잡아 두면 이후엔 무할당.
  • 재사용 버퍼는 스레드 안전하지 않음: 하나의 버퍼를 여러 곳에서 동시에 넘기면 결과가 덮어써짐. 오브젝트별/시스템별로 분리하거나 호출 시점을 분리할 것.
  • RaycastCommand 배치가 항상 더 빠른 건 아님: 쿼리 수가 적으면 잡 스케줄·커맨드 준비 오버헤드가 이득을 상쇄할 수 있고 통상 1프레임 지연이 생김. '대량·병렬 가능·지연 허용' 상황에서만 유효.
  • Boehm GC의 incremental 모드나 향후 CoreCLR/generational GC 여부와 무관하게 유효한 기법이지만, '얼마나' 이득인지의 체감은 프로젝트 할당 패턴에 따라 다름 — 프로파일러(GC.Alloc 마커)로 실측 권장.

07 · 직렬화

JSON 대신 바이너리 직렬화(MemoryPack)로 GC 부하 줄이기

JSON은 문자열 파싱·리플렉션·박싱 때문에 직렬화/역직렬화마다 임시 할당이 폭증합니다. MemoryPack 같은 "zero encoding" 바이너리 직렬화기는 C# 메모리를 거의 그대로 복사하는 방식이라 할당과 CPU 비용을 크게 줄여주고, 리플렉션 대신 소스 제너레이터를 쓰기 때문에 Unity IL2CPP(AOT) 환경에서도 안전하게 동작합니다.

그림 임시 할당이 어디서 생기나 — JSON 파이프라인 vs MemoryPack

핵심 — "바이너리라서" GC가 주는 게 아니라 임시 할당을 안 만드는 설계라서다. MemoryPack은 리플렉션·boxing·텍스트 변환을 원천 제거(소스젠 + 메모리 복사)해 그 결과를 얻는다.

내부 순수 C#·최고 성능이면 MemoryPack, 외부 시스템·타 언어와 포맷 호환이 필요하면 MessagePack. 둘 다 JSON보다 할당·속도에서 크게 유리하다.

왜 JSON이 GC에 불리한가부터 정리하겠습니다. JSON은 텍스트 포맷이라 숫자 하나를 저장할 때도 int/float을 문자열로 변환해야 하고, 역직렬화 시에는 반대로 문자열을 파싱해 숫자로 되돌립니다. 이 과정에서 중간 string, 토큰 배열, StringBuilder 버퍼 같은 임시 객체가 대량 생성됩니다. 여기에 리플렉션 기반 직렬화기(Unity 내장 JsonUtility, Newtonsoft.Json 등)는 런타임에 타입 정보를 뒤져 필드를 읽고 쓰는데, 값 타입을 object로 다룰 때 boxing이 일어나 힙 할당이 추가됩니다. 세이브 파일 한 번, 네트워크 패킷 한 번마다 수백~수천 개의 짧은 수명 객체가 쏟아지고, 이것들이 곧바로 GC 대상이 되어 프레임 스파이크로 나타납니다.

MemoryPack(Cysharp)의 핵심은 README가 직접 표현하듯 "가능한 한 C# 메모리를 그대로 복사하는 zero encoding 설계"입니다. VarInt 인코딩이나 태깅 같은 변환을 하지 않고, 특히 unmanaged 구조체(예: Vector3, 또는 blittable 필드만 가진 struct 배열)는 메모리 블록을 통째로 복사하듯 직렬화합니다. 그래서 struct 배열 같은 이상적인 데이터에서는 다른 직렬화기 대비 극단적으로 빠릅니다(README 벤치마크 기준 표준 객체 약 x10, struct 배열은 x50~x200). 다만 이 방식의 트레이드오프도 정확히 알아야 합니다 — MemoryPack 포맷은 C# 전용 바이너리라 언어 중립적이지 않고, 필드가 많을 때는 태그를 안 붙이는 대신 순서/스키마에 민감합니다.

Unity/IL2CPP 관점에서 가장 중요한 특성은 "리플렉션·동적 코드 생성(IL.Emit)을 쓰지 않고 Roslyn Incremental Source Generator로 직렬화 코드를 컴파일 타임에 미리 만든다"는 점입니다. IL2CPP는 AOT(Ahead-Of-Time) 컴파일이라 런타임 IL.Emit이 막혀 있는데, MemoryPack은 애초에 코드를 미리 생성하므로 이 제약에 자연스럽게 부합합니다. 사용법은 대상 타입을 partial로 선언하고 [MemoryPackable] 특성을 붙이면 됩니다(class, struct, record, record struct, interface 모두 가능하되 partial 필수). 소스 제너레이터가 나머지 직렬화 멤버를 채워줍니다. Unity에서 쓰려면 Roslyn 소스 제너레이터를 지원하는 에디터 버전이 필요하며, README는 최소 Unity 2022.3.12f1을 명시합니다 — 프로젝트가 쓰는 Unity 6.3 LTS는 이 요건을 충분히 만족합니다.

GC를 더 줄이는 실전 팁은 "할당을 재사용으로 바꾸는" API를 쓰는 것입니다. MemoryPack은 기존 인스턴스에 덮어쓰기(overwrite)하는 Deserialize 오버로드(ref 파라미터로 기존 객체를 넘김)를 지원해 새 객체 생성을 피할 수 있고, List<>·Stack<>·Queue<> 같은 컬렉션은 Clear() 후 재사용합니다. 이는 사용자가 다른 스터디 주제에서 헷갈려 한 "재활용 맞어?"와 연결되는 부분입니다 — 여기서의 재사용은 GC가 뒤에서 메모리를 재활용하는 것과 별개로, 애플리케이션 코드가 명시적으로 같은 버퍼/인스턴스를 다시 채워 애초에 garbage를 안 만드는 기법입니다. 세이브 슬롯 구조체나 매 프레임 갱신되는 상태 스냅샷처럼 반복 역직렬화하는 대상에 특히 효과적입니다.

대안인 MessagePack-CSharp(같은 저자 neuecc)도 훌륭한 선택지입니다. MessagePack은 msgpack이라는 언어 중립 표준 포맷을 쓰므로 서버·다른 언어 클라이언트와 상호운용이 필요할 때 유리하고, IBufferWriter<byte>와 버퍼 풀(pool)을 활용해 GC 압박을 낮춥니다. MessagePack의 Unity/IL2CPP 대응은 예전 mpc(코드 생성 CLI)와 최신 소스 제너레이터(MessagePackAnalyzer) 두 방식이 있으며, 어느 쪽이든 IL2CPP에서는 런타임 IL.Emit(Dynamic 리졸버)을 못 쓰므로 사전 코드 생성이 필수입니다. 정리하면 "순수 C# 내부용(세이브/스냅샷)이고 최고 성능·최소 할당이 목표"면 MemoryPack, "외부 시스템과 포맷 호환이 필요"하면 MessagePack이 무난한 판단 기준입니다. 두 라이브러리 모두 JSON 대비 할당·속도에서 크게 유리하다는 결론은 동일합니다.

실무 적용 시 주의점입니다. MemoryPack README는 .NET 7 이상 환경과 Unity 사이에 [StructLayout(LayoutKind.Auto)]가 걸리는 일부 타입(DateTimeOffset, ValueTuple 등)의 바이너리 호환성 차이(양쪽에서 서로 역직렬화가 안 됨), Unity 버전에서 CustomFormatter 미지원, 그리고 (README 작성 시점 기준) .NET 7 Native AOT 크래시 같은 제약을 명시합니다. 이런 항목들은 라이브러리·런타임 버전에 따라 상태가 바뀌므로, 실제 도입 전 사용 중인 MemoryPack/Unity 버전의 최신 README와 CHANGELOG로 반드시 재확인하는 것을 권합니다. 또한 바이너리 포맷은 사람이 못 읽으므로 세이브 파일 디버깅·마이그레이션 전략(스키마 버저닝)을 별도로 마련해 두는 편이 좋습니다.

✅ 정리 & 바로잡기

메모에 적으신 방향은 정확합니다. "JSON 대신 MemoryPack 같은 바이너리 직렬화를 쓰면 GC가 줄어든다"는 사실이며, 그 이유를 한 단계 더 정확히 짚어드리면 이렇습니다. GC가 주는 근본 원인은 "바이너리라서"가 아니라 "직렬화 과정에서 임시 힙 할당(garbage)이 얼마나 생기느냐"입니다. JSON은 (1) 사람이 읽는 텍스트라 int·float을 문자열로 바꾸는 과정에서 중간 string이 생기고, (2) 파싱 시 substring/토큰 문자열이 대량으로 만들어지며, (3) 리플렉션 기반 직렬화기(JsonUtility, Newtonsoft 등)는 필드 접근·boxing(값 타입을 object로 감쌈)에서 추가 할당이 발생합니다. 이 임시 객체들이 곧 GC 대상이 되어 프레임 스파이크를 유발합니다. 반면 MemoryPack은 텍스트 변환·태깅 없이 C# 메모리 레이아웃을 거의 그대로 바이트로 복사("zero encoding")하고, 리플렉션이 아니라 컴파일 타임 소스 제너레이터로 직렬화 코드를 미리 생성하므로 boxing과 리플렉션 할당이 원천 제거됩니다. 즉 "바이너리 = GC 감소"가 아니라 "임시 할당을 안 만드는 설계 = GC 감소"이고, MemoryPack이 마침 그 설계를 택한 대표적인 바이너리 직렬화기라고 이해하시면 정확합니다. 참고로 이 최적화는 오늘의 Boehm GC(비세대별·non-compacting)든 앞으로 올 CoreCLR의 세대별 GC든 양쪽 모두에 유효합니다 — 할당 자체를 줄이면 어떤 GC에서든 수집 빈도와 스파이크가 줄기 때문입니다.

📌 핵심 정리

  • JSON의 GC 부하 원인은 텍스트 변환·파싱 시 임시 string, 그리고 리플렉션 직렬화기의 boxing으로 인한 다수의 짧은 수명 할당입니다.
  • MemoryPack은 C# 메모리를 거의 그대로 복사하는 zero encoding 설계로 이런 임시 할당을 크게 줄여 GC 빈도와 프레임 스파이크를 낮춥니다.
  • MemoryPack은 리플렉션/IL.Emit 대신 Roslyn 소스 제너레이터로 직렬화 코드를 컴파일 타임에 생성해 Unity IL2CPP(AOT)와 호환됩니다.
  • 사용법: 타입을 partial로 선언하고 [MemoryPackable] 특성을 붙이면 소스 제너레이터가 직렬화 코드를 만들어 줍니다.
  • 기존 인스턴스에 덮어쓰는 Deserialize 오버로드(ref 파라미터)와 컬렉션 Clear() 재사용으로 새 인스턴스 할당을 추가로 피할 수 있습니다.
  • MessagePack-CSharp는 언어 중립 표준 포맷이라 외부 시스템 상호운용이 필요할 때 대안으로 적합합니다(내부 순수 C#·최고 성능은 MemoryPack).
  • 이 할당 절감 최적화는 현재의 Boehm GC와 앞으로 올 CoreCLR 세대별 GC 양쪽 모두에서 유효합니다 — 할당 자체를 줄이기 때문입니다.

08 · 문자열

string → StringBuilder → ZString: 문자열 조립의 할당 진화

C#에서 문자열을 반복 조립할 때 발생하는 GC 할당을 줄이는 세 단계 진화입니다. 불변(immutable) string의 + 연결은 매번 새 객체를 낳고, StringBuilder는 중간 할당을 버퍼로 줄이며, ZString은 풀링/스택 버퍼로 최종 문자열 외의 할당을 사실상 0으로 만듭니다.

그림 문자열 조립 방식별 GC 할당량 (적을수록 좋음)

뉘앙스 — ZString이 없애는 건 "중간 쓰레기"다. 최종 string을 만들면 그것만큼은 할당되며, 완전 0은 내부 char 버퍼를 TMP의 SetCharArray 같은 stringless API에 직접 넘길 때만 성립(TMP 버전별 실측 필요).

왜 string 연결이 문제인가부터 짚겠습니다. C#의 string은 불변(immutable) 참조 타입입니다. a = a + b 처럼 이어 붙이면 기존 a를 수정하는 게 아니라 a와 b의 문자를 모두 담은 완전히 새로운 string을 힙에 할당하고, 이전 a는 아무도 안 쓰는 순간 GC 대상 쓰레기가 됩니다. 한 번이면 무해하지만 루프 안에서 문제가 폭증합니다. 예를 들어 for로 N번 이어 붙이면 중간 string이 O(N)개 생기고 총 복사 비용은 O(N^2)에 가깝습니다. Update()에서 매 프레임 점수 문자열을 "Score: " + score 로 만드는 흔한 패턴이 바로 이 함정으로, 초당 60개 이상의 단명 string을 Gen0에 쏟아부어 GC 스파이크(프레임 끊김)의 단골 원인이 됩니다.

StringBuilder는 이 중간 쓰레기를 줄이는 표준 도구입니다. 내부에 char[] 버퍼(용량, capacity)를 하나 들고 Append할 때 그 버퍼에 직접 써 넣습니다. 버퍼가 꽉 차면 더 큰 배열로 재할당(대략 2배 성장)하지만, 매 연결마다 새 string을 만드는 일은 사라집니다. 그래서 반복 조립에서는 string + 보다 훨씬 적은 할당과 낮은 복잡도(대략 O(N))를 냅니다. 다만 StringBuilder에도 두 종류의 할당이 남습니다. 하나는 StringBuilder 인스턴스와 그 내부 버퍼(그리고 용량 초과 시 재할당된 버퍼들)이고, 다른 하나는 마지막에 ToString()을 부를 때 만들어지는 최종 string입니다. 참고로 .NET의 StringBuilder는 내부적으로 단일 char[] 하나가 아니라 청크(chunk) 연결 리스트로 성장하는 구조라 재할당 시 기존 내용을 통째로 복사하지 않는 최적화가 있지만, "빌더 객체 + 최종 string 할당"이 남는다는 결론은 동일합니다. 초기 용량을 넉넉히 잡아(new StringBuilder(256)) 재할당을 줄일 수는 있지만, 이 두 종류 할당 자체를 없애지는 못합니다. 즉 StringBuilder는 매 프레임 새로 생성하면 오히려 GC를 늘리므로, 재사용하려면 필드로 캐시하고 Clear()로 비워 쓰는 게 정석입니다.

ZString(Cysharp 오픈소스)은 여기서 한 단계 더 나아가 "빌더 객체 + 중간 버퍼" 할당까지 없앱니다. 핵심 아이디어는 두 가지입니다. 첫째, 빌더를 struct(값 타입)로 만들어 힙이 아닌 스택에 두고, 실제 문자 버퍼는 스레드 정적(thread-static) 버퍼나 ArrayPool<char>에서 빌려 씁니다. 다 쓰면 Dispose로 버퍼를 풀에 반납하므로 반복 사용 시 새 배열 할당이 발생하지 않습니다. 둘째, 타입별 전용 포매터를 내장해 int, float, DateTime 등을 값의 .ToString()을 거치지 않고 버퍼에 직접 씁니다. 일반적으로 sb.Append(intValue)는 내부에서 int를 문자열로 변환하며(구현/런타임에 따라 임시 string이 생길 수 있음) 오버헤드를 남길 수 있는데, ZString은 이 임시 문자열 없이 곧장 char 버퍼에 숫자를 렌더링합니다. 공식 README 표현으로는 "all zstring methods only allocate final string(모든 zstring 메서드는 최종 문자열만 할당한다)"이며, 여기에 더해 내부 버퍼에 접근할 수 있어 TextMeshPro의 SetCharArray처럼 string을 요구하지 않는 API에 버퍼를 그대로 넘기면 그 최종 string마저 없애 완전한 zero-allocation을 노릴 수 있습니다.

ZString의 API는 크게 두 갈래입니다. (1) 한 방에 조립: ZString.Concat, ZString.Join, ZString.Format 은 string.Concat/Join/Format을 그대로 대체하며 중간 할당 없이 최종 string 하나만 만듭니다. (2) 점진 조립: ZString.CreateStringBuilder()로 Utf16ValueStringBuilder(struct)를 얻어 StringBuilder처럼 Append/AppendFormat을 쓰고, using으로 Dispose하여 버퍼를 반납합니다. UTF-8이 필요하면 Utf8ValueStringBuilder(CreateUtf8StringBuilder)를 써서 네트워크/파일 출력에 바이트로 바로 쓸 수도 있습니다. 주의할 함정 하나: CreateStringBuilder(notNested: true)는 ArrayPool 대신 더 빠른 스레드 정적(thread-static) 버퍼를 쓰는데, 이 버퍼는 스레드당 하나뿐이라 같은 스레드에서 빌더를 중첩(nested)해 쓰거나 그 안에서 ZString.Format/Concat/Join을 호출하면 같은 버퍼가 충돌합니다. 중첩 가능성이 있으면 기본 오버로드(notNested 인자 없음 = ArrayPool 사용)를 쓰고, Dispose를 반드시(using으로) 즉시 호출해야 버퍼가 정상 반납됩니다.

Unity/CoreCLR 맥락에서 이 최적화의 위상을 정리하겠습니다. 현재 출시된 Unity(Mono/IL2CPP + Boehm GC)는 비세대별(non-generational)·non-compacting·보수적(conservative) GC라 단명 할당이 쌓이면 STW(stop-the-world) 스파이크가 프레임에 그대로 드러나기 쉽습니다(Incremental GC로 완화는 가능하나 성격 자체는 동일). 그래서 문자열 조립 할당을 줄이는 것이 지금 당장 체감 프레임 안정성에 직결됩니다. Unity가 전환 중인 .NET CoreCLR GC는 정밀(precise)·세대별(generational)·이동/압축(moving/compacting) GC라 단명 객체(Gen0)를 훨씬 싸게 회수하므로 string 쓰레기의 상대적 부담은 줄어듭니다. 다만 "싸다"가 "공짜"는 아니고, 매 프레임 대량 할당은 여전히 Gen0 GC 빈도를 높여 지터(jitter)를 만듭니다. 또한 아주 큰 문자열(단일 객체가 85,000바이트 이상)은 LOH(Large Object Heap)로 가서 Gen2와 함께(즉 풀 GC 때만) 드물게, 그리고 비싸게 수집되므로 큰 로그/직렬화 문자열을 반복 생성하는 경로는 특히 조심해야 합니다. 결론적으로 StringBuilder 재사용과 ZString은 Boehm이든 CoreCLR이든 유효한 최적화이며, 특히 매 프레임 갱신되는 HUD 텍스트(TextMeshPro)에서는 ZString + stringless 경로가 가장 확실한 zero-allocation 해법입니다.

화살표는 "무엇이 무엇을 대체한다"가 아니라 할당(GC 쓰레기)을 줄여가는 최적화 단계입니다. 셋 다 여전히 유효한 도구입니다.

“문자열 -> sting builder -> zstring ??”

✅ 정리 & 바로잡기

메모의 "문자열 -> string builder -> zstring ??"는 "무엇을 무엇으로 바꾼다"가 아니라 문자열 조립 방식의 할당 특성이 점점 좋아지는 단계적 진화를 뜻합니다. 셋은 서로 대체 관계가 아니라 "얼마나 GC 쓰레기(garbage)를 덜 만드느냐"의 스펙트럼이라고 보시면 정확합니다. (1) string 직접 + 연결: 가장 편하지만 연결 한 번마다 새 string이 힙에 할당됩니다. string은 불변(immutable)이라 기존 객체를 못 고치고 항상 새로 만들 수밖에 없기 때문입니다. (2) StringBuilder: 내부에 크는 char[] 버퍼 하나를 두고 거기에 이어 붙여, 중간 중간 새 string을 만드는 낭비를 없앱니다. 다만 StringBuilder 객체 자신과 마지막 ToString()이 만드는 최종 string은 여전히 힙에 할당됩니다. (3) ZString(Cysharp): 버퍼를 스레드 정적(thread-static)이나 ArrayPool에서 빌려 쓰고 다 쓰면 반납하므로, StringBuilder가 남기던 "빌더 객체 + 중간 버퍼" 할당까지 없앱니다. 그래서 "사실상 zero-allocation"이라고 부릅니다. 다만 오해하기 쉬운 지점 하나: ZString도 최종적으로 string 객체를 만들어 돌려주면 그 최종 string만큼은 할당됩니다(공식 README 표현: "all zstring methods only allocate final string"). 진짜 완전 0 할당은 string을 만들지 않고 내부 char 버퍼를 그대로 TextMeshPro의 SetCharArray 같은 문자열 없는(stringless) API에 넘길 때만 성립합니다. 정리하면, ZString이 없애는 것은 "중간 쓰레기"이고, 최종 string 자체를 안 만들려면 stringless 경로까지 써야 한다는 것이 핵심 뉘앙스입니다.

📌 핵심 정리

  • string은 불변이라 + 연결마다 새 객체가 힙에 할당되고, 루프에서는 O(N)개의 중간 string과 O(N^2) 복사 비용으로 폭증합니다.
  • StringBuilder는 내부 char[] 버퍼로 중간 string 할당을 없애지만, 빌더 객체 자신과 마지막 ToString()의 최종 string 할당은 남습니다.
  • StringBuilder는 매 프레임 새로 만들지 말고 필드로 캐시 + Clear()로 재사용해야 GC 이득이 생깁니다.
  • ZString은 struct 빌더 + 스레드 정적/ArrayPool 버퍼 + 타입별 포매터로 '중간 쓰레기'를 없애 사실상 zero-allocation입니다.
  • 단, ZString도 최종 string을 만들면 그것만큼은 할당됩니다. 완전 0 할당은 내부 버퍼를 TextMeshPro SetCharArray 같은 stringless API에 넘길 때만 성립합니다.
  • ZString.CreateStringBuilder(notNested: true)의 스레드 정적 버퍼는 중첩 사용/중첩 ZString.Format 호출 시 충돌하므로, 중첩 가능성이 있으면 기본 오버로드(ArrayPool)를 쓰고 반드시 using으로 즉시 Dispose해야 합니다.
  • Boehm(현행 Mono/IL2CPP)에서는 비세대별·보수적 GC라 문자열 할당 절감이 프레임 스파이크 방지에 직접 기여하고, CoreCLR 세대별·압축 GC에서도 Gen0 부담을 줄이므로 여전히 유효합니다.
  • 단일 문자열이 85,000바이트를 넘으면 LOH로 가서 Gen2(풀 GC)와 함께 드물고 비싸게 수집되므로 대용량 문자열 반복 생성은 특히 위험합니다.

예시 (csharp) · 세 단계 비교: string + (매번 새 string) → 캐시된 StringBuilder → ZString + TMP stringless 경로

// (1) 나쁨: 매 프레임 단명 string 2개 이상 할당 ("Score: " 리터럴 제외, 연결 결과 string)
tmpText.text = "Score: " + score;

// (2) 개선: StringBuilder를 필드로 캐시 + Clear() 재사용
// 남는 할당: 최종 ToString() 결과 string 1개
private readonly StringBuilder _sb = new StringBuilder(64);
void UpdateScore(int score) {
    _sb.Clear();
    _sb.Append("Score: ").Append(score);
    tmpText.text = _sb.ToString(); // 최종 string 1개 할당
}

// (3) 최적: ZString 점진 조립 + TMP SetCharArray(stringless)
// 중첩 가능성이 없으면 notNested:true (thread-static 버퍼, 더 빠름)
void UpdateScoreZeroAlloc(int score) {
    using var sb = ZString.CreateStringBuilder(notNested: true);
    sb.Append("Score: ");
    sb.Append(score);                 // int 전용 포매터: 임시 string 없이 버퍼에 직접 렌더
    var span = sb.AsArraySegment();   // 내부 char 버퍼 그대로 접근
    tmpText.SetCharArray(span.Array, span.Offset, span.Count); // string 미생성
    // 주의: TMP SetCharArray 내부 할당은 TMP 버전에 따라 다름 → Profiler로 실측
}

  • [버전/플랫폼 의존] LOH 임계값 85,000바이트와 LOH가 Gen2와 함께 수집된다는 점은 .NET/CoreCLR GC 기준입니다(공식 문서 확인됨). 이 값은 성능 튜닝으로 정해진 기본값이며 .NET Core 3.0부터 런타임 설정으로 조정 가능합니다. 현행 Unity의 Boehm GC(Mono/IL2CPP)에는 LOH나 세대(generation) 개념 자체가 없으므로, LOH 관련 서술은 Unity가 전환 중인 CoreCLR 백엔드에 해당합니다.
  • [라이브러리 의존] ZString은 Unity 내장이 아닌 Cysharp 오픈소스 서드파티 패키지(MIT)이며, 별도 설치(UPM/NuGet)가 필요합니다. CreateStringBuilder의 인자 이름(notNested)/오버로드, 스레드 정적 vs ArrayPool 전환 세부 동작(예: 기본 오버로드가 ArrayPool에서 빌리는 버퍼 크기)은 ZString 버전에 따라 다를 수 있으니 사용 중인 버전의 README/소스로 확인하세요.
  • [확인 필요/플랫폼 의존] TextMeshPro의 SetCharArray로 최종 string까지 없애는 경로는 이론상 stringless지만, ZString 저장소의 실제 이슈(#77)에서 TMP_Text.SetCharArray가 내부적으로 상당량을 할당한다는 지적이 있습니다. 즉 'ZString 쪽은 0 할당이어도 TMP 렌더링 쪽에서 할당이 발생'할 수 있으므로 '완전한 zero-allocation'은 사용 중인 TMP 버전에서 Profiler로 반드시 실측해야 합니다. 또한 Unity 6.3에서 TMP가 UITK 등으로 통합/변경되는 흐름이 있어 stringless API 제공 여부 자체가 버전에 따라 달라질 수 있습니다.
  • [측정 권장] '사실상 zero-allocation'은 벤치마크 상 최종 string 외 추가 할당이 없다는 의미입니다. 실제 코드에서는 캡처된 람다, 박싱(object 파라미터), 인터폴레이션 문법($"...") 등 부수 할당이 섞일 수 있으므로 Unity Profiler의 GC Alloc 컬럼으로 실측 확인을 권장합니다.
  • [불확실] Unity의 CoreCLR 스크립팅 백엔드 전환 시점과 기본화 여부는 진행 중인 로드맵 사안으로, 특정 Unity 6.x 패치에서의 정식 지원 여부는 단정하기 어렵습니다. CoreCLR GC가 정밀·세대별·압축 GC라는 성격 자체는 Unity 공식 블로그(Porting Unity to CoreCLR)로 확인됩니다.

09 · 네이티브 메모리

GC가 안 건드리는 영역: Destroy와 Dispose를 구분해서 직접 정리하기

Unity에는 C# GC가 관리하지 않는 두 종류의 네이티브 메모리가 있습니다. UnityEngine.Object(GameObject·Texture·Mesh 등)는 관리 껍데기 + C++ 실체의 이중 구조라 Object.Destroy()로 실체를 지워야 하고, NativeArray/NativeList 같은 NativeContainer는 언매니지드 힙에 있어 Dispose()(또는 using)로 직접 해제해야 합니다. 둘 다 "GC가 안 봐준다"는 점은 같지만 해제 API가 완전히 다릅니다.

그림 네이티브 정리 — Object면 Destroy, NativeContainer면 Dispose

주의 — Object는 Destroy 후 껍데기가 남아 == null이 true인 fake null 상태(is null·?.·ReferenceEquals는 우회하니 쓰지 말 것). NativeContainer는 미해제 시 "Native Collection has not been disposed" 경고가 뜬다.

"네이티브 = 무조건 Destroy"가 아니다 — 대상이 Object인지 NativeContainer인지 먼저 가르는 습관이 핵심.

UnityEngine.Object의 이중 구조부터 짚겠습니다. GameObject를 하나 만들면 C# 쪽에는 얇은 관리 껍데기(managed shell) 객체가, C++ 엔진 쪽에는 실제 데이터를 들고 있는 네이티브 객체가 만들어집니다. 우리가 코드에서 다루는 것은 항상 C# 껍데기이고, 엔진은 그와 짝지어진 네이티브 실체를 관리합니다. 그래서 gameObject = null처럼 관리 참조만 끊으면, 그 껍데기는 이제 참조가 없어 언젠가 GC 대상이 되지만 네이티브 실체는 씬/엔진이 여전히 붙들고 있어 사라지지 않습니다. 네이티브 실체를 실제로 없애려면 Object.Destroy(obj)를 호출해야 하고, 이것이 사용자 메모의 핵심 직관과 일치합니다.

여기서 Unity 특유의 'fake null'을 이해해야 오해가 안 생깁니다. Object.Destroy가 실행되면 네이티브 실체는 파괴되지만 C# 껍데기 객체는 그 프레임 이후에도 잠시 관리 힙에 남아 있습니다. Unity는 UnityEngine.Object의 == 연산자와 bool 변환을 오버로드해서, 껍데기는 살아 있어도 네이티브 실체가 파괴됐으면 obj == null이 true를 돌려주도록 만들어 뒀습니다. 즉 '진짜 C# null'은 아니지만 null처럼 보이는 상태입니다. 이 비교는 순수 C# null 체크와 달리 네이티브로 넘어가 실체 생존 여부를 확인하므로 상대적으로 비용이 크다는 점도 알아두면 좋습니다. (주의: is null, ?., ??, ReferenceEquals()는 이 오버로드를 우회해 C# 껍데기만 보므로, 파괴된 UnityEngine.Object에 대해 '아직 null이 아님'으로 잘못 판정할 수 있습니다. UnityEngine.Object의 생존 확인에는 == null / != null을 쓰세요.)

두 번째 갈래는 NativeContainer입니다. NativeArray<T>, NativeList<T>, NativeHashMap<T> 등은 Unity의 Collections 패키지가 제공하는 struct로, C# Job System/Burst와 함께 쓰라고 만든 것입니다. 이들의 실제 버퍼는 관리 힙이 아니라 언매니지드(네이티브) 힙에 할당됩니다. 생성 시 Allocator를 지정하는데, 크게 Allocator.Temp(1프레임 수명, 자동 해제), Allocator.TempJob(짧은 수명, 대략 몇 프레임 안에 해제 기대), Allocator.Persistent(수명 제한 없음)로 나뉩니다. Persistent로 잡은 메모리는 GC가 전혀 추적하지 않으므로, 개발자가 명시적으로 Dispose()를 호출하지 않으면 그대로 릭(leak)이 됩니다.

NativeContainer 해제의 정석은 두 가지입니다. 첫째, 수명이 짧고 한 메서드 안에서 끝나는 경우 using 선언/블록을 쓰면 스코프를 벗어날 때 Dispose가 자동 호출됩니다. 둘째, MonoBehaviour 필드처럼 여러 프레임에 걸쳐 살아 있어야 하는 Persistent 컨테이너는 보통 OnDestroy()나 OnDisable()에서 Dispose()를 직접 불러 정리합니다. 여기서 헷갈리기 쉬운 지점: NativeContainer에는 Object.Destroy를 쓰지 않습니다. NativeArray는 UnityEngine.Object가 아니라서 Destroy 대상이 아니며, 오직 Dispose로만 해제합니다. (덧붙여, Job 내부에서는 .Dispose()를 직접 호출할 수 없고 'The native container may not be deallocated on a job' 예외가 납니다. 이 경우 Job에 넘긴 컨테이너는 Schedule이 반환한 JobHandle을 Dispose(handle)에 넘겨 완료 후 해제하거나, [DeallocateOnJobCompletion] 같은 메커니즘을 씁니다 — 실제 Job 도입 시 별도로 학습 필요.)

실무에서 릭을 잡아주는 안전장치도 있습니다. Allocator.TempJob이나 Persistent로 잡은 컨테이너를 해제하지 않고 흘려보내면, Unity의 leak detection이 'A Native Collection has not been disposed, resulting in a memory leak.' 같은 경고를 콘솔에 띄웁니다(에디터/개발 빌드 기준, 검출 모드 설정에 따라 동작이 달라질 수 있습니다). 검출 모드는 Edit > Preferences > Jobs > Leak Detection에서, 또는 코드로 Unity.Collections.NativeLeakDetection.Mode로 조절합니다. 반대로 Object.Destroy를 잊은 GameObject는 이런 컨테이너 릭 경고 대신, 씬에 유령 오브젝트가 남거나 씬 언로드 전까지 네이티브 메모리를 계속 점유하는 형태로 나타납니다. 두 문제의 증상과 진단 경로가 다르므로, 애초에 '이 대상이 Object인가 NativeContainer인가'를 먼저 구분하는 습관이 중요합니다.

이 프로젝트(Dusk Hollow)의 현재 코드베이스는 2D 스토리북 퍼즐 게임이라 Job System/NativeContainer를 쓰는 곳이 아직 없고, 네이티브 해제는 전적으로 UnityEngine.Object 쪽입니다. 예를 들어 PlayMode 테스트의 TearDown에서 테스트가 만든 GameObject를 Object.Destroy(_bootstrapGo)로 정리하는 패턴(assets/Tests/PlayMode/Bootstrap/GameBootstrapPlayModeTests.cs)이 대표적입니다. 만약 향후 야간 조명·안개·경로탐색 등에서 Burst/Job 최적화를 도입해 NativeArray를 쓰게 되면, 그때부터는 Dispose 규칙을 별도로 적용해야 한다는 점을 미리 기억해 두면 좋습니다.

✍ 세션에서 받아적은 메모

“native memory는 C++ 영역에서 생성이 되며 GC로 관리되지 않기 때문에 Destroy를 호출해줘야한다.”

✅ 정리 & 바로잡기

직관은 정확합니다. C++ 영역에서 만들어진 네이티브 메모리는 C# GC의 추적 대상이 아니라서, C# 참조를 null로 밀어넣거나 스코프를 벗어나게 해도 네이티브 실체는 그대로 살아 있습니다. 다만 "그러니까 Destroy를 호출한다"는 부분은 반쪽만 맞습니다. 네이티브 메모리에는 두 갈래가 있고 해제 방법이 서로 다르기 때문입니다. (1) GameObject·Component·Texture·Mesh·Material 같은 UnityEngine.Object는 Object.Destroy(obj)(에디터 즉시 삭제는 DestroyImmediate)로 해제합니다. 이때 C# 껍데기 객체 자체는 여전히 관리 힙에 남아 GC 대상이지만, 그 껍데기가 가리키던 네이티브 C++ 실체가 사라져 이른바 "fake null" 상태가 됩니다. (2) 반면 NativeArray<T>·NativeList<T> 같은 NativeContainer는 UnityEngine.Object가 아니라 struct이고 실제 데이터는 언매니지드 힙(Allocator.Persistent 등)에 있습니다. 여기에 Destroy를 호출하는 것이 아니라 반드시 Dispose()(또는 using 블록)로 해제해야 합니다. 정리하면 "네이티브 = 무조건 Destroy"가 아니라, Object 계열은 Destroy, NativeContainer 계열은 Dispose라고 기억하시면 됩니다.

📌 핵심 정리

  • 네이티브 메모리는 C# GC가 추적하지 않아, 참조를 null로 밀거나 스코프를 벗어나도 실체는 살아남는다 (사용자 직관 맞음).
  • 해제 API가 대상별로 다르다: UnityEngine.Object는 Object.Destroy(), NativeContainer(NativeArray 등)는 Dispose() — '네이티브=무조건 Destroy'는 아님.
  • UnityEngine.Object는 관리 C# 껍데기 + 네이티브 C++ 실체의 이중 구조이며, Destroy 후에는 껍데기가 남아 'fake null'(== null이 true) 상태가 된다.
  • fake null 판정은 == / != 연산자 오버로드로만 동작한다. is null·?.·??·ReferenceEquals는 오버로드를 우회하므로 파괴된 오브젝트에 쓰면 안 된다.
  • NativeArray/NativeList는 struct이고 Allocator.Persistent 등 언매니지드 힙을 쓰므로, Dispose를 안 하면 그대로 릭이다.
  • 짧은 수명은 using으로 자동 Dispose, 오래 사는 Persistent 컨테이너는 OnDestroy/OnDisable에서 명시적으로 Dispose한다.
  • Unity는 미해제 NativeContainer에 'Native Collection has not been disposed' 경고를 띄워 릭을 잡아준다(에디터/개발 빌드, Preferences > Jobs > Leak Detection).
  • 현 프로젝트는 NativeContainer 미사용 — 네이티브 해제는 전부 Object.Destroy 계열(PlayMode 테스트 TearDown 등)이다.

⚠ 버전·플랫폼 주의 (공식 문서·실기 재확인 권장)

  • Allocator.Temp/TempJob/Persistent의 수명 규칙(예: TempJob '대략 4프레임 내 해제 기대', Temp '1프레임')은 Collections 패키지 버전에 따라 세부 문구·동작이 달라질 수 있음 — 버전 의존. 정확한 수치는 사용 중인 com.unity.collections 버전 문서로 확인 권장.
  • Native Collection 미해제 경고의 발생 여부·상세 스택 표시는 Jobs > Leak Detection 모드(대략 Disabled / Enabled / Enabled With Stack Trace)와 빌드 종류(에디터/개발/릴리스)에 따라 다름. 메뉴 명칭·모드 이름 문구는 Unity 버전에 따라 조금씩 다를 수 있음 — 플랫폼/설정/버전 의존.
  • 'fake null'과 == 연산자 오버로드 동작은 현행 Unity(6.x)에서 유효하나, Unity 포럼에 이 오버로드/암묵 bool 변환의 향후 변경(deprecation)을 논의한 공식 스레드가 실재함('Deprecation of == operator overload and fake null for UnityEngine.Object'). 실제 제거 시점·방식은 미확정이므로 장기적으로 버전 의존 — 현재는 그대로 동작.
  • Job 내부에서 NativeContainer를 직접 Dispose할 수 없다는 점([DeallocateOnJobCompletion] 또는 JobHandle 기반 Dispose 필요)은 이번 정리 범위 밖이며 Job System 실제 도입 시 별도 검증 필요 — 버전/API 의존.
  • NativeContainer가 struct라서 값 복사/포인터 보관 시 Dispose 소유권이 헷갈릴 수 있음(복사본을 Dispose하거나 원본 참조를 잃는 등) — 실제 코드 도입 시 소유권 규칙을 별도 설계 필요.
  • 핵심 사실은 WebSearch로 Unity 공식 매뉴얼(class-Object)·Unity Discussions·UnityCsReference(DisposeSentinel.cs) 등을 교차 확인함. Context7 공식 문서 정밀 조회는 이번 세션에서 수행하지 않음.

10 · GPU 인스턴싱

RenderMesh와 GPU Instancing — "인스턴스"는 재활용이 아니라 드로우 콜 병합입니다

여기서 말하는 "인스턴스"는 오브젝트 풀링 같은 메모리 재활용이 아니라, 같은 메시+머티리얼 조합의 여러 복사본을 인스턴스드 드로우 콜 하나로 GPU에 그려 CPU 오버헤드를 줄이는 GPU Instancing입니다. 인스턴싱 ≠ 풀링입니다.

그림 1000번의 드로우 콜 vs 인스턴스드 드로우 콜 1회

재사용되는 것 — C# 객체가 아니라 GPU에 이미 세팅된 메시/머티리얼/셰이더 상태다. 그래서 인스턴싱(렌더링 최적화)과 풀링(메모리 최적화)은 다른 층위다.

"인스턴스"라는 단어가 겹쳐 헷갈리지만, 둘은 목적도 대상도 다르다.

GPU Instancing이 이득인 이유는 '드로우 콜(draw call)'의 구조 때문입니다. 화면에 오브젝트 하나를 그리려면 CPU가 GPU에게 '이 메시를, 이 머티리얼/셰이더로, 이 트랜스폼에 그려라'라는 명령을 준비해서 보내야 합니다. 이 준비 과정(상태 세팅, 명령 인코딩)에는 GPU가 실제로 그리는 시간과 별개로 CPU 시간이 듭니다. 똑같이 생긴 나무 1000그루를 각각 별도 드로우 콜로 보내면 CPU가 1000번 이 준비를 반복하고, 이게 프레임 타임을 잡아먹어 CPU 바운드가 됩니다. GPU Instancing은 '메시도 같고 머티리얼도 같으니, 상태는 한 번만 세팅하고 트랜스폼(과 몇몇 per-instance 데이터)만 배열로 넘겨 1000개를 한 번에 그려라'라고 지시합니다. 결과적으로 드로우 콜 수와 CPU 준비 비용이 크게 줄어듭니다. 이 프로젝트(Dusk Hollow)의 성능 예산이 '드로우 콜 < 200/frame, Steam Deck 60fps'인 점을 생각하면, 반복되는 배경 요소(나무, 풀, 돌 등)에 인스턴싱은 직접적인 이득입니다.

'인스턴스별로 다른 것'은 어떻게 처리하느냐가 핵심 포인트입니다. 인스턴싱은 메시/머티리얼/셰이더가 공유되어야 하지만, 위치·회전·스케일(트랜스폼)은 인스턴스마다 다르고, 색깔 같은 몇몇 속성도 다를 수 있습니다. 이 per-instance 데이터는 하나의 버퍼에 배열로 담아 GPU에 함께 전달되고, 셰이더 안에서 각 인스턴스가 자기 인덱스로 자기 데이터를 읽어갑니다. 트랜스폼은 objectToWorld 행렬(Matrix4x4) 배열로 넘기는 것이 기본이고, 색상 등 추가 값은 MaterialPropertyBlock의 배열(SetVectorArray/SetFloatArray 등)이나 RenderMeshInstanced의 커스텀 인스턴스 데이터 구조체로 넘깁니다. 주의할 점: 셰이더가 GPU Instancing을 지원하도록 작성되어 있어야 하고(#pragma multi_compile_instancing, UNITY_SETUP_INSTANCE_ID 등), 머티리얼에서 'Enable GPU Instancing'이 켜져 있어야 합니다. 다만 원본 메모의 '안 켜져 있으면 예외가 난다'는 부분은 정정이 필요합니다 — MeshRenderer 기반 렌더링에서 인스턴싱 옵션이 꺼져 있으면 예외가 아니라 인스턴싱 없이 개별 드로우 콜로 폴백(fallback)됩니다(성능 이득만 못 볼 뿐). 예외가 발생하는 것은 뒤에 나오는 코드 기반 RenderMeshInstanced 계열을 미지원 환경에서 호출할 때의 별개 이야기입니다.

API 이름과 상태 정리(Unity 6.x 기준, 공식 ScriptReference 확인): 예전에 널리 쓰이던 즉시(immediate) 인스턴싱 API인 Graphics.DrawMeshInstanced와 Graphics.DrawMeshInstancedIndirect는 현재 obsolete(deprecated) 처리되어, 각각 Graphics.RenderMeshInstanced와 Graphics.RenderMeshIndirect로 대체되었습니다(관련으로 DrawMeshInstancedProcedural → RenderMeshPrimitives). 새 API들은 RenderParams 구조체(머티리얼, 레이어, 그림자/카메라 옵션 등을 한데 묶음)를 첫 인자로 받는 것이 특징입니다. RenderMeshInstanced는 인스턴스 데이터를 배열/NativeArray<T>로 받는데, T가 Matrix4x4면 트랜스폼 배열로, 커스텀 구조체면 첫 멤버가 objectToWorld 행렬이고 뒤에 추가 데이터를 붙이는 형태입니다. 이 API 계열은 매 프레임 호출하는 즉시 렌더 방식이라, MeshRenderer 컴포넌트 없이 코드로 대량 렌더할 때 씁니다.

중요한 한계 수치(공식 문서로 정정): RenderMeshInstanced/DrawMeshInstanced는 한 번 호출로 최대 1023개 인스턴스까지만 그릴 수 있습니다. 다만 Unity가 기본적으로 각 인스턴스에 objectToWorld 행렬과 worldToObject 행렬 두 개를 함께 쓰기 때문에, 기본 상태의 실질 한계는 절반인 511개입니다. 셰이더에 '#pragma instancing_options assumeuniformscaling'을 넣어 worldToObject 행렬을 생략하면 1023개 한계를 온전히 쓸 수 있습니다. 이 1023 상한은 상수 버퍼에 배열로 데이터를 싣는 구조에서 비롯됩니다. 이 한계를 넘어 수만 개를 한 배치로 그리려면 GPU 쪽 버퍼(GraphicsBuffer/ComputeBuffer)에 데이터를 상주시키고 GPU가 스스로 그리기 인자를 결정하는 Indirect 방식, 즉 Graphics.RenderMeshIndirect를 씁니다. Indirect는 매 프레임 CPU에서 행렬을 업로드하지 않아도 되므로(데이터가 GPU에 남아 있음) 초대량 렌더에서 훨씬 효율적입니다. 대신 셋업이 복잡하고, 컬링/트랜스폼을 컴퓨트 셰이더로 직접 다뤄야 하는 경우가 많습니다.

DOTS/Entities 쪽과 Unity 6의 자동화 흐름도 알아두면 좋습니다. 저수준 API인 BatchRendererGroup(BRG)이 이 모든 인스턴싱의 밑바탕입니다. Entities Graphics 패키지는 이 BRG 위에서 RenderMeshArray / RenderMeshDescription 같은 컴포넌트로 엔티티들의 메시 렌더를 관리하며 자동으로 인스턴싱합니다(DOTS 프로젝트용). 그리고 Unity 6에서 새로 들어온 GPU Resident Drawer는, 원래 DOTS 전용이던 BRG를 일반 GameObject(MeshRenderer)에도 적용해 주는 기능입니다. URP/HDRP에서 GPU Resident Drawer를 쓰려면 렌더 경로가 Forward+여야 하고, URP Asset에서 SRP Batcher가 켜져 있어야 하며, Project Settings > Graphics의 Shader Stripping에서 'BatchRendererGroup Variants'를 Keep All로 두어야 합니다(빌드 시간이 늘어나는 대가가 있습니다). 이 조건에서 GPU Resident Drawer를 Instanced Drawing으로 켜면, MeshRenderer들의 데이터를 GPU 버퍼에 상주시키고 CPU 드로우 콜 준비 비용을 줄여줍니다(감소폭은 씬 구성에 따라 크게 달라지며, Unity 공식이 '최대 절반' 같은 고정 수치를 보장하지는 않습니다 — 반복 오브젝트가 많은 씬일수록 이득이 큽니다). 즉, 코드로 RenderMeshInstanced를 직접 부르지 않아도 씬의 반복 오브젝트에 대해 자동 인스턴싱을 얻을 수 있는 길이 Unity 6에서 열린 셈입니다.

정리하면 선택지는 세 층위입니다. (1) 손으로 코드에서 대량 렌더 — Graphics.RenderMeshInstanced(호출당 ≤1023, 기본 실질 511) 또는 RenderMeshIndirect(초대량, GPU 버퍼). (2) DOTS 엔티티 렌더 — Entities Graphics의 RenderMeshArray/BRG(이 2D 프로젝트에선 쓸 일이 거의 없음). (3) 일반 GameObject 씬에서 손 안 대고 자동 인스턴싱 — Unity 6 GPU Resident Drawer. 이 프로젝트처럼 2D URP 스토리북 스타일이라면, 대부분의 스프라이트는 SpriteRenderer가 SRP Batcher/동적 배칭으로 처리하고(스프라이트 자체는 GPU Resident Drawer의 대상이 아닙니다), 반복되는 3D 요소(예: 밤 분위기용 안개 평면, 배경 메시)가 생길 때 GPU Resident Drawer나 RenderMeshInstanced가 후보가 됩니다. 어느 경우든 핵심은 동일합니다 — '재활용'이 아니라 '같은 것을 한 번에 몰아 그려 CPU 비용을 줄이는' 것입니다.

✍ 세션에서 받아적은 메모

“렌더 메쉬 인스턴스가 뭔데? 인스턴스..? 재활용하는거 맞어?”

✅ 정리 & 바로잡기

결론부터 말씀드리면, 여기서의 "인스턴스"는 재활용(오브젝트 풀링)이 아닙니다. 헷갈리신 이유는 이해가 됩니다 — "인스턴스"라는 단어가 프로그래밍에서 두 가지 전혀 다른 맥락으로 쓰이기 때문입니다. (1) OOP/풀링 맥락의 "인스턴스"는 클래스의 실제 객체 하나를 만들거나(new), 만들어 둔 객체를 버리지 않고 다시 쓰는(풀링) 것을 뜻합니다. 이건 메모리/GC 절약 기법이죠. (2) 반면 렌더링 맥락의 "GPU Instancing"은 완전히 다른 개념입니다. 똑같은 메시와 똑같은 머티리얼을 쓰는 오브젝트가 화면에 100개, 1000개 있을 때, 그것들을 하나하나 별개의 드로우 콜로 GPU에 보내는 대신, "이 메시를 이 위치들에다 1000번 그려라"라는 인스턴스드 드로우 콜 한 번으로 묶어 보내는 GPU 하드웨어 기능입니다. 여기서 "재활용"에 가장 가까운 표현을 쓰자면, 재사용되는 것은 C# 오브젝트가 아니라 GPU에 이미 세팅된 메시/머티리얼/셰이더 상태(state)입니다 — 즉 CPU가 매 오브젝트마다 그리기 명령을 새로 준비하고 GPU 파이프라인 상태를 다시 바인딩하는 비용을 없애는 것이지, C# 객체를 재사용하는 게 아닙니다. 정리하면: GPU Instancing은 CPU→GPU 드로우 콜 오버헤드를 줄이는 렌더링 최적화이고, 풀링은 GC/할당을 줄이는 메모리 최적화입니다. 이번 스터디 주제(GC/메모리)와 나란히 나와서 헷갈리셨겠지만, 둘은 다른 층위의 최적화입니다.

📌 핵심 정리

  • GPU Instancing은 오브젝트 재활용(풀링)이 아니라, 같은 메시+머티리얼 복사본들을 인스턴스드 드로우 콜 하나로 그려 드로우 콜/CPU 오버헤드를 줄이는 렌더링 최적화입니다.
  • 재사용되는 것은 C# 객체가 아니라 GPU에 세팅된 메시/머티리얼/셰이더 상태입니다 — CPU가 오브젝트마다 반복하던 준비 비용을 없앱니다.
  • 트랜스폼(Matrix4x4)·색상 등 인스턴스별 데이터는 per-instance 버퍼(배열/MaterialPropertyBlock/커스텀 구조체)로 전달됩니다.
  • Unity 6.x에서 Graphics.DrawMeshInstanced / DrawMeshInstancedIndirect는 obsolete이고, Graphics.RenderMeshInstanced / RenderMeshIndirect(RenderParams 인자)로 대체되었습니다.
  • RenderMeshInstanced/DrawMeshInstanced는 호출당 최대 1023 인스턴스 한계가 있으며, 기본(objectToWorld+worldToObject 두 행렬)에서는 실질 511개입니다. 그 이상 대량은 GPU 버퍼 기반 RenderMeshIndirect를 씁니다.
  • 저수준 BatchRendererGroup 위에 DOTS의 Entities Graphics(RenderMeshArray)와 Unity 6의 GPU Resident Drawer가 얹혀 있으며, GPU Resident Drawer는 일반 GameObject에도 자동 인스턴싱을 적용합니다(Forward+ · SRP Batcher · BRG Variants Keep All 필요).
  • 머티리얼의 'Enable GPU Instancing'이 꺼져 있으면 MeshRenderer는 예외가 아니라 인스턴싱 없이 폴백됩니다. 셰이더도 인스턴싱을 지원해야 이득을 봅니다.

예시 (hlsl) · 인스턴싱 지원 셰이더의 최소 골격 — worldToObject 생략으로 1023 한계를 온전히 쓰려면 assumeuniformscaling 추가

#pragma multi_compile_instancing
#pragma instancing_options assumeuniformscaling // objectToWorld만 사용 -> 실질 한계 511 -> 1023

struct appdata {
    float4 vertex : POSITION;
    UNITY_VERTEX_INPUT_INSTANCE_ID   // 인스턴스 인덱스 입력
};

v2f vert(appdata v) {
    v2f o;
    UNITY_SETUP_INSTANCE_ID(v);      // 이 인스턴스의 데이터 세팅
    o.pos = UnityObjectToClipPos(v.vertex);
    return o;
}

⚠ 버전·플랫폼 주의 (공식 문서·실기 재확인 권장)

  • 버전 의존: DrawMeshInstanced/DrawMeshInstancedIndirect의 obsolete 처리 방식(경고 vs 에러)과 RenderMeshInstanced/RenderMeshIndirect의 메서드 시그니처 세부는 Unity 마이너 버전마다 다를 수 있습니다. 공식 6.3/6.4 ScriptReference에서 시그니처를 그때그때 확인하세요.
  • 수치 의존: '1023 인스턴스' 한계 중 기본 실질값 511은 Unity가 objectToWorld+worldToObject 두 행렬을 쓰는 기본 설정 기준입니다. 'assumeuniformscaling'으로 worldToObject를 생략하면 1023까지 쓸 수 있으나, 정확한 상한은 셰이더 상수 버퍼 구성/플랫폼에 따라 달라질 수 있습니다.
  • 플랫폼 의존/확인 필요: 미지원 그래픽 API·디바이스에서 RenderMeshInstanced 호출 시 예외가 발생할 수 있으나, 정확한 예외 타입(InvalidOperationException 등)은 버전·상황에 따라 다를 수 있어 실제 타깃(Steam Deck/Vulkan 등)에서 확인이 필요합니다. 원본 메모의 'InvalidOperationException' 단정은 근거가 약해 완화했습니다.
  • 플랫폼/설정 의존: GPU Resident Drawer는 URP/HDRP의 Forward+ 렌더 경로 + SRP Batcher 활성화 + 'BatchRendererGroup Variants: Keep All' + 호환 셰이더 조합에서만 동작합니다. Unity 6.x 마이너 버전별로 지원 범위와 제약이 다르며, 드로우 콜 감소폭은 씬 구성에 크게 좌우됩니다('최대 절반' 같은 고정 수치는 공식 보장이 아님 — 확인 필요).
  • 적용 범위: 이 프로젝트는 2D URP 스프라이트 중심이라 스프라이트는 주로 SRP Batcher/동적 배칭으로 처리되며 GPU Resident Drawer/RenderMeshInstanced의 직접 대상이 아닙니다. 이들 기능은 반복되는 3D 메시 요소가 생길 때 검토 대상입니다.
  • DOTS Entities Graphics(RenderMeshArray/RenderMeshDescription) 세부 API는 com.unity.entities.graphics 패키지 버전에 강하게 묶여 있어, 실제 사용 시 프로젝트에 설치된 패키지 버전 문서를 확인해야 합니다.

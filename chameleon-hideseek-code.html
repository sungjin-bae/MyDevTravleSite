카멜레온 위장 게임 — 코드로 더 깊이

앞선 분석 노트의 “몸에 색 칠하기”와 “색 동기화”를, 이번엔 실제 소스 코드로 확인합니다. 세 가지를 코드 근거와 함께 봅니다 — ① 좌클릭 한 번이 몸 색으로 남는 경로, ② 월드에 광선을 쏴 표면색을 읽는 스포이드, ③ 유저들의 몸 색이 서버에서 동기화되는가(결론부터: 지금은 안 됩니다).

이 글의 코드아래 코드는 모두 저장소에서 그대로 복사한 것이고, 각 블록 우측 상단에 파일명과 라인 번호를 달았습니다. UE C++이라 낯선 함수명이 있어도, 각 블록 위 한두 줄 설명만 따라가면 흐름이 잡힙니다.

A · 색칠

좌클릭 한 번이 몸에 색으로 남기까지

좌클릭이 몸 색으로 남는 과정은 여섯 함수를 지납니다. 입력 → 광선 → (가만히 선 몸 기준으로) 자국 기록 → 정점색 다시 계산, 순서예요.

StartPaint좌클릭 down
→
PaintTriggered누르는 동안 반복
→
TraceFromView내 몸에 광선
→
ApplyPaintStrokeFromHit자국 1개 생성
→
ApplyPaintStrokeLocalPaintStrokes.Add
→
RebuildVertexColors색 다시 칠함

1) 입력 연결. 좌클릭은 PaintAction, E키는 SampleColorAction에 묶여 있습니다(입력은 코드가 아니라 데이터애셋 DA_ChameleonPainterInputConfig에 매핑). 누름(Started)·유지(Triggered)·뗌(Completed)이 각각 다른 함수로 갑니다.

2) 클릭 → 광선. StartPaint은 bPaintHeld=true로 두고 PaintTriggered를 부릅니다. PaintTriggered는 TraceFromView(BrushTraceDistance, Hit, true)로 내 몸에만(세 번째 인자 bTraceSelfBody=true) 광선을 쏴 맞은 지점을 찾고, 맞으면 ApplyPaintStrokeFromHit(...)에 현재 브러시 색(CurrentBrushColor)과 반경(BrushRadiusCm=18cm)을 넘깁니다. 스프레이 파티클은 색과 무관한 연출일 뿐입니다.

3) “가만히 선 몸” 기준으로 자국 기록. 몸은 걸을 때 출렁이므로, 맞은 삼각형(FaceIndex)의 세 꼭짓점을 무게중심(barycentric)으로 섞되 출렁이는 좌표(Animated…)가 아니라 원본 좌표(CachedVertices=rest pose)로 위치·노멀을 계산해 스트로크에 저장합니다. 그래서 걸어도 무늬가 몸에 붙어 따라옵니다. 그다음 두 갈래 — ApplyPaintStrokeLocal(정점색) + ApplyMaterialTextureStrokeLocal(표면 텍스처) — 를 함께 적용합니다.

※ 위 코드블록의 함수 앞부분(가드·폴백)은 생략하고 핵심만 보여줍니다. 조건이 안 맞으면 ApplyPaintStrokeWorld(월드 좌표 폴백)로 빠집니다.

4) 배열에 추가 + 다시 칠하기. ApplyPaintStrokeLocal은 값을 정리(alpha=1, clamp)해 PaintStrokes.Add로 넣고, 곧바로 RebuildVertexColors()로 색을 다시 계산합니다.

5) 색 블렌드 공식(핵심). 모든 정점을 바탕색(CamouflageBaseColor)에서 시작해, 반경 안의 스트로크마다 Alpha = Strength · pow(1 − 정규화거리, Falloff)만큼 HSV 색공간에서 보간합니다(LerpUsingHSV). RGB 직선 보간과 색 전이가 달라 물감 섞임처럼 보이죠. 다만 스트로크가 추가될 때마다 전 정점을 처음부터 다시 도는 O(정점 × 스트로크) 구조라, 저장소 TODO도 이를 최적화 과제로 적어 뒀습니다.

B · 스포이드

월드에 광선을 쏴 표면의 색을 읽기

💧

쉽게 말하면배경에 맞춰 위장하려면 주변 색을 그대로 찍어와야 합니다. 스포이드는 두 가지 소스가 있어요 — 월드에 광선을 쏴 “맞은 표면의 색”을 읽거나(기본), 화면에 실제로 찍힌 픽셀 색을 그대로 읽습니다.

어느 소스를 쓸지는 EChameleonColorPickSource 한 값으로 정해집니다(SurfaceData=월드 표면, FinalScreen=화면 픽셀). 기본은 SurfaceData.

1) 광선 쏘기. 컬러피커가 열려 있으면 마우스 위치를 월드로 디프로젝트(DeprojectMousePositionToWorld), 아니면 카메라 정면으로 광선을 만듭니다. 길이는 스포이드용 SampleTraceDistance(=2000cm). 중요한 건 QueryParams.bReturnFaceIndex = true — 맞은 삼각형 번호를 받아야 뒤에서 UV·면별 머티리얼을 얻을 수 있습니다. 자기 몸이면 컴포넌트 트레이스, 아니면 GetWorld()->LineTraceSingleByChannel(..., ECC_Visibility, ...)로 월드를 때립니다.

2) 맞은 지점을 “색”으로 해석. TrySampleColorFromHit은 아래 순서로 하나씩 시도해 처음 성공하는 색을 씁니다(위에서부터 폴백).

  1. 내 카멜레온 몸에 맞았나? → 그 몸에 이미 칠해진 base color를 읽음 TrySampleBaseColorFromHit
  2. 맞은 면의 머티리얼을 면 인덱스로 얻음 GetMaterialFromCollisionFaceIndex(Hit.FaceIndex)
  3. base color 텍스처를 히트 UV로 샘플(있으면) — UV는 UGameplayStatics::FindCollisionUV로 얻고, 텍셀을 읽어 tint를 곱함
  4. 머티리얼 벡터 파라미터를 이름 후보로 조회 ChameleonSampleColor · PaintColor · BodyColor · BaseColor · Color

UV 해석은 이 헬퍼가 담당합니다 — 엔진 API가 실패하면 스태틱메시 무게중심 폴백으로 재시도.

3) 대안 — 화면 픽셀 그대로 읽기. FinalScreen 소스일 때는 마우스 아래 1×1 픽셀을 Viewport->ReadPixels로 읽어 FromSRGBColor로 변환합니다. “표면의 재질”이 아니라 “화면에 최종적으로 찍힌 그 색”을 집는 방식이죠.

4) 소스 선택 + 확정. TrySampleEyedropperColor가 소스에 따라 위 둘 중 하나를 고릅니다(FinalScreen이면 화면 먼저 → 실패 시 표면으로 폴백).

마지막으로 E키(SampleColor)나 컬러피커에서 좌클릭(PickEyedropperColor)하면 읽은 색이 CurrentBrushColor가 되어, 다음 붓질부터 그 색으로 칠해집니다.

C · 색 동기화

유저들의 몸 색은 서버에서 동기화되나?

⛔ 짧은 답: 지금은 동기화되지 않습니다

위장 게임인데도, 내가 칠한 몸 색은 나만 봅니다. 채색은 전부 “내 화면에서만” 일어나고, 서버로 올라가거나 다른 유저에게 내려가는 경로가 코드에 아예 없습니다. 근거를 네 가지로 확인합니다.

근거 ① — 자국 배열이 복제 대상이 아니다. 칠한 자국을 담는 PaintStrokes는 UPROPERTY조차 아닌 순수 멤버라, 복제는커녕 저장 파이프라인에도 안 올라갑니다. 색을 담는 텍스처 3장은 UPROPERTY(Transient)(저장·복제 안 됨), 픽셀 버퍼도 순수 멤버입니다.

근거 ② — 실제로 복제되는 값에 “색”이 없다. 서버가 모두에게 내려보내는 값(DOREPLIFETIME)을 전수 조사하면 아래가 전부입니다. 라운드·역할·발각 여부뿐, 페인트/색은 한 줄도 없습니다.

근거 ③ — 색을 실어 보낼 RPC 통로가 없다. RPC는 딱 2개, 둘 다 Client, Reliable(서버→소유 클라)입니다 — 입력 잠금과 화면 전환 연출용. 클라→서버(Server RPC)도, 전체 방송(NetMulticast)도 0개라, 클라가 서버에 “나 이 색 칠했어”라고 알릴 방법 자체가 없습니다.

근거 ④ — 채색이 로컬 입력에서 곧장 실행된다. 앞 A절에서 봤듯 PaintTriggered가 서버를 거치지 않고 ApplyPaintStrokeFromHit를 직접 부릅니다. 그래서 각 클라의 색 상태가 처음부터 따로 놉니다.

🧷

정리서버가 심판을 보는 것(서버 권위)은 라운드·역할·시계까지입니다. 정작 이 게임의 핵심인 위장 색은 서버 바깥, 각자 화면에만 있습니다 — 분석 노트가 말한 “가장 큰 함정”의 코드 근거가 바로 이것입니다.

그럼 “어떻게” 동기화하려고 하나 — 계획된 설계

저장소 문서 Docs/eos-integration-plan.md의 §2 “채색/위장 상태 복제 설계”가 방향을 담고 있습니다(아직 문서만, 코드엔 없음). 핵심은 “몸 색 자체가 아니라, 어디에 무슨 붓질을 했나라는 사건(stroke)을 서버가 심판해 복제한다”입니다.

  1. 클라 → 서버 요청. 좌클릭 입력을 ServerRequestPaintStroke(Server RPC)로 서버에 보낸다. 클라는 자기 멋대로 칠하지 않는다.
  2. 서버 검증·확정. 서버가 trace/입력을 검증(샘플 색·브러시 반경·강도·쿨다운)하고, 경량 데이터 FChameleonPaintStrokeNet로 stroke 하나를 확정한다.
  3. 전 클라에 복제. 확정 stroke를 FFastArraySerializer(또는 순번 기반 replicated array)로 모두에게 전파한다.
  4. 각자 재적용. 각 클라는 받은 stroke를 로컬 절차 메시의 vertex color에 다시 칠한다(지금의 RebuildVertexColors와 같은 방식).
  5. 따라잡기. 나중에 접속한 클라를 위해 base color + stroke revision + 최근 N개 snapshot을 두어 현재 색 상태를 재동기화한다.

왜 이 구조인가 — 이유가 셋입니다.

  • 대역폭 — 정점색 결과를 통짜로 복제하면 비싸다. “붓질 사건”만 보내면 훨씬 가볍다(문서 원칙 #4: 정점색 전체를 매 프레임 보내지 않고 압축 가능한 도메인 이벤트로 복제).
  • 치트 방지 — 클라 권위 페인트는 조작 위험이 있어, 서버가 확정한 stroke만 복제한다.
  • 늦게 온 사람 — late-join 클라가 현재 hider의 색을 따라잡아야 하므로 revision·snapshot을 둔다.

문서가 직접 짚는 “현재 위험 → 권장 구조” 대목을 그대로 옮기면 이렇습니다.

우선순위도 명확합니다 — 이 복제는 EOS(온라인 접속)보다 먼저 해야 할 P0 항목(“페인트 stroke 서버 권위 복제”)으로 잡혀 있고, TODO에도 완료 기준이 “base color와 stroke 또는 paint texture 상태가 서버 권위로 복제된다”로 적혀 있습니다.

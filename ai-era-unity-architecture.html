AI 코딩 시대의 유니티 대규모 프로젝트 설계

AI가 코드를 값싸게 쓰는 시대에 “좋은 설계”란 무엇인가 — 검수 비용, 클린 아키텍처의 이득과 비용, 함수형 코어·데이터 지향, 그리고 계층 분리로 수정 단위를 줄이는 이야기를 유니티 맥락에서 정리한 노트입니다.

관점 · 전제

AI가 코드를 값싸게 “쓰는” 시대에는 병목이 작성 → 검수·이해로 옮겨갑니다. 그래서 설계의 목표가 “지금 짜기 편함”이 아니라 미래 총비용(작성+검수+수정+이해) 최소화로 바뀌고, 사람의 역할은 코더에서 감독·리뷰어로 이동합니다. (이 노트의 중심 관점 — 사실이라기보다 하나의 설계 렌즈)

함수형 + 데이터 중심

값(불변 데이터)을 넘겨 순수 계산 함수로 처리하고(functional core), 데이터를 한곳에 모아 다루면(data-oriented) 부작용이 없어 독립 단위 테스트가 쉽고 입출력이 값이라 AI가 문맥을 파악하기 좋습니다.

계층 = 수정 단위 축소

경계가 뚜렷하면 한 변경의 blast radius(파급 범위)가 좁아져 diff가 작아지고, 작은 diff는 검수가 쉽습니다. 계층 분리는 AI가 한 번에 안전하게 건드릴 범위를 줄이는 구조적 안전망입니다.

만능은 아님

“AI가 보일러플레이트를 대신 쓰니 경계 명확한 클린 아키텍처가 유리하다”는 매력적이지만 만능은 아닙니다 — 잘못된 추상화·과설계는 AI가 있어도 부채이고, 경계가 늘면 오히려 blast radius가 커질 수도 있습니다. 솔로·소규모는 가벼운 경계 + 함수형 코어부터가 실용적입니다.

01 · 논지

병목의 이동: 작성에서 검수로, 그리고 설계의 목표 함수가 바뀐다

AI가 코드를 값싸게 생성하면 개발의 병목은 "짜는 일"에서 "이해하고 검수하는 일"로 옮겨갑니다. 그래서 좋은 설계의 기준은 "지금 짜기 편함"이 아니라 "미래의 총비용(작성+검수+수정+이해)을 낮추는 것"으로 바뀌고, 사람의 역할은 코더에서 감독/리뷰어로 이동합니다. 다만 이는 제 관점 논지이지 확립된 정리가 아니며, 규모·맥락에 따라 뒤집힐 수 있습니다.

소프트웨어의 총비용을 작성 원가로만 보면, AI는 명백한 순이익입니다. 하지만 프로그램의 수명 전체를 놓고 보면 작성은 한 번, 읽기·이해·검증·수정은 수십 번 일어납니다. 저는 이 비대칭이 AI 시대에 더 극단화된다고 봅니다. 작성이라는 항목의 단가가 급락하면, 상대적으로 값이 그대로인 항목 — 이 코드가 무엇을 하는지 이해하고, 기존 아키텍처/규칙과 어긋나지 않는지 검수하고, 문제가 생겼을 때 원인을 특정하는 일 — 이 전체 비용을 지배하게 됩니다. 이것이 메모의 첫 줄, '검수의 비용은 더 증가, 코드가 쓰이는데 에너지가 적으니'의 정확한 의미입니다. 절대량이 아니라 비중의 이야기입니다. 다만 정직하게 덧붙이면, AI가 산출하는 코드량 자체가 폭증하는 경우 검수의 절대량까지 함께 늘어날 수 있습니다 — 비중 증가는 거의 필연이지만 절대량 감소는 보장되지 않습니다.

이 관점은 제 사변이 아니라 최근 업계 관측과 겹칩니다. Addy Osmani와 O'Reilly Radar가 다루는 'comprehension debt(이해 부채)'는 팀이 배포한 코드와 실제로 이해하는 코드 사이의 벌어지는 격차를 가리킵니다. AI가 만든 코드는 문법적으로 깨끗하고 표면적으로 그럴듯하지만 더 길고 방어적이며 시스템의 아키텍처·규약·보안 요구와 '거의 맞지만 완전히는 아닌' 경우가 많아, 빠르게 리뷰를 통과하면서도 디버깅·검증·유지보수 비용을 늘린다는 것이 요지입니다. 조직 지표로도 AI 도입이 높은 팀에서 개인이 완료한 태스크와 머지된 PR은 크게 늘었지만 PR 리뷰 시간과 PR 크기가 함께 급증하고, DORA류 조직 지표는 개선되지 않았다는 관측이 보고됩니다. 다만 이 수치들은 특정 조사·블로그 인용이며 맥락에 따라 크게 달라질 수 있으므로, 저는 이를 '방향성의 증거'로만 사용하고 확정된 법칙으로 취급하지 않습니다.

따라서 설계의 목표 함수를 다시 정의할 필요가 있습니다. 전통적으로 '좋은 설계'는 종종 '지금 이 기능을 빠르게 짜는 데 유리한 구조'와 혼동되었습니다. AI가 작성을 대신하는 세계에서는 이 기준이 힘을 잃습니다. 지금 짜기 편한 것은 AI가 어차피 싸게 해 주기 때문입니다. 남는 비용은 미래에 있습니다 — 6개월 뒤의 나(또는 AI)가 이 코드를 다시 읽고, 왜 이렇게 되어 있는지 이해하고, 안전하게 바꿀 수 있는가. 그래서 저는 설계의 목표를 '미래의 총비용(작성+검수+수정+이해) 최소화'로 잡아야 한다고 주장합니다. 메모의 '설계? 미래의 작업 시간까지 내다보고 전체 비용을 낮추는 것'이 이 지점입니다. 이 프레이밍이 뒤에서 이야기할 데이터 중심·함수형 코어·계층 분리·심지어 클린 아키텍처 채택 논의의 공통 판단 기준이 됩니다: 어떤 구조가 검수와 이해를 싸게 만드는가. 다만 이 목표 함수 자체가 만능은 아닙니다 — '미래 비용'은 관측 불가능한 미래 요구사항에 대한 추정이므로, 잘못 추정하면 오지 않을 미래를 위한 과설계(YAGNI 위반)로 귀결됩니다.

여기서 사람의 역할이 코더에서 감독/리뷰어로 이동합니다. Unity 맥락으로 좁히면 이 이동은 추상론이 아니라 구체적인 작업 습관의 변화입니다. 예를 들어 밸런스 공식이나 시간-사이클 상태 머신 같은 순수 로직을 MonoBehaviour에서 떼어 내 값을 입력받아 값을 돌려주는 순수 함수/클래스로 두면, EditMode 테스트로 독립 검증이 가능해지고 제가 AI의 산출을 '읽어서' 검수하는 대신 '테스트로' 검수할 수 있습니다. 감독의 일은 코드를 한 줄씩 신뢰하는 것이 아니라, 무엇이 옳은지를 정의하는 경계(테스트, 데이터 스키마, ScriptableObject 계약, 인터페이스)를 세우고 AI 산출물을 그 경계에 통과시키는 것입니다. 감독은 손이 아니라 판단으로 품질을 통제합니다. 물론 테스트로 검수한다는 것은 '테스트가 곧 명세'라는 위험을 안습니다 — AI가 구현과 테스트를 함께 생성하면 둘이 같은 오해를 공유해 통과할 수 있으므로, 경계(테스트·계약)를 정의하는 일만큼은 감독이 직접 사고해야 하는 대체 불가능한 몫으로 남습니다.

다만 이 결론에는 자기반성이 필요합니다. 병목이 검수로 옮겨간다는 관측은 오히려 낙관을 경계하라는 신호이기도 합니다. AI가 코드를 대량 생산하면 검수해야 할 표면적이 폭증하고, 인간의 이해 대역폭은 그대로이므로, 설계로 검수 비용을 낮추지 못하면 '감독'은 곧 병목 그 자체가 됩니다. 즉 이 노트의 나머지 주장들 — 데이터를 한곳에 모으고, 순수 함수로 계산하고, 계층으로 blast radius를 제한하고, 경계가 명확한 아키텍처를 고르는 것 — 은 '있으면 좋은 것'이 아니라 '감독이 실제로 감독일 수 있게 만드는 전제 조건'이 됩니다. 설계가 곧 검수 가능성의 설계라는 관점에서 이 세션의 나머지 논의를 읽어 주시면 좋겠습니다. 그리고 규모에 대한 정직한 단서도 답니다 — 이 논지는 대규모 프로젝트에서 힘을 얻지만, Dusk Hollow 같은 솔로~소규모에서는 검수 병목이 작아 같은 처방이 과설계로 뒤집힐 수 있습니다.

✍ 세션에서 받아적은 메모

“검수의 비용은 더 증가 코드가 쓰이는데 에너지가 적으니 / 설계? 미래의 작업 시간까지 내다보고 전체 비용을 낮추는것 / 사람은 결국 감독이된다.”

✅ 풀어 정리 & 관점 구분

이 노트의 중심 주장은 제 개인적 관점입니다. 즉 "AI가 코드를 싸게 쓰는 시대에는 병목이 작성에서 검수로 넘어가고, 따라서 설계는 지금의 편의가 아니라 미래 총비용을 최소화하도록 판단해야 한다"는 것은 제 사유의 결론이지, 확립된 정리(theorem)가 아닙니다. 다만 이 주장을 뒷받침하거나 정교하게 만들어 주는 인접한 사실/관찰들은 존재합니다. 이 둘을 섞지 않는 것이 이 노트의 지적 정직성의 핵심입니다. 사실(관찰) 쪽부터 정리하면 이렇습니다. 첫째, "코드는 쓰이는 것보다 훨씬 더 많이 읽힌다"는 것은 오래된 업계 상식입니다(흔히 유지보수 비용이 소프트웨어 총비용의 대부분을 차지한다고 이야기합니다). 둘째, 최근에는 AI 생성 코드로 인해 리뷰가 실제 병목으로 관측된다는 보고가 나오고 있습니다. Addy Osmani와 O'Reilly가 정리한 "comprehension debt(이해 부채)" 개념은 "팀이 배포한 코드와 팀이 실제로 이해하는 코드 사이의 격차"를 가리키며, 업계 데이터로는 AI 도입이 높은 팀에서 개인 생산성(머지된 PR 수 등)은 크게 늘었지만 PR 리뷰 시간과 PR 크기가 함께 급증하고 조직 수준 지표(DORA류)는 개선되지 않았다는 관측이 인용됩니다. 저는 이 관측이 제 주장과 "결이 같다"고 보지만, 이것들이 제 주장을 증명하는 것은 아니라는 점을 분명히 합니다. 오해 교정도 필요합니다. 제 메모의 "코드가 쓰이는데 에너지가 적으니 검수 비용이 더 증가"라는 표현은, 검수의 절대 비용이 마법처럼 늘어난다는 뜻이 아니라 상대적 비중이 커진다는 뜻입니다. 작성 원가가 0에 가까워질수록, 전체 비용에서 아직 값비싼 항목(읽기·이해·검증·통합·수정)이 지배적이 됩니다. 단, 여기에는 조건이 붙습니다. AI가 코드를 대량으로 쏟아내면 검수해야 할 물량 자체가 늘어나므로, 검수의 절대량까지 함께 증가하는 경우도 흔합니다. 즉 "비중은 반드시 커지지만, 절대량은 상황에 따라 늘 수도 있다"가 더 정확한 서술입니다. 또한 "사람은 감독이 된다"는 열망이자 방향성이지, 이미 도달한 상태의 서술이 아닙니다. 감독이 되려면 검수를 실제로 감당할 수 있어야 하고, 그건 설계가 검수 가능성(reviewability)을 갖추도록 설계될 때만 성립합니다.

📌 핵심 정리

  • 작성 원가가 급락하면 총비용의 지배 항목이 읽기·이해·검수·수정으로 옮겨간다 — 검수 비용의 '비중'이 커진다는 뜻이며, AI 산출량이 많으면 '절대량'도 함께 늘 수 있다(메모의 '검수 비용 증가'를 이렇게 읽어야 정확).
  • 설계의 목표 함수가 '지금 짜기 편함'에서 '미래 총비용(작성+검수+수정+이해) 최소화'로 바뀐다 — 이건 저의 관점 논지이며, '코드는 읽히는 게 더 많다'는 오래된 상식과 결이 같다. 단 '미래 비용'은 추정치라 과설계로 미끄러질 수 있다.
  • 업계 관측('comprehension debt', AI 도입 팀의 PR 리뷰 시간·크기 급증 등)이 이 방향을 지지하지만, 증명하지는 않는다 — 방향성의 증거로만 취급.
  • 사람의 역할이 코더 → 감독/리뷰어로 이동. Unity에서는 순수 로직을 MonoBehaviour에서 분리해 EditMode 테스트로 '읽지 않고 검증'하는 습관이 감독의 실제 도구 — 단 경계(테스트·계약) 정의만은 감독이 직접 사고해야 한다.
  • 가장 중요한 반전: 검수가 병목이 되므로, 검수 비용을 낮추는 설계(데이터 중심·함수형 코어·계층 분리·명확한 경계)가 사치가 아니라 감독이 성립하기 위한 전제 조건이 된다 — 그러나 규모가 작으면 같은 처방이 과설계가 된다.

예시 (csharp) · 감독의 도구: 순수 로직을 MonoBehaviour에서 떼어 내면, AI 산출물을 '읽어서'가 아니라 '테스트로' 검수할 수 있다. 위처럼 프레임 루프와 로직이 얽히면 검수 표면이 커지고, 아래처럼 값-입력/값-출력 순수 함수로 두면 EditMode 테스트가 곧 검수가 된다. (단 테스트와 구현을 AI가 함께 만들면 같은 오해를 공유할 수 있으니, 경계 정의는 감독의 몫이다.)

// 검수하기 어려운 형태: 상태와 로직이 MonoBehaviour에 얽혀 있어
// 이해하려면 씬/타임/프레임 컨텍스트를 통째로 머릿속에 올려야 한다.
public class DayNightCycle : MonoBehaviour {
    float _t;
    void Update() {
        _t += Time.deltaTime;
        if (_t > 90f) { /* 밤 전환 + 조명 + 스폰 ... */ }
    }
}

// 검수하기 쉬운 형태: 순수 계산 함수. 값을 넣으면 값이 나온다.
// 의존성 없음 -> EditMode 테스트로 독립 검증. AI 산출물을 읽지 않고도 옳음을 증명.
public static class Cycle {
    // 경과 시간 t와 하루 길이 dayLen을 받아 Phase를 결정하는 순수 함수
    public static Phase Resolve(float t, float dayLen)
        => (t % (dayLen * 2f)) < dayLen ? Phase.Day : Phase.Night;
}

⚖ 트레이드오프 · 반론 · 유의

  • 핵심 주장('작성→검수로 병목 이동, 설계 목표를 미래 총비용 최소화로')은 확립된 정리가 아니라 저의 관점 논지입니다. 인접한 사실(유지보수 비용 우세, comprehension debt 관측)과 결이 같을 뿐, 이들이 주장을 증명하지 않습니다.
  • 반론(steelman): AI 생성이 검수량 자체를 폭증시켜, 설계를 아무리 잘해도 리뷰가 진짜·최종 병목이 될 수 있습니다. 이 경우 결론은 '설계가 불필요'가 아니라 '설계가 더 절실'로 강화되지만, '사람은 감독이 된다'가 곧 '사람이 편해진다'를 뜻하지는 않습니다. 감독이 곧 병목일 수 있습니다.
  • 반론(추가): '미래 총비용 최소화'는 미래 요구사항 추정에 의존하므로, 추정이 틀리면 오지 않을 유연성을 위한 과설계(YAGNI 위반)가 됩니다. '검수 싸게'라는 목표가 곧 '추상 계층을 늘려라'로 오독되면 오히려 이해 비용을 키울 수 있습니다.
  • 반론(추가): '테스트로 검수'는 만능이 아닙니다. AI가 구현과 테스트를 함께 생성하면 동일한 오해를 공유해 함께 통과할 수 있고(테스트가 명세를 검증하지 못함), 게임의 '느낌·타이밍·비주얼'처럼 자동 검증이 어려운 영역은 여전히 사람이 읽고 플레이해 봐야 합니다.
  • 인용한 수치(개인 생산성 상승 대비 PR 리뷰 시간·크기 급증, DORA 지표 정체)는 특정 조사/블로그 인용이며 표본·맥락·측정 방식에 따라 크게 달라집니다. 일반 법칙으로 과대 해석하지 마세요.
  • 출처 신뢰도 구분: 클린 아키텍처의 의존성 규칙(R. C. Martin, Clean Architecture 2017 및 2012 블로그), 함수형 코어/명령형 셸(G. Bernhardt, 'Boundaries' 강연 2012), 데이터 지향 설계(M. Acton, CppCon 2014 'Data-Oriented Design and C++'), 포트&어댑터/헥사고날(A. Cockburn), Humble Object(G. Meszaros 'xUnit Test Patterns', M. Fowler 정리)는 원저자가 명확한 정의입니다. 반면 'comprehension debt'와 AI 생산성 통계는 최근 2차 자료(블로그/리포트)로, 정의는 유용하나 수치는 잠정적으로 다루었습니다. (검증 주: WebSearch가 세션 중 529 과부하로 응답하지 않아 위 귀속은 편집자의 확립된 지식에 근거해 확인했습니다.)
  • 스케일 caveat: 이 논지는 규모가 커질수록(대규모 유니티 프로젝트) 힘을 얻습니다. Dusk Hollow 같은 솔로~소규모 프로젝트에서는 검수 병목이 상대적으로 작아, '미래 총비용 최소화'가 과설계로 뒤집힐 위험이 있습니다 — 이 균형은 후속 주제(클린 아키텍처 채택/과설계 트레이드오프)에서 다룹니다.
  • '값을 통해 순수 함수로'가 항상 싼 검수를 보장하지는 않습니다. 게임에서는 실시간 상태·프레임 루프·성능 제약 때문에 순수성 유지 자체가 비용일 수 있어, 함수형 코어의 이점과 성능/편의의 트레이드오프를 별도로 저울질해야 합니다.

02 · MVP 비대화

MVP에서 Product로 갈수록 기능이 비대해진다 — 부채는 어디서, 왜, 그리고 AI 시대에 왜 더 빨리 쌓이는가

MVP에서 Product로 가는 과정에서 코드가 비대해지는 것은 개발자의 게으름이 아니라 "초기 속도 우선"이라는 합리적 선택이 누적시킨 이자입니다. AI가 코드를 값싸게 생성하는 시대에는 이 부채가 더 빠르게 쌓일 수 있다는 것이 이 노트의 주장이며, 그렇다면 설계 선행의 가치가 오히려 커집니다 — 다만 그 반대 방향(AI가 상환도 가속한다)의 반론도 함께 살펴봅니다.

부채가 생기는 인과는 대체로 다음 순서를 따릅니다. (1) MVP 단계에서는 "일단 돌아가는 것"을 빠르게 보여주는 것이 최우선 가치입니다. 이때는 검증되지 않은 가정이 많아 경계를 미리 긋는 것 자체가 낭비일 수 있고, 그래서 편의적 결합은 합리적 선택이기도 합니다. (2) 속도를 위해 기능들이 경계 없이 서로 직접 참조하며 결합합니다. (3) Product로 성장하면서 요구사항이 늘어날 때마다 이미 뒤엉킨 코드에 새 조건 분기를 덧대게 되고, 한 곳을 고치면 예상치 못한 다른 곳이 깨지는 상태 — 즉 변경 비용(이자)이 기능 수에 비례하거나 그 이상으로 증가합니다. 이 궤적의 종착점이 Foote와 Yoder가 말한 빅 볼 오브 머드입니다. 여기까지가 사용자님이 관찰한 "기능이 점점 비대해짐"의 메커니즘입니다.

Unity 맥락에서는 이 결합이 매우 구체적으로 드러납니다. 전형적 증상은 하나의 MonoBehaviour가 입력 처리, 게임 규칙 계산, 세이브 직렬화, UI 갱신을 한꺼번에 담당하는 God 컴포넌트입니다. 여기에 GetComponent와 (Unity 6.3 기준) 신형 FindAnyObjectByType/FindFirstObjectByType(구형 FindObjectOfType는 Unity 2023/6.x에서 Obsolete 경고가 붙어 사실상 폐기 수순)로 다른 오브젝트를 런타임에 직접 붙잡고, 밸런스 수치를 [SerializeField] 필드나 코드에 하드코딩합니다. 그 결과 규칙(로직)이 씬 계층 구조·프리팹 참조·프레임 루프에 얽혀서, 순수 계산을 EditMode 테스트로 떼어내 검증하기가 불가능해집니다. 프로젝트 규약(coding-standards.md)이 "게임플레이 값은 데이터 주도로, 하드코딩 금지"와 "싱글턴보다 의존성 주입"을 요구하는 이유가 바로 이 결합을 초기에 끊기 위해서입니다.

이 노트의 핵심 주장은 "AI 코딩 시대에 이 문제가 더 위험해진다"는 것인데, 이것은 사실이 아니라 사용자/세션의 논지임을 분명히 해 둡니다. 논거는 이렇습니다. 부채가 쌓이는 속도는 대체로 "코드를 얼마나 빨리 생성하느냐"에 연동되는데, AI는 바로 그 생성을 극적으로 값싸게 만듭니다. 이것은 양날의 검입니다. 좋은 경계 위에서 쓰면 보일러플레이트를 순식간에 채워 주지만, 경계가 없는 코드베이스에서는 기존의 뒤엉킨 패턴을 그대로 이어받아 더 많은 God 컴포넌트, 더 많은 직접 참조, 더 많은 중복 분기를 빠르게 찍어낼 수 있습니다 — 세션의 표현을 빌리면 "빅 볼 오브 머드를 광속으로" 짓는 셈입니다. 나아가 CLAUDE.md 세션 논지대로 이 시대에는 작성 비용이 아니라 검수(리뷰) 비용이 상대적으로 커지는데, 경계 없는 코드는 한 변경의 blast radius가 넓어서 AI가 만든 변경을 사람이 검수하기가 어려워진다는 것입니다. 다만 이 명제는 아직 대규모 실증으로 확립된 정설이 아니며(정리 참조), 정반대로 "AI가 상환도 가속한다"는 반론도 성립합니다. AI는 부채를 찍어낼 뿐 아니라 리팩터링·테스트 생성·부채 탐지를 자동화해 갚는 쪽 비용도 동시에 낮출 수 있으므로, 순효과는 팀이 AI를 "생성기"로만 쓰는지 "생성+상환+검수 보조기"로 쓰는지에 달려 있습니다.

여기서 설계 선행(design-first)의 가치가 나옵니다. 좋은 설계란 미래의 작업 시간까지 내다보고 전체 비용을 낮추는 것이라는 세션의 정의를, 부채 언어로 다시 쓰면 "이자율을 미리 낮춰 두는 것"입니다. 데이터를 한곳에 모으고(Unity에서는 ScriptableObject로 밸런스·설정을 자산화), 값을 통해 순수 함수에 넘겨 계산하면(입력→출력이 결정적), 그 로직은 씬과 무관하게 EditMode에서 독립 테스트가 가능해지고 AI가 파악·수정하기도 쉬워집니다. 이 "순수 계산 코어 + 얇은 유니티 껍데기" 구도는 Gary Bernhardt가 "Boundaries" 강연에서 제시한 Functional Core, Imperative Shell 패턴의 게임 엔진판입니다(코어는 값만 받아 값을 돌려주는 순수 함수, 껍데기가 입력·렌더·세이브 같은 부수효과를 담당). 계층을 분리해 두면 AI가 한 번에 건드리는 수정 단위가 물리적으로 제한되어 구조적 안전망이 됩니다. 중요한 것은 이것이 "MVP를 건너뛰라"는 말이 아니라, MVP 단계에서도 최소한의 경계 — 특히 순수 로직과 Unity 런타임 사이의 경계 — 만큼은 미리 그어 두라는 실용적 권고라는 점입니다.

다만 이 처방을 절대화하면 안 됩니다. 첫째, Cunningham의 원래 의도는 부채가 항상 나쁘다는 것이 아니라, 초기의 소액 부채는 합리적이며 관건은 "갚을 계획"이라는 것입니다. MVP 단계의 결합을 곧바로 죄악시하면 오히려 과설계로 흐릅니다. 둘째, 설계 선행이 부채를 없애 주지는 않습니다 — 도메인 이해가 아직 얕은 MVP 단계에서 정교한 경계를 미리 그으면, 그 경계가 "틀린 경계"라는 더 비싼 부채가 될 수 있습니다. 잘못 그은 인터페이스와 계층은 나중에 재정렬 비용이 크고, 경우에 따라 계층 자체가 변경을 여러 파일에 퍼뜨려 오히려 blast radius를 키우기도 합니다(경계 하나 옮기려면 인터페이스·구현·주입 지점·테스트를 함께 손대야 함). 솔로~소규모 프로젝트(예: Dusk Hollow, 솔로 4~6개월)에서는 리뷰어가 사실상 본인 한 명이고 코드 수명이 짧으므로, 완전한 계층 분리보다 "불확실한 부분은 편의적으로 빠르게, 그러나 변하지 않을 핵심 규칙(시간-사이클 상태 기계, 아이템 이중 기능 해석, 세이브 직렬화 같은 로직)만큼은 처음부터 순수 함수로 분리"라는 최소 경계가 비용 대비 효과가 큽니다. 부채를 지되, 어디에 얼마나 질지를 의도적으로 고르는 것 — 그것이 감독(supervisor)으로서 사람이 하는 판단입니다.

✍ 세션에서 받아적은 메모

“기존의 방식 mvp 에서 p 에 기능이 점점 비대해짐.”

✅ 풀어 정리 & 관점 구분

메모의 뜻을 먼저 풀면 이렇습니다. "MVP(Minimum Viable Product)에서 P(Product)로 넘어갈수록 기능이 점점 비대해진다"는 관찰은, 최소 기능 제품이 정식 제품으로 성장하는 동안 코드베이스가 통제 없이 부풀고 아키텍처 부채가 축적되는 현상을 가리킵니다. 여기서 의견과 사실을 구분해 두겠습니다. "기능이 비대해진다"는 표현 자체는 사용자님의 경험적 관찰(의견)이지만, 이 현상을 설명하는 두 개념은 업계에서 확립된 정의를 갖습니다. 첫째, "기술 부채(Technical Debt)"는 Ward Cunningham이 1992년(WyCash 포트폴리오 관리 시스템 작업 중) 제안한 은유로, 지금 당장 편의적인(expedient) 코드를 출하하는 것은 빚을 지는 것과 같으며, 적은 부채는 곧바로 리팩터링(rewrite)으로 갚는 한 개발 속도를 높여 주지만 갚지 않으면 이자(추가 기능을 넣을 때 드는 여분의 노력)가 누적된다는 개념입니다(Fowler는 이를 "원금=코드 수정, 이자=기능 추가 시 부담"으로 정리). 둘째, "빅 볼 오브 머드(Big Ball of Mud)"는 Brian Foote와 Joseph Yoder가 1997년 PLoP 논문에서 명명한 안티패턴으로, 설계가 아니라 편의(expediency)에 의해 구조가 결정되어 버린, 경계 없이 뒤엉킨(haphazardly structured, sprawling) 코드 덩어리를 뜻합니다. 한 가지 흔한 오해도 바로잡겠습니다. 기술 부채를 "일부러 나쁜 코드를 짜는 것"으로 이해하는 경우가 많은데, Cunningham 본인은 이를 명확히 부정했습니다. 그가 말한 부채는 "현재의 이해 수준을 최선을 다해 반영한 깨끗한 코드"를 출하하되, 나중에 더 나은 이해가 생겼을 때 리팩터링으로 갚는 것을 전제로 합니다. 특히 그는 후일(2009년 인터뷰) 이 은유의 핵심이 지저분한 코드가 아니라 "문제 도메인에 대한 불완전한 이해가 코드에 새겨지는 것"이라고 부연했습니다. 즉 부채의 위험은 "지저분하게 짜는 것"이 아니라 "이해가 자라났는데도 갚지 않고 방치하는 것"에 있습니다.

📌 핵심 정리

  • '기능이 비대해진다'의 정체는 축적된 기술 부채의 이자다 — 원금(코드 수정)을 갚지 않으면 기능 추가마다 드는 여분의 노력(이자)이 늘어난다(Ward Cunningham 1992, Fowler 정리).
  • 인과 사슬: 초기 속도 우선 → 경계 없는 직접 결합 → 변경 비용 증가 → 종착점은 Big Ball of Mud(Foote & Yoder, PLoP 1997).
  • Unity 전형 증상: 입력·규칙·세이브·UI를 한 데 담은 God MonoBehaviour, GetComponent/FindAnyObjectByType 직접 참조, 하드코딩된 밸런스 수치 — 순수 로직을 EditMode로 떼어내 테스트할 수 없게 만든다.
  • AI 시대의 가속 위험(주장): 생성이 값싸질수록 부채도 빨리 쌓일 수 있고, 경계 없는 코드는 blast radius가 넓어 검수 비용이 커진다 — 단, AI가 상환·검수도 가속한다는 반론이 함께 성립한다.
  • 설계 선행 = 이자율을 미리 낮추기: 데이터를 ScriptableObject로 자산화하고 순수 함수로 로직을 분리(=Functional Core/Imperative Shell)하면 독립 테스트·AI 파악·수정 단위 제한이 동시에 얻어진다.
  • 핵심 오해 정정: 기술 부채는 '나쁜 코드를 짜는 것'이 아니라 '더 나은 이해가 생겼는데도 갚지 않고 방치하는 것'이 문제다(Cunningham 본인 견해).

예시 (csharp) · 결합된 God MonoBehaviour(위) vs. 순수 로직 분리(아래, = Functional Core/Imperative Shell). 아래만 EditMode에서 씬 없이 독립 테스트되고, AI 수정의 blast radius가 로직 함수 안으로 제한된다.

// [안티패턴] 규칙 + 데이터 + 런타임이 한 덩어리 → 테스트 불가, blast radius = 클래스 전체
public class EnemyBad : MonoBehaviour {
    public int hp = 30;              // 밸런스 하드코딩
    void Update() {
        var player = FindAnyObjectByType<Player>();   // 씬 결합
        hp -= Mathf.Max(0, player.attack - 5);        // 규칙이 프레임 루프에 묻힘
        if (hp <= 0) Destroy(gameObject);             // 로직 검증 불가
    }
}

// [Functional Core] 순수 함수: 값만 받아 값을 돌려줌 → EditMode 단위 테스트 대상
public static class CombatRules {
    // data-in, data-out. 씬/프레임/유니티 API 의존 없음
    public static int ResolveDamage(int attack, int armor)
        => System.Math.Max(0, attack - armor);   // Mathf 대신 순수 System.Math로 유니티 의존 제거
}

// [Imperative Shell] MonoBehaviour는 얇은 껍데기로만: 값을 모아 순수 함수에 위임
public class EnemyGood : MonoBehaviour {
    [SerializeField] EnemyStats _stats;   // ScriptableObject: 데이터 자산화
    int _hp;
    void Awake() => _hp = _stats.MaxHp;
    public void TakeHit(int attack)
        => _hp -= CombatRules.ResolveDamage(attack, _stats.Armor);
}

⚖ 트레이드오프 · 반론 · 유의

  • 기술 부채는 항상 악(惡)이 아니다. Cunningham의 원 의도상 초기의 의도적 소액 부채는 학습·검증 속도를 위한 합리적 투자이며, 관건은 '갚을 계획'의 유무다. MVP 단계의 결합을 곧바로 죄악시하면 오히려 과설계로 흐른다.
  • 설계 선행이 부채를 없애 주지는 않는다. 도메인 이해가 얕은 시점의 잘못된 초기 설계는 '틀린 경계'라는 더 비싼 부채가 될 수 있고(잘못 그은 인터페이스는 재정렬 비용이 큼), 계층 분리 자체가 변경을 여러 파일에 퍼뜨려 blast radius를 오히려 키우는 경우도 있다.
  • 'AI가 부채를 광속으로 쌓는다'는 명제는 사용자/세션의 논지에 기반한 강한 주장이며, 아직 대규모 실증 연구로 확립된 정설은 아니다. 반대로 AI가 리팩터링·부채 탐지·테스트 생성을 자동화해 상환 속도도 함께 올린다는 반론이 성립하므로, 순효과는 AI를 '생성기'로만 쓰느냐 '생성+상환+검수 보조기'로 쓰느냐에 달려 있다.
  • 솔로~소규모 스케일에서는 트레이드오프가 다르다. 리뷰어가 사실상 본인 한 명이고 코드 수명이 짧은 프로토타입이라면, 완전한 계층 분리보다 '핵심 로직만 순수 함수로'라는 최소 경계가 비용 대비 효과가 크다.
  • 인용한 정의(Cunningham 1992, Fowler, Foote & Yoder 1997, Bernhardt 'Boundaries')는 1차/권위 있는 2차 출처로 교차 확인했으나, 인터뷰류의 직접 인용(예: Cunningham의 정확한 문장, 2009년 부연)은 매체마다 표현 차이가 있으므로 축자 인용이 아니라 취지 요약으로 받아들이는 것이 안전하다.

03 · 클린 아키텍처란

클린 아키텍처: 의존성 규칙과 동심원, 그리고 Unity에서의 경계

클린 아키텍처의 핵심은 "레이어가 4개"라는 그림이 아니라, 소스코드 의존이 오직 안쪽(고수준 정책)을 향한다는 단 하나의 규칙입니다. Unity에서는 이것이 "게임 규칙을 엔진에서 떼어낸다"로 번역되지만, 실제 프로젝트에서 그 경계가 얼마나 순수한지는 코드를 열어봐야 정직하게 말할 수 있습니다.

클린 아키텍처를 정확히 서술하면 이렇습니다. 안쪽부터 바깥으로 네 개의 개념 레이어가 있습니다. (1) Entities — Martin의 표현으로 '엔터프라이즈 전반의 비즈니스 규칙(Enterprise wide business rules)'을 캡슐화합니다. 가장 일반적이고 가장 덜 변하는 규칙입니다. (2) Use Cases(Interactors) — '애플리케이션에 특정한(application specific) 비즈니스 규칙'을 담고, 시스템의 모든 유스케이스를 구현합니다. '주문 생성', '결제 처리' 같은 애플리케이션 목표를 위해 Entities를 조율하되, 전달 메커니즘(UI/DB)은 몰라야 합니다. (3) Interface Adapters — 컨트롤러/프리젠터/게이트웨이가 여기 삽니다. 원문: '유스케이스와 엔터티에 가장 편한 데이터 포맷을, DB나 웹 같은 외부 기관에 가장 편한 포맷으로 변환하는 어댑터의 집합'입니다. MVC의 GUI 부분이 통째로 이 레이어에 들어갑니다. (4) Frameworks & Drivers — 가장 바깥으로, DB, 웹 프레임워크, 그리고 게임에서는 '게임 엔진'이 여기 속합니다. 원문 표현으로 '바깥 원들은 메커니즘(mechanisms)'입니다.

이 구조를 작동시키는 단 하나의 규칙이 의존성 규칙(The Dependency Rule)입니다. 원문 그대로: '소스코드 의존은 오직 안쪽을 향한다(Source code dependencies can only point inwards). 안쪽 원의 어떤 것도 바깥쪽 원의 무엇에 대해서도 전혀 알아서는 안 된다.' 더 엄격하게는, 바깥 원에서 선언된 이름(함수/클래스/변수 등)이 안쪽 원 코드에서 언급되어서도 안 되고, 프레임워크가 만든 데이터 포맷을 안쪽에서 써서도 안 됩니다. 목표는 두 가지로 요약됩니다 — 독립성(프레임워크/UI/DB/외부 세부로부터 비즈니스 규칙을 격리)과 테스트 용이성(핵심 규칙을 엔진·DB·UI 없이 검증 가능). 사용자 세션의 '함수형 코어를 독립 테스트한다'는 논지와 정확히 맞닿는 지점입니다.

그런데 흐름을 보면 모순처럼 보이는 지점이 있습니다. 실행 흐름(control flow)은 바깥에서 안으로 들어왔다가(예: 웹 요청 → 유스케이스), 다시 바깥으로 나가야 합니다(유스케이스 → DB 저장). 그런데 의존은 항상 안쪽만 향해야 합니다. 유스케이스가 DB를 직접 부르면 안쪽이 바깥을 알게 되어 규칙 위반입니다. 이 모순을 푸는 것이 의존성 역전 원칙(DIP, Dependency Inversion Principle)입니다. 방법은 이렇습니다 — 안쪽(유스케이스)에 인터페이스(port, 예: IOrderRepository)를 선언해 두고, 바깥(어댑터)이 그 인터페이스를 구현(adapter)합니다. 유스케이스는 인터페이스만 호출하므로 여전히 바깥을 모르고, 컴파일타임 의존은 바깥→안쪽으로 정상 방향을 유지합니다. 참고로 이 '안쪽에 포트를 두고 바깥이 구현' 패턴은 Alistair Cockburn의 Hexagonal(Ports & Adapters) 아키텍처와 본질적으로 같은 아이디어이며, 클린 아키텍처는 그 계보(Hexagonal, Jeffrey Palermo의 Onion 등)를 명시적으로 통합한 것입니다.

Unity/게임 맥락으로 번역하면 규칙은 단순해집니다: 게임 규칙은 순수 C#으로 쓰고, UnityEngine(MonoBehaviour, Transform, Time.deltaTime 등)은 가장 바깥 Frameworks & Drivers 레이어로 밀어낸다. 즉 '엔진은 세부(detail)일 뿐'이라는 태도입니다. 이 프로젝트(Dusk Hollow)는 그 방향의 절충을 채택하고 있습니다. 각 시스템이 로직 어셈블리(예: DuskHollow.Gameplay.Npc, DuskHollow.TimeCycle)와, 그것을 엔진에 연결하는 별도의 .Driver 어셈블리(예: DuskHollow.Gameplay.Npc.Driver)로 분리되어 있고, Unity의 Assembly Definition(.asmdef)이 references를 통해 의존 방향을 컴파일러 수준에서 강제합니다 — Driver는 로직 어셈블리를 참조하지만 로직 어셈블리는 Driver를 참조하지 않습니다. 이 패턴 자체는 ADR-003(GameClock Host Pattern)에 '순수 C# core + 얇은 Driver MonoBehaviour'로 명문화되어 있고, 로직/엔진을 분리해 로직만 EditMode로 검증한다는 점에서 사실상 Humble Object 패턴의 적용입니다. EditMode 테스트는 로직을, PlayMode 테스트는 엔진 통합(예: GameClockDriver의 Time.deltaTime 누적)을 검증합니다.

다만 여기서 지적으로 정직해야 할 지점 — 이 프로젝트의 '로직' 어셈블리들을 클린 아키텍처의 '안쪽 원'으로 부르는 것은 상당히 관대한 서술입니다. 실제 코드를 확인하면 세 가지가 드러납니다. 첫째, 로직 어셈블리들의 asmdef가 모두 noEngineReferences: false이고, 대표 예로 든 NpcInteractor는 MonoBehaviour를 상속합니다(사실 이건 Driver 성격이라 당연). 둘째, 초안이 '순수 코어'라 지목했던 NpcDialogueService.cs조차 파일 상단에서 using UnityEngine;을 선언합니다 — 즉 로직 클래스 자체가 엔진에 묶여 있습니다. 셋째, 더 근본적으로 DuskHollow.Gameplay.Npc 어셈블리는 DIP로 역전된 포트가 아니라 형제 어셈블리(Player, Inventory, Items, Crafting, TimeCycle)를 '직접·구체적으로' 참조합니다. 클린 아키텍처의 안쪽 원이라면 이 의존들은 인터페이스로 역전되어 있어야 합니다. 따라서 이 프로젝트가 실천하는 것은 '의존성 규칙 + DIP를 갖춘 클린 아키텍처'가 아니라, '엔진 결합을 Driver 쪽으로 최대한 몰고 어셈블리로 blast radius를 나눈' 실용적 절충입니다. 이건 결함이 아니라 솔로~소규모 스케일에서 흔히 옳은 선택입니다. 클린 아키텍처의 가치는 all-or-nothing이 아니라 '어느 경계를 얼마나 단단히 그을지'의 스펙트럼이고, 이 프로젝트는 그 스펙트럼 위의 합리적 지점에 서 있습니다. 사용자의 메모('AI가 인터페이스 부담을 대신 진다면 채택할 만하다')는 바로 이 스펙트럼을 '더 안쪽 경계(진짜 포트/역전)까지' 밀 수 있게 됐다는 주장으로 읽는 것이 가장 정확합니다.

✅ 풀어 정리 & 관점 구분

먼저 사실과 의견을 구분하겠습니다. "클린 아키텍처(Clean Architecture)"는 Robert C. Martin(Uncle Bob)이 2012년 8월 블로그 글 "The Clean Architecture"와 2017년 동명의 책에서 제시한 구체적 개념입니다. 그림으로 자주 인용되는 네 개의 동심원(Entities → Use Cases → Interface Adapters → Frameworks & Drivers)은 확립된 사실입니다. 그러나 흔한 오해가 하나 있습니다 — 클린 아키텍처의 본질은 "레이어를 4개로 나누는 것"이 아닙니다. Martin 본인이 원문에서 명시합니다: "원들은 도식적일 뿐이고(schematic), 네 개보다 더 필요할 수도 있다. 다만 의존성 규칙은 언제나 적용된다." 즉 레이어 개수는 협상 가능하지만, 의존성 규칙(The Dependency Rule)은 협상 불가입니다. 사용자의 메모에서 "레이어를 세분화해 경계가 명확하다"는 부분은 정확한 관찰이지만, 클린 아키텍처의 정체성을 "세분화" 자체에 두면 초점이 어긋납니다. 정체성은 "의존 방향의 일방통행"에 있습니다. 또 하나, 사용자가 말한 "동심원 문제"와 "인터페이스가 계속 늘어난다"는 것은 사실(정의)이 아니라 사용자의 평가/의견입니다 — 타당한 비판이지만 클린 아키텍처의 정의가 아니라 그 대가(cost)에 대한 관점으로 분류하는 것이 정직합니다. 마지막으로 이 노트에서 가장 중요한 정직성 하나 — 초안은 이 프로젝트(Dusk Hollow)가 클린 아키텍처를 "이미 실천 중"이라고 서술했지만, 코드를 열어 확인하면 그 경계는 교과서적 클린 아키텍처(포트 + 의존성 역전)라기보다 "얇은 Driver로 엔진 결합을 몰아내는 Humble Object 절충 + 어셈블리 방화벽"에 훨씬 가깝습니다. 이 차이를 흐리지 않고 정정했습니다.

📌 핵심 정리

  • 핵심은 레이어 4개가 아니라 의존성 규칙 하나: 소스코드 의존은 오직 안쪽(고수준 정책)을 향한다. Martin 본인이 '원은 도식일 뿐, 규칙만이 불변'이라고 명시.
  • 네 동심원(안→밖): Entities(엔터프라이즈 규칙) → Use Cases(애플리케이션 규칙) → Interface Adapters(컨트롤러/프리젠터/게이트웨이) → Frameworks & Drivers(UI/DB/엔진).
  • 경계를 넘을 때 DIP로 해결: 인터페이스(port)를 안쪽에 두고 바깥이 구현(adapter)한다. 실행 흐름은 밖→안→밖이어도 컴파일 의존은 항상 안쪽 방향 유지.
  • 목표는 프레임워크/UI/DB 독립성 + 테스트 용이성. Hexagonal(Cockburn)/Onion(Palermo) 계보와 같은 아이디어를 통합한 것.
  • Unity 번역: 게임 규칙은 로직 어셈블리, UnityEngine은 .Driver로. Dusk Hollow는 로직/Driver 어셈블리 분리 + asmdef references로 의존 방향을 컴파일러가 강제 + EditMode/PlayMode 테스트 분리 — 이는 ADR-003에 명문화된 Humble Object 절충.
  • 정정: 이 프로젝트의 '로직' 어셈블리는 클린 아키텍처의 '안쪽 원'이 아니다. asmdef noEngineReferences=false, NpcDialogueService조차 using UnityEngine, 그리고 형제 어셈블리를 포트가 아닌 구체 참조로 의존한다. 즉 DIP 없는 Humble Object + 어셈블리 방화벽에 가깝다.

예시 (csharp) · 교과서적 목표형: 유스케이스(안쪽)가 port 인터페이스를 소유하고 어댑터(바깥/엔진)가 구현한다. 이 예시는 클린 아키텍처가 '지향하는' 형태이며, Dusk Hollow의 현재 로직 어셈블리는 이 수준의 DIP까지는 가지 않고(형제 어셈블리를 구체 참조), 대신 얇은 Driver로 엔진 결합만 몰아내는 Humble Object 절충을 씁니다.

// [안쪽] Application 레이어 — 목표형: UnityEngine 참조 없음, port로만 바깥과 대화.
// (주의: Dusk Hollow의 NpcDialogueService 등 실제 로직 클래스는 아직 using UnityEngine을
//  포함하고 형제 어셈블리를 구체 참조한다. 아래는 '더 안쪽 경계까지 밀었을 때'의 모습.)
public interface ISaveGateway            // <- port, 안쪽에 위치
{
    void Persist(GameSnapshot snapshot);
    GameSnapshot Load();
}

public sealed class AdvanceToNightUseCase // <- Use Case (Interactor)
{
    private readonly ISaveGateway _save;
    public AdvanceToNightUseCase(ISaveGateway save) => _save = save; // 생성자 주입

    // 순수 계산 + port 호출. Time.deltaTime, MonoBehaviour, PlayerPrefs 모름.
    public GameSnapshot Execute(GameSnapshot current)
    {
        var next = current with { Phase = CyclePhase.Night };
        _save.Persist(next);   // 흐름은 밖으로 나가지만, 의존은 인터페이스(=안쪽)만 향함
        return next;
    }
}

// [바깥] Frameworks & Drivers 레이어 — 여기서만 엔진/파일 세부를 안다.
// 의존 방향: 이 파일은 안쪽(ISaveGateway)을 참조. 안쪽은 이 파일을 모름.
public sealed class JsonFileSaveAdapter : ISaveGateway   // <- adapter, 바깥이 구현
{
    public void Persist(GameSnapshot s) => System.IO.File.WriteAllText(Path, ToJson(s));
    public GameSnapshot Load() => FromJson(System.IO.File.ReadAllText(Path));
    // Path/ToJson/FromJson 등 프레임워크 세부는 전부 이 바깥 레이어에 격리
}

⚖ 트레이드오프 · 반론 · 유의

  • 'AI가 보일러플레이트를 대신 지니 클린 아키텍처가 유리하다'는 사용자 주장의 반론: AI가 인터페이스/어댑터를 '작성'하는 비용은 줄여도, 세션 논지대로 '검수 비용'은 오히려 커질 수 있음. 얇은 위임 레이어와 포트가 늘수록 리뷰어가 따라가야 할 간접 계층(indirection)이 늘고, 버그가 '어느 경계에서 났는지' 추적하는 인지 비용이 증가함. 즉 AI는 작성 비용을 옮길 뿐, 총비용을 자동으로 낮추지 않음.
  • 경계가 blast radius를 줄인다는 주장의 반례: 잘못 그은 경계는 오히려 blast radius를 키운다. 하나의 개념 변경이 Entity·UseCase·Port·Adapter·DTO 매핑을 동시에 건드리게 되는 'shotgun surgery'가 대표적. 특히 데이터 형태(포맷)가 자주 바뀌는 게임 초기에는 경계마다 DTO 변환이 마찰이 됨.
  • 과설계(over-engineering) 위험: 솔로~소규모 프로젝트에서 모든 시스템에 4레이어와 포트를 다는 것은 순비용일 수 있음. Martin도 '레이어 개수는 필요에 따라'라고 했지 '항상 4개 이상'이라고 하지 않음. Dusk Hollow처럼 '2단(로직 + Driver) + asmdef 경계 + 구체 참조'가 대개 최적점이며, 무리하게 포트를 도입하면 손해일 수 있음.
  • 정의의 정확성: 클린 아키텍처(2012 블로그/2017 책)는 Hexagonal(Cockburn), Onion(Palermo), DCI, BCE 등 선행 아키텍처의 '통합·재명명'에 가깝다. '완전한 독창'으로 서술하면 부정확함 — Martin 본인이 원문에서 이들을 인용하며 공통점이 '의존성 규칙'이라고 밝힘.
  • Unity 특유의 한계: MonoBehaviour 생명주기(Awake/Update)·직렬화·인스펙터 편집·씬 참조는 본질적으로 프레임워크에 묶임. '순수 코어 100%'는 게임에서 종종 비현실적이며(이 프로젝트도 로직 클래스가 UnityEngine을 참조), DOTS/ECS는 데이터 지향(값 중심)이라 오히려 객체지향형 포트/어댑터 패턴과 결이 다름 — 클린 아키텍처를 DOTS에 그대로 이식하려 하면 마찰이 생김.
  • 이 프로젝트에 대한 사실 정정: 초안은 Dusk Hollow가 클린 아키텍처를 '이미 실천 중'이라 했으나, 실제 경계는 DIP로 역전된 포트 없이 형제 어셈블리를 직접 참조하는 Humble Object + 어셈블리 방화벽이다. '클린 아키텍처를 지향하는 절충'이라고 표현하는 것이 정직함.
  • 출처 신뢰도: 'Functional Core, Imperative Shell'=Gary Bernhardt(그의 'Boundaries' 강연 / DestroyAllSoftware 스크린캐스트)는 검색으로 재확인함(신뢰 높음). 네 레이어 정의·의존성 규칙·'원은 도식일 뿐' 문구는 Martin 원문(blog.cleancoder.com, 2012-08-13)에 근거하나 이번 세션에서는 WebSearch 서버 과부하로 원문 원자 인용을 재확인하지 못함(지식 기반, 신뢰 중상). Hexagonal=Cockburn, Onion=Palermo, 'Humble Object' 패턴 귀속은 널리 통용되는 통설(신뢰 중간). 반면 Dusk Hollow 코드 사실(asmdef noEngineReferences=false, NpcDialogueService의 using UnityEngine, Npc 어셈블리의 형제 구체 참조, ADR-003 존재)은 이번 세션에서 파일을 직접 열어 확인함(신뢰 높음).

04 · CA의 비용

경계의 대가: 클린 아키텍처가 청구하는 비용과 "동심원"의 함정

클린 아키텍처는 경계를 명확히 하는 대가로 학습 비용, 인터페이스·DTO·매핑 보일러플레이트, 그리고 "레이어를 어떻게 나눌 것인가"라는 해석 편차를 청구합니다. 게임처럼 작고 성능에 민감한 프로젝트에서는 이 비용이 이득을 넘어설 수 있으므로, 원칙(의존성 규칙)만 지키고 세리머니는 필요할 때 도입하는 균형점이 현실적입니다.

첫째, 학습 비용과 개념적 오버헤드입니다. 클린 아키텍처는 의존성 규칙이라는 단순한 핵심을 갖지만, 이를 실전에서 구현하려면 의존성 역전(DIP), 경계 인터페이스, 유스케이스와 엔티티의 구분, 무엇보다 '제어 흐름은 바깥에서 안으로 가는데 컴파일타임 의존성은 안에서 바깥을 모른다'는 제어흐름-의존성 역전의 감각을 팀 전체가 공유해야 합니다. 이 정신 모형은 처음 접하는 개발자에게 결코 저렴하지 않습니다. 게임 개발자에게는 특히 낯설 수 있는데, Unity의 기본 사고방식(MonoBehaviour 하나에 데이터·로직·엔진 훅을 뭉쳐 넣고, 인스펙터 드래그로 참조를 잇는 방식)이 의존성 규칙과 사실상 정반대 방향을 가리키기 때문입니다. 결과적으로 '왜 이 인터페이스가 여기 있어야 하는가'를 매번 팀원(또는 6개월 뒤의 자신)에게 설명해야 하는 인지 세금이 붙습니다. 다만 이 학습 비용은 일회성 고정비에 가깝다는 반론도 성립합니다. 한 번 정신 모형을 갖춘 팀에게는 매 기능마다 '이건 어디 두지'를 재발명하지 않아도 되는 이득으로 상각되며, 이 점은 뒤의 균형점 논의에서 다시 다룹니다.

둘째, 사용자 메모의 핵심인 보일러플레이트 폭증, 즉 '인터페이스가 계속 늘어난다'입니다. 안쪽 레이어가 바깥(DB, 파일, 엔진, UI)에 의존하지 않으려면, 안쪽에 포트(인터페이스)를 선언하고 바깥에서 어댑터로 구현해야 합니다. 그래서 저장 기능 하나를 추가할 때마다 ISaveRepository 같은 인터페이스, 그 구현체, 도메인 모델과 영속 모델을 잇는 DTO, 그리고 둘을 오가는 매퍼가 세트로 생겨납니다. 비판자들이 지적하는 전형적 실패 양상은 '데이터를 그대로 통과시키기만 하는 인터페이스 레이어'와 '아무 변환도 하지 않는 매핑 함수'가 프로젝트를 뒤덮는 것입니다. 게임 맥락으로 옮기면, 인벤토리 아이템 하나에 도메인 엔티티·ScriptableObject 데이터·세이브 DTO·뷰모델이 각각 존재하고 그 사이를 매퍼가 오가는 상황이 됩니다. 표현력이 늘어난 만큼 '읽고 검수해야 할 표면적'도 함께 늘어난다는 점이 핵심 비용입니다. 공정하게 반대편을 세우면, 이 '통과용' 매핑이 실은 값을 하는 경우도 있습니다. 영속 모델(세이브 포맷)과 도메인 모델을 분리해 두면, 세이브 파일 포맷을 바꿀 때 도메인이 흔들리지 않습니다. 즉 지금은 동일해 보이는 두 모델이 '서로 다른 이유로 변하는' 축이라면 분리는 정당합니다. 판단 기준은 '지금 같아 보이는가'가 아니라 '변화의 이유가 같은가'입니다.

셋째, 작은 프로젝트와 게임에서의 과설계(YAGNI 위반) 위험입니다. 클린 아키텍처의 인터페이스 상당수는 '미래의 교체 가능성'에 값을 지불하는 옵션 계약입니다. 그런데 솔로~소규모 게임에서 데이터베이스를 교체하거나 렌더 파이프라인을 통째로 바꾸는 시나리오는 거의 발생하지 않습니다. 구현체가 사실상 하나뿐이고 테스트 대역조차 두지 않는 인터페이스는 순수한 간접층(indirection)이며, 코드를 따라가려면 인터페이스에서 구현으로 점프를 한 번 더 해야 하므로 오히려 읽기 비용을 올립니다. YAGNI('필요해질 때까지 만들지 말라')와 충돌하는 지점이고, 실제로 다수의 실무 글이 '소규모 프로젝트에서 엄격한 클린 아키텍처는 이득보다 유지보수 부담'이라고 비판합니다. 다만 이 명제에는 정직한 반론이 있습니다. 인터페이스의 값은 '미래 교체'만이 아니라 '지금 당장의 테스트 가능성'에서도 나옵니다. 구현체가 하나여도 테스트 대역(fake/in-memory)이라는 두 번째 구현이 생기면 그 인터페이스는 이미 값을 회수한 것입니다. 따라서 YAGNI 비판은 '테스트 대역조차 필요 없는, 순수 통과용 경계'에 한정해야 정확하며, Dusk Hollow(솔로 4~6개월)에서도 순수 로직에 붙는 경계까지 뭉뚱그려 잘라내면 오히려 손해입니다.

넷째, 사용자가 정확히 짚은 '동심원'의 경직성과 해석 편차입니다. 동심원 다이어그램은 방향(안쪽=고수준 정책, 바깥쪽=저수준 세부)만 규정할 뿐, '무엇이 어느 원에 속하는가'는 규정하지 않습니다. 그래서 같은 코드를 두고 A는 '이건 유스케이스야', B는 '이건 도메인 서비스야', C는 '이건 인프라 어댑터야'라고 서로 다르게 분류하고, 이 경계가 팀마다·사람마다·시점마다 흔들립니다. 사용자의 '해석이 달라짐'은 바로 이 현상을 가리키며, 이는 클린 아키텍처에 대해 널리 지적되는 약점입니다(단, '약점'이라는 규정은 근거 있는 의견이지 정리된 정설은 아닙니다). 규칙이 느슨한 만큼 일관성은 팀의 규율에 의존하고, 규율이 흔들리면 경계는 '명확한 구조'가 아니라 '끝없는 배치 논쟁'의 원천이 됩니다. AI 협업 관점에서도 이 애매함은 위험한데, 경계 기준이 문서로 못 박혀 있지 않으면 AI가 매번 다른 레이어에 코드를 배치해 오히려 구조가 무너질 수 있습니다. 반대로, 이 '느슨함'을 유연성으로 옹호하는 시각도 있습니다. Uncle Bob이 원의 개수를 강제하지 않은 것은 도메인마다 적절한 분할이 다르기 때문이며, 규칙이 배치를 강제하지 않는 것은 결함이 아니라 의도된 여백이라는 것입니다. 결국 이 여백을 문서(ADR/매니페스트)로 메우면 유연성으로, 방치하면 논쟁의 씨앗으로 귀결됩니다.

다섯째, 성능 민감한 게임에서의 추상화 부담과 균형점입니다. 인터페이스 디스패치(가상 호출), 레이어를 넘나드는 객체 매핑, 방어적 복사는 프레임당 수천 번 도는 핫패스에서 GC 할당과 캐시 미스로 나타날 수 있습니다. 다만 이 우려는 반드시 프로파일링으로 확인해야 하며, 핫패스가 아닌 곳에서 '추상화=느림'으로 일반화하는 것은 조기 최적화입니다. 흥미롭게도 이 성능 우려는 클린 아키텍처를 게임에 옹호하는 쪽조차 '핫패스에 한해 정당한 비판'으로 인정하는 경향이 있으며, 흔한 절충은 '설계가 안정될 때까지는 유연하게 두고, 이후 핫패스의 추상화를 걷어내 성능을 회복한다'는 것입니다. 실용적 균형점은 이렇습니다. (1) 강제 규칙은 의존성 방향 하나로 좁히고, 원의 개수와 인터페이스는 실제 교체·테스트 필요가 증명될 때만 도입합니다. (2) 세이브/로드·시간 상태머신·퍼즐 규칙 같은 '순수 로직'은 MonoBehaviour와 분리된 순수 C# 코어로 두어 EditMode 테스트를 붙이되(여기서 경계의 이득이 가장 큼), 렌더·입력·물리 핫패스는 DOTS/ECS의 데이터 지향 배치를 따르며 추상화를 최소화합니다. (3) 이 배치 기준을 ADR과 컨트롤 매니페스트에 명문화해 '해석 편차'를 코드가 아니라 문서로 제거합니다. 이 절충안 자체에도 함정이 있는데, '나중에 걷어낸다'는 정리 작업은 실무에서 자주 미뤄져 부채로 굳으므로, 걷어낼 지점을 처음부터 ADR에 기록해 두는 편이 안전합니다.

✍ 세션에서 받아적은 메모

“clean architecture 해석이 달라짐 … 레이어를 세분화하여 경계가 명확하지만 학습 비용이 높음. 의존이 필요하여 인터페이스가 계속 늘어나고 클린 아키텍쳐 동심원이라는 문제가 있다.”

✅ 풀어 정리 & 관점 구분

사실과 의견을 먼저 구분하겠습니다. "클린 아키텍처"라는 용어와 그 핵심 규칙은 Robert C. Martin(Uncle Bob)이 2012년 블로그 글("The Clean Architecture", cleancoder.com)과 이후 저서 『Clean Architecture』(2017)에서 제시한 것으로, 여기에는 동심원(concentric circles) 다이어그램과 단 하나의 핵심 규칙인 의존성 규칙(The Dependency Rule)이 등장합니다. 의존성 규칙의 정의는 "소스 코드 의존성은 오직 안쪽을 향해야 하며, 안쪽 원은 바깥쪽 원에 대해 아무것도 알아서는 안 된다"입니다. 여기까지는 1차 출처에서 검증되는 사실입니다. 반면 사용자가 지적한 "학습 비용이 높다 / 인터페이스가 계속 늘어난다 / 동심원이 문제다"는 평가는 의견에 가깝지만, 업계에서 광범위하게 공유되는 비판이라는 점에서 근거 있는 의견으로 분류하는 것이 정확합니다. 또 하나 바로잡을 오해는, 클린 아키텍처가 명시적으로 요구하는 것은 "의존성 방향" 하나뿐이며, 4개의 원·유스케이스 인터랙터·리포지토리 인터페이스·DTO와 매퍼는 규칙이 아니라 그 규칙을 지키기 위해 흔히 쓰이는 구현 관례라는 점입니다. Uncle Bob 본인도 원본 글에서 "이 네 개만 있어야 한다는 규칙은 없다(there's no rule that says you must always have just these four)"고 명시했으며, 동심원 다이어그램 자체가 "도식적(schematic)"이라고 밝혔습니다. 즉 인터페이스 폭증과 매핑 보일러플레이트는 아키텍처가 강제하는 것이 아니라, 사람들이 도그마적으로 적용할 때 발생하는 결과입니다. 사용자가 느낀 "인터페이스가 계속 늘어난다"는 감각은 실재하지만, 그 원인은 아키텍처의 본질보다 "적용 방식"에 있다는 점을 분리해서 봐야 합니다. 다만 한 가지 공정하게 덧붙이면, "의존성 방향을 지키려면 안쪽에 포트(인터페이스)를 두어야 한다"는 것 자체는 관례가 아니라 규칙에서 거의 필연적으로 따라나오는 귀결이므로, 인터페이스의 존재 자체까지 "순수한 도그마"로 치부하는 것은 과합니다. 문제가 되는 것은 인터페이스의 "존재"가 아니라 "개수와 세분화 정도"입니다.

📌 핵심 정리

  • 의존성 규칙만이 클린 아키텍처의 강제 사항이다: '소스 의존성은 안쪽으로만, 안쪽은 바깥쪽을 모른다'. 4개의 원·유스케이스·리포지토리 인터페이스·DTO·매퍼는 규칙이 아니라 관례이며, Uncle Bob도 원본 글에서 '이 네 개만 있어야 한다는 규칙은 없다'고 했다(1차 출처 사실).
  • 단, '안쪽에 포트를 둔다'는 것 자체는 규칙에서 따라나오는 귀결이다. 문제는 인터페이스의 '존재'가 아니라 '개수와 세분화'다.
  • 인터페이스 폭증과 매핑 보일러플레이트는 아키텍처의 본질이 아니라 도그마적 적용의 결과다. 테스트 대역조차 없는 순수 통과용 인터페이스만이 순전한 읽기·검수 비용이다.
  • 동심원의 여백은 '무엇이 어느 원인가'를 규정하지 않는다는 점이다. 이는 결함이자 의도된 유연성의 양면이며, 문서(ADR/매니페스트)로 메우면 유연성, 방치하면 '해석 편차'다.
  • 게임/솔로 스코프에서 '거의 오지 않을 미래 교체'만을 위한 경계는 YAGNI와 충돌한다. 하지만 '지금 테스트 가능성'을 주는 경계는 YAGNI 비판의 대상이 아니다.
  • 성능 핫패스에서 가상 호출·객체 매핑·방어적 복사는 GC/캐시 비용이 될 수 있으나, 핫패스가 아니라면 조기 최적화다. 판단은 프로파일링이 선행해야 한다.
  • 실용적 균형점: 강제 규칙은 의존성 방향 하나로 좁히고, 순수 로직만 순수 C# 코어로 분리해 EditMode 테스트를 붙이며, 핫패스는 DOTS 데이터 지향으로 두고, 레이어 배치 기준과 '걷어낼 지점'을 ADR/컨트롤 매니페스트에 명문화한다.

예시 (csharp) · 구현체가 사실상 하나뿐인 경계 인터페이스 — 의존성 규칙은 지키지만 '순수 간접층'이 되기 쉽다. 이 인터페이스의 값은 오직 '엔진 없이 세이브 로직을 EditMode에서 테스트할 수 있는가'로 정당화되어야 한다.

// 도메인(안쪽)이 선언하는 포트 — 바깥(파일/엔진)을 모른다
public interface ISaveRepository {
    SaveData Load();
    void Save(SaveData data);
}

// 인프라(바깥)의 어댑터 — 프로덕션의 유일한 구현체
public sealed class JsonFileSaveRepository : ISaveRepository {
    private readonly string _path;
    public JsonFileSaveRepository(string path) => _path = path;
    public SaveData Load() => JsonConvert.DeserializeObject<SaveData>(File.ReadAllText(_path));
    public void Save(SaveData d) => File.WriteAllText(_path, JsonConvert.SerializeObject(d));
}

// 이득이 실현되는 지점: 파일 I/O 없이 순수 로직을 결정론적으로 테스트
// InMemorySaveRepository가 '두 번째 구현'이 되는 순간, 이 인터페이스는
// '미래 교체'가 아니라 '지금 테스트 가능성'만으로 이미 값을 회수한다.
[Test]
public void SaveThenLoad_RoundTrips() {
    var repo = new InMemorySaveRepository();      // 테스트용 두 번째 구현체
    var svc  = new SaveService(repo);             // 도메인 로직은 포트에만 의존
    svc.Persist(new SaveData { Day = 3 });
    Assert.AreEqual(3, repo.Load().Day);
}

⚖ 트레이드오프 · 반론 · 유의

  • '게임에서 클린 아키텍처는 과하다'는 전면적 명제는 스코프 의존적입니다. 라이브옵스가 붙는 장수 라이브 게임, 여러 팀이 같은 코드베이스를 만지는 조직에서는 명확한 계약과 경계의 이득이 비용을 넘어섭니다. Dusk Hollow(솔로 4~6개월)에 대한 판단을 대규모 프로젝트로 일반화하면 안 됩니다.
  • '인터페이스=비용'이라는 프레이밍은 테스트 이득을 과소평가할 수 있습니다. 구현체가 하나여도, 그 경계 덕분에 순수 로직을 엔진 없이 EditMode에서 결정론적으로 테스트할 수 있다면 인터페이스 값은 이미 회수된 것입니다. '읽기 비용 증가'와 '테스트 가능성 확보'는 저울의 양쪽이며, 어느 쪽이 무거운지는 그 코드가 순수 로직인지 얇은 접착 코드인지에 달려 있습니다.
  • 성능 비판은 측정 없이 일반화하면 위험합니다. 프레임당 수천 번 도는 핫패스가 아니라면 가상 호출 한두 번의 비용은 무시 가능한 수준일 때가 많고, '추상화=느림'은 프로파일링으로 확인하기 전까지는 추정에 불과합니다(조기 최적화 경계).
  • 이 세션 전체의 상위 논지인 'AI가 보일러플레이트를 대신 져 주므로 클린 아키텍처가 유리하다'는 사용자의 의견이며, 여기에도 반론이 성립합니다. AI가 인터페이스를 값싸게 '생성'해도, 늘어난 간접층과 매핑을 '검수'하는 비용은 여전히 사람 몫입니다. 오히려 AI가 경계 기준 없이 코드를 배치하면 동심원의 '해석 편차'가 증폭될 수 있어, AI 시대에는 경계의 문서화(ADR/매니페스트)가 아키텍처 채택보다 먼저 와야 한다는 것이 이 노트의 입장입니다.
  • 출처 신뢰도: 의존성 규칙과 동심원의 정의, '네 개만 있어야 한다는 규칙은 없다'·'다이어그램은 도식적'이라는 진술은 Uncle Bob의 2012 블로그 글/저서에서 확인되는 1차 사실입니다(WebSearch로 원문 존재 재확인). 반면 '보일러플레이트 폭증', 'YAGNI 위반', '통과용 인터페이스/무의미한 매퍼', '동심원은 클린 아키텍처의 약점'은 다수의 실무 블로그에서 반복되는 광범위한 비판이나, 저자별 강도와 맥락이 달라 '지배적 의견'으로 보되 정설·보편 진리로 단정하지 않았습니다.
  • 게임에서의 '설계가 안정된 뒤 추상화를 걷어낸다'는 절충은 실무에서 자주 미뤄지다 부채로 굳는 경향이 있습니다. 이론적 절충안이 실제로 실행된다는 보장은 없으며, 그래서 '걷어낼 지점'을 처음부터 ADR에 기록해 두는 보완이 필요합니다.
  • Hexagonal(Ports & Adapters, Alistair Cockburn)·Onion(Jeffrey Palermo)·Clean(Martin)은 '의존성을 안쪽/도메인으로 향하게 한다'는 공통 목표를 공유하는 사촌 격 아키텍처입니다. 본 노트에서 '포트'라는 용어를 쓴 것은 Hexagonal 어휘를 빌린 것이며, 세 아키텍처를 동일시한 것은 아닙니다.

05 · AI가 바꾸는 저울

AI가 보일러플레이트를 대신 쓰면, 클린 아키텍처의 저울이 기우는가

AI가 인터페이스·어댑터·보일러플레이트를 대신 써 준다면 클린 아키텍처의 "작성 비용"이 낮아지므로 경계가 명확한 설계의 순이득이 커진다 — 이는 충분히 설득력 있는 관점입니다. 다만 검수 비용은 그대로 남고, 잘못된 추상화·비대해진 경계·비관례적 구조는 AI가 있어도 오히려 부채가 될 수 있다는 반론을 함께 저울에 올려야 합니다.

먼저 사용자 관점을 가장 강한 형태로 세워 보겠습니다(steelman). 클린 아키텍처를 실무에서 꺼리게 만드는 가장 현실적인 이유는 흔히 '보일러플레이트 세금'입니다. Entities와 Use Case가 바깥 세계(DB, UI, 프레임워크)를 직접 알지 못하게 하려면, Alistair Cockburn의 헥사고날 아키텍처(Ports & Adapters — 2005년경 그의 위키에 공개된 이후 'Ports and Adapters'라는 이름이 정착)가 말하는 포트(인터페이스)와 어댑터(구현)를 계속 만들어야 합니다. 리포지토리 인터페이스, 프리젠터 출력 포트, DTO 매핑, 어댑터 클래스 — 기능 하나에 파일 여러 개가 붙습니다. 만약 이 반복적이고 규칙적인 코드를 AI가 정확히·일관되게·지치지 않고 생성한다면, 클린 아키텍처 채택을 막던 가장 큰 진입 장벽 하나가 실제로 낮아지는 것은 맞습니다. 이 지점에서 사용자의 직관은 타당합니다.

더 깊은 근거도 있습니다. 클린 아키텍처가 지향하는 '경계가 명확하고 안쪽이 순수한 구조'는 Gary Bernhardt가 'Boundaries' 강연(SCNA/RubyConf 2012)에서 정식화한 'Functional Core, Imperative Shell' — 부수효과 없는 순수 코어를 얇은 명령형 껍질이 감싸는 구조 — 와 사실상 같은 방향을 가리킵니다. 그리고 이런 구조는 AI에게 특히 친화적입니다. 순수한 계산 영역은 입력→출력이 값으로 닫혀 있어 AI가 문맥을 적게 읽고도 파악·수정할 수 있고, 인터페이스라는 계약이 명시되어 있으면 '무엇을 구현해야 하는지'를 AI가 추측하지 않아도 됩니다. 또한 계층이 분리되어 있으면 AI가 한 번에 건드리는 수정 반경(blast radius)이 한 레이어 안으로 제한되는 경향이 있어, 구조가 그 자체로 안전망 역할을 합니다. 즉 '경계가 명확하다'는 성질은 사람에게만이 아니라 AI 협업에서도 순이득이 있다는 주장은 개념적으로 일관됩니다.

그러나 저울의 반대편도 정직하게 올려야 합니다. 첫째, 작성 비용이 낮아진다고 검수 비용이 함께 낮아지지 않으며 오히려 늘 수 있습니다. AI가 파일 여덟 개짜리 유스케이스를 30초에 생성하면, 사람은 그 여덟 파일이 의존성 규칙을 위반하지 않았는지(예: 안쪽 Entity가 실수로 바깥쪽 어댑터 타입을 참조하지 않았는지)를 여전히 눈으로 확인해야 합니다. AI 시대에 리뷰가 병목이 된다는 이 세션의 대전제를 여기에 그대로 적용하면, 경계가 많은 아키텍처는 생성은 싸지만 '검증해야 할 경계의 수'가 늘어 검수 총량이 오히려 커질 수 있습니다. 생성 속도가 리뷰 속도를 앞지를수록 이 격차는 벌어집니다. 게다가 순수 코어가 '읽기 편하다'는 성질은 역으로 리뷰어가 '깔끔해 보인다'는 이유로 검증을 대충 넘기게 만드는 함정(verification theater)이 될 수도 있습니다 — 보기 좋은 구조가 곧 옳은 구조는 아닙니다.

둘째, 잘못된 추상화는 AI가 있어도, 아니 AI가 있어서 더 빠르게 축적되는 부채입니다. 클린 아키텍처의 진짜 어려움은 인터페이스를 '타이핑'하는 것이 아니라 '경계를 어디에 그을지' 정하는 판단인데, 이건 AI가 대신 져 주기 가장 어려운 부분입니다. 경계가 도메인의 실제 이음새와 어긋나면, 기능 하나를 바꿀 때 여러 레이어를 동시에 수정해야 하는 상황이 벌어집니다 — 경계가 blast radius를 줄이기는커녕 키우는 경우입니다. 게다가 AI가 그 잘못된 어댑터·포트를 순식간에 대량 복제해 두면, 나중에 추상화를 되돌리는 리팩터링 비용은 사람이 손으로 쌓았을 때보다 오히려 커집니다. 더 미묘한 위험은, AI가 만든 경계가 '규칙을 형식적으로는 지키지만 도메인적으로는 틀린' 경우입니다 — 컴파일도 되고 의존 방향도 맞지만 개념이 어긋난 코드는 겉보기 정합성 때문에 리뷰를 통과하기 더 쉽습니다. 셋째, AI는 널리 쓰이는 관례에 강하고 커스텀 경계에 약합니다. 표준적인 리포지토리 패턴은 잘 다루지만, 프로젝트 고유의 비관례적 레이어 규약을 주면 규칙을 조용히 어기거나 경계를 가로지르는 지름길 코드를 만들어 낼 위험이 있습니다. 이는 오히려 검수 부담을 키웁니다.

Unity/게임 맥락에서 이 저울을 실제로 달아 보면 결론은 '전부 아니면 전무'가 아니라 '어디에 경계를 둘 것인가'입니다. MonoBehaviour는 프레임워크에 강하게 결합된 바깥 껍질(imperative shell / 어댑터)로, ScriptableObject는 데이터의 단일 출처로, 그리고 순수 C# 클래스(시간-사이클 상태 머신, 아이템 이중기능 해석기, 퍼즐 상태, 세이브/로드 직렬화 같은 것)는 MonoBehaviour에 의존하지 않는 함수형 코어로 두는 절제된 분리는, 솔로~소규모 프로젝트에서도 EditMode 테스트로 코어를 독립 검증할 수 있게 해 주는 명백한 순이득입니다. 이 프로젝트의 테스트 프리퍼런스가 '로직 시스템 50% 커버리지'를 요구하는 것도 이 코어를 겨냥합니다. 반대로 DOTS/ECS 같은 데이터 지향 설계는 그 자체가 이미 데이터-로직 분리를 강제하므로 별도의 포트/어댑터 층을 겹겹이 얹으면 과설계가 되기 쉽습니다. 정리하면, AI가 보일러플레이트를 져 준다는 이유로 풀(full) 클린 아키텍처의 동심원 네 겹을 통째로 도입하기보다는, '함수형 코어 / 명령형 껍질'이라는 최소한의 경계 하나를 확실히 긋고, 그 경계가 실제로 검증·수정을 싸게 만드는지 프로젝트에서 측정하며 필요할 때만 층을 늘리는 편이 이 세션의 '총비용 최소화' 논지에 더 충실합니다. 사람이 감독(supervisor)이 된다는 것은 곧 '어디에 경계를 그을지'와 '경계가 지켜졌는지'를 판단하는 역할을 떠맡는다는 뜻이며, 그 두 가지는 AI가 대신 져 줄 수 없는, 아키텍처의 진짜 비용입니다.

✍ 세션에서 받아적은 메모

“AI 가 코드를 쓴다면 부담이 적어지기 떄문에 경계가 명확한 클린 아키텍쳐를 채택할거 같다.”

✅ 풀어 정리 & 관점 구분

먼저 사실과 의견을 구분하겠습니다. 클린 아키텍처(Clean Architecture)는 Robert C. Martin이 2012년 블로그 글과 2017년 동명의 책에서 정리한 구조로, 핵심은 네 겹의 "동심원(concentric circles)"과 "의존성 규칙(Dependency Rule)"입니다. 규칙 자체는 확립된 정의입니다 — 소스 코드의 의존성은 오직 안쪽(고수준 정책)을 향해야 하며, 안쪽 원은 바깥쪽 원의 존재를 전혀 알아서는 안 됩니다. 이 경계를 넘을 때는 안쪽이 인터페이스를 정의하고 바깥쪽이 구현하는 의존성 역전(Dependency Inversion)을 씁니다. 여기까지는 정의입니다. 반면 "AI가 짜 주니 클린 아키텍처를 채택하겠다"는 것은 사용자의 관점(의견)이며 검증된 결론이 아닙니다. 그리고 바로잡을 오해가 하나 있습니다: 메모의 논리는 "AI가 코드를 쓰면 부담이 적어진다"인데, 여기서 줄어드는 것은 어디까지나 '작성' 부담입니다. 클린 아키텍처의 총비용은 (1) 경계를 어디에 그을지 정하는 설계 판단, (2) 생성된 코드가 규칙을 실제로 지켰는지 확인하는 검수, (3) 시간이 지나며 경계가 옳았는지 재평가하는 유지보수를 모두 포함합니다. AI가 값싸게 낮추는 것은 이 셋 중 주로 '타이핑'이지 판단과 검수가 아닙니다. 저울의 한쪽 접시(작성)만 가벼워졌다고 저울 전체가 유리한 쪽으로 기운다고 단정할 수는 없습니다.

📌 핵심 정리

  • 사용자 주장(의견): AI가 보일러플레이트·인터페이스·어댑터를 대신 작성/유지하면 클린 아키텍처의 주된 비용이 낮아져, 경계가 명확한 설계의 순이득이 커진다 — 비용-편익 저울이 기운다.
  • 확립된 정의(사실): 클린 아키텍처(R.C. Martin)의 핵심은 동심원 4겹 + 의존성 규칙(의존성은 오직 안쪽을 향한다). 경계 통과는 의존성 역전으로 처리. 헥사고날/포트&어댑터는 Cockburn, '함수형 코어/명령형 껍질'은 Bernhardt('Boundaries', 2012).
  • 저울에서 낮아지는 것은 '작성' 비용뿐. 경계 위치를 정하는 설계 판단과 규칙 준수를 확인하는 검수는 AI가 대신 지기 어렵다.
  • 반론 (a): 검수 비용은 AI가 짜도 남고 오히려 늘 수 있다 — 검증할 경계의 수가 많아지면 리뷰 총량이 커진다.
  • 반론 (b): '깔끔해 보이는' 순수 코어와 형식적으로만 규칙을 지킨 코드는 리뷰를 헐겁게 만드는 함정(verification theater)이 될 수 있다.
  • 반론 (c): 잘못된 추상화는 AI가 있어서 더 빠르게 대량 복제되어 되돌리기 어려운 부채가 된다.
  • 반론 (d): 경계가 도메인 이음새와 어긋나면 한 기능 변경이 여러 레이어를 건드려 blast radius가 오히려 커진다.
  • 반론 (e): AI는 표준 관례에 강하고 비관례적 커스텀 경계에 약해, 규칙을 조용히 어겨 검수 부담을 키울 수 있다.
  • 실용 결론(게임/솔로 스케일): 동심원 4겹을 통째로 도입하기보다 'MonoBehaviour=껍질 / 순수 C# 코어=함수형 코어 / ScriptableObject=데이터' 최소 경계 하나를 확실히 긋고, EditMode 테스트로 코어를 독립 검증하며 필요할 때만 층을 늘린다. DOTS/ECS는 이미 데이터-로직 분리를 강제하므로 추가 층은 과설계 위험.

예시 (csharp) · 경계 최소화 예: MonoBehaviour(명령형 껍질)는 순수 C# 코어(함수형 코어)를 값으로만 호출한다. 코어는 Unity에 의존하지 않아 EditMode 테스트로 독립 검증되고, AI도 계약(입력→출력)만 보고 안전하게 다룰 수 있다. 이 최소 경계 하나가 동심원 4겹보다 솔로 스케일에서 검증·수정을 싸게 만든다.

// 함수형 코어 — Unity 비의존, 순수 계산. AI가 문맥 없이도 파악/수정 가능.
public static class DayNightResolver
{
    public static Phase Resolve(float clock01) =>
        clock01 < 0.75f ? Phase.Day : Phase.Night; // 값 in, 값 out
}

// 명령형 껍질(어댑터) — 프레임워크 결합은 여기로 격리.
public sealed class DayNightCycle : MonoBehaviour
{
    void Update()
    {
        var phase = DayNightResolver.Resolve(_clock01); // 경계를 값으로 통과
        _lantern.SetActive(phase == Phase.Night);
    }
}

// EditMode 테스트 — 씬/재생 없이 코어만 검증.
[Test] public void Resolve_AtDusk_ReturnsNight()
    => Assert.AreEqual(Phase.Night, DayNightResolver.Resolve(0.8f));

⚖ 트레이드오프 · 반론 · 유의

  • 이 결론('AI가 쓰니 클린 아키텍처가 유리하다')은 사용자의 관점이자 아직 프로젝트에서 측정으로 검증되지 않은 가설입니다. 실제 순이득 여부는 팀·도메인·AI 도구 성숙도에 따라 달라집니다.
  • 핵심 트레이드오프: 클린 아키텍처는 생성 비용을 낮추더라도 '검증해야 할 경계'를 늘립니다. AI 시대에 리뷰가 병목이라는 이 세션의 전제를 따르면, 경계 증가가 총비용을 낮출지 높일지는 리뷰 자동화 수준에 크게 좌우됩니다.
  • '경계가 blast radius를 줄인다'는 것은 경계가 도메인의 실제 이음새와 일치할 때만 성립합니다. 어긋난 경계는 오히려 변경 반경을 키웁니다 — 경계의 개수가 아니라 위치가 관건입니다.
  • 출처 확신도: R.C. Martin의 의존성 규칙·동심원(2012 블로그/2017 책), Bernhardt의 'Functional Core, Imperative Shell'('Boundaries' 강연, SCNA/RubyConf 2012)은 확인했습니다(Bernhardt 강연 출처는 라이브 검색으로 재확인). Cockburn의 Ports & Adapters는 '2005년경 위키 공개 후 명칭 정착'까지가 신뢰할 만하며, 초안에 있던 '1994년 착안'은 널리 인용되나 1차 출처로 확증하지 못해 삭제했습니다(불확실). 웹 검색 서버 과부하(529)로 Cockburn·Humble Object 항목은 라이브 재검증을 완료하지 못했습니다.
  • 'AI가 커스텀 경계를 표준 관례보다 못 다룬다' 및 'verification theater' 관찰은 일반적 경험칙에 기반한 정성적 주장으로, 정량 근거는 제시하지 못했습니다(불확실).
  • 'Humble Object' 패턴(테스트하기 어려운 껍질에서 로직을 분리)은 흔히 Michael Feathers가 용어를 제시하고 Gerard Meszaros가 xUnit Test Patterns(2007)에서 카탈로그화한 것으로 귀속됩니다(라이브 재확인은 못 함). 이 노트에서 직접 인용하지는 않았으나, 함수형 코어/명령형 껍질과 같은 계열의 테스트 전략임을 밝혀 둡니다.
  • 스케일 의존성: 위 실용 결론은 솔로~소규모 2D 프로젝트(Dusk Hollow) 기준입니다. 대규모 팀·장수 라이브 서비스에서는 풀 클린 아키텍처의 경계 비용이 정당화될 여지가 더 큽니다. 스케일을 바꾸면 저울추도 바뀝니다.

06 · 함수형·데이터 중심

함수형 코어와 데이터 중심: 값으로 넘기고, 순수 함수로 처리한다

불변 값(데이터)을 API에 넘겨 순수 함수로 처리하면 부작용이 사라지고, 독립 단위 테스트와 AI의 문맥 파악이 함께 쉬워집니다. 다만 "함수형/데이터 지향"과 "인터페이스 지향 클린 아키텍처"는 강조점이 다르므로, 그 긴장은 정직하게 짚어야 합니다.

출발점은 "값으로 넘긴다"는 한 문장입니다. 함수에 넘기는 입력이 불변 값(순수 데이터)이고 반환도 값이면, 그 함수의 동작은 오직 인자에만 의존합니다. 숨은 상태나 시점 의존이 없으니 테스트는 "이 입력을 주면 이 출력이 나온다"를 단언하는 것으로 끝납니다. 목(mock)도, 씬(scene) 로딩도, 프레임 진행도 필요 없습니다. 이것이 Bernhardt가 말한 함수형 코어의 실질적 이득입니다. 코어는 순수 함수로 판단만 하고, 그 판단 결과인 값을 명령형 껍데기가 받아 실제 부작용(저장, 렌더, 네트워크)을 집행합니다. 유니티에 대응시키면 껍데기는 MonoBehaviour의 Update/OnTriggerEnter 같은 진입점이고, 코어는 그 안에서 호출되는 static 순수 함수 뭉치입니다.

두 번째로, 왜 이 구조가 "독립적으로 테스트하기 좋은가"를 유니티 관점에서 구체화하면 이렇습니다. 유니티의 Play Mode 테스트는 실제 런타임 루프를 돌려야 해 느리고 불안정하며, MonoBehaviour는 GameObject 수명주기와 씬 컨텍스트에 묶여 있어 격리가 어렵습니다. 반대로 순수 함수는 Edit Mode 테스트에서 엔진 부팅 없이 밀리초 단위로 수천 번 돌릴 수 있습니다. 프로젝트 규칙(technical-preferences.md)이 요구하는 시간-사이클 상태 머신, 아이템 이중 기능 해석기, 퍼즐 상태 전이, 세이브/로드 직렬화 같은 로직 시스템의 50% 커버리지 목표는, 이 로직들이 MonoBehaviour 밖의 순수 함수로 나와 있을 때 현실적으로 달성 가능합니다. 반대로 로직이 Update() 안에 흩어져 있으면 커버리지는 사실상 Play Mode 통합 테스트에 인질로 잡힙니다.

세 번째로, 데이터를 한곳에 모으는 실천은 유니티에서 두 축으로 나타납니다. 정적 설정 데이터는 ScriptableObject로 자산화하여 밸런스 값·아이템 정의·시간 곡선을 코드가 아닌 데이터 자산으로 외부화합니다(coding-standards의 "게임플레이 값은 데이터 주도" 규칙과 정확히 맞물립니다). 런타임 상태 데이터는 가급적 순수 struct/record 스냅샷으로 모아, 순수 함수가 (상태, 입력) → (다음 상태, 이벤트 목록)을 계산하도록 만듭니다. 그러면 MonoBehaviour는 그 다음 상태를 화면과 물리에 반영하는 얇은 껍데기로 축소됩니다. 이 패턴은 사실 테스트 문헌의 'Humble Object' 패턴과 같은 얼개입니다. 계보를 정확히 하면, Michael Feathers가 2002년 논문 "The Humble Dialog Box"에서 "테스트하기 어려운 GUI 요소의 로직을 테스트 가능한 별도 객체로 빼낸다"는 아이디어를 처음 제시했고, Gerard Meszaros가 xUnit Test Patterns(2007)에서 이를 GUI를 넘어 일반화해 'Humble Object'라는 이름을 붙였습니다(두 출처·연도 검색 확인). 즉 경계에 붙은 부분을 테스트가 필요 없을 만큼 겸손하게 비우고, 로직을 테스트 가능한 별도 단위로 빼내는 것입니다. 함수형 코어/명령형 껍데기는 이 패턴을 아키텍처 스케일로 확장한 이름으로 볼 수 있습니다.

네 번째로, DOD/DOTS와의 관계는 겹치되 동일하지 않습니다. Unity DOTS/ECS는 컴포넌트(IComponentData struct = 순수 데이터, 메서드 없음)와 시스템(ISystem = 데이터를 일괄 변환하는 로직)을 강제로 분리한다는 점에서 "데이터와 로직 분리"라는 사용자님의 지향과 구조적으로 같은 방향입니다. 다만 DOTS의 일차 동기는 캐시 친화 메모리 레이아웃과 Burst/Job 기반 대량 병렬 성능이지, 테스트 용이성이 아닙니다. Dusk Hollow는 2D 스토리북 컷아웃 퍼즐 호러의 솔로~소규모 프로젝트이고 성능 예산도 여유가 있으므로(엔티티 수천 개를 병렬 처리할 일이 거의 없음), DOTS의 러닝코스트와 툴링 부담을 감수할 이유는 약합니다. 여기서 취할 것은 DOTS 프레임워크 자체가 아니라 그 철학, 즉 "데이터는 데이터로 모으고 로직은 순수 변환으로"라는 원칙을 평범한 C#(POCO struct + static 함수 + ScriptableObject)으로 구현하는 쪽입니다.

마지막으로, 이것이 메모의 큰 논지(AI 시대엔 검수 비용이 상대적으로 커진다)와 어떻게 연결되는지입니다. 순수 함수는 입출력이 값이라 계약(contract)이 서명 하나에 거의 다 드러납니다. 리뷰어(사람이든 AI든)가 "이 함수가 무엇을 하는가"를 판단할 때 추적해야 할 숨은 상태·전역 부작용·시점 의존이 없으므로, 검수의 문맥 로딩 비용이 낮아집니다. AI에게 넘길 때도 함수 하나와 그 테스트 케이스만 컨텍스트로 주면 자족적이라, 잘못 건드릴 수 있는 범위(blast radius)가 좁아집니다. 다만 여기에는 두 가지 정직한 유보가 필요합니다. 첫째, "AI가 파악하기 좋다"는 명제는 강한 실증이 아닌 합리적 추론입니다(뒤 caveat 참조). 둘째, 순수 함수화는 검수 부담을 근본적으로 없애는 것이 아니라 그 성격과 위치를 바꿉니다 — 부작용은 껍데기로 밀려나 여전히 통합 테스트로 검증해야 하고, '함수는 옳지만 조합이 틀린' 버그나 잘못된 상태 모델링은 순수성만으로 걸러지지 않습니다. 오히려 로직을 과도하게 잘게 쪼개면 호출 흐름이 여러 순수 함수에 흩어져 전체 그림 파악이 더 어려워질 수도 있습니다.

✍ 세션에서 받아적은 메모

“함수형 / 데이터 중심 / 구조적 안정망(계층 분리) / 결국 값을 통해 각 API 들에 정보를 넘길수 있어야하고 해당 값으로 순수한 계산 함수 같은 함수형으로 동작시켜야 독립적으로 테스트하기 좋고 AI 도 관련 내용을 파악하기좋다 / 데이터 를 한곳에 모아서 처리하고자한다.”

✅ 풀어 정리 & 관점 구분

먼저 용어를 정리하겠습니다. 메모에서 말씀하신 "순수한 계산 함수"는 함수형 프로그래밍의 순수 함수(pure function) 정의와 일치합니다. 즉 (1) 같은 입력이면 항상 같은 출력을 내고(참조 투명성), (2) 관찰 가능한 부작용(전역 상태 변경, I/O, 시간·난수 의존)이 없는 함수입니다. 이 정의 자체는 확립된 사실입니다. 반면 "값을 통해 API에 정보를 넘기면 테스트하기 좋고 AI가 파악하기 좋다"는 부분은, 앞 절(부작용 없음 → 테스트 용이)은 널리 받아들여지는 사실에 가깝고, 뒷 절(AI가 파악하기 좋다)은 아직 강한 실증 근거가 정립되지 않은 합리적 추론, 즉 사용자님의 의견으로 구분하는 것이 정직합니다. "함수형 코어, 명령형 껍데기(Functional Core, Imperative Shell)"는 Gary Bernhardt가 2012년 SCNA(Software Craftsmanship North America) 발표 "Boundaries" 및 동명의 destroyallsoftware.com 스크린캐스트에서 대중화한 패턴입니다(발표 연도·명칭은 검색으로 확인). 핵심은 "코어는 순수 함수로 생각(thinking)만 하고, 바깥 세계와의 대화(I/O, DB, 네트워크, 화면)는 얇은 명령형 껍데기가 실행(doing)한다"는 것입니다. 이는 그가 발명한 완전 신개념이라기보다, 예전부터 있던 관심사 분리 아이디어를 "값(단순 데이터)을 컴포넌트 사이 경계로 삼는다"는 관점으로 명료하게 재정식화한 것에 가깝습니다. 이 '최초 창안 여부' 판단은 caveat로 완화해 표기합니다. "데이터 중심"이라는 표현은 두 가지 서로 다른 것을 가리킬 수 있어 오해를 바로잡을 필요가 있습니다. 하나는 Mike Acton이 CppCon 2014 기조 "Data-Oriented Design and C++"에서 정식화한 데이터 지향 설계(DOD)로, "데이터의 변환이야말로 모든 프로그램의 유일한 목적"이라는 명제(원문: the transformation of data is the only purpose of any program — 검색으로 원문 확인) 아래 캐시 친화적 메모리 레이아웃과 일괄 처리로 성능을 얻는 접근입니다. 다른 하나는 사용자님이 실제로 강조하신 "로직과 데이터를 분리하고, 데이터를 한곳에 모아 순수 함수로 처리한다"는 설계 위생(hygiene) 관점입니다. 이 둘은 "데이터와 로직을 분리한다"는 결에서 겹치지만, DOD의 일차 동기는 성능(캐시)이고 함수형 코어의 일차 동기는 테스트 용이성·검증 가능성이라는 점에서 목적이 다릅니다. 메모의 맥락(AI 시대의 검수 비용 절감, 독립 테스트)은 함수형 코어 쪽에 훨씬 가깝습니다.

📌 핵심 정리

  • 순수 함수 = 같은 입력이면 같은 출력 + 관찰 가능한 부작용 없음. 이 정의는 확립된 사실이며, 테스트가 '입력→출력 단언'으로 끝나는 근거다.
  • 함수형 코어/명령형 껍데기(Bernhardt, SCNA 2012 'Boundaries'): 코어는 순수 함수로 판단만, 껍데기(유니티에선 MonoBehaviour 진입점)가 I/O·부작용을 집행.
  • 유니티 실익: 순수 로직은 Edit Mode에서 엔진 부팅 없이 빠르게 테스트 가능 → 프로젝트의 로직 50% 커버리지 목표가 현실화된다.
  • 데이터를 모으는 두 축: ScriptableObject(정적 설정 자산화) + 순수 struct/record 스냅샷(런타임 상태). MonoBehaviour는 반영만 하는 얇은 껍데기로 축소.
  • 이 얼개는 테스트 문헌의 'Humble Object' 패턴과 동형이다 — Feathers 2002 '(The) Humble Dialog Box'에서 출발, Meszaros가 xUnit Test Patterns(2007)에서 'Humble Object'로 일반화.
  • DOD(Acton, CppCon 2014)와 DOTS/ECS는 데이터-로직 분리를 강제하지만 일차 동기는 성능(캐시). 2D 소규모 프로젝트에선 프레임워크가 아니라 그 '철학'만 평범한 C#으로 취하는 편이 실용적.
  • 검수 비용 관점: 값 계약이 서명에 드러나 blast radius가 좁아진다 — 단 'AI가 파악하기 좋다'는 사실이 아닌 합리적 추론이며, 순수 함수화는 검수 부담을 없애기보다 껍데기로 이동시킨다.

예시 (csharp) · 부작용 섞인 MonoBehaviour vs. 순수 함수 코어 + 얇은 껍데기 — 코어만 Edit Mode에서 독립 테스트 가능

// [X] 부작용이 섞여 테스트가 어려운 형태: 상태 변경 + 시간 의존 + 로직이 한 덩어리
public class DayNightCycle_Bad : MonoBehaviour {
    public float dayLength = 120f;
    float _elapsed;
    void Update() {
        _elapsed += Time.deltaTime;           // 시간 의존(부작용)
        if (_elapsed >= dayLength) {
            _elapsed = 0f;
            GetComponent<Light2D>().intensity = 0.2f; // I/O(렌더 상태 변경)
            FindObjectOfType<AudioManager>().PlayNight(); // 전역 접근
        }
    }
}

// [O] 순수 코어: (상태, 경과시간) -> (다음 상태, 발생 이벤트). 부작용 없음.
public readonly record struct CycleState(float Elapsed, bool IsNight);
public enum CycleEvent { None, DayStarted, NightStarted }

public static class DayNightCore {
    public static (CycleState next, CycleEvent evt) Tick(
        CycleState s, float dt, float dayLength) {
        float e = s.Elapsed + dt;
        if (e >= dayLength) {
            bool night = !s.IsNight;
            return (new CycleState(0f, night),
                    night ? CycleEvent.NightStarted : CycleEvent.DayStarted);
        }
        return (new CycleState(e, s.IsNight), CycleEvent.None);
    }
}

// 얇은 껍데기: 코어가 낸 '값'을 받아 실제 부작용만 집행 (Humble Object)
public class DayNightCycle : MonoBehaviour {
    [SerializeField] float _dayLength = 120f;   // ScriptableObject로 외부화 가능

⚖ 트레이드오프 · 반론 · 유의

  • 긴장 관계(정직하게): 함수형/DOD의 '값·데이터 직결'은 얇은 경계를 지향하고, 클린 아키텍처의 '인터페이스 지향'은 추상 경계(인터페이스)를 늘려 의존을 역전한다. 순수 함수는 인터페이스가 거의 필요 없다(값만 주고받으므로). 따라서 두 사조를 동시에 강하게 밀면 '인터페이스는 최소로'와 '경계마다 인터페이스'가 충돌한다. 실무 절충은 부작용 경계(I/O, 저장, 렌더)에만 인터페이스를 두고, 순수 코어 내부는 인터페이스 없이 값으로 연결하는 것이다.
  • 부작용은 사라지지 않고 껍데기로 밀려날 뿐이다. 껍데기 자체(씬 반영, 저장, 네트워크)는 여전히 통합 테스트/플레이테스트로 검증해야 하며, 여기서 나는 버그는 순수 함수 커버리지로 잡히지 않는다. 또한 개별 함수가 모두 옳아도 '조합·상태 모델링'이 틀리면 버그가 나므로, 순수성은 검수의 충분조건이 아니다.
  • 불변 값 패턴은 할당(allocation)과 복사 비용을 유발할 수 있다. 유니티의 60fps/GC 스파이크 회피 요구상, 매 프레임 새 불변 스냅샷을 만드는 순진한 구현은 오히려 성능 예산을 위협한다 — struct/스택 할당, 재사용 버퍼, 변경 최소화로 완화 필요.
  • '순수 함수화하면 AI가 잘 파악한다'는 명제는 직관적으로 그럴듯하나 통제된 실증 근거는 약하다. 사용자님의 의견으로 다루는 것이 정직하며, 반례로 '지나치게 잘게 쪼갠 순수 함수 다발'은 오히려 호출 흐름 추적을 어렵게 해 사람·AI 모두의 파악을 방해할 수 있다.
  • 과설계 위험: 소규모 솔로 프로젝트(Dusk Hollow)에서 모든 것을 함수형 코어로 강제하면, 단순한 UI 상태 토글이나 애니메이션 트리거처럼 부작용이 본질인 코드까지 인위적으로 순수화하려다 코드가 늘고 오히려 비용이 커질 수 있다. 상태 머신·직렬화·퍼즐 해석기 같은 '판단' 로직에 집중 적용하고, '표현/연출' 코드는 껍데기에 남기는 선별이 현실적이다.
  • 출처 신뢰도: 'Functional Core, Imperative Shell'은 Bernhardt의 2012 SCNA 'Boundaries' 발표/스크린캐스트가 대중화 출처라는 점을 검색으로 확인했으나, 그가 최초 창안자인지에 대해선 확신을 낮춘다(선행 관심사 분리 아이디어의 재정식화로 보는 편이 안전). 'Humble Object'는 Meszaros(2007)의 명명이고 그 뿌리인 'The Humble Dialog Box'는 Feathers(2002)임을 구분해 두었다.

07 · 계층 = 수정단위 축소

계층 분리는 AI의 "수정 반경"을 줄이는 구조적 안전망이다 — 단, 경계를 잘 그었을 때만

계층 경계는 AI가 한 번에 건드리는 변경 범위(blast radius)를 좁혀, 잘못된 수정을 격리하고 리뷰를 쉽게 만듭니다. 다만 이는 계층의 '개수'가 아니라 경계의 '정확성'에서 나오는 효과이며, 경계를 잘못 그으면 오히려 파급이 커진다는 반대 방향의 위험도 함께 존재합니다.

핵심 메커니즘부터 짚겠습니다. AI가 코드를 값싸게 생성하는 시대의 병목은 작성이 아니라 검수라는 것이 이 시리즈의 전제였습니다. 검수 비용은 대체로 diff의 크기와 diff가 걸쳐 있는 문맥의 폭에 비례합니다. 리뷰어(사람이든 상위 AI든)는 바뀐 줄만 보는 게 아니라, 그 변경이 무엇을 깨뜨릴 수 있는지 주변 문맥을 함께 머릿속에 올려야 하기 때문입니다. 계층 경계는 바로 이 문맥의 폭을 물리적으로 제한합니다. 규칙이 '이 변경은 도메인 계층 안에서만 일어나고, 바깥으로 새어 나가는 것은 잘 정의된 값 하나뿐'이라면, 리뷰어가 확인해야 할 표면적이 계층 하나로 줄어듭니다. 좁고 검증 가능한 diff는 검수 비용을 낮추고, 이것이 AI 시대의 설계 목표와 정확히 정합합니다. 사용자님의 '수정 단위를 줄여라'는 직관은 이 지점에서 옳습니다. 다만 이 '검수 비용은 diff 크기 × 문맥 폭에 비례한다'는 공식 자체는 엄밀히 측정된 법칙이 아니라 저의 근사적 모델임을 밝혀 둡니다.

두 번째 효과는 '격리'입니다. 이것이 메모가 말한 '구조적 안전망'의 실체입니다. 경계가 강제되면 AI의 잘못된 수정이 물리적으로 넘어갈 수 없는 벽에 갇힙니다. 예를 들어 아이템의 이중 기능 판정 로직을 순수 계산 함수로 도메인 계층에 두고, MonoBehaviour나 저장 시스템은 그 함수를 '호출만' 한다면, AI가 판정 로직을 잘못 고쳐도 그 오류는 도메인 계층의 EditMode 테스트에서 잡히지 컴파일과 씬 실행 단계까지 번지지 않습니다. 이 '순수한 코어 + 얇은 명령형 껍데기' 구조는 Gary Bernhardt가 'Functional Core, Imperative Shell'(Destroy All Software, 2012)로 정식화한 것과 같은 것입니다 — 생각(계산·판정)은 순수한 코어가, 행위(I/O·씬 조작·렌더링)는 껍데기가 맡되 껍데기는 최대한 멍청하게 유지합니다. 여기서 규율의 방향이 중요합니다. 계층이 존재한다는 사실만으로는 격리가 되지 않습니다. 의존성이 한 방향(바깥에서 안쪽으로, 세부에서 정책으로)으로만 흐르도록 강제되어야 벽이 벽으로 기능합니다. 이것이 Robert C. Martin의 Clean Architecture가 정식화한 의존성 규칙(Dependency Rule)의 취지이고 — 소스 코드 의존성은 오직 안쪽(Entities·Use Cases)으로만 향해야 한다 — Alistair Cockburn의 Hexagonal(Ports and Adapters)이 '안쪽 도메인은 바깥 어댑터를 모르며, 애플리케이션을 실행 장치·DB와 격리해 개발·테스트할 수 있게 한다'로 표현한 것과 같은 방향입니다.

테스트 경계와의 연결이 이 논지의 실무적 핵심입니다. Humble Object 패턴은 테스트하기 어려운 부분(프레임워크·I/O·렌더링에 묶인 코드)을 최대한 얇고 멍청하게(humble) 남기고, 판단과 계산 같은 테스트하기 쉬운 로직을 그 옆의 순수한 객체로 뽑아내는 설계입니다. 이 패턴은 Gerard Meszaros의 xUnit Test Patterns(Addison-Wesley Signature Series, Fowler 감수)에 정식 명칭으로 정리되어 있고, Martin Fowler가 이를 널리 소개했습니다. Unity 맥락에서는 'humble한 껍데기 = MonoBehaviour', '테스트 가능한 알맹이 = 순수 C# 클래스/구조체'라는 매핑이 자연스럽습니다. MonoBehaviour는 씬·생명주기·시간에 의존해 EditMode 테스트가 어렵지만, 그 안의 로직을 순수 함수로 밀어내면 그 함수는 Play Mode 없이도 결정론적으로 검증됩니다. 요점은 이것입니다. Humble Object가 그은 '테스트 경계'와 계층이 그은 'blast radius 경계'는 대개 같은 선입니다. 테스트하기 쉽게 자르면 파급도 좁아지고, 파급을 좁히려고 자르면 테스트도 쉬워집니다. 이 둘이 정렬되는 지점이 AI에게 안전하게 위임할 수 있는 최소 단위가 됩니다.

반대 방향의 위험을 정직하게 다루겠습니다. 경계는 잘못 그으면 blast radius를 오히려 키웁니다. 대표적으로 두 축이 서로 다른 이유로 변하는데 같은 계층에 묶여 있으면, 한 축의 변경이 다른 축을 흔듭니다. 반대로 함께 변해야 할 지식이 여러 계층으로 흩어져 있으면(예: 하나의 밸런스 규칙이 데이터 정의·판정 로직·표시 계층 세 곳에 조각나 있으면), 규칙 하나를 바꾸는 데 세 계층을 동시에 열어야 합니다. 이때 계층은 안전망이 아니라 change amplification 그 자체가 됩니다. 게다가 AI는 이런 잘못된 경계를 '순응적으로' 따라가는 경향이 있습니다. AI는 세 계층에 걸친 수정을 마다하지 않고 그럴싸하게 해내기 때문에, 오히려 나쁜 경계의 비용이 리뷰 단계까지 감춰집니다. 사람이 손으로 짤 때는 '이거 왜 세 군데를 고쳐야 하지?'라는 마찰이 경계 오류를 알려주는 신호였는데, AI는 그 마찰을 흡수해 버려 신호를 지웁니다. 한 가지 더 정직하게 덧붙이면, 계층 분리는 계층 '내부' 변경의 diff 폭은 줄이지만, 경계를 '넘나드는' 변경 — 즉 계약·시그니처·값 스키마 변경 — 의 검수 부담은 오히려 키웁니다. 경계 계약이 바뀌면 코어와 그것을 호출하는 모든 어댑터가 동시에 흔들리므로, 이런 변경은 계층 내부 변경과 분리해 별도로 신중히 취급해야 합니다.

솔로~소규모 프로젝트의 실용 균형으로 마무리하겠습니다. Dusk Hollow 규모에서 계층을 무한정 세분화하는 것은 과설계입니다. 권장하는 절충은 '얇은 3분할'입니다. (1) 순수 도메인 코어: 시간 사이클 상태 머신, 아이템 이중 기능 리졸버, 퍼즐 상태, 저장 직렬화 같은 로직을 프레임워크 의존 없는 순수 C#로 두고 EditMode로 덮습니다. (2) 얇은 어댑터: MonoBehaviour, ScriptableObject, 저장 파일 I/O는 코어를 호출하고 값을 넘겨주는 껍데기로만 유지합니다. (3) 조립부: 씬과 부트스트랩. 이 정도만으로도 AI에게 위임할 때 'domain 코어 안에서만 고쳐라'라는 명령이 성립하고, 그 diff는 EditMode 테스트로 격리 검증됩니다. DOTS/ECS는 데이터 지향 특성상 시스템(로직)과 컴포넌트(데이터)가 이미 분리되어 이 구조와 궁합이 좋지만, 이 프로젝트의 기술 선호는 MVP 단계에서 성숙한 Physics 2D와 일반 MonoBehaviour 경계를 쓰는 쪽이므로 ECS 도입은 콘텐츠 볼륨이 커진 뒤로 미루는 편이 실용적입니다. 규칙은 하나로 요약됩니다. 계층의 수를 늘리지 말고, 함께 변하는 것을 모으고 다른 이유로 변하는 것을 갈라, 그 경계를 테스트로 봉인하십시오.

✍ 세션에서 받아적은 메모

“계층 분리를 통해 AI 가 수정 단위를 줄여라 / 구조적 안정망(계층 분리).”

✅ 풀어 정리 & 관점 구분

먼저 용어를 정리하겠습니다. 메모의 "수정 단위"는 소프트웨어 아키텍처에서 흔히 blast radius(변경 파급 반경) 또는 change amplification(변경 증폭)이라 부르는 개념과 사실상 같은 것을 가리킵니다. 하나의 요구사항 변경이 몇 개의 모듈·파일·함수를 동시에 건드리도록 강제하는가를 뜻합니다. 이 개념 자체는 확립된 사실입니다. John Ousterhout는 "A Philosophy of Software Design"에서 change amplification을 복잡성의 세 가지 대표 증상(change amplification, cognitive load, unknown-unknowns) 중 하나로 정의합니다. 한 가지 지적 정직성 차원의 단서를 덧붙이면, Ousterhout 본인은 change amplification을 세 증상 중 상대적으로 '덜 치명적인' 것으로 봅니다 — 고칠 곳만 분명하면 번거로울 뿐 결국 시스템은 동작한다는 것이죠. 정말 위험한 것은 '어디를 고쳐야 할지 모르는' unknown-unknowns입니다. 다만 "AI 시대라서 이 원칙이 특히 더 중요하다"는 것은 사용자님의 해석이자 저의 동의이며, 하나의 의견으로 구분해 두겠습니다. / 두 번째로 바로잡을 오해가 있습니다. "계층을 나누기만 하면 blast radius가 줄어든다"는 명제는 조건부 참입니다. 파급 반경을 실제로 줄이는 것은 계층의 개수가 아니라 경계의 정확성입니다. 함께 변하는 것을 한쪽에 모으고(응집), 서로 다른 이유로 변하는 것을 갈라놓았을 때만(Robert C. Martin의 Common Closure Principle의 취지) 파급이 좁아집니다. 경계를 엉뚱한 곳에 그으면 하나의 변경이 여러 계층을 관통해 오히려 파급이 커집니다. 즉 "계층 분리 = 안전망"은 목표가 아니라 잘 그었을 때의 결과입니다.

📌 핵심 정리

  • blast radius(변경 파급 반경) / change amplification(변경 증폭)은 확립된 개념 — 하나의 요구 변경이 동시에 건드리도록 강제하는 코드의 양. Ousterhout가 복잡성의 세 증상(change amplification·cognitive load·unknown-unknowns) 중 하나로 정의하며, 이 중 change amplification은 상대적으로 덜 치명적이라고 본다.
  • 검수 비용은 대략 diff 크기 × 문맥 폭에 비례한다(엄밀한 법칙이 아닌 근사 모델). 계층 경계는 문맥 폭을 물리적으로 제한해 좁고 검증 가능한 diff를 만든다 = AI 시대 목표와 정합.
  • 격리 효과: 의존성이 한 방향(바깥->안쪽)으로만 흐를 때 AI의 오류가 벽을 넘지 못한다. Clean Architecture의 Dependency Rule(Martin), Hexagonal의 Ports and Adapters(Cockburn), Functional Core/Imperative Shell(Bernhardt)이 모두 같은 방향.
  • Humble Object 패턴(Meszaros, xUnit Test Patterns; Fowler 소개): 테스트 어려운 껍데기는 얇게, 로직은 순수 객체로. Unity에서는 MonoBehaviour=humble 껍데기, 순수 C#=테스트 가능한 알맹이.
  • 테스트 경계와 blast radius 경계는 대개 같은 선 — 이 둘이 정렬되는 지점이 AI에 위임 가능한 최소 안전 단위.
  • 핵심 반론: 파급을 줄이는 것은 계층의 '개수'가 아니라 경계의 '정확성'. 잘못 그으면 계층이 곧 change amplification이 된다. 또한 경계를 '넘나드는' 계약 변경의 검수 부담은 오히려 커진다.
  • Dusk Hollow 실용안: 얇은 3분할(순수 도메인 코어 + 얇은 어댑터 + 조립부). 도메인 코어를 EditMode로 봉인하면 'domain 안에서만 고쳐라'가 성립.

예시 (csharp) · Humble Object / Functional Core를 Unity에 매핑: MonoBehaviour는 얇은 껍데기, 판정은 순수 함수. 파급 경계와 테스트 경계가 같은 선에 놓인다.

// [순수 도메인 코어 = Functional Core] 프레임워크 무의존 = EditMode로 격리 검증 가능
// AI가 규칙을 잘못 고쳐도 오류는 이 경계 안에 갇힌다.
public static class ItemResolver
{
    // 값을 받아 값을 돌려주는 순수 계산: 씬/시간/I/O 의존 없음
    public static ItemEffect Resolve(ItemDef item, Phase phase) =>
        phase == Phase.Night ? item.NightEffect : item.DayEffect;
}

// [얇은 어댑터 = humble 껍데기 = Imperative Shell] 로직 없음. 코어를 '호출만' 한다.
public sealed class ItemUseBehaviour : MonoBehaviour
{
    [SerializeField] private ItemDefSO _def;      // ScriptableObject = 데이터

    public void Use(Phase phase)
    {
        var effect = ItemResolver.Resolve(_def.ToDef(), phase); // 판정은 코어에 위임
        ApplyToScene(effect);                                   // 껍데기의 유일한 책임
    }

    private void ApplyToScene(ItemEffect e) { /* VFX/사운드/씬 상태 */ }
}

⚖ 트레이드오프 · 반론 · 유의

  • 'AI 시대라서 계층 분리가 특히 유리하다'는 사용자님의 해석이자 저의 동의로, 확립된 사실이 아니라 의견입니다. change amplification을 줄이는 게 좋다는 원칙 자체는 AI 이전부터 확립돼 있었습니다.
  • 출처 정밀도: WebSearch로 개념 귀속을 재확인했습니다. Humble Object=Gerard Meszaros(xUnit Test Patterns, Fowler 감수 시리즈)/Fowler 소개, Functional Core Imperative Shell=Gary Bernhardt(Destroy All Software, 2012), change amplification=John Ousterhout(A Philosophy of Software Design), Dependency Rule 및 4계층·Common Closure Principle=Robert C. Martin(Clean Architecture), Ports and Adapters=Alistair Cockburn 귀속은 모두 확인되었습니다. 다만 페이지·판본 등 세부 인용은 발행 전 원문 대조를 권합니다.
  • 반대 논거: 경계를 잘못 그으면 blast radius가 오히려 커진다. 서로 다른 이유로 변하는 것을 한 계층에 묶거나, 함께 변할 지식을 여러 계층에 흩으면 하나의 변경이 여러 계층을 관통한다.
  • AI 특유의 위험: AI는 나쁜 경계를 순응적으로 따라 여러 계층을 한 번에 그럴싸하게 고쳐, '왜 여러 군데를 고쳐야 하지?'라는 인간의 마찰 신호를 흡수해 경계 오류를 리뷰까지 감춘다.
  • 여전한 검수 부담: 계층 분리는 계층 내부 diff의 '폭'을 줄일 뿐, 경계를 '넘나드는' 변경(계약/시그니처/값 스키마 변경)의 검수 부담은 오히려 커질 수 있다. 경계 계약 변경은 계층 내부 변경과 분리해 별도로 취급해야 한다.
  • Ousterhout의 관점 단서: change amplification은 그의 세 복잡성 증상 중 상대적으로 덜 치명적인 축이다(고칠 곳이 분명하면 번거로워도 시스템은 동작). 따라서 계층 분리의 더 큰 가치는 파급 자체보다 '어디를 고쳐야 할지 명확하게 만드는 것'(unknown-unknowns 감소)에 있을 수 있다.
  • 과설계 위험: 솔로~소규모에서 계층·인터페이스를 과도하게 늘리면 학습·탐색 비용이 파급 감소 이득을 초과한다. Dusk Hollow에서는 얇은 3분할 정도가 균형점이며, DOTS/ECS 전면 도입은 콘텐츠 볼륨 확장 이후로 미루는 편이 낫다.
  • 정량화 어려움: blast radius 감소가 실제로 검수 시간을 얼마나 줄이는지에 대한 이 프로젝트 고유의 측정치는 아직 없다. '검수 비용 = diff 크기 × 문맥 폭' 역시 근사 모델이며 위 논지는 일반 원칙에 기반한 추론이다.

08 · Unity 실천

Unity 실천 가이드: 얇은 셸, 순수한 코어, 그리고 최소한의 경계

Unity에서는 MonoBehaviour를 입력·엔진 연동·부작용만 담는 얇은 "명령형 셸"로 두고, 게임 규칙은 엔진에 의존하지 않는 순수 C# "함수형 코어"로 떼어내 EditMode에서 독립 테스트하는 것이 핵심입니다. 다만 이 저장소에서 그 경계가 "별도 asmdef로 컴파일 단계에서 강제"되는 것은 아니며, 대체로 코어 소스가 UnityEngine을 import하지 않는 규율(convention)로 지켜집니다 — 이 구분은 뒤에서 정직하게 짚겠습니다. 솔로/소규모 프로젝트에서는 전면 클린 아키텍처 4계층을 그대로 얹기보다 "가벼운 경계 + 함수형 코어"가 비용 대비 이득이 크다는 것이 이 글의 실용 결론입니다(권고이지 보편 법칙은 아닙니다).

구체적으로 이 프로젝트(Dusk Hollow)의 시간 순환 시스템이 정확히 이 패턴으로 짜여 있습니다. Assets/Scripts/GameClock/GameClock.cs는 using System만 참조하는 순수 C# 클래스입니다(확인함: UnityEngine을 전혀 import하지 않습니다). 상태 머신(Day→Dusk→Night→Dawn)·시간 누적·이벤트 디스패치를 모두 담되, 프레임 델타를 Update(float deltaTime)처럼 '값으로' 인자를 받고, 델타가 0이면 no-op, 음수면 예외를 던집니다. 반면 Assets/Scripts/GameClock/Runtime/GameClockDriver.cs는 70줄짜리 MonoBehaviour로, 하는 일이라곤 Awake에서 GameClock을 만들고 Update()에서 _clock?.Update(Time.deltaTime) 한 줄을 호출하는 것뿐입니다(실측 라인 수와 구조 확인함). 즉 엔진 연동(Time.deltaTime을 읽는 부작용)은 셸에, 규칙은 코어에 있습니다. 이렇게 하면 코어를 EditMode 테스트에서 clock.Update(1200f) 같은 값을 넣어 위상 전이가 맞는지 검증할 수 있고, 실제로 이 저장소에는 GameClockBasicTransitionTests, GameClockEventsTests, ForceTransitionTests 등 다수의 EditMode 테스트가 존재합니다(확인함). Unity 에디터를 띄우거나 씬을 로드할 필요 없이 순수 함수의 반환값/상태만 어서션하면 됩니다 — 이것이 Bernhardt가 말한 '테스트 더블 없이 값만 확인'하는 이점의 실제 사례입니다.

데이터는 한곳에 모으되 두 종류의 그릇을 구분해 쓰길 권합니다. (1) 튜닝 값·에셋 참조처럼 '디자이너가 만지고 여러 씬이 공유하는 설정'은 ScriptableObject가 적합합니다. Unity의 확립된 사실로서 ScriptableObject는 씬 인스턴스와 분리된 에셋이라 인스펙터로 편집·핫스왑이 쉽고 참조를 공유합니다(예: LanternConfig, GameClockConfig). (2) 매 프레임 계산에 쓰는 '런타임 스냅샷/불변 상태'는 readonly struct 같은 값 타입으로 두는 편이 낫습니다 — 이 저장소에서 실제로 readonly struct인 것은 GameClockState와 LanternStateSnapshot입니다(둘 다 IEquatable<T> 구현, UnityEngine 비의존 확인함). 여기서 초안의 오류 하나를 바로잡습니다: 초안은 런타임 상태 struct 예시로 InventoryState를 들었지만, 이 저장소의 InventoryState는 struct가 아니라 인벤토리 수명주기(Empty/Active/Restoring)를 나타내는 enum입니다. 값 타입 상태의 올바른 예시는 GameClockState·LanternStateSnapshot입니다. 핵심 규칙은 '코어가 소비하는 데이터 타입은 UnityEngine에 의존하지 않게' 하는 것입니다(이들 세 타입 모두 이 규칙을 지킵니다).

이 지점에서 초안의 더 중요한 사실 오류를 정정합니다. 초안은 'DuskHollow.TimeCycle 코어 asmdef과 Runtime/의 드라이버 asmdef이 분리돼 있어 컴파일 단계에서 경계가 강제된다'고 썼지만, 실제로는 그렇지 않습니다. GameClock(순수 코어)과 GameClockDriver(MonoBehaviour)는 같은 단일 어셈블리 DuskHollow.TimeCycle 안에 함께 들어 있고, 그 asmdef은 noEngineReferences: false입니다(확인함). 즉 이 어셈블리는 UnityEngine을 참조할 수 있고, 코어의 '순수성'은 컴파일러가 강제하는 게 아니라 코어 소스 파일이 using UnityEngine을 쓰지 않는다는 규율(convention)로만 유지됩니다. 프로젝트 전체를 뒤져봐도 noEngineReferences: true로 엔진 참조를 물리적으로 차단한 asmdef은 없었습니다. 다만 코어/드라이버 asmdef 분리 자체가 아예 없는 것은 아닙니다 — 예컨대 Input 계열은 DuskHollow.Input(코어)과 DuskHollow.Input.Driver(드라이버)로 실제로 나뉘어 있습니다. 그러나 이 둘조차 noEngineReferences: false라, '컴파일 단계에서 엔진 의존이 금지된다'는 강한 주장은 이 저장소 기준으로는 사실이 아닙니다. 정직한 서술은 이렇습니다: 경계는 대체로 규율로 지켜지며, asmdef 분리는 재컴파일 단위를 좁혀 blast radius를 줄이는 효과가 있지만(그건 사실입니다), 순수성 자체를 강제하지는 않습니다. 순수성을 컴파일러로 강제하고 싶다면 코어 asmdef에 noEngineReferences: true를 명시적으로 켜야 합니다.

인터페이스는 '경계에서, 필요할 때만' 도입하는 최소주의를 권합니다. 이건 강한 의견이지만 근거가 있습니다 — 클린 아키텍처의 확립된 원리인 '의존성 규칙(Dependency Rule: 소스 의존성은 항상 안쪽을 향한다)'을 지키기 위해, 클린 아키텍처는 안쪽 코어가 바깥 세부(프레임워크/DB)를 부르지 않도록 인터페이스로 의존을 뒤집습니다(DIP). 이 프로젝트도 그런 지점에만 인터페이스를 둡니다: IGameClock, IDataPersistence, ISceneLoader, IItemDatabase 정도가 확인됩니다(다만 IGameClock·IItemDatabase·IDataPersistence는 Inventory 관련 폴더에, ISceneLoader는 SceneManagement에 위치합니다 — 초안이 암시한 위치와는 조금 다릅니다). 반대로 모든 클래스에 인터페이스를 기계적으로 붙이는 '전면 클린 아키텍처 4계층(Entities / Use Cases / Interface Adapters / Frameworks & Drivers)'을 솔로 인디 규모에 그대로 얹으면 경계를 넘기 위한 DTO 매핑·포트·어댑터가 폭증합니다. 이것이 사용자가 지적한 '동심원' 부담의 실제 모습입니다. 규모가 작을 때는 '핵심 도메인만 엔진에서 떼어낸다'는 실용 수준이 4계층보다 저렴합니다. 단, '최소'가 어디까지인지는 판단이 필요한 규칙이며, 경계를 너무 늦게 그으면 나중에 목킹·교체가 어려워진다는 반대 위험도 함께 안고 가야 합니다.

DOTS/ECS는 '데이터 지향 설계(Data-Oriented Design)'의 극단적·전면적 형태로 이해하는 게 정확합니다. DOD는 Mike Acton(당시 Insomniac Games 엔진 디렉터, CppCon 2014 강연 'Data-Oriented Design and C++')이 정식화·대중화한 사고방식으로, 핵심 명제는 '프로그램의 유일한 목적은 데이터를 변환하는 것이며, 하드웨어(캐시·메모리 레이아웃)를 존중해 데이터를 배치하라'입니다(원 강연의 표현을 확인함). Unity DOTS/ECS는 이를 엔진 차원에서 구현해 컴포넌트를 연속 메모리(chunk)에 몰고 Burst/Jobs로 병렬화합니다. 여기서 중요한 구분: '함수형 코어(부작용 없는 계산)'와 'DOD(캐시 친화적 데이터 배치)'는 둘 다 '데이터를 값으로 다룬다'는 결은 공유하지만 목적이 다릅니다 — 전자는 테스트성·이해가능성, 후자는 성능입니다. 실제로 이 프로젝트의 GameClock.cs 주석도 'DOTS / multi-thread support는 post-MVP'라고 명시합니다(확인함). 솔로 2D 프로젝트에서 수천~수만 엔티티의 캐시 병목이 실측되기 전에는 DOTS의 학습·아키텍처 비용을 지불할 이유가 거의 없습니다. '데이터를 한곳에 모아 순수 함수로 처리'라는 사용자의 목표는 DOTS 없이도 plain struct + 순수 클래스만으로 충분히 달성됩니다.

마지막으로 AI 협업 관점의 실천입니다. AI가 코드를 잘 이해·수정·테스트하려면 (a) 순수 함수 — 입력과 출력이 명시적이라 AI가 씬 상태나 숨은 싱글턴을 추측할 필요가 없고, (b) 명확한 데이터 타입 — readonly struct(예: GameClockState)와 enum(예: CyclePhase, InventoryState)이 계약을 문서화해 주며, (c) 좁은 파일·asmdef 경계 — AI가 한 번에 건드리는 수정 단위(blast radius)를 물리적으로 제한합니다. 이 저장소가 시스템별로 asmdef를 잘게 쪼갠 것(DuskHollow.Inventory, DuskHollow.Lantern, DuskHollow.Input / DuskHollow.Input.Driver 등, 확인함)은 AI에게 '이 파일을 고치면 이 어셈블리만 다시 컴파일되고 나머지는 계약으로 보호된다'는 신호를 줍니다. 다만 앞서 정정했듯 이 경계는 재컴파일 단위와 참조 그래프를 좁힐 뿐, 엔진 의존 금지 같은 순수성까지 강제하지는 않습니다. 그럼에도 순수 코어는 AI가 진 변경을 사람이 검수할 때 유리합니다 — EditMode 테스트가 초록불이면 '이 함수는 여전히 명세대로 동작한다'가 값으로 증명되므로, 검수 비용(사용자가 세션에서 강조한 그 비용)이 실제로 내려갑니다. 반론도 함께 기억할 값어치가 있습니다: 계층·인터페이스가 늘수록 '읽고 검수해야 할 표면적'도 늘어, 코드 생성 비용 절감이 곧 이해/검수 비용 절감을 뜻하지는 않습니다.

✍ 세션에서 받아적은 메모

“Unity에서의 실천 가이드(구체적, 실용 균형). MonoBehaviour = imperative shell(입력/엔진 연동/부작용)로 얇게, 게임 규칙 = 순수 C#(functional core)로 분리해 EditMode 테스트. 데이터는 ScriptableObject/plain struct로 한곳에. 인터페이스는 "경계에서 필요할 때만"(최소주의) — 전면 클린 아키텍처 4계층을 솔로/소규모에 그대로 얹지 말고, 핵심 도메인만 엔진에서 떼어내는 실용적 수준부터. DOTS/ECS는 데이터 지향의 극단 형태(도입 비용 큼, 필요할 때). AI 협업 팁: 순수 함수+명확한 데이터 타입+좁은 파일 경계로 AI가 이해·수정·테스트하기 좋게. 이 프로젝트(솔로 인디, Dusk Hollow)처럼 규모가 작으면 "가벼운 경계 + 함수형 코어"가 풀 클린 아키텍처보다 비용 대비 낫다는 실용 결론.”

✅ 풀어 정리 & 관점 구분

먼저 용어를 정리하겠습니다. "함수형 코어, 명령형 셸(Functional Core, Imperative Shell)"은 Gary Bernhardt가 2012년 Destroy All Software 스크린캐스트("Functional Core, Imperative Shell", 2012-07-12)와 같은 해 강연 "Boundaries"에서 대중화한 패턴으로, 확립된 정의는 이렇습니다 — 부작용 없이 값만 다루는 순수 로직을 "코어"에 모으고, I/O·네트워크·DB·엔진 호출처럼 부작용이 있는 부분은 그 코어를 감싸는 "셸"에 몰아넣습니다. Bernhardt가 강조한 이점은 정확히 두 가지입니다: (1) 코어는 테스트 더블 없이 값만 넣고 반환을 확인해 검증할 수 있고, (2) 셸은 분기(conditional)가 거의 없어 시간에 따른 상태 추론이 쉬워집니다. 이때 "MonoBehaviour가 셸이고 게임 규칙이 코어"라는 매핑은 Bernhardt의 원본 정의가 아니라 그 패턴을 Unity에 적용한 저(그리고 널리 통용되는) 해석·의견입니다. 사실과 의견을 섞지 않기 위해 명확히 구분합니다.

📌 핵심 정리

  • MonoBehaviour는 얇은 명령형 셸(입력/Time/엔진 호출/부작용)로, 게임 규칙은 UnityEngine에 의존하지 않는 순수 C# 코어로 분리한다. 이 저장소의 GameClock.cs(코어, UnityEngine 미import 확인) ↔ GameClockDriver.cs(셸)가 실제 사례.
  • 코어는 엔진 없이 EditMode에서 값만 넣고 반환/상태를 어서션해 테스트한다(테스트 더블 불필요). 실제로 GameClockBasicTransitionTests 등이 존재(확인).
  • 데이터는 두 그릇으로: 디자이너가 튜닝·공유하는 설정은 ScriptableObject(GameClockConfig, LanternConfig), 런타임 불변 스냅샷은 UnityEngine 비의존 readonly struct(GameClockState, LanternStateSnapshot). 주의: InventoryState는 struct가 아니라 enum이다(초안 정정).
  • 정정: 코어(GameClock)와 드라이버(GameClockDriver)는 같은 단일 DuskHollow.TimeCycle asmdef에 함께 있고 noEngineReferences: false다. 순수성은 '컴파일 강제'가 아니라 코어 소스가 UnityEngine을 안 쓰는 규율로 유지된다. 프로젝트에 noEngineReferences: true인 asmdef은 없다.
  • 코어/드라이버 asmdef 분리 자체는 존재한다(예: DuskHollow.Input + DuskHollow.Input.Driver). 이는 재컴파일 단위(blast radius)를 좁히는 효과가 있으나, 두 어셈블리 모두 엔진 참조를 허용하므로 엔진 의존을 금지하지는 않는다.
  • 인터페이스는 진짜 경계(IGameClock, IDataPersistence, ISceneLoader, IItemDatabase)에만 최소로. 전 클래스 인터페이스화 = 동심원 보일러플레이트 폭증. 단 '최소'의 선은 판단 규칙이며 늦게 그으면 목킹/교체가 어려워지는 반대 위험이 있다.
  • DOTS/ECS는 데이터 지향 설계(Acton, CppCon 2014)의 극단 형태로 성능 도구다. 함수형 코어의 목적(테스트성)과 다르며, 솔로 2D에서는 성능 병목 실측 전엔 도입 비용이 이득을 초과. GameClock.cs 주석도 'DOTS는 post-MVP'.
  • AI 협업 3요소: 순수 함수 + 명확한 데이터 타입(enum/readonly struct) + 좁은 파일·asmdef 경계 → blast radius 축소, 검수 비용 하락. 단 계층·인터페이스가 늘면 검수 표면적도 늘어(생성 비용↓ ≠ 검수 비용↓).
  • 솔로 인디 규모 결론(보편 법칙 아닌 권고): 전면 클린 아키텍처 4계층보다 '가벼운 경계 + 함수형 코어'가 비용 대비 우수. 핵심 도메인만 엔진에서 떼어내는 데서 시작한다.

예시 (csharp) · 함수형 코어(순수 C#) ↔ 명령형 셸(MonoBehaviour) 분리. 이 저장소 GameClock.cs / GameClockDriver.cs 구조의 축약. 코어는 UnityEngine을 import하지 않고 프레임 델타를 '값'으로 받아 EditMode에서 테스트 더블 없이 검증한다. 단, 이 순수성은 별도 asmdef가 아니라 '코어가 UnityEngine을 import하지 않는 규율'로 유지된다는 점에 유의(둘은 실제로 같은 DuskHollow.TimeCycle 어셈블리에 있다).

// --- 함수형 코어: using System 만. UnityEngine 없음 -> EditMode 단독 테스트 ---
// (규율로 순수하게 유지. 컴파일 강제를 원하면 코어 asmdef에 noEngineReferences:true)
public sealed class GameClock
{
    private CyclePhase _phase;
    private float _elapsed;

    // 부작용 없음: 델타를 '값'으로 받아 상태만 전이. 엔진/시간 조회 안 함.
    public void Update(float deltaTime)
    {
        if (deltaTime < 0f) throw new ArgumentOutOfRangeException(nameof(deltaTime));
        if (deltaTime == 0f) return; // Time.timeScale=0 -> no-op
        _elapsed += deltaTime;
        while (_elapsed >= DurationOf(_phase)) { _elapsed -= DurationOf(_phase); _phase = Next(_phase); }
    }
    public CyclePhase CurrentPhase => _phase;
}

// --- 명령형 셸: 엔진 연동(Time.deltaTime 읽기)이라는 부작용만 담당 ---
public sealed class GameClockDriver : MonoBehaviour
{
    private GameClock _clock;
    private void Awake()  => _clock = new GameClock(/* config */);
    private void Update() => _clock?.Update(Time.deltaTime); // 셸이 하는 일은 이 한 줄
}

// --- EditMode 테스트: 씬/에디터 재생 없이 값만 어서션 (테스트 더블 불필요) ---
[Test] public void Update_FullDay_AdvancesToDusk()
{
    var clock = new GameClock(/* config: Day=1200 */);
    clock.Update(1200f);
    Assert.AreEqual(CyclePhase.Dusk, clock.CurrentPhase);
}

⚖ 트레이드오프 · 반론 · 유의

  • 'MonoBehaviour=셸, 규칙=코어' 매핑은 Bernhardt 원본 정의가 아니라 Unity 적용 해석(의견)입니다. Bernhardt의 원 출처는 Destroy All Software 스크린캐스트('Functional Core, Imperative Shell', 2012-07-12)와 강연 'Boundaries'(2012)이며, 세부 표현은 원 강연과 다를 수 있습니다.
  • 가장 큰 정정: '코어 asmdef과 드라이버 asmdef이 분리돼 컴파일 단계에서 경계가 강제된다'는 초안 주장은 TimeCycle에 대해 사실이 아닙니다. GameClock과 GameClockDriver는 같은 DuskHollow.TimeCycle 어셈블리에 있고 noEngineReferences: false입니다. 순수성은 규율로 유지되며, 컴파일러 강제를 원하면 코어 asmdef에 noEngineReferences: true를 켜야 합니다.
  • 초안이 런타임 상태 struct 예시로 든 InventoryState는 struct가 아니라 enum(Empty/Active/Restoring)입니다. 실제 readonly struct 예시는 GameClockState, LanternStateSnapshot뿐임을 확인했습니다.
  • 함수형 코어가 항상 공짜는 아닙니다. 엔진과 밀착된 기능(물리 콜백 타이밍, 애니메이션 이벤트, 트리거 충돌)을 코어로 떼어낼 때 데이터를 왕복 복사하고 셸-코어 왕래 코드가 늘어 오히려 blast radius가 커질 수 있습니다 — '경계가 수정 단위를 키우는' 반례가 존재합니다.
  • 'AI가 보일러플레이트를 대신 지므로 클린 아키텍처가 유리하다'는 주장의 반론: AI가 코드를 싸게 쓰더라도 계층·인터페이스가 많을수록 '읽고 검수해야 할 표면적'이 늘어, 검수 비용이 되레 커질 수 있습니다. 코드 생성 비용↓ ≠ 이해/검수 비용↓.
  • ScriptableObject vs struct 선택은 트레이드오프입니다. SO는 공유·핫스왑에 강하지만 런타임 가변 상태를 SO에 두면 플레이 종료 후 값이 남거나(에디터) 인스턴스 공유로 의도치 않은 변이가 생깁니다. 런타임 가변/불변 스냅샷은 struct·클래스, 불변 설정은 SO라는 분리가 안전.
  • '최소 인터페이스'는 판단 규칙입니다. 너무 늦게 그으면 목킹·교체가 어렵고, 너무 일찍 그으면 과설계입니다. 본문의 '핵심 도메인만'은 솔로 인디 기준 권고이지 보편 법칙이 아닙니다.
  • DOD/DOTS: Acton의 DOD는 '캐시/성능' 지향이지 '테스트성' 지향이 아닙니다. 두 개념을 '데이터 중심' 한 단어로 묶으면 오해가 생깁니다. Unity DOTS의 API·성숙도는 버전 의존적이라(프로젝트가 6.3 LTS, LLM 지식 컷오프 이후) 구체 API 권고는 의도적으로 배제했습니다.
  • 클린 아키텍처 4계층(Entities / Use Cases / Interface Adapters / Frameworks & Drivers)과 '의존성 규칙'은 Robert C. Martin의 확립된 정의이지만, Unity에 정식 매핑한 표준은 없습니다. 본문의 Unity 적용은 해석이며, 헥사고날(Cockburn, Ports & Adapters)·어니언과 세부 경계 정의가 갈리는 지점이 있습니다.

09 · 계층별 테스트

Data / ViewEntity / View — 순수한 쪽으로 로직을 몰아 검수 비용을 낮추기

테스트를 세 층으로 나누는 이유는 단순합니다. 값 입력·값 출력의 순수한 계층(Data, ViewEntity)은 빠르고 결정적이라 값싸게 대량으로 검증할 수 있고, 엔진·UI가 붙는 View 계층은 느리고 비싸니 최대한 얇게 만들어 테스트를 최소화하려는 것입니다. 이것이 테스트 피라미드와 Humble Object 패턴의 게임 버전이며, 이 노트 전체의 "검수 비용↓ + AI 친화" 논지와 곧장 맞닿아 있습니다.

첫 번째 층인 Data 테스트는 가장 안쪽, 즉 함수형 코어(functional core)를 겨냥합니다. 도메인 규칙과 데이터를 값으로 받아 값으로 내보내는 순수 계산 — 예컨대 '피해량 = 기본공격력 - 방어력, 하한 0', '인벤토리에 아이템 추가 시 용량 초과면 거부', 'Dusk Hollow의 낮/밤 상태 전이 규칙' 같은 것 — 을 검증합니다. 이 계층은 MonoBehaviour도, Scene도, GameObject도 필요 없습니다. 그래서 Unity에서는 EditMode 테스트로 밀리초 단위에 수백 개가 돌고, 엔진을 켜지 않으니 결정적입니다. 이 프로젝트의 기술 선호 문서가 '시간 사이클 상태 머신, 아이템 이중 기능 리졸버, 퍼즐 상태, 세이브/로드 직렬화'를 필수 테스트 대상으로 못박은 것도 정확히 이 함수형 코어를 겨냥한 것입니다. 로직을 여기에 몰아둘수록 검증이 값싸집니다.

두 번째 층인 ViewEntity 테스트는 도메인 데이터를 '뷰가 그대로 그릴 수 있는 형태'로 바꾸는 변환(프리젠터/매핑) 로직을 검증합니다. 여기서 ViewEntity는 앞서 말한 View Model / Presentation Model이고, 이 변환을 담당하는 코드가 MVP로 치면 Presenter입니다. 핵심은 '무엇을 화면에 보여줄지'를 실제 UI 없이 순수 값으로 확정한다는 점입니다. HealthPresenter.Build(hp: 30, max: 100)이 { fillRatio: 0.3, barColor: Red, label: "위험" }을 돌려주는지 검증하면, 색·라벨·게이지 비율을 결정하는 모든 표시 규칙(임계값 30%에서 빨강으로 바뀌는가, 경계값 30%는 빨강인가 노랑인가 같은 경계 케이스 포함)을 UI를 띄우지 않고 잡아낼 수 있습니다. Data 테스트와 마찬가지로 순수하므로 EditMode에서 빠르게 돌고, 사실상 표시 규칙 버그의 대부분이 여기서 걸립니다.

세 번째 층인 View 테스트는 실제 View — Unity라면 UI Toolkit의 UXML/USS 바인딩, 또는 SpriteRenderer/UGUI — 가 주어진 ViewEntity를 올바르게 렌더·바인딩하는지를 봅니다. 여기서부터는 엔진과 UI가 필요합니다. Unity에서는 PlayMode 테스트로 Scene을 로드하고 실제 컴포넌트를 붙여 돌려야 하며, 최종 확인은 스크린샷 대조 같은 시각/통합 검증으로 넘어갑니다. 느리고, 세팅이 무겁고, 결정성이 떨어집니다(프레임 타이밍, 폰트 렌더, 해상도 의존). 이 프로젝트의 코딩 표준이 UI/Visual 스토리의 테스트를 'ADVISORY(수동 워크스루 + 스크린샷 + 리드 사인오프)'로 분류하고 자동화 대상에서 빼둔 것도 같은 이유입니다. 그래서 전략은 명확합니다 — View는 로직을 갖지 않는 Humble View로 얇게 유지하고(주어진 ViewEntity를 기계적으로 바인딩만), 판단은 전부 아래 두 순수 계층으로 밀어냅니다. View 테스트는 '배선이 끊기지 않았는가' 정도의 소수 스모크로 최소화합니다.

이 세 층을 겹쳐 보면 그대로 테스트 피라미드입니다. 아래(Data)로 갈수록 테스트는 빠르고 값싸고 많고, 위(View)로 갈수록 느리고 비싸고 적습니다. Humble Object 패턴의 처방('테스트하기 어려운 것에서 로직을 빼내 테스트하기 쉬운 것으로 옮겨라')을 게임 UI에 적용한 결과가 바로 이 구조이고, 로직을 순수한 쪽으로 몰수록 전체 테스트 비용이 내려갑니다. 반대로 View 안에 '체력 30% 이하면 색 바꾸기' 같은 판단을 넣어버리면, 그 규칙을 검증하려고 엔진을 켜야 하니 값싼 EditMode 테스트로 잡을 수 있던 것을 비싼 PlayMode 테스트로 밀어 올린 셈이 됩니다. 계층을 나누는 진짜 이득은 코드의 미학이 아니라 '검증 단가'를 낮추는 데 있습니다.

이 구조가 이 노트의 큰 논지 — AI 시대에는 '쓰기'보다 '검수(리뷰)' 비용이 상대적으로 커진다 — 와 직결되는 지점이 여기입니다(이 인과는 사용자의 주장에 해당하며, 아래 caveat의 반론과 함께 읽어 주십시오). 순수한 Data/ViewEntity 계층은 입출력이 값이라 명세가 명확하고, AI가 테스트를 짜기도 쉽고 사람이 그 테스트를 읽고 승인(검수)하기도 쉽습니다. 회귀 검증도 재실행만으로 결정적으로 끝납니다. 즉 로직을 순수 계층으로 몰아두면 'AI가 짠 코드가 맞는지'를 사람이 값싸게 확인할 안전망이 자동으로 생깁니다. 반대로 로직이 엔진에 얽힌 View에 흩어져 있으면 AI가 무엇을 바꿨는지 검수하려 매번 무거운 통합 실행이 필요해지고, 이것이 바로 AI 시대에 가장 비싸지는 종류의 검수입니다. 그래서 '순수한 쪽으로 로직을 몰아라'는 오래된 조언이, AI가 코드를 값싸게 쏟아내는 지금 오히려 더 강한 실용적 근거를 갖는다고 볼 수 있습니다 — 다만 이는 개연성 있는 논증이지 측정된 사실은 아닙니다.

테스트하기 쉬운(순수) 쪽으로 로직을 몰아 값싼 Data·ViewEntity 테스트로 대부분을 덮고, 비싼 View 테스트는 얇게 유지(Humble View) — 테스트 피라미드와 같은 원리.

✍ 세션에서 받아적은 메모

“계층별 테스트 전략 — 세션에서 들은 "Data 테스트 / ViewEntity 테스트 / View 테스트" 세 가지. Data 테스트: 가장 안쪽, 순수 도메인 로직/데이터(값 입력→값 출력)를 검증, 엔진·UI 불필요, 빠르고 결정적(Unity EditMode 단위 테스트), functional core를 테스트하는 것. ViewEntity 테스트: 중간, "ViewEntity"(=뷰가 그대로 그릴 수 있도록 도메인 데이터를 가공해 만든 뷰 전용 데이터, 일반 개념으로는 View Model / Presentation Model)를 만들어내는 프리젠터/매핑 로직을 검증, "무엇을 화면에 보여줄지"를 실제 UI 없이 순수 값으로 테스트(예: HP 30%면 게이지 색=빨강, 라벨="위험"), 도메인→표시데이터 변환의 정확성. View 테스트: 가장 바깥, 실제 View가 주어진 ViewEntity를 올바르게 렌더/바인딩하는지, 엔진·UI 필요→느리고 통합/시각 테스트 성격, 그래서 View는 최대한 얇게(Humble View) 만들어 로직을 Data/ViewEntity로 밀어내고 View 테스트는 최소화. 핵심: 테스트하기 쉬운(순수) 쪽으로 로직을 몰아 값싼 Data/ViewEntity 테스트로 대부분을 커버, 비싼 View 테스트는 얇게 — 테스트 피라미드/Humble Object와 정합하고, 이 노트의 "검수 비용↓ + AI 친화" 논지와 직결.”

✅ 풀어 정리 & 관점 구분

먼저 사실과 의견을 구분하겠습니다. 확립된 사실/정의는 이렇습니다. (1) 순수 함수(같은 입력이면 항상 같은 출력, 부수효과 없음)는 결정적이라 단위 테스트가 빠르고 안정적입니다 — 정의상 참입니다. (2) Gerard Meszaros의 『xUnit Test Patterns』(2007)에 나오는 Humble Object 패턴은 "환경에 강하게 결합되어 테스트하기 어려운 부분(예: UI 컨트롤)은 로직을 최소화하고, 진짜 로직은 환경 독립적인 테스트 가능한 컴포넌트로 뽑아낸다"는 것입니다. Martin Fowler는 이 패턴을 UI 맥락에서 Presentation Model과 Passive View로 구체화했고, Presentation Model은 오늘날 MVVM의 ViewModel과 사실상 같은 개념으로 이야기됩니다. (3) 테스트 피라미드(느리고 비싼 상위 테스트는 적게, 빠르고 값싼 하위 테스트는 많이 — Mike Cohn이 대중화)는 널리 받아들여진 경험칙입니다. (4) '함수형 코어, 명령형 셸(Functional Core, Imperative Shell)'은 Gary Bernhardt의 개념으로, SCNA 2012 'Boundaries' 강연과 같은 해(2012-07) 발표한 동명의 스크린캐스트에서 제시했습니다 — 순수한 값으로 이뤄진 함수형 코어를, 입출력·DB·네트워크 같은 부수효과를 다루는 얇은 명령형 셸이 감싸는 구조입니다. 여기까지는 업계 표준 정의로 봐도 무방합니다. 반면 세션 메모의 "Data 테스트 / ViewEntity 테스트 / View 테스트"라는 3분할 명칭 자체는 특정 팀·프레임워크의 관용어일 가능성이 높습니다(이건 제 판단이자 주의점입니다). 일반 소프트웨어 아키텍처 문헌에 "ViewEntity"라는 표준 용어는 없습니다. 여기서 말하는 ViewEntity는 정확히 View Model / Presentation Model, 즉 "뷰가 추가 판단 없이 그대로 그릴 수 있도록 도메인 데이터를 미리 가공해 담아둔 표시 전용 데이터 구조"를 가리킵니다. 그러니 명칭에 매이지 말고 "무엇을 테스트하는가"로 이해하시면 됩니다. 흔한 오해 하나를 바로잡겠습니다. "ViewEntity 테스트는 UI 테스트"가 아닙니다. ViewEntity 테스트는 UI를 전혀 띄우지 않습니다. "HP 30%면 게이지 색=빨강, 라벨='위험'"이라는 규칙은 순수한 값→값 변환(도메인 상태 → 표시용 데이터)이므로, 실제 이미지가 빨갛게 칠해지는지가 아니라 매핑 함수가 Color.red와 "위험"이라는 값을 반환하는지를 검증합니다. 진짜 렌더링(그 값이 화면 픽셀로 나오는지)은 맨 바깥 View 테스트의 몫이고, 이건 엔진이 필요해 느립니다. 이 경계를 흐리면 세 층으로 나눈 의미가 사라집니다.

📌 핵심 정리

  • 세 층은 순수도 순서: Data(순수 도메인 코어) → ViewEntity(도메인→표시데이터 순수 변환) → View(실제 렌더/바인딩). 아래일수록 빠르고 값싸고 결정적, 위일수록 느리고 비쌈.
  • Data/ViewEntity 테스트는 둘 다 UI·엔진 없이 값→값을 검증하므로 Unity EditMode로 밀리초 단위 실행. '무엇을 보여줄지'는 여기서 순수 값으로 확정 (예: HP 30% → color=Red, label='위험').
  • View는 판단을 갖지 않는 Humble View로 얇게 유지하고, View 테스트는 '배선 안 끊겼나' 수준의 소수 통합/시각 검증으로 최소화 — 이 프로젝트에서 UI/Visual 테스트가 ADVISORY로 분류된 이유와 정합.
  • 이론적 뿌리: 테스트 피라미드(Cohn) + Meszaros의 Humble Object 패턴 + Fowler의 Presentation Model/Passive View + Bernhardt의 Functional Core, Imperative Shell(SCNA 2012).
  • AI 시대 연결(사용자 주장): 순수 계층은 명세가 값이라 AI가 테스트를 짜기도, 사람이 검수·회귀검증하기도 값쌈 → '검수 비용↓' 논지의 구체적 실행 수단. 개연성 있는 논증이며 측정된 사실은 아님.
  • 'ViewEntity'는 표준 용어가 아니라 View Model/Presentation Model의 사내식 이름일 가능성이 큼 — 명칭이 아니라 '무엇을 테스트하는가'로 이해할 것.

예시 (csharp) · Domain→ViewEntity 순수 매핑 함수와 그 EditMode 테스트. UI·엔진 없이 값→값만 검증하므로 빠르고 결정적이다(ViewEntity 테스트). 실제 게이지가 빨갛게 렌더되는지는 별도의 느린 View 테스트 몫.

// --- 표시 전용 데이터 (ViewEntity == View Model / Presentation Model) ---
public readonly struct HealthView
{
    public readonly float FillRatio;   // 0..1
    public readonly Color BarColor;
    public readonly string Label;
    public HealthView(float fill, Color color, string label)
        => (FillRatio, BarColor, Label) = (fill, color, label);
}

// --- 순수 매핑: 도메인 상태 -> 표시 데이터. MonoBehaviour/Scene 불필요 ---
public static class HealthPresenter
{
    public static HealthView Build(int hp, int maxHp)
    {
        float ratio = maxHp <= 0 ? 0f : Mathf.Clamp01((float)hp / maxHp);
        // 30% '이하'가 위험 (경계값 포함 규칙)
        var (color, label) = ratio <= 0.30f
            ? (Color.red,    "위험")
            : (Color.green,  "정상");
        return new HealthView(ratio, color, label);
    }
}

// --- EditMode 단위 테스트 (Unity Test Framework, NUnit) ---
[TestFixture]
public class HealthPresenterTests
{
    [Test]
    public void Build_At30Percent_IsDangerAndRed() // 경계값
    {
        var vm = HealthPresenter.Build(hp: 30, maxHp: 100);
        Assert.AreEqual(0.30f, vm.FillRatio, 1e-4f);
        Assert.AreEqual(Color.red, vm.BarColor);
        Assert.AreEqual("위험", vm.Label);
    }

    [Test]
    public void Build_ZeroMax_DoesNotDivideByZero() // 엣지 케이스
    {
        var vm = HealthPresenter.Build(hp: 5, maxHp: 0);
        Assert.AreEqual(0f, vm.FillRatio);
    }
}

⚖ 트레이드오프 · 반론 · 유의

  • 'ViewEntity'와 'Data 테스트 / ViewEntity 테스트 / View 테스트'라는 3분할 명칭은 표준 아키텍처 용어가 아니며, 특정 팀·사내 프레임워크의 관용어일 가능성이 높습니다(제 추정). 일반 개념으로는 각각 도메인 모델 테스트 / View Model(Presentation Model) 테스트 / View 통합 테스트에 해당합니다. 정확한 용어 귀속은 세션 발표자에게 확인이 필요합니다.
  • 출처 귀속의 확신도: Humble Object 패턴이 Meszaros 『xUnit Test Patterns』(2007)의 개념이고 Fowler가 Presentation Model/Passive View로 연결한다는 점, 그리고 '함수형 코어, 명령형 셸'이 Gary Bernhardt의 개념(SCNA 2012 'Boundaries' 강연 + 2012-07 동명 스크린캐스트)이라는 점은 이번에 웹 검색으로 재확인했습니다. Presentation Model을 'MVVM ViewModel과 같다'고 보는 것은 널리 통용되는 해석이나 엄밀히 100% 동일한 정의는 아니라는 점만 유의해 주세요.
  • 층을 나누는 것 자체가 공짜가 아닙니다. Domain→ViewEntity 매핑 계층과 그 DTO를 유지하려면 보일러플레이트가 늘고, 작은 HUD 하나에도 클래스가 여러 개 생깁니다. 솔로~소규모 프로젝트에서 표시 규칙이 자명하면(단순히 값을 문자열로 찍는 수준) ViewEntity 계층을 강제하는 것이 오히려 과설계일 수 있습니다. 규칙에 분기·임계값·포맷팅이 있을 때 비로소 값을 합니다.
  • 반론: '검수 비용을 낮춘다'는 이득은 테스트가 실제 위험을 잡을 때만 성립합니다. ViewEntity 테스트가 매핑 함수를 그대로 되풀이하는 동어반복(예: Assert.AreEqual(Red, vm.color)인데 매핑도 그냥 Red 리터럴)이면 회귀 방어력이 없고 유지보수 짐만 됩니다. 임계값·경계값·조합 규칙처럼 '틀릴 수 있는' 로직에만 테스트를 집중해야 합니다.
  • 얇은 View라도 '얇음'을 보장하는 규율이 필요합니다. 개발자(또는 AI)가 편의상 View 안에 조건 분기를 슬쩍 넣으면 로직이 다시 비싼 계층으로 새어 나갑니다. 이 경계는 자동으로 지켜지지 않으며 코드리뷰/컨벤션으로 지켜야 합니다 — 즉 아키텍처가 검수 부담을 없애주는 게 아니라 '검수할 지점을 좁혀줄' 뿐입니다.
  • 반론(경계가 오히려 검수를 늘리는 경우): 한 기능이 세 계층에 걸쳐 흩어지면, 단순한 표시 변경 하나가 Data·ViewEntity·View를 모두 건드리는 산탄총 수술(shotgun surgery)이 될 수 있습니다. 이때는 오히려 검수 대상 파일 수가 늘어 '한눈에 파악'이 어려워집니다. 계층 분리가 blast radius를 항상 줄인다는 보장은 없으며, 변경이 계층 경계를 '따라' 일어날 때만 이득이 큽니다.
  • Unity 특이사항: EditMode 테스트는 순수 C#이라 이상적이지만, 도메인 데이터를 ScriptableObject로 들고 있으면 ScriptableObject.CreateInstance가 필요해 순수성이 약간 깨집니다(엔진 타입 의존). 가능하면 도메인 값은 순수 struct/class로 두고 ScriptableObject는 그 값을 담는 얇은 껍데기로 쓰는 편이 Data 테스트의 순수성을 지킵니다.
